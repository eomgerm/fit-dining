# RB-11 Modal 장애·예산, 임베딩 모델 교체

- 검증 기준: develop `7470db6`, 2026-10-28. 서버 A에서 킬스위치 값과 키 목록을 읽고, 알림 규칙과 지표 계약을 코드에서 확인했다. Modal을 실제로 끄거나 모델을 바꿔 본 적은 없다. BE가 Modal 지표를 아직 내지 않아 이 런북의 알림은 지금 실제로 울릴 수 없다(범위 참고).
- 쓰는 때: `FitModalFallbackHigh`(주의, 폴백 비율 30% 초과 15분), `FitModalBudgetHigh`(주의, 일일 호출 예산 80% 사용), `FitModalMetricMissing`(주의, 예산 지표 없음)이 울릴 때. 검색이 평소보다 단순하게 나온다는 신고(폴백 중일 수 있다). AI 팀이 임베딩 모델을 바꿀 때(**AI 팀이 주도하고 인프라는 서버 쪽을 맡는다**).
- 준비: [README.md](README.md)의 접속. env를 바꾸고 반영하는 방법은 [RB-02](RB-02.md)와 `infra/host/envset.py`다. 재색인은 [RB-07](RB-07.md) 4절을 쓴다.

## 1. 구조(복습)

- AI는 Modal의 환경별 앱(`fit-dev-*`, `fit-prod-*`)이고 A·B에는 AI 컨테이너가 없다. BE가 `Modal-Key`, `Modal-Secret` 헤더로 HTTPS 호출한다(설계 11.2절). 주소와 키는 BE의 서버 env에 있다.
- Modal이 안 될 때를 위한 방어가 BE에 있다: 타임아웃, 재시도, 서킷 브레이커, 동시성 상한, **일일 호출 예산**(Redis 카운터), **킬스위치**(`MODAL_ENABLED`). 임베딩 호출이 실패하거나 막히면 임베딩 없이 키워드 검색(OpenSearch nori)으로 대체하고 리랭커는 건너뛴다(설계 11.2절). 폴백은 사용자가 거의 못 느끼는 실패라서 폴백 비율을 알림으로 본다(A603 교훈).
- 임베딩 모델이 바뀌면 **벡터 공간이 달라진다.** 문서와 질의가 같은 모델로 만든 벡터여야 비교가 되므로, 새 인덱스를 새 모델로 만들어 채우고 별칭을 옮긴다(설계 11.1, 12.2절 7번).

## 2. 확인 명령

킬스위치와 예산 설정은 비밀이 아닌 값이라 그대로 볼 수 있다. 서버 A에서:

```bash
sudo grep -E '^(MODAL_ENABLED|GMS_ENABLED|BATCH_ENABLED|MODAL_DAILY_CALL_BUDGET)=' /etc/fit/prod.env /etc/fit/dev.env
for f in prod dev; do printf '%s: ' $f; sudo grep -o -E '^MODAL_[A-Z_]+=' /etc/fit/$f.env | tr -d '=' | tr '\n' ' '; echo; done   # 키 이름만(값은 안 나온다)
```

2026-10-28 값: prod와 dev 모두 `MODAL_ENABLED=false`(Modal을 쓰지 않는 상태, 모든 검색이 키워드), `GMS_ENABLED=true`, `BATCH_ENABLED`는 prod true, dev false. 두 환경에 `MODAL_BASE_URL`, `MODAL_KEY`, `MODAL_SECRET`, `MODAL_ENABLED`가 있고 `MODAL_DAILY_CALL_BUDGET`은 없다(선택 키다).

폴백 비율과 예산은 Prometheus(A의 `127.0.0.1:9090`)에서 본다.

```bash
q() { curl -s -G http://127.0.0.1:9090/api/v1/query --data-urlencode "query=$1"; echo; }
q 'fit:modal_fallback_ratio:rate15m'          # 구성요소(embedding, reranker, llm)별 15분 폴백 비율. 0.3이 알림 기준
q 'fit:modal_calls:rate15m'                   # 15분 호출률(초당)
q 'max by (env) (modal_daily_budget_used_ratio)'   # 일일 예산 사용 비율(0~1). 0.8이 알림 기준
```

**2026-10-28 현재 세 질의 모두 결과가 비어 있다.** BE가 Modal 지표를 아직 내지 않기 때문이다(지표 계약, BE 계약 #11). 그래서 `FitModalMetricMissing`이 울리고 있고 prod BE 배포 전이면 정상이다. 지표가 생기면 위 질의에 값이 나온다.

## 3. 증상별 조치

### A. 폴백 비율이 높다(`FitModalFallbackHigh`)

Modal 쪽 장애이거나 콜드 스타트 타임아웃일 수 있다(알림 설명).

1. 구성요소(`embedding`, `reranker`, `llm`) 중 어느 것인지 2절 질의로 본다.
2. BE 로그에서 Modal 호출 오류(타임아웃, 401·403, 429, 5xx)를 본다: `sudo docker logs --since 30m be-prod-<활성 색> 2>&1 | grep -i modal | tail -n 30`(로그 형식은 BE 구현 (미확인)). 401·403이면 키 문제(RB-08의 Modal 항목), 429면 Modal 계정 한도다.
3. AI 팀에게 Modal 앱 상태를 확인해 달라고 한다. 콜드 스타트면 상시 가동 컨테이너 수를 늘려야 하는데 비용 상한을 AI 팀이 정한다(설계 12.2절 3번).
4. **당장 줄여야 하면 킬스위치를 끈다.** Modal 호출이 멈추고 키워드 검색으로 간다. 서버 A에서:

   ```bash
   sudo python3 ~/host/envset.py set prod MODAL_ENABLED=false      # 비밀이 아니라 값을 바로 줄 수 있다. 이미 값이 있어 덮어쓸지 묻는다
   # 같은 SHA를 다시 배포해 반영한다(prod는 반대 색을 새 값으로 띄워 전환하므로 끊기지 않는다): GitLab에서 master 최신 파이프라인의 deploy:prod를 Retry
   ```

   반영한 뒤 `smoke.sh`가 폴백으로 처리된 응답을 알아본다(BE 계약 #17의 `X-Fallback` 헤더가 구현된 뒤에는 폴백이 통과로 가려지지 않는다).
5. 원인이 풀리면 `MODAL_ENABLED=true`로 되돌리고 같은 방식으로 다시 배포한다. 되돌린 뒤 15분 폴백 비율이 내려가는지 본다.

### B. 일일 예산 80% 사용(`FitModalBudgetHigh`)

예산이 다 차면 키워드 폴백으로 내려간다. 예산 한도와 카운터는 BE와 Redis가 관리한다.

1. 예산 설정을 본다: `sudo grep '^MODAL_DAILY_CALL_BUDGET=' /etc/fit/prod.env`(없으면 BE의 기본값이다 (미확인)).
2. 호출이 몰린 이유를 본다. 새벽 배치(문서 임베딩)가 대량이면 정상이다. 비정상 호출(남용)이면 사용자별·IP별 제한이 막는지 본다(BE 계약 #18).
3. 오늘 더 써야 한다면 예산을 올린다. **Modal 비용이 늘어나므로 팀의 승인 뒤에 한다.** `envset.py set prod MODAL_DAILY_CALL_BUDGET=<값>`과 같은 SHA 재배포다.
4. 올릴 수 없으면 소진될 때까지 폴백으로 가는 것을 받아들이거나 킬스위치(A절 4단계)로 미리 내린다.

### C. 지표가 없다(`FitModalMetricMissing`)

prod BE가 `modal_daily_budget_used_ratio`를 내지 않는 것이다. 배포 전이면 정상이다. 배포된 뒤에도 울리면 BE의 `/actuator/prometheus`(관리 포트 8081)에 지표가 있는지 본다: `sudo docker exec be-prod-<활성 색> sh -c 'curl -s localhost:8081/actuator/prometheus | grep -c modal_'`(BE 컨테이너에 `curl`이 있다. 2026-10-28 `be-prod-blue`로 확인). 없으면 BE 팀에 지표 계약 이행을 요청한다.

## 4. 임베딩 모델 교체(AI 팀 주도)

아래는 설계 문서에서 도출한 순서다. 질의 벡터와 문서 벡터의 모델이 어긋나는 구간이 없어야 해서 **순서가 중요하다.** 실제로 해 본 적은 없다(설계 10.3절의 리허설 항목 "모델 교체(재색인 포함)"가 남아 있다).

1. **AI 팀이 새 모델을 Modal에 올린다.** 응답의 `model`(이름@버전)과 `dim`(차원)을 받는다. 차원이 바뀌면 인덱스 매핑도 바뀐다.
2. **용량을 다시 계산한다.** k-NN 네이티브 메모리 한도가 약 0.6GB이고 1024차원이면 약 13만 건이 상한이다(설계 4.4절). 차원이 커지면 상한이 줄어든다. 새 인덱스와 옛 인덱스가 둘 다 올라가는 동안은 절반으로 본다(RB-07 4절 1단계).
3. **새 인덱스를 만들고 채운다**(RB-07 4절 2~4단계). 문서 전량을 새 모델로 다시 임베딩하므로 Modal 호출량이 크다. 일일 예산(B절)이 모자라면 단계를 나누거나 예산을 임시로 올린다(팀 승인). 사용자 요청 시간대를 피하고 배치와 겹치지 않게 한다.
4. **BE의 질의 임베딩을 새 모델로 바꾸는 시점과 별칭 전환 시점을 맞춘다.** BE가 새 모델 주소(`MODAL_BASE_URL`)로 질의하게 바꾸는 배포와 별칭 전환(RB-07 4절 5단계)이 어긋나면 그 사이 질의 벡터와 문서 벡터가 안 맞아 결과가 이상해진다. 어긋나는 동안은 킬스위치(A절 4단계)로 키워드 검색으로 가린다. 한 번에 맞추는 구체적인 방법(스위치로 질의 모델을 고르는지 등)은 BE 구현에 달려 있다 (미확인).
5. **검증한다.** 별칭으로 검색해 결과가 맞는지, 폴백 비율이 낮은지, 모델 버전이 응답과 BE 지표에 노출되는지 본다(설계 11.1절).

### 되돌리기

옛 인덱스를 지우기 전이면 별칭을 옛 인덱스로 되돌리고 BE의 Modal 주소를 옛 앱으로 되돌려 다시 배포한다(RB-07 4절의 되돌리기). 옛 인덱스는 새 모델이 안정적임이 확인된 뒤(24시간 이상)에 지운다. 새 모델이 문제면 새 인덱스를 이름으로 지운다.

- 실행하지 못함: Modal을 실제로 끄거나 켜기(`MODAL_ENABLED` 변경과 재배포), 알림이 실제로 울리는 상황(지표가 없다), 예산 초과 동작, 모델 교체 전체(AI 팀의 새 모델 배포, 새 인덱스에 임베딩, 질의 모델과 별칭의 동시 전환). 3절 C의 `/actuator/prometheus` 질의는 현재 prod 컨테이너가 master 미리보기 이미지라 실제 BE의 모양과 다를 수 있다.
