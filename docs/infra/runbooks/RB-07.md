# RB-07 OpenSearch(검색), 재색인, 새벽 배치

- 검증 기준: develop `7470db6`, 2026-10-28. 서버 A에서 확인 명령을 실제로 실행했고, 재색인의 OpenSearch 쪽 명령(별칭 전환과 되돌리기)은 연습용 인덱스로 돌려 봤다. 인덱스를 채우는 BE·AI 쪽은 아직 구현이 없어 해 보지 못했다(범위 참고).
- 쓰는 때: `FitOpensearchDown`(장애), `FitOpensearchRed`(장애), `FitOpensearchHeapHigh`, `FitSearchLatencyHigh`, `FitBatchStale`, `FitBatchMetricMissing`이 울릴 때. 검색 결과가 이상하다는 신고. 모델을 바꾸거나 인덱스를 다시 만들 때(RB-11이 이 런북의 4절을 쓴다).
- 준비: [README.md](README.md)의 접속.

## 1. 구조(복습)

- OpenSearch는 A의 컨테이너 `fit-data-opensearch-1`이다. 3.9.0에 한국어 분석기(nori)를 더한 이미지이고, 노드 하나, 메모리 한도 2GB, 힙 768MB, 보안 플러그인을 끈 상태이며 호스트에 게시하지 않는다(같은 망의 BE만 닿는다).
- prod와 dev가 한 OpenSearch를 나눠 쓴다. 인덱스 이름 접두사가 `prod-`, `dev-`로 갈리고, 인증이 없어 접두사는 관례일 뿐이다(설계 13.4절). prod는 **별칭**으로 서빙한다(검색은 별칭을 부르고, 별칭이 가리키는 인덱스를 바꾸면 무중단으로 교체된다).
- **백업하지 않는다.** 데이터가 사라지면 Postgres에서 다시 색인한다(설계 7.2절). 복제본이 없는 단일 노드라서 샤드가 깨지면 그 인덱스는 잃는 것이다.
- **BE는 아직 OpenSearch를 쓰지 않는다(2026-10-28, develop).** BE의 환경 검사가 OpenSearch 키를 "아직 쓰지 않아 값이 있을 때만" 맞춰 본다. 서버에는 사용자 인덱스도 별칭도 없다. 그래서 이 런북에서 "인덱스를 채우는" 단계는 BE·AI 구현 뒤에 맞춰 고친다.

## 2. 확인 명령

모두 읽기만 한다. 서버 A에서:

```bash
OS='sudo docker exec fit-data-opensearch-1 curl -s -m 10'
$OS 'localhost:9200/_cluster/health?pretty'                                    # status: green, yellow, red
$OS 'localhost:9200/_cat/indices?v&h=health,status,index,docs.count,store.size&s=index'
$OS 'localhost:9200/_cat/aliases?v'                                            # 별칭이 가리키는 인덱스
$OS 'localhost:9200/_cat/nodes?v&h=name,heap.percent,heap.max,ram.percent,cpu,load_1m'
$OS 'localhost:9200/_cat/shards?v&h=index,shard,prirep,state,unassigned.reason' | grep -v STARTED
$OS 'localhost:9200/_plugins/_knn/stats?filter_path=nodes.*.graph_memory_usage_percentage,nodes.*.circuit_breaker_triggered'
sudo docker stats --no-stream fit-data-opensearch-1
sudo docker logs --tail 40 fit-data-opensearch-1
```

2026-10-28 정상 값: 클러스터 green, 샤드 8개 모두 started(전부 시스템 인덱스), 힙 51%(768MB 중), 컨테이너 메모리 1.44GiB/2GiB, 사용자 인덱스와 별칭은 없다. `top_queries-<날짜>-…` 인덱스가 하루에 하나씩 생기는 것은 정상이다(query-insights 플러그인이 만든다. 모두 합쳐 수십 KB).

배치(`FitBatch*`)는 prod 설정과 지표를 본다.

```bash
sudo grep '^BATCH_ENABLED=' /etc/fit/prod.env /etc/fit/dev.env          # 스위치 값(비밀이 아니다). 2026-10-28: prod true, dev false
curl -s -G http://127.0.0.1:9090/api/v1/query --data-urlencode 'query=time() - max(batch_last_success_timestamp_seconds{env="prod"})'
```

두 번째 명령은 마지막 성공 뒤 몇 초가 지났는지 낸다. 결과가 비어 있으면 prod BE가 지표를 내지 않는 것이다(아래 E).

## 3. 증상별 조치

### A. `FitOpensearchDown`(장애, 2분)

OpenSearch가 죽으면 **검색 자체가 안 된다.** 알림 설명은 "키워드 폴백으로 내려간다"고 적고 있으나 키워드 폴백도 OpenSearch(nori)를 쓰므로(설계 11.2절) 맞지 않는 문구다. BE가 이때 무엇을 응답하는지는 (미확인)이다.

1. 컨테이너 상태와 마지막 로그를 본다.

   ```bash
   sudo docker ps -a --filter name=fit-data-opensearch-1 --format '{{.Names}} {{.Status}}'
   sudo docker logs --tail 60 fit-data-opensearch-1
   ```

2. 흔한 원인: 메모리 부족으로 컨테이너가 OOM으로 종료(RB-03), 디스크 가득(RB-04), 커널 설정 `vm.max_map_count`(`sysctl vm.max_map_count`가 262144여야 한다).
3. 컨테이너만 내려갔으면 올린다. 기동에 1~2분 걸린다.

   ```bash
   sudo docker start fit-data-opensearch-1
   # 데이터 스택 전체를 확인하며 올리려면: sudo bash ~/fit-repo/infra/deploy/fit-up.sh
   ```

4. 올라온 뒤 위 2절 명령으로 green인지, 사용자 인덱스가 남아 있는지 본다. 볼륨(`fit-data_osdata`)이 사라졌다면 인덱스는 없다. 4절로 다시 만든다.

### B. `FitOpensearchRed`(장애)

주 샤드가 할당되지 않았다. 복제본이 없는 단일 노드라서 그 인덱스의 데이터는 읽을 수 없다.

1. 어느 인덱스인지와 이유를 본다.

   ```bash
   $OS 'localhost:9200/_cat/shards?v&h=index,shard,prirep,state,unassigned.reason' | grep -v STARTED
   $OS 'localhost:9200/_cluster/allocation/explain?pretty'
   ```

2. 디스크가 원인(워터마크 초과로 읽기 전용이 됨)이면 RB-04로 여유를 만든 뒤 풀린다.
3. 샤드가 손상된 것이면 복구 수단이 없다(스냅샷 없음). 그 인덱스를 **이름을 정확히 써서** 지우고 4절로 Postgres에서 다시 색인한다.

### C. `FitOpensearchHeapHigh`(힙 90% 초과, 10분)

1. 힙 사용률과 k-NN 네이티브 메모리를 본다(2절의 `_cat/nodes`, `_knn/stats`). 네이티브 메모리 한도는 (컨테이너 메모리 − 힙)의 50%로 약 0.6GB, 차원 1024 기준 약 13만 건이 상한이다(설계 4.4절). 문서가 이 근처면 근본 원인은 용량이다. BE·AI 팀과 문서 수나 차원을 다시 정한다.
2. 캐시를 비우면 잠깐 내려갈 수 있다: `$OS -XPOST 'localhost:9200/_cache/clear'`.
3. 안 내려가면 재시작한다. 검색이 1~2분 끊긴다: `sudo docker restart fit-data-opensearch-1`.

### D. `FitSearchLatencyHigh`(검색 p95가 4초 초과, 10분)

원인을 셋으로 가른다.

1. **OpenSearch:** `$OS 'localhost:9200/_cat/thread_pool/search?v&h=name,active,queue,rejected'`에서 큐나 거절이 쌓였는지, 힙이 높은지(C절).
2. **Modal:** 임베딩과 리랭커 호출이 느린 것이다. 폴백 비율과 예산을 본다(RB-11).
3. **호스트 CPU:** RB-09. A가 baseline을 넘으면 모든 응답이 느려진다.

### E. `FitBatchStale`, `FitBatchMetricMissing`(주의)

- **`FitBatchMetricMissing`:** prod BE가 `batch_last_success_timestamp_seconds`를 내지 않는 것이다(BE 계약 #11). prod가 아직 master 미리보기라면 정상이다(2026-10-28 현재 울리고 있다).
- **`FitBatchStale`(마지막 성공이 26시간 초과):** 새벽 4시(KST) 배치가 한 번 이상 건너뛰어졌다.
  1. `BATCH_ENABLED`가 prod에서 `true`인지 본다(2절). 값을 바꾸면 같은 SHA를 다시 배포해야 반영된다(RB-02).
  2. 배치 시각 전후의 BE 로그에서 오류를 본다: `sudo docker logs --since 26h be-prod-<활성 색> 2>&1 | grep -i batch | tail -n 30`(로그 형식은 BE 구현에 따라 (미확인)).
  3. Modal 예산 소진이나 킬스위치(`MODAL_ENABLED=false`)로 건너뛴 것인지 RB-11로 본다.
  4. 두 색이 겹쳐 중복 실행되지 않는지(BE 계약 #19, 한 번에 하나만 돈다)는 BE가 보장한다. 지표가 색별로 갈리는지 본다.
  5. 배치를 지금 한 번 돌리는 방법은 BE 구현에 달려 있다 (미확인, 수동 실행 경로가 아직 없다).

## 4. 재색인(별칭 전환)

새 인덱스를 옆에 만들어 채우고, 맞으면 별칭을 한 번에 옮기고, 문제가 있으면 별칭을 되돌린다. 옛 인덱스를 지우기 전까지는 언제든 되돌릴 수 있다. 아래 이름은 예시다(`<별칭>`은 BE가 정한다).

1. **용량을 본다.** 새 인덱스를 채우는 동안 옛 인덱스와 둘이 있다. 디스크 여유(RB-04), 힙(C절), k-NN 한도(약 13만 건, 새 인덱스와 옛 인덱스가 같이 올라가면 절반)를 확인한다.
2. **새 인덱스를 만든다.** 이름은 `<접두사><이름>-v<번호>`로 한다(prod는 `prod-`, dev는 `dev-`. 다른 환경 접두사로 만들지 않는다). 인덱스 템플릿이 현재 없어서(2026-10-28 확인) 만들 때 `"number_of_replicas": 0`을 직접 준다. 안 주면 복제본이 할당되지 않아 yellow가 된다.

   ```bash
   sudo docker exec fit-data-opensearch-1 curl -s -X PUT -H 'Content-Type: application/json' localhost:9200/<새 인덱스> -d '{"settings":{"number_of_shards":1,"number_of_replicas":0,"analysis":{"analyzer":{"ko":{"type":"custom","tokenizer":"nori_tokenizer"}}}},"mappings":{"properties":{"text":{"type":"text","analyzer":"ko"}}}}'
   ```

   매핑은 BE가 정한 것을 쓴다(위는 시험용 최소 예). 벡터 필드의 차원은 모델이 정한다(RB-11).
3. **채운다.** Postgres에서 읽어 새 인덱스에 넣는다. 문서 벡터를 Postgres에도 저장해 두었다면 Modal을 다시 부르지 않는다. 아니면 문서 전체를 다시 임베딩해야 해서 시간과 비용이 든다(설계 7.2절, 16절 #21). 이 단계의 실행 주체와 명령은 BE·AI 구현에 달려 있다 (미확인).
4. **검증한다.** 별칭은 아직 옛 인덱스에 있다. 새 인덱스의 문서 수를 Postgres의 건수와 비교하고(`$OS 'localhost:9200/_cat/count/<새 인덱스>?v'`), 새 인덱스로 직접 검색해 본다.
5. **별칭을 옮긴다.** 한 요청 안에서 떼고 붙이므로 중간 상태가 없다.

   ```bash
   sudo docker exec fit-data-opensearch-1 curl -s -X POST -H 'Content-Type: application/json' localhost:9200/_aliases -d '{"actions":[{"remove":{"index":"<옛 인덱스>","alias":"<별칭>"}},{"add":{"index":"<새 인덱스>","alias":"<별칭>"}}]}'
   ```

   `{"acknowledged":true}`가 나온다. 이어서 별칭으로 검색해 새 결과가 나오는지, `smoke.sh`를 한 번 돌린다(RB-02).
6. **옛 인덱스는 24시간 둔다.** 문제가 없음이 확인되면 이름을 정확히 써서 지운다: `sudo docker exec fit-data-opensearch-1 curl -s -X DELETE localhost:9200/<옛 인덱스>`. 와일드카드(`dev-*`)로는 지워지지 않는다(서버가 400으로 거부한다. `action.destructive_requires_name=true`).

### 되돌리기

옛 인덱스를 지우기 전이면 5단계의 `remove`와 `add`의 인덱스만 맞바꿔 같은 요청을 보낸다. 별칭이 옛 인덱스로 돌아간다. 새 인덱스는 문제를 본 뒤 이름으로 지운다.

### 전체를 다시 만들 때(데이터 손실, 샤드 손상)

옛 인덱스가 없거나 못 쓰는 경우다. 별칭을 옮기는 대신 새 인덱스를 만들어 채운 뒤 별칭을 처음 붙인다. 채우는 동안 검색은 되지 않는다. 소요 시간은 아직 모른다(설계 7.2절은 측정해 기록하라고 한다). 처음 하는 재색인 때 걸린 시간과 문서 수를 여기에 한 줄 적는다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-28, A): 2절의 OpenSearch 확인 명령 전부(클러스터 green, 인덱스·별칭·노드·k-NN 통계), 컨테이너 메모리, 디스크 확인, 배치 스위치 확인. **연습용 인덱스 `dev-rb07test-v1`, `-v2`로** 4절을 돌렸다: 인덱스 생성(복제본 0, nori), 별칭 붙이기, 별칭 검색(문서 2건), nori 검색(`닭`이 `닭가슴살` 문서에 맞음), 원자적 별칭 전환(별칭 검색이 3건으로 바뀜), 되돌리기 전환(2건으로 복귀), 와일드카드 삭제가 HTTP 400으로 거부됨, 이름으로 삭제, 정리 뒤 연습용 인덱스와 별칭이 남지 않고 green.
- 실행하지 못함: 3절 C의 캐시 비우기와 재시작, A의 컨테이너 재시작(운영 영향), 장애 알림을 실제로 일으킨 상황(Down, Red, 힙, 지연, 배치), BE가 인덱스를 채우는 3단계(BE 구현 전), 문서 수 대조(비교할 Postgres 문서 테이블이 아직 없다), 배치 수동 실행.
