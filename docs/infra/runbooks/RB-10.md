## 3. 절차

### 1단계. 공지와 중지(종료일)

1. 팀 채널에 종료 시각과 이후 데이터가 사라진다는 것을 알린다.
2. 새 쓰기가 없게 prod를 멈춘다. 활성 색은 `sudo bash ~/fit-repo/infra/edge/edgectl.sh status`로 본다.

   ```bash
   sudo docker stop be-prod-<활성 색> fe-prod-<활성 색> be-dev fe-dev
   ```

3. 새벽 배치를 막는다(`BATCH_ENABLED=false`는 컨테이너를 멈췄으므로 실제 동작과는 무관하지만 재시작 사고를 막으려고 꺼 둔다): `sudo python3 ~/host/envset.py set prod BATCH_ENABLED=false`.

### 2단계. 마지막 백업과 합성 덤프

1. **안전망 백업.** 삭제를 되돌릴 수 없으니 마지막 백업을 만들고 B에 도착하는 것을 확인한다.

   ```bash
   sudo systemctl start fit-backup@pg.service fit-backup@photos.service
   sudo journalctl -u fit-backup@pg.service -n 5 --no-pager -o cat       # 성공 줄
   ```

   B에서 `sudo ls -lt /srv/vault/store/pg | head -n 3`로 새 파일이 보이는지 본다(RB-06 2절). 노트북에서 한 번 풀어 보고(RB-06 4절) 삭제 전 마지막 확인으로 삼는다.
2. **합성 데이터 덤프(포팅 매뉴얼용).** 도구가 없다 (미작성). 구조(테이블 정의)는 데이터 없이 뜰 수 있다. 2026-10-28 `fit_dev`로 확인했다(테이블 11개 정의, 데이터 행 0건).

   ```bash
   sudo docker exec fit-data-postgres-1 pg_dump -U postgres -s -d fit_dev > schema-fit_dev.sql
   ```

   데이터가 든 시연용 덤프는 BE·AI 팀이 합성 데이터를 만들어 새 DB에 넣고 뜬다. **실데이터에서 뜬 덤프를 포팅 매뉴얼이나 저장소에 넣지 않는다.** 만든 덤프에 이메일 같은 실제 값이 있는지 `grep -c '@'` 등으로 눈으로 확인한다.

### 3단계. 실데이터 삭제(A)

`down -v`가 가장 빠르고 빠짐이 없다. 데이터 스택의 볼륨(Postgres, OpenSearch, Redis, 사진)이 한 번에 지워진다.

```bash
sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env down -v
sudo docker volume ls --format '{{.Name}}' | grep '^fit-data_'          # 아무것도 안 나와야 한다
```

스택을 남겨 두고 내용만 지우려면(예: 시연용으로 남기는 경우) 이름을 정확히 써서 지운다.

```bash
# Postgres: 접속을 끊고 지운다
sudo docker exec fit-data-postgres-1 psql -U postgres -qAt \
  -c "SELECT count(pg_terminate_backend(pid)) FROM pg_stat_activity WHERE datname IN ('fit_prod','fit_dev') AND pid <> pg_backend_pid()" \
  -c "DROP DATABASE fit_prod" -c "DROP DATABASE fit_dev"
# OpenSearch: 목록을 보고 인덱스를 하나씩 이름으로 지운다(와일드카드는 서버가 거부한다)
sudo docker exec fit-data-opensearch-1 curl -s 'localhost:9200/_cat/indices?h=index' | grep -E '^(prod|dev)-'
sudo docker exec fit-data-opensearch-1 curl -s -X DELETE localhost:9200/<인덱스 이름>
```

이어서 암호화 백업과 임시 파일, 로그를 지운다.

```bash
sudo find /srv/fit/backups /srv/fit/predeploy -type f -exec shred -u {} +
sudo rm -rf /srv/fit/backups/* /srv/fit/predeploy/* /dev/shm/*.dump
sudo docker rm -f $(sudo docker ps -aq)                                  # 컨테이너와 함께 컨테이너 로그가 지워진다
sudo journalctl --rotate && sudo journalctl --vacuum-time=1s
```

> `shred`는 ext4 같은 저널링 파일시스템과 EBS 같은 가상 디스크에서 덮어쓰기를 보장하지 않는다. 암호화 사본이라 괜찮지만, "물리적으로 지웠다"고 기록하지 않는다. **파일을 지웠다**고 적는다.

### 4단계. 실데이터 삭제(B)

```bash
sudo rm -rf /srv/vault/store/* /srv/vault/incoming/*                      # store 안의 quarantine도 함께 지워진다
sudo journalctl --rotate && sudo journalctl --vacuum-time=1s
```

러너 캐시 볼륨에는 실데이터가 없다. 서버를 비울 때는 `sudo docker volume prune -a`로 지운다.

### 5단계. 호스트 밖

사람이 하나씩 확인하고 체크한다.

1. 노트북: 받았던 `pg-*.dump.age`, 풀어 둔 `restore.dump`, 리허설 임시 폴더(Windows는 `C:/Users/<이름>/AppData/Local/Temp`의 `tmp.*`와 `restore.dump`)를 지운다. 휴지통도 비운다.
2. 수신자 2명: 개인키 파일의 폐기 시점을 정한다(1절). 폐기하면 남은 암호화 사본이 어디 있든 풀 수 없다.
3. 팀 비밀번호 관리자의 env 사본을 지운다.
4. 외부 서비스: Modal 앱과 토큰을 폐기하고 보관된 데이터가 있으면 삭제를 요청한다. GMS 키, Apify 토큰과 데이터셋, 소셜 로그인 앱의 secret, 분석 도구 프로젝트를 폐기한다. 폐기 순서와 방법은 [RB-08](RB-08.md)의 외부 서비스 키 절을 따른다.
5. GitLab: CI 변수, 러너(서버 A·B에서 `sudo gitlab-runner unregister --all-runners`), 개인 액세스 토큰, 오래된 파이프라인 로그를 정리한다.
6. 서버의 비밀(`/etc/fit/*.env`)은 외부 키를 다 폐기한 뒤에 지운다: `sudo shred -u /etc/fit/*.env`.

### 6단계. 확인과 기록

A와 B에서 다음이 모두 비어 있거나 없는지 본다(읽기만 한다).

```bash
sudo docker volume ls --format '{{.Name}}'                                # A: fit-data_* 가 없어야 한다
sudo du -sh /srv/fit/backups /srv/fit/predeploy 2>/dev/null               # 거의 0이어야 한다
sudo docker ps -a --format '{{.Names}}'                                   # 컨테이너가 없어야 한다
sudo du -sh /srv/vault/store /srv/vault/incoming                          # B: 거의 0이어야 한다
```

삭제 기록을 팀 문서에 남긴다: 날짜, 한 사람과 확인한 사람, 지운 대상 목록, 호스트 밖 항목의 체크, 남긴 것과 그 이유. 값(비밀)은 적지 않는다.

## 되돌리기

**없다.** 2단계의 안전망 백업과 개인키가 있는 동안에만 복구할 수 있다(RB-06 D절). 삭제 전에 "정말 지워도 되는가"를 팀이 마지막으로 확인한다. 개인키를 폐기하고 모든 사본을 지운 뒤에는 복구가 불가능하다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-28, A·B): 2절의 목록을 만든 읽기 명령(컨테이너, Docker 볼륨 이름, `/srv/fit`·`/srv/vault`·`/etc/fit`의 크기와 이름, B의 금고 건수와 디스크). 스키마만 뜨는 덤프(`pg_dump -s`, 테이블 11개 정의, 데이터 행 0건). 연습용 DB(`fit_dev_rb13test`)를 접속을 끊고 `DROP DATABASE`한 것, 연습용 OpenSearch 인덱스를 이름으로 지우고 와일드카드 삭제는 거부되는 것(RB-07 시험).
- 실행하지 못함: `down -v`, 운영 DB·인덱스·백업·금고 삭제, `shred`, `docker rm -f $(docker ps -aq)`, 로그 정리, 러너 등록 해제, 외부 서비스 폐기(운영 데이터를 지우는 일이라 하지 않았다). 합성 데이터 덤프는 도구가 없어 만들지 못했다. 로그에 개인정보가 남는지(BE 로그 마스킹 구현 전)는 확인하지 못했다. 종료 전에 마이그레이션 전 덤프(평문)가 생겼다면 3단계의 `shred`가 반드시 지워야 한다.
