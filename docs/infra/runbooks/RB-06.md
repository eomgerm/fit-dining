# RB-06 백업이 안 올 때, Postgres 장애, DB 복원, 복원 리허설

- 검증 기준: develop `52c661d`, 2026-10-27. 서버 A·B에서 확인 명령을 실제로 실행했고, 복원 절차의 DB 쪽(새 DB에 복원, 이름 교체, 되돌리기)은 시험용 DB로 돌려 봤다. 운영 DB에는 복원을 한 적이 없다(범위 참고).
- 쓰는 때: `FitBackupPgStale`, `FitBackupPhotosStale`, `FitBackupVerifyFailed`, `FitBackupVerifyStale`, `FitBackupOutboxStuck`, `FitBackupMetricMissing`(A), `FitVaultStale`, `FitVaultRestoreCheckOverdue`, `FitVaultQuarantine`, `FitVaultIngestFailing`, `FitVaultIngestStale`, `FitVaultMetricMissing`(B), `FitPostgresDown`, `FitPostgresConnectionsHigh`(A)가 울릴 때. 데이터를 되살려야 할 때.
- 준비: [README.md](README.md)의 접속. 백업 구조는 [infra/backup/README.md](../../../infra/backup/README.md)다.

## 1. 구조(복습)

```
A  4시간마다 fit_prod 덤프 → (하루 1회) 임시 DB에 복원해 검증 → age 암호화 → /srv/fit/backups/pg → 금고로 전송
B  10분마다 incoming 검증(이름, sha256, 크기) → store/pg (통과) 또는 store/quarantine (실패), 보관: 48시간 전부 + 14일 하루 1벌
```

백업은 `age`로 암호화돼 있고 **개인키는 A·B 어디에도 없다.** 수신자 2명이 노트북에 오프라인으로 보관한다. 그래서 서버가 뚫려도 백업 평문은 나가지 않지만, 복원은 사람이 키로 풀어야 한다. 복원 목표는 RPO 4시간, RTO 2시간이다(제안값, 리허설 #2의 RTO는 7초였지만 데이터가 거의 없는 DB였다).

## 3. 증상별 조치

### A. 백업이 안 만들어진다(A의 `FitBackup*Stale`, `FitBackupVerifyFailed`, `FitBackupMetricMissing`)

1. `journalctl`로 마지막 실행의 실패 이유를 본다. 지금 한 번 돌려 본다.

   ```bash
   sudo systemctl start fit-backup@pg.service        # photos, caddy도 같다
   sudo journalctl -u fit-backup@pg.service -n 15 --no-pager -o cat
   ```

2. `FitBackupVerifyFailed`(덤프를 임시 DB에 복원하는 검증 실패)면 그 덤프는 금고로 보내지 않고 `/srv/fit/backups/pg/failed-verify-<시각>.dump`로 남는다. 평문이 A에 남은 것이므로 원인을 보고 확인이 끝나면 지운다. DB가 정말 손상됐을 수 있으므로 C절로 간다.
3. `age-recipients.txt`가 비었거나 형식이 틀리면 백업이 거부된다: `sudo grep -c '^age1' /etc/fit/keys/age-recipients.txt`가 2여야 한다(수신자 2명, 값은 출력하지 않는다).
4. 디스크가 찼으면 RB-04다.

### B. 금고에 안 들어온다(`FitBackupOutboxStuck`, B의 `FitVault*`)

1. A의 `outbox`에 파일이 쌓였으면 전송이 막힌 것이다. A에서 B의 22가 닿는지 본다(RB-01의 `FitVaultUnreachable`). B의 금고 계정은 `from="<A의 공인 IP>"`로 제한돼 있어서 **A의 IP가 바뀌면 전송이 막힌다**(설계 1.3절).
2. 닿는데 안 들어가면 B의 `incoming`과 ingest 로그를 본다. ingest는 파일 이름, sha256, 크기를 `.meta`와 대조해 통과하면 `store/`로, 아니면 `store/quarantine/`로 보낸다.
3. 격리된 파일(`FitVaultQuarantine`)은 지우지 않는다. `.meta`의 sha256과 실제 파일을 비교한다(`sudo sha256sum <파일>`). 전송 중 깨진 것이면 A에서 다시 백업해 보낸다(`sudo systemctl start fit-backup@pg.service`).
4. ingest를 지금 한 번 돌린다: `sudo systemctl start fit-vault-ingest.service`(B). 이어서 `fit_vault_last_received_timestamp_seconds{kind="pg"}`가 갱신되는지 본다.
5. `FitVaultStale`(pg를 8시간 넘게 못 받음)은 critical이다. 8시간이면 RPO 4시간을 이미 넘긴 것이다. A와 B 어느 쪽이 막혔는지 가른 뒤 위 순서로 푼다.

### C. Postgres가 죽었거나 데이터가 이상하다(`FitPostgresDown`, `FitPostgresConnectionsHigh`)

1. 죽었으면 이유를 본다.

   ```bash
   sudo docker ps -a --filter name=fit-data-postgres-1 --format '{{.Names}} {{.Status}}'
   sudo docker logs --tail 60 fit-data-postgres-1
   ```

2. 컨테이너만 내려간 것이면 올린다. 디스크가 찼거나 OOM이면 먼저 RB-04, RB-03이다. 데이터 스택 전체를 올리려면 `sudo bash ~/fit-repo/infra/deploy/fit-up.sh`다(`up -d --wait`와 DB·role·버킷 초기화. 몇 번 실행해도 같은 결과다).
3. 연결이 몰리면 위 2절의 연결 현황으로 어느 DB·상태가 많은지 본다. 대개 BE의 연결 풀이나 오래 도는 쿼리다. 원인 BE를 재시작하거나 롤백한다(RB-02).
4. 올라오지 않거나 데이터가 손상됐으면 D절(복원)이다.

### D. DB를 백업에서 되살린다(데이터 손상·삭제, RPO 안에서)

이 절차는 **사람이 개인키로** 한다(수신자 2명 중 한 명과 인프라 담당). prod DB(`fit_prod`)에 한다. dev는 [RB-13](RB-13.md)이다. 모든 단계의 목적은 **원래 DB를 지우지 않고 옆에 둔 채** 새 DB로 갈아끼우는 것이다.

0. **먼저 복원 리허설 절차(4절)로 그 백업이 풀리는지 확인한다.** 복원이 시작된 뒤에 풀리지 않는다는 걸 알면 늦다.
1. 어느 시점으로 돌릴지 정한다. 4시간 단위 백업은 48시간 안에서 전부, 그 이전은 하루 1벌이다(`sudo ls -lt /srv/vault/store/pg`, 이름의 UTC 시각). 가장 최근 정상 시점을 고른다.
2. **노트북**에서 받아 푼다(개인키는 노트북에서만 쓴다).

   ```bash
   ssh -i <B 키> ubuntu@52.78.33.39 'sudo cat /srv/vault/store/pg/pg-<UTC 시각>.dump.age' > pg-<UTC 시각>.dump.age
   age -d -i <개인키 파일> -o restore.dump pg-<UTC 시각>.dump.age
   ```

   Windows Git Bash에서는 `age` 경로와 `C:/...` 경로를 쓴다([infra/backup/README.md](../../../infra/backup/README.md) 참고). B가 죽었으면 A의 `/srv/fit/backups/pg/`에 같은 암호화 사본이 있다(`sudo cat`으로 받는다).
3. 평문을 A의 **메모리 파일시스템**(`/dev/shm`)에 올린다. 디스크에는 쓰지 않는다.

   ```bash
   scp -i <A 키> restore.dump ubuntu@k15a302.p.ssafy.io:/dev/shm/restore.dump
   ```

4. **서버 A**에서 새 DB를 만들고 복원한다. 소유자는 원본과 같이 `fit_migrator`로 둔다. `--no-owner`나 `--role`을 주지 않는다(주면 `pg_stat_statements` 확장을 못 만들거나 테이블 소유자가 `postgres`가 된다. 둘 다 시험에서 겪었다).

   ```bash
   sudo docker exec fit-data-postgres-1 psql -U postgres -c "CREATE DATABASE fit_prod_new OWNER fit_migrator"
   sudo docker exec -i fit-data-postgres-1 pg_restore -U postgres -d fit_prod_new --exit-on-error < /dev/shm/restore.dump
   echo "종료 코드 $?"                                   # 0이어야 한다
   sudo docker exec fit-data-postgres-1 psql -U postgres -d fit_prod_new -qAt -c "SELECT count(*) FROM pg_tables WHERE schemaname='public'" -c "SELECT count(*) FROM flyway_schema_history"
   ```

   테이블 수와 Flyway 기록 수가 기대와 맞는지, 핵심 테이블(예: 사용자 수)이 말이 되는지 본다.
5. **쓰기를 막는다.** prod BE를 멈춘다(FE는 DB에 쓰지 않는다). 활성 색은 `sudo bash ~/fit-repo/infra/edge/edgectl.sh status`로 본다.

   ```bash
   sudo docker stop be-prod-<활성 색>
   ```

6. **이름을 바꾼다.** 접속을 끊고 `fit_prod`를 `fit_prod_old`로 두고 새 DB를 `fit_prod`로 한다.

   ```bash
   sudo docker exec fit-data-postgres-1 psql -U postgres -qAt \
     -c "SELECT count(pg_terminate_backend(pid)) FROM pg_stat_activity WHERE datname IN ('fit_prod','fit_prod_new') AND pid <> pg_backend_pid()" \
     -c "ALTER DATABASE fit_prod RENAME TO fit_prod_old" \
     -c "ALTER DATABASE fit_prod_new RENAME TO fit_prod"
   ```

7. **접속 권한을 다시 맞춘다.** 새 DB에는 `PUBLIC` 접속 차단과 앱 role의 `CONNECT`가 없다(`CREATE DATABASE`로 만들었으므로). `ensure-databases.sh`가 멱등으로 맞춘다(role 비밀번호, 확장, 접속·테이블 권한). `init-data.sh`는 이것에 더해 Garage가 healthy가 될 때까지 기다리고 사진 저장소 설정까지 건드리므로, DB만 맞추는 이 단계에서는 `ensure-databases.sh`를 쓴다(2026-10-28 A에서 Garage가 unhealthy여서 `init-data.sh`는 멈췄을 것이다. `wait_healthy garage`가 120초 뒤 실패한다).

   ```bash
   sudo bash ~/fit-repo/infra/data/ensure-databases.sh
   ```

8. BE를 올리고 확인한다.

   ```bash
   sudo docker start be-prod-<활성 색>
   sudo bash ~/fit-repo/infra/deploy/smoke.sh prod --sha <배포된 전체 SHA>
   ```

   복원한 DB의 `flyway_schema_history`가 배포된 코드가 기대하는 마이그레이션보다 오래됐으면 마이그레이션을 한 번 돌려야 한다(같은 SHA 재배포는 마이그레이션 변경이 없다고 건너뛰므로 `FIT_FORCE_MIGRATE=1`을 준다. 배포 README 참고).
9. **평문을 지운다.** A: `rm -f /dev/shm/restore.dump`. 노트북: `restore.dump`와 내려받은 사본을 지운다(최신 암호화 사본 1벌은 세 번째 사본으로 남긴다. 설계 13.4절).
10. `fit_prod_old`는 24시간은 그대로 둔다. 문제없음이 확인되면 `DROP DATABASE fit_prod_old`로 지운다.

**복원이 DB만 되살린다는 점.** OpenSearch 색인(검색)과 Garage의 사진은 DB 복원으로 돌아오지 않는다. 색인은 재색인([RB-07](RB-07.md)), 사진은 `photos` 백업 복원이다. **사진을 되살리는 도구는 아직 없다**([RB-12](RB-12.md)의 알려진 빈칸).

### 되돌리기(D절)

- 복원 뒤 문제가 있으면 BE를 멈추고 이름을 다시 맞바꾼다(`fit_prod`→`fit_prod_bad`, `fit_prod_old`→`fit_prod`). 위 6~8단계를 반대로 한다. 2026-10-27 시험 DB로 확인한 방법이다.
- 4단계 이후 어느 때든 원래 DB(`fit_prod_old`)는 24시간 동안 그대로다. 그 안에서는 데이터를 잃지 않는다.

## 4. 복원 리허설(주 1회, 11/06 전 최소 2회)

사람이 노트북(Docker Desktop과 `age`)에서 한다. B의 사본을 받아 풀고 임시 Postgres에 복원해 보고 걸린 시간(RTO)을 잰다. 서버의 운영 DB는 건드리지 않는다.

```bash
# 1. 받는다(걸린 시간을 잰다)
time ssh -i <B 키> ubuntu@52.78.33.39 'sudo cat /srv/vault/store/pg/pg-<UTC 시각>.dump.age' > pg-<UTC 시각>.dump.age
# 2. 풀고 복원하고 RTO를 낸다(저장소 루트에서)
bash infra/backup/restore-check.sh -i <개인키 파일> --fetch-seconds <1에서 잰 초> \
  --sql 'SELECT count(*) FROM flyway_schema_history' pg-<UTC 시각>.dump.age
```

- 끝에 `RTO: <초>초`가 나온다. 결과를 금고 지표로 남기려면 B에서 안내된 `sudo /usr/local/lib/fit/repo/infra/backup/vault-ingest.sh record-restore <epoch> <RTO>`를 실행한다(`--record <user>@<B>`로 한 번에도 된다).
- 사진·인증서 백업(`photos-*.tar.age`, `caddy-*.tar.age`)은 풀어서 tar 목록을 본다. BE가 아직 마이그레이션하기 전의 빈 DB는 `--allow-empty`를 붙인다.
- Windows Git Bash는 `age`를 PATH에 넣고 `C:/...` 경로와 `TMPDIR=C:/Users/<이름>/AppData/Local/Temp`가 필요하다.
- 결과는 [infra/backup/README.md](../../../infra/backup/README.md)의 "리허설 기록"에 한 줄 더한다. `FitVaultRestoreCheckOverdue`는 마지막 리허설이 8일을 넘으면 info로 알린다.
