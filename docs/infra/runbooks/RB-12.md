# RB-12 서버 A 소실 시 재구축(DR)

- 검증 기준: develop `7470db6`, 2026-10-28. **이 절차를 서버에서 따라 해 본 적이 없다.** 각 스크립트의 설명, README, 다른 런북에서 확인한 사실로 순서를 짰고, 서버 A에서 "지금 A에 무엇이 있고 무엇이 백업되는가"를 읽기만 해서 확인했다(범위 참고). 설계 10.3절의 리허설 항목 "B 중단, A 재구축 + 금고 복원"이 남아 있고, 그 리허설 전에는 이 런북을 믿지 말고 빈칸을 아래 "알려진 빈칸"에서 먼저 메운다.
- 쓰는 때: A에 접속이 안 되고 복구할 수 없을 때(인스턴스가 사라졌거나 디스크가 깨졌을 때). A가 잠깐 죽은 것이면 이 런북이 아니라 RB-01(`fit-up.sh`)이다. **A는 SSAFY가 준 서버라 새 서버를 받는 것도 SSAFY 담당에게 요청해야 한다**(우리에게 콘솔이 없다).
- 준비: [README.md](README.md)의 접속, [RB-06](RB-06.md)(DB 복원), [RB-07](RB-07.md)(재색인), [RB-05](RB-05.md)(인증서).
- 목표: 복원 목표는 RPO 4시간, RTO 2시간(제안값)이다. 시험한 것은 DB 복원뿐이고(리허설 #2는 7초, 빈 DB에 가까웠다) **서버 전체를 다시 세우는 시간은 한 번도 재 본 적이 없다.**

| age 수신자 공개키 파일 | A의 `/etc/fit/keys/age-recipients.txt`에 있다. 서버 밖 사본이 있는지는 확인하지 못했다 (미확인). 공개키라 어디에 두어도 안전하다 | RB-06 |
| 배포 상태 파일(`/srv/fit/state`) | 사라진다. 첫 배포로 다시 만들어진다 | 배포 README |

| dev DB와 dev 사진 | 백업하지 않는다. **잃는다** | 설계 8절 |

## 3. 순서

번호 순서를 지킨다. 5번(env)이 없으면 이후가 모두 막히고, 인증서(9번)는 엣지를 올리기 전에 해야 한다.

### 0. 판단과 공지

A가 정말 안 되는지 본다(RB-01 `FitPortUnreachable`, 콘솔은 없으므로 SSH와 80/443 연결로 판단한다). 팀 채널에 알린다. SSAFY에 새 서버를 요청한다(같은 사양: x86, 4 vCPU, 16GB, 300GB급 디스크, Ubuntu 24.04).

### 1. 새 서버를 받으면(공인 IP 확인)

IP가 **같으면** 아래 "IP가 바뀐 경우"는 건너뛴다. **다르면** 먼저 해 둔다.

- **DNS:** 가비아의 A 레코드(`PROD_HOST`, `DEV_HOST`, TTL 600초)를 새 IP로 바꾼다. DNS 변경은 우리가 직접 하므로 도메인 변경 요청 절차는 없다(설계 1.3절). 퍼지는 데 TTL(10분)만큼 걸린다. 인증서 발급(HTTP-01)이 이 DNS를 따라간다.
- **B 쪽:** B의 방화벽과 fail2ban 허용에 A의 IP가 들어 있다. 다시 맞춘다: `sudo ROLE=ops FIT_PEER_IP=<새 A IP> bash ~/host/bootstrap.sh`(몇 번 해도 같은 결과다).
- **금고 전송 제한:** B의 금고 계정은 A의 IP에서만 들어오게 묶여 있다(`from=`). 6번에서 새 키를 등록할 때 새 IP를 준다.
- 알려진 위험: 새 IP를 그대로 받을 수 있는지(Elastic IP 여부)는 알 수 없다. 위험 19(설계).

### 2. 호스트를 만든다(bootstrap)

[infra/host/README.md](../../../infra/host/README.md)의 "서버에서 하는 순서" 1~5번을 따른다. 관리자 계정으로 키 접속이 되는지 **다른 터미널에서 먼저 확인**하고, `infra/host/`를 `~/host`로 복사하고(`scp -r infra/host <서버>:~/host`), 적용한다.

```bash
sudo ROLE=app FIT_PEER_IP=<B의 공인 IP> bash ~/host/bootstrap.sh
sudo bash ~/host/verify-host.sh          # 전부 PASS
```

공유 Docker 망 여섯 개와 `/srv/fit/state`, `/srv/fit/web`도 이때 만들어진다. 팀원의 `fit-dev` 공개키(터널용)는 host README의 7번대로 따로 다시 넣는다.

### 3. 저장소 사본을 올린다

README의 "서버에 있는 스크립트 사본"을 따른다. 새 서버라 `~/fit-repo`가 없으므로 디렉터리를 만들고 푼다.

```bash
# 노트북, 저장소 루트에서(HEAD가 올릴 커밋)
git archive HEAD infra docs/infra/contracts | ssh -i <A 키> ubuntu@<A> 'mkdir -p ~/fit-repo && tar -x --overwrite -C ~/fit-repo'
```

### 4. 엣지 상태 파일을 둔다

엣지는 활성 색을 가리키는 파일이 있어야 뜬다. 첫 배포 전이라 견본을 둔다(배포가 이후에 이 파일을 쓴다).

```bash
sudo cp ~/fit-repo/infra/edge/state-sample/upstream-*.caddy /srv/fit/state/
```

### 5. env 파일을 되돌린다

팀 비밀번호 관리자의 사본을 `/etc/fit/`에 넣는다. 모드는 `root:docker 0640`이다. 값을 화면에 내지 않는다. 확인한다.

```bash
sudo python3 ~/host/envset.py status | tail -n 3      # 키와 형식(값은 안 나온다)
```

`DEV_GATE_KEY`, 웹훅, 외부 키는 그대로 옛 값이다. 유출 걱정이 있으면 이 시점에 RB-08로 바꾼다.

### 6. 백업 구성과 금고 연결

```bash
sudo bash ~/fit-repo/infra/backup/install.sh app        # 키 디렉터리와 새 전송 키(vault_ed25519)를 만들고 남은 수동 단계를 안내한다
# 그 뒤 /etc/fit/keys/age-recipients.txt에 수신자 공개키 2개(age1…)를 한 줄씩 넣는다(root 0600, RB-08 H절의 방식)
```

`install.sh app`은 `backup.env`가 이미 있으면(5번에서 되돌렸으면) 건드리지 않는다. 안내대로 **B에서** 새 공개키를 등록한다: `sudo bash infra/backup/vault-authorize.sh '<새 공개키 한 줄>' <새 A IP>`. 이어서 **A에서** B의 호스트 키 지문을 B의 지문과 대조한 뒤 `sudo bash ~/fit-repo/infra/backup/install.sh pin-vault-host --yes`.

### 7. 데이터 스택을 올린다

```bash
sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env up -d --wait
sudo bash ~/fit-repo/infra/data/init-data.sh            # DB, role, 버킷, 키(빈 볼륨이라 새로 만든다)
sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 2
```

`fit-up.sh`(RB-01)는 엣지, 앱, 관측까지 이어서 올리므로 여기서는 쓰지 않는다. 인증서(9번)를 먼저 되돌린 뒤에 엣지를 올리기 위해서다.

### 8. DB를 복원한다

[RB-06](RB-06.md) D절을 따른다. 새 서버에는 `fit_prod`가 비어 있다(7번이 만들었다). D절의 4~8단계(새 DB에 복원, 이름 교체, `ensure-databases.sh`로 권한 맞춤)를 그대로 쓴다. **5단계의 "prod BE 정지"는 이 시점에 BE가 없으므로 건너뛴다.** 복원한 DB의 Flyway 이력이 배포할 코드보다 오래됐으면 12번 배포 때 마이그레이션이 돈다.

### 9. 인증서를 되돌린다(권장, 엣지를 올리기 전에)

`caddy-*.tar.age`를 B에서 받아 노트북에서 풀고(RB-06 2·4절의 방법), 볼륨을 만들어 풀어 넣는다. 인증서를 새로 받아도 되지만 발급 한도(같은 호스트의 재발급 횟수 제한)에 걸리면 한동안 HTTPS가 안 된다([RB-05](RB-05.md)).

```bash
# 노트북: age -d -i <개인키> -o caddy.tar caddy-<UTC 시각>.tar.age  → scp로 A의 /dev/shm/caddy.tar에 올린다
sudo docker volume create fit-edge_caddy_data
sudo docker run --rm -v fit-edge_caddy_data:/d -v /dev/shm/caddy.tar:/in.tar:ro python:3.12.15-slim tar -C /d -x -f /in.tar
rm -f /dev/shm/caddy.tar
```

(이 명령은 `files-backup.sh caddy`가 `tar -C /d -c .`로 묶는 것의 반대다. 서버에서 실행해 본 적은 없다.)

### 10. 엣지와 관측을 올린다

```bash
sudo bash ~/fit-repo/infra/deploy/fit-up.sh              # 공유 망, data(이미 있음), 엣지, 앱(없으면 건너뜀), 관측
sudo bash ~/fit-repo/infra/edge/edgectl.sh status
sudo bash ~/fit-repo/infra/obs/install.sh                # 일일 요약 타이머와 사본
```

`ACME_MODE`가 `production`이면 곧바로 인증서를 받는다. 9번을 못 했고 한도가 걱정이면 먼저 `staging`으로 확인한다(edge README의 단계).

### 11. 러너를 다시 등록한다

GitLab에서 A용 러너(`fit-deploy`, 태그 `deploy`, Protected)를 새로 만들고(Maintainer 권한), 토큰으로 등록한다. 토큰은 채팅에 붙이지 않는다.

```bash
sudo bash ~/host/runner.sh install
sudo bash ~/host/runner.sh register        # 토큰을 숨김 입력으로 받는다
```

### 12. 앱을 배포한다

A의 이미지가 모두 사라졌으므로 CI가 이미지를 다시 만들어야 한다. GitLab에서 `develop`의 최신 파이프라인의 `build:images`와 `deploy:dev`를 실행하고(dev), prod는 `master`의 `deploy:prod`를 수동으로 실행한다([RB-02](RB-02.md)). **RB-02b의 번들 방식은 쓸 수 없다**(서버에 이미지가 없어서 preflight가 막는다). 처음 prod 배포라 `deploy-prod.env` 상태 파일이 없다는 점도 첫 배포와 같다.

### 13. 검색과 사진

- **검색:** [RB-07](RB-07.md) 4절의 "전체를 다시 만들 때"로 Postgres에서 다시 색인한다. 색인이 끝날 때까지 검색이 안 된다.
- **사진:** 되살리는 도구가 없다. 알려진 빈칸이다.

### 14. 확인

```bash
sudo env FIT_PEER_IP=<B의 공인 IP> bash ~/fit-repo/infra/host/verify-host.sh | tail -n 2
sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 2
sudo bash ~/fit-repo/infra/obs/verify-obs.sh | tail -n 2
sudo bash ~/fit-repo/infra/deploy/smoke.sh prod --sha <배포된 전체 SHA>
sudo systemctl start fit-backup@pg.service        # 백업이 B에 도착하는지(RB-06 2절)
```

B에서 `FitPortUnreachable`, `FitExternalDown`, `FitVaultStale` 등이 풀렸는지 본다. 이어서 복원 리허설을 한 번 한다(RB-06 4절).

## 알려진 빈칸(서버를 다시 세우기 전에 메워야 할 것)

1. **사진 복원 도구가 없다.** `files-backup.sh photos`가 prod 버킷 전체를 tar로 묶어 암호화하지만, 그 tar를 풀어 Garage에 다시 올리는 명령이 없다. `infra/data/s3tool.py`는 `put`(텍스트만), `get`, `tar-stdout`(읽기)뿐이다. 도구를 만들어(tar를 읽어 객체로 올리는 명령) 노트북 시험으로 확인해야 한다. 새 Jira 티켓이 필요하다.
2. **env 사본이 USB 하나뿐이다.** 2026-11-12에 만든 암호화 사본(`fit-env-20261112.tar.age`)을 USB에 저장했고 수신자 2명이 복호화를 확인했다. 두 번째 보관 위치가 없고 팀 비밀번호 관리자에 있는지는 확인하지 못했다 (미확인). 위 "미리 해 둘 것"의 첫 항목.
3. **전체 재구축 시간(RTO)을 모른다.** 리허설로 재야 한다.
4. **새 IP를 어떻게 받는지 모른다.** 콘솔이 없어 Elastic IP를 우리가 붙이지 못할 가능성이 크고, 그러면 SSAFY가 어떤 IP를 줄지에 달렸다.
5. **9번(인증서 복원)과 6번(금고 키 교체)의 명령은 시험하지 않았다.**

## 되돌리기

이 런북은 새로 만드는 절차라서 "원래대로"는 없다. 단계마다 실패하면 그 단계의 확인 명령으로 원인을 보고 다시 한다(스크립트는 몇 번 실행해도 같은 결과다). 새 서버를 쓰지 못하게 되면 SSAFY에 다시 요청한다. DNS를 새 IP로 바꿨다가 옛 서버가 살아나면 A 레코드를 옛 IP로 되돌린다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-28): 서버 A에서 무엇이 어디에 있는지 읽기만 했다(env 파일 이름과 권한, 백업 폴더, 볼륨 목록, `/srv/fit` 구조, `/etc/fit/keys` 존재). 순서에 쓴 스크립트(`bootstrap.sh`, `runner.sh`, `install.sh`, `vault-authorize.sh`, `fit-up.sh`, `init-data.sh`, `files-backup.sh`)와 README의 설명을 읽고 인자와 순서를 확인했다. 노트북에서 데이터 스택의 초기화(`init`)와 DB 복원·비밀번호 교체 시험을 돌렸다(RB-08).
- 실행하지 못함: **이 절차 전체.** 새 서버에서의 bootstrap, env 되돌리기, 금고 키 교체, DB 복원 이어 붙이기, 인증서 복원, 엣지·관측 기동, 러너 등록, 재배포, 재색인, 사진 복원(도구 없음). 옛 IP와 새 IP 사이의 DNS 전환도 해 본 적이 없다.
