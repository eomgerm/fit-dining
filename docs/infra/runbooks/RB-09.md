# RB-09 CPU 버스트 소진 의심

- 검증 기준: develop `7470db6`, 2026-10-28. 서버 A에서 확인 명령을 실제로 실행했다. CPU를 일부러 올려 보거나 크레딧 잔액을 본 적은 없다(콘솔이 없다. 범위 참고).
- 쓰는 때: `FitCpuHigh30m`(주의, 30분 평균 40% 초과), `FitCpuHigh2h`(장애, 2시간 평균 40% 초과)가 울릴 때. 서버 전체가 느린데 메모리와 디스크는 괜찮을 때.
- 준비: [README.md](README.md)의 접속.

## 1. 무엇을 의심하나

A는 EC2 `t3.xlarge`(4 vCPU)다(2026-10-28 인스턴스 메타데이터로 확인). T3는 **CPU 크레딧**으로 도는 버스트형 인스턴스다. t3.xlarge는 vCPU당 40%가 baseline이라, 평균 CPU 사용률이 40%를 넘기면 쌓아 둔 크레딧을 쓰고 크레딧이 떨어지면 baseline으로 눌린다(AWS 문서). 알림의 40%가 이 기준선이다.

| 값 | t3.xlarge (AWS 문서) |
|---|---|
| baseline | vCPU당 40%, 전체 평균 사용률 40%(지속 약 1.6 vCPU) |
| 크레딧 적립 | 시간당 96개 |
| 적립 한도 | 2304개(하루치) |
| 크레딧 1개 | vCPU 하나를 100%로 1분 쓴 양 |

평균 사용률이 `u`(0~1)일 때 크레딧은 분당 `4u − 1.6`개씩 변한다(양수면 줄고 음수면 쌓인다). 가득 찬 2304개로 평균 100%를 버티면 약 16시간, 평균 60%면 약 48시간이다. **이 시간은 AWS 문서의 식으로 계산한 값이다.** 실제 잔액은 보지 못했다.

**크레딧 모드는 모른다(미확인).** T3의 기본은 `unlimited`(크레딧이 떨어져도 안 눌리고 추가 요금)이고 `standard`는 눌린다. A는 SSAFY가 준 서버라 콘솔이 없어 어느 쪽인지 확인하지 못했다. `unlimited`면 느려지지 않을 수 있다. 눌리는 징후는 아래 CPU steal이다.

## 2. 확인 명령

모두 읽기만 한다. 서버 A에서:

```bash
nproc; lscpu | grep -E 'Model name|Hypervisor'
vmstat 1 4                                      # 마지막 열 st가 steal(%). 눌리면 이 값이 커진다
uptime                                           # load average가 4(vCPU 수)를 오래 넘으면 CPU가 모자란 것이다
sudo docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}'
top -b -n 1 -o %CPU | head -n 15                # 컨테이너 밖 프로세스(백업, 러너, apt)도 본다
systemctl list-timers --no-pager | head -n 20   # 지금 시각에 도는 타이머(백업, 정리, 일일 점검)
```

Prometheus(A의 `127.0.0.1:9090`)로 추이를 본다.

```bash
q() { curl -s -G http://127.0.0.1:9090/api/v1/query --data-urlencode "query=$1"; echo; }
q '1 - avg(rate(node_cpu_seconds_total{mode="idle"}[30m]))'      # 알림 FitCpuHigh30m이 보는 값(0.4 = 40%)
q '1 - avg(rate(node_cpu_seconds_total{mode="idle"}[2h]))'       # 알림 FitCpuHigh2h
q 'avg(rate(node_cpu_seconds_total{mode="steal"}[5m]))'          # steal 비율
q 'topk(5, sum by (name) (rate(container_cpu_usage_seconds_total{name!=""}[5m])))'   # 컨테이너별 CPU(코어 수 단위)
```

인스턴스 유형은 이렇게 읽는다(메타데이터 IMDSv2).

```bash
T="$(curl -s -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')"
curl -s -H "X-aws-ec2-metadata-token: $T" http://169.254.169.254/latest/meta-data/instance-type
```

2026-10-28 정상 값: 30분 평균 6.0%, 2시간 평균 6.1%, steal 0.2%, vmstat st 0~1, load average 0.3. 컨테이너별로는 cadvisor 0.023코어, fe-dev 0.019, postgres 0.018, redis-dev 0.013이 상위였다(합쳐도 0.1코어 안팎). 최근 3일 평균 5.8%였고 5분 평균의 최댓값은 42.9%였다(설계 1.2절).

## 3. 조치

### A. 일시적인 몰림(30분 알림만, 몇 분 안에 내려감)

배포(`build:images`와 `deploy:*`는 A의 러너가 돈다), 백업(4시간마다 덤프와 압축, 사진은 매일 새벽), 주간 정리, 마이그레이션이 CPU를 쓴다. 위 2절의 `systemctl list-timers`와 `docker stats`로 어느 것인지 본다. 일이 끝나면 내려가므로 조치는 없다. `FitCpuHigh2h`가 울리지 않으면 지켜본다.

### B. 오래 높다(2시간 알림, 장애)

1. **누가 쓰는지** 2절의 `topk`와 `top`으로 찾는다. 대개 한 컨테이너나 한 프로세스다.
2. **원인이 서비스면** 그 서비스를 본다. BE의 무한 루프나 스레드 폭주면 로그를 보고 재시작하거나 롤백한다(RB-02). OpenSearch면 RB-07.
3. **사람이 줄일 수 있는 부하를 끈다(비상안).** dev 스택이 가장 먼저 줄일 수 있다(설계 위험 표 1번, 비상안은 dev 스택 중지).

   ```bash
   sudo docker stop be-dev fe-dev
   ```

   dev 사용자(팀원)에게 알린다. prod와 데이터 스택은 건드리지 않는다.
4. 몇 분 뒤 vmstat의 id와 Prometheus 값이 내려가는지 본다. 크레딧은 평균 사용률이 40% 아래일 때 쌓인다. 이후 2시간 알림은 창이 지나야 풀린다.
5. 그래도 높고 steal이 평소(1% 안팎)보다 눈에 띄게 높은 채 계속되면 눌리고 있는 것이다(`standard` 모드로 보인다. 몇 %부터인지는 실측한 적이 없다). 서버 사양을 올려야 하는데 A는 SSAFY가 준 서버라 우리가 못 바꾼다. SSAFY 담당에게 더 큰 인스턴스나 `unlimited` 설정을 요청한다.

### 되돌리기

끈 서비스를 다시 올린다.

```bash
sudo docker start be-dev fe-dev
# 확인: sudo bash ~/fit-repo/infra/deploy/smoke.sh dev --sha <배포된 전체 SHA>
```

부하가 내려간 뒤에 올린다. 올리자마자 다시 2시간 알림이 울릴 수 있으니 올린 뒤 30분은 값을 지켜본다.

## 4. 기록

알림이 울릴 때마다 시작 시각, 원인(컨테이너나 타이머), 끈 것, 해소 시각을 팀 채널에 적는다. 쌓이면 설계 1.2절의 "크레딧 실측"을 채우고 부하 시험(경량, 4.4절 가정)의 기준으로 쓴다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-28, A): 2절의 확인 명령 전부(nproc, lscpu, vmstat, uptime, Prometheus 질의 네 개, 인스턴스 유형 조회). 인스턴스 유형은 `t3.xlarge`였다.
- 실행하지 못함: CPU를 일부러 올려 알림을 일으키기, 3절 B의 dev 스택 중지와 재시작(팀원이 쓰는 환경이라 하지 않았다), 크레딧 잔액과 모드 확인(AWS 콘솔이 없다), steal이 실제로 오르는 상황. 평균 사용률 계산식은 AWS 문서의 값으로 계산한 것이고 서버에서 실측하지 않았다.
