# RB-13 dev DB 초기화

- 검증 기준: develop `7470db6`, 2026-10-28. 서버 A에서 확인 명령과 연습용 DB의 만들기·소유자·삭제를 실제로 실행했다. **실제 `fit_dev`를 초기화해 본 적은 없고**, 마이그레이션 컨테이너로 빈 DB를 채우는 단계는 연습용 DB로 시험하지 못했다(범위 참고).
- 쓰는 때: dev 배포(`deploy:dev`)가 "마이그레이션에 실패했다"로 멈추고 원인이 dev DB의 Flyway 이력이 코드와 어긋난 것일 때. 기능 브랜치를 dev에 올렸다가 내려서 `develop`에 없는 마이그레이션이 dev DB에 적용돼 있을 때(설계 10.8절). dev 데이터를 일부러 비우고 싶을 때.
- **prod에는 쓰지 않는다.** prod DB는 RB-06이다.
- 준비: [README.md](README.md)의 접속.

## 1. 알아 둘 것

- 이 절차는 **dev DB(`fit_dev`)의 데이터를 비운다.** 팀원의 시험 계정(소셜 로그인으로 만든 것 포함), 온보딩 취향, 로그인 세션이 사라진다. dev는 백업하지 않는다(설계 8절은 `fit_prod`만 백업한다). 시작 전에 팀 채널에 알린다.
- Flyway 원칙: 적용된 마이그레이션 파일은 고치지 않고, 실패해도 되돌리지 않는다(forward-fix, 배포 README). 어긋남은 "고쳐서 맞추기"가 아니라 DB를 새로 만들어 처음부터 적용하는 것으로 푼다.
- **`fit_dev`를 지우지 않고 옆에 둔다.** 이름만 바꿔 두고 새 DB를 만든다(RB-06 D절과 같은 방식). 문제가 생기면 이름을 되돌린다.
- 이 절차 중에는 `be-dev`가 멈춘다. FE(`fe-dev`)는 DB를 직접 쓰지 않아 그대로 두어도 된다(BE가 응답하지 않을 뿐이다).

## 2. 확인 명령(진단)

모두 읽기만 한다. 서버 A에서:

```bash
# 배포가 어디서 멈췄나(마이그레이션이면 이 DB 문제다)
sudo tail -n 6 /srv/fit/state/history-dev.log
# dev DB에 적용된 마이그레이션
sudo docker exec fit-data-postgres-1 psql -U postgres -d fit_dev -c "SELECT installed_rank, coalesce(version,'(repeatable)') AS version, description, success FROM flyway_schema_history ORDER BY installed_rank"
# 지금 배포된 SHA와 BE 이미지
sudo grep -E '^(DEPLOYED_SHA|BE_DEV_TAG)=' /srv/fit/state/deploy-dev.env
```

코드 쪽 마이그레이션 목록은 노트북에서 본다: `git ls-tree --name-only <SHA> be/src/main/resources/db/migration/`.

- **어긋남의 모양:** DB에는 있는데 코드에 없는 버전이 있다(기능 브랜치가 만든 것), 또는 같은 버전의 내용이 다르다(적용된 파일을 고쳤다). 배포 로그에는 `마이그레이션에 실패했다`가 나온다. 이때 배포는 트래픽을 건드리기 전에 멈추므로 dev는 이전 버전으로 계속 떠 있다.
- 마이그레이션이 정말 이 이유로 실패한 것인지는 일회성 컨테이너의 로그로 확인한다(CI 잡 로그, 또는 3절 5단계의 출력). **한 번 시도한 뒤 판단한다. 파일 내용이 바뀐 것이면 DB를 초기화해도 같은 파일이 또 실패한다.** 그때는 BE 팀이 마이그레이션 파일을 고친다.
- 2026-10-28 정상 값: 적용 이력 6건(V1~V5와 반복 시드 1건), 모두 `success=t`, `fit_dev`는 테이블 11개.

## 3. 초기화 절차

0. 팀 채널에 알린다. 다시 올릴 SHA를 정한다(보통 `develop`의 배포 가능한 최신).
1. (선택) 안전 사본을 **메모리**에 뜬다. 개인정보(소셜 이메일 등)가 있으므로 디스크에 쓰지 않는다.

   ```bash
   sudo docker exec fit-data-postgres-1 pg_dump -U postgres -Fc -d fit_dev > /dev/shm/fit_dev-$(date +%Y%m%d).dump
   ```

   스키마만 필요하면 `-s`를 준다(데이터 없이 테이블 정의만 나온다. 2026-10-28 `fit_dev`로 확인: `CREATE TABLE` 11건, `COPY` 0건). 작업이 끝나면 `rm -f /dev/shm/fit_dev-*.dump`로 지운다.
2. `be-dev`를 멈춘다.

   ```bash
   sudo docker stop be-dev
   ```

3. 접속을 끊고 이름을 바꾼다.

   ```bash
   sudo docker exec fit-data-postgres-1 psql -U postgres -qAt \
     -c "SELECT count(pg_terminate_backend(pid)) FROM pg_stat_activity WHERE datname='fit_dev' AND pid <> pg_backend_pid()" \
     -c "ALTER DATABASE fit_dev RENAME TO fit_dev_old"
   ```

4. 새 `fit_dev`를 만들고 권한을 맞춘다. `ensure-databases.sh`가 DB가 없으면 만들고(소유자 `fit_migrator`), 확장(`vector`, `pg_stat_statements`)과 접속·테이블 권한, 앱 role 비밀번호를 설계대로 맞춘다. 몇 번 실행해도 같은 결과다.

   ```bash
   sudo bash ~/fit-repo/infra/data/ensure-databases.sh
   ```

   `init-data.sh`가 아니라 이것을 쓰는 이유: `init-data.sh`는 Garage가 healthy가 될 때까지 기다린 뒤 사진 저장소 설정까지 건드린다. DB만 맞추면 되는 이 절차에서는 필요 없고, Garage가 불안정하면 멈춘다.
5. 마이그레이션을 **지금 한 번** 돌린다. 코드가 바뀐 적 없는 같은 SHA의 배포는 "마이그레이션 변경 없음"으로 건너뛰므로(배포 README, `FIT_FORCE_MIGRATE=1`이 이를 강제한다), 배포 전에 일회성 컨테이너로 직접 돌린다. 이미지는 다시 올릴 SHA의 것이다(`sudo docker images --format '{{.Repository}}:{{.Tag}}' | grep '^be:'`).

   ```bash
   sudo docker run --rm --name fit-migrate-dev --network net-data \
     --env-file /etc/fit/migrate-dev.env be:<다시 올릴 전체 SHA>
   echo "종료 코드 $?"      # 0이어야 한다
   ```

   `deploy.sh`가 마이그레이션 때 쓰는 명령과 같다. 끝나면 새 DB의 이력을 본다(2절의 `flyway_schema_history` 질의에 `-d fit_dev`). 테이블 수와 반복 시드(이유 태그 28건)가 들어갔는지 본다.
6. dev를 올린다. 이미 그 SHA가 떠 있으면 `be-dev`를 시작하면 된다. 다른 SHA로 올릴 것이면 GitLab에서 그 SHA의 `deploy:dev`를 Retry한다(마이그레이션은 이미 했으므로 배포가 변경 없음으로 건너뛰어도 괜찮다).

   ```bash
   sudo docker start be-dev            # 같은 SHA를 그대로 쓸 때
   sudo bash ~/fit-repo/infra/deploy/smoke.sh dev --sha <배포된 전체 SHA>
   ```

7. 정리한다. `fit_dev_old`는 24시간 둔 뒤 문제가 없으면 지운다: `sudo docker exec fit-data-postgres-1 psql -U postgres -c "DROP DATABASE fit_dev_old"`. 안전 사본(1단계)도 지운다.

   BE가 시작하면 간소 모드의 **데모 계정은 자동으로 다시 만들어진다**(비어 있는 DB에 없을 때만 만드는 시드). 소셜 계정은 각자 다시 로그인하면 새로 생긴다. 온보딩 취향은 다시 입력해야 한다.

### 되돌리기

원래 데이터로 돌아가려면 BE를 멈추고 이름을 다시 맞바꾼다(`fit_dev_old`가 남아 있는 동안).

```bash
sudo docker stop be-dev
sudo docker exec fit-data-postgres-1 psql -U postgres -qAt \
  -c "SELECT count(pg_terminate_backend(pid)) FROM pg_stat_activity WHERE datname IN ('fit_dev','fit_dev_old') AND pid <> pg_backend_pid()" \
  -c "ALTER DATABASE fit_dev RENAME TO fit_dev_bad" \
  -c "ALTER DATABASE fit_dev_old RENAME TO fit_dev"
sudo docker start be-dev
```

돌아간 DB는 어긋난 상태 그대로라서 배포 문제는 남는다. 원인(기능 브랜치의 마이그레이션)을 정리한 뒤 다시 시도한다.

## 4. 연습해 둘 만한 것

- 이 절차의 5단계는 BE의 환경 검사에 걸려 **DB 이름을 바꿔 연습할 수 없었다.** 마이그레이션 컨테이너는 `APP_ENV=dev`일 때 DB 이름이 `fit_dev`여야 기동한다(`환경변수 계약을 어겨 기동을 거부한다`). 진짜 `fit_dev`로만 시험할 수 있어서, 처음 하는 날 팀이 `fit_dev`를 비워도 되는 때에 한 번 해 보고 걸린 시간을 이 문서에 적는다.
