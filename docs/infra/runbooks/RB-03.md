# RB-03 메모리 부족과 OOM

- 검증 기준: develop `52c661d`, 2026-10-27. 서버 A에서 확인 명령을 실제로 실행했다(평상시 값 포함). 조치 중 dev 중지와 러너 동시 실행 수 조절은 실행하지 않았다(범위 참고).
- 쓰는 때: `FitMemoryLow`, `FitSwapHigh`, `FitOomKill`, `FitContainerRestartLoop`, `FitContainerMemoryHigh`, `FitOpsMemoryLow`가 울릴 때. BE·FE가 이유 없이 재시작하거나 502가 날 때.
- 준비: [README.md](README.md)의 접속.

## 1. 평상시 값과 한도

서버 A는 RAM 15.8GB(스왑 4GB), 서버 B는 RAM 3.8GB(스왑 2GB)다. 컨테이너 한도는 compose가 정한다(`mem_limit`).

| 구성 | 한도 | 2026-10-27 사용량(A) |
|---|---|---|
| `be-prod-*` / `fe-prod-*` | 1.5GB / 512MB | BE 약 370MB(master 미리보기) |
| `be-dev` / `fe-dev` | 1GB / 400MB | BE 약 340MB |
| `fit-data-postgres-1` | 1GB | |
| `fit-data-opensearch-1`(힙 768m) | 2GB | 약 1.4GB(가장 큼) |
| redis 둘, garage | 128MB, 128MB, 192MB | |
| 관측 스택(`fit-obs-*`) | 합계 약 1.3GB | cadvisor가 한도의 76% |
| 엣지 caddy | 150MB | |

평상시 A의 가용 메모리(`available`)는 약 12GB다(2026-10-27). 한도 합계 약 9.2GB가 동시에 다 차지 않는다는 가정에 기댄 설계라서, 아래 방어선을 둔다(설계 4.1절): 스왑, 컨테이너 OOM 알림, 배포 직렬화, 비상안(dev 중지).

## 2. 확인 명령

모두 읽기만 한다.

```bash
free -m ; swapon --show                                                       # 호스트 메모리와 스왑
sudo docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}' | sort -t$'\t' -k3 -rn | head -n 8
sudo dmesg -T | grep -iE 'out of memory|oom-kill|killed process' | tail -n 5     # 커널이 죽인 프로세스(없으면 비어 있다)
sudo docker ps -aq | xargs -r sudo docker inspect -f '{{.Name}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}'
```

- `docker inspect`의 `oom=true`는 그 컨테이너가 자기 한도에 걸려 죽었다는 뜻이다. `restarts`가 계속 늘면 재시작 반복이다(`FitContainerRestartLoop`: 10분에 3회).
- 정상에서는 `dmesg`가 비어 있고 `oom=false restarts=0`이 아닌 컨테이너가 없다(2026-10-27 확인).
- 시간에 따른 추이는 Grafana(터널)나 Prometheus에서 본다. 예: `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes`.

## 3. 원인별 조치

### A. 컨테이너 하나가 한도에 걸려 죽었다(`oom=true`, `FitContainerMemoryHigh`)

1. 어느 컨테이너인지, 언제부터인지 본다(`docker inspect`, Grafana의 컨테이너 메모리).
2. BE·FE면 직전 배포가 원인인지 본다(RB-02 이력). 배포 직후부터면 롤백한다(`rollback.sh`, RB-02). 한도 안에서 도는 것이 목표이므로 한도를 올려 해결하지 않는다.
3. 한도를 바꿔야 하면 compose의 `mem_limit`을 고치는 MR이다. 호스트 전체 여유(위 1절)를 먼저 계산한다. 서버에서 직접 고치지 않는다.
4. OpenSearch가 한도(2GB)에 붙어 있으면 검색이 느려지거나 재시작한다. 힙(768m)과 인덱스 크기를 보고 BE·AI 팀과 상의한다. 급하면 `sudo docker restart fit-data-opensearch-1`로 재시작한다(데이터는 볼륨에 있어 남지만 몇십 초 검색이 끊긴다).

### B. 호스트 전체 메모리가 부족하다(`FitMemoryLow`, `FitSwapHigh`)

1. 위 `docker stats`로 상위 컨테이너를 본다. 배포가 겹치는 중(prod BE 1.5GB + FE 0.5GB가 잠시 두 배)이면 배포가 끝나기를 기다린다. 사전 점검이 여유(prod 2.5GB, dev 0.5GB)가 없으면 배포를 막는다.
2. 배치(새벽 1.2GB)나 이미지 조립이 겹친 것이면 끝나면 풀린다.
3. 계속 부족하면 **비상안: dev 스택을 일시 중지한다**(be-dev·fe-dev, 합계 약 1.4GB). prod가 먼저다.

   ```bash
   sudo docker stop be-dev fe-dev
   free -m | sed -n 2p                      # available이 늘었는지
   ```

   dev를 쓰는 팀원에게 먼저 알린다. 복구는 `sudo docker start be-dev fe-dev`이거나 `fit-up.sh`다(dev는 `unless-stopped`라 수동으로 멈추면 재부팅해도 `fit-up.sh`가 올릴 때까지 꺼져 있다).
4. 스왑이 50%를 넘어 계속 쓰이면(`vmstat 1 5`의 `si`, `so`가 0이 아님) 호스트가 느려진다. 원인 컨테이너를 찾아 재시작하거나 위 비상안을 쓴다.
5. 메모리가 모자란 채로 반복되면 한도 합계나 평상시 사용량을 다시 계산해 설계(4절)를 고친다.

### C. 서버 B의 메모리가 부족하다(`FitOpsMemoryLow`)

B는 RAM 3.8GB에 감시 스택 약 350MB가 상시 떠 있고, CI의 verify 잡이 `docker` 실행기로 잡당 2GB, 동시 3개까지 돈다(`concurrent 3`. 무거운 BE 하나와 FE 하나가 겹치면 스왑을 조금 쓴다).

```bash
sudo docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}'      # 도는 CI 잡 컨테이너
sudo docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}'
```

- 잡이 겹쳐서면 GitLab에서 오래된 파이프라인을 취소하거나 동시 실행 수를 1로 줄인다: `sudo env FIT_RUNNER_CONCURRENT=1 bash ~/fit-repo/infra/host/runner.sh tune`(러너를 재시작하지 않고 `config.toml`만 바꾼다. 원래 값은 2).
- 서비스는 B와 무관하게 돈다. B가 멈추면 CI와 감시가 멈춘다(설계 6.7절, 긴급 배포는 RB-02b).

## 4. 되돌리기

- dev 중지는 `sudo docker start be-dev fe-dev`로 되돌린다.
- 러너 동시 실행 수는 `sudo bash ~/fit-repo/infra/host/runner.sh tune`(값 없이)로 역할 기본값(B는 3)으로 돌아온다.
- OpenSearch 재시작은 되돌릴 것이 없다. 재시작 뒤 `sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 2`로 확인한다.
- compose 한도 변경은 MR을 되돌린다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-27, A): 2절의 확인 명령 전부(정상 상태: 가용 약 12GB, 스왑 8.7MB 사용, OOM 이력 없음, `oom=false restarts=0` 아닌 컨테이너 없음)와 compose에서 한도 읽기.
- 실행하지 못함: `docker stop be-dev fe-dev`와 복구(공유 dev를 끊어서), 러너 `tune`, OpenSearch 재시작, 실제 OOM이 난 상황에서의 조치(없었다). OOM 알림이 cgroup OOM도 세는지는 설계에도 "구현 시 확인"으로 남아 있고 이 런북에서도 확인하지 못했다.
