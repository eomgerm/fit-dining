# RB-02 배포와 롤백, BE·FE 응답 이상

- 검증 기준: develop `52c661d`, 2026-10-27. 서버 A에서 아래 확인 명령을 실제로 실행했다(dev 기준). prod는 아직 이 스크립트로 배포한 적이 없다.
- 쓰는 때: 배포 파이프라인이 실패했을 때, 배포 직후 문제가 생겼을 때, `FitBeProdDown`, `FitBeDevDown`, `FitHttp5xxHigh`, `FitHttpLatencyHigh`, `FitHttpMetricMissing`, `FitExternalDown`이 울릴 때.
- 준비: [README.md](README.md)의 접속과 `~/fit-repo` 사본. CI 없이 직접 배포해야 하면 [RB-02b](RB-02b.md)다.

**지금 prod는 `infra/deploy`로 배포한 적이 없다.** 공개 prod는 master 코드를 임시로 올린 미리보기(`be-prod-blue`, `fe-prod-blue`)이고 `/srv/fit/state/deploy-prod.env`가 없다. 그래서 아래 prod 명령(`rollback.sh prod`, 상태 파일)은 첫 prod 배포(Jira S15P31A302-75) 뒤에 쓴다. dev는 CI가 `develop` 병합마다 배포한다.

- AI API(`ai-prod`, `ai-dev`)를 켠 환경은 배포 로그에 `경고: [ai]`가 나올 수 있다. AI 실패는 BE·FE 배포를 막지 않는다. 대응은 [RB-14](RB-14.md)다.

## 1. 지금 상태를 본다

값은 출력하지 않는다. A에서 한다.

```bash
sudo bash ~/fit-repo/infra/edge/edgectl.sh status                  # 엣지와 활성 색(환경 × be·fe가 어느 컨테이너를 보는지)
sudo docker ps --filter name=be- --filter name=fe- --format '{{.Names}}\t{{.Status}}'
sudo grep -E '^(DEPLOYED_SHA|PREVIOUS_SHA|BE_ACTIVE|FE_ACTIVE)=' /srv/fit/state/deploy-<prod|dev>.env
sudo tail -n 10 /srv/fit/state/history-<prod|dev>.log              # 배포·롤백 이력(시각, 단계, SHA, 결과, 누가)
sudo bash ~/fit-repo/infra/deploy/smoke.sh <prod|dev> --sha <전체 SHA>   # 엣지를 거친 점검(PASS/FAIL/SKIP)
```

- SHA는 **전체 40자리**다. 이미지 태그(`be:<SHA>`, `fe:<SHA>`)가 전체 SHA여서 짧은 SHA로 이미지를 찾으면 `이미지 ... 가 있다` 점검이 실패한다.
- 정상 smoke 출력(2026-10-27 dev): BE `/healthz` 200, 엣지 경유 버전이 배포한 SHA, FE `/` 200과 HTML, `/fe-healthz` 200, `/config.json`의 env가 dev이다. 검색 폴백 점검은 `FIT_SMOKE_SEARCH_PATH`를 줄 때만 한다(없으면 SKIP).
- 밖에서 보는 값: `curl -sS -o /dev/null -w '%{http_code}\n' https://<PROD_HOST>/healthz`(B에서 해도 된다. `FitExternalDown`이 이 주소를 본다).
- BE 로그: `sudo docker logs --since 15m <be 컨테이너> 2>&1 | tail -n 50`. 로그를 채팅이나 이슈에 붙이기 전에 민감한 값이 없는지 한 번 훑는다.
- 배포 CI 잡 로그는 GitLab(`deploy:dev`, `deploy:prod`)에서 본다. 서버의 상태 파일과 이력이 진실이고, 파이프라인이 취소돼도 이력은 남는다.

## 2. 증상별 조치

### A. 방금 배포한 뒤 문제가 생겼다

가장 빠른 조치는 직전 배포로 되돌리는 것이다. 이전 색의 컨테이너와 이미지가 남아 있다(이미지는 서비스당 최근 5개만 남긴다).

```bash
sudo bash ~/fit-repo/infra/deploy/rollback.sh <prod|dev> [be|fe|all]     # 기본 all
sudo bash ~/fit-repo/infra/deploy/smoke.sh <prod|dev> --sha <되돌아간 전체 SHA>
```

- prod: 이전 색을 다시 띄워 확인한 뒤 엣지를 옮기고 지금 색을 멈춘다(끊김 없음을 목표로 한다. prod는 아직 시험하지 못했다). dev: 직전 이미지로 교체한다(서비스가 몇십 초 끊긴다).
- 되돌리기에 실패하면 지금 상태를 그대로 두고 종료 코드 1이다. 사유를 입력할 필요가 없다(긴급 복구).
- **DB 마이그레이션은 되돌리지 않는다**(forward-fix). 이전 버전이 새 스키마에서도 돌아야 한다는 expand/contract 원칙에 기댄다. 스키마가 문제의 원인이면 롤백이 아니라 고쳐서 새로 배포한다. 데이터가 망가졌으면 RB-06이다.
- BE는 성공했는데 FE만 실패한 배포는 FE만 이전 색이다. 새 BE는 직전 FE와 호환돼야 한다(BE 계약 #16). 고쳐서 같은 SHA를 다시 배포하거나 `rollback.sh prod be`로 BE를 되돌린다.

### B. 배포 파이프라인이 실패했다

실패한 단계에 따라 서버 상태가 이미 안전하게 돌아와 있다.

| 실패한 단계 | 서버에서 일어난 일 | 할 일 |
|---|---|---|
| 사전 점검, 잠금, 사전 덤프, 마이그레이션 | 서비스를 건드리지 않고 멈춤 | 로그의 FAIL 줄을 고치고 같은 파이프라인의 배포 잡을 **Retry** |
| 새 색이 안 뜸, 준비·직접 확인 실패 | 새 색을 지우고 트래픽은 그대로 | 위와 같다. BE 로그에서 기동 실패 원인을 본다 |
| 엣지 전환 뒤 확인 실패 | 엣지를 이전 색으로 되돌리고 새 색을 지움 | 위와 같다 |
| BE 성공, FE 실패 | FE만 이전 색, BE는 새 버전 | 위 A의 마지막 항목 |

사전 점검에서 자주 보는 FAIL:

- `다운그레이드가 아니다` 실패: 이미 더 새로운 SHA가 배포돼 있다. 옛 SHA를 일부러 올리려는 것이면 하지 않는다(롤백은 `rollback.sh`다).
- `이미지 ... 가 있다` 실패: `build:images` 잡이 이미지를 만들지 못했거나 짧은 SHA를 줬다. `sudo docker images --format '{{.Repository}}:{{.Tag}}' | grep -E '^(be|fe):'`로 서버에 있는 태그를 본다.
- env 점검 실패: `sudo python3 ~/host/envset.py status <prod|dev|fe-prod|fe-dev|migrate-prod|migrate-dev>`로 어느 키가 비었는지 본다. `REPLACE_ME`가 남아 있으면 막는다.
- 디스크나 메모리 여유 실패: RB-04, RB-03이다.
- 같은 SHA를 다시 배포하려면 그 파이프라인의 배포 잡을 Retry한다. 다른 배포가 돌고 있으면 잠금(`/srv/fit/state/deploy-<환경>.lock`)이 거부한다. 같은 환경의 두 번째 파이프라인은 기다린다(GitLab `resource_group`).
- **같은 SHA를 다시 배포해도 롤백 대상은 유지된다**(Jira S15P31A302-98 수정 이후의 `deploy.sh`와 `rollback.sh`). `PREVIOUS_SHA`는 그대로이고 dev는 `*_DEV_PREV_TAG`, prod는 `*_PROD_PREV_TAG`가 재배포 전의 직전 릴리스를 가리킨다.
- 수정 전의 스크립트로 이미 같은 SHA를 재배포했다면 `PREVIOUS_SHA`가 같은 SHA로 덮여 있을 수 있다(2026-10-27 dev: `a04e167…` → `52c661d…`). 그러면 `rollback.sh`는 같은 버전으로 "되돌아가서" 효과가 없고, 다운그레이드 가드가 옛 SHA를 직접 배포하는 것도 막으므로 옛 상태로 가려면 문제 커밋을 되돌리는 새 커밋을 배포해야 한다. 재배포 전에 `PREVIOUS_SHA`를 적어 두면 안전하다.

### C. 배포와 상관없이 BE·FE가 죽었다

- 컨테이너가 떠 있는지(`docker ps -a`), 재시작 횟수와 OOM 여부(`sudo docker inspect -f '{{.Name}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}' <이름>`)를 본다. OOM이면 RB-03이다.
- DB나 Redis 문제인지 본다(`FitPostgresDown`이면 RB-06). BE 로그에 접속 오류가 나오면 `sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 3`.
- 호스트를 재부팅했거나 컨테이너가 전부 내려갔으면 `sudo bash ~/fit-repo/infra/deploy/fit-up.sh`로 올린다(활성 색만 올린다).
- 컨테이너 하나만 다시 띄우면 되면 `sudo docker restart <이름>`이다. **`docker restart`는 env 파일을 다시 읽지 않는다.**

### D. env 값을 바꿨는데 반영이 안 된다

BE·FE 컨테이너는 만들어질 때 `env_file`을 한 번만 읽는다. 값을 바꾼 뒤에는 같은 SHA를 다시 배포한다(prod는 반대 색을 새 값으로 띄워 전환한다). `envset.py`의 안내 문구도 같다. 같은 SHA 재배포여도 롤백 대상은 유지된다(위 B절). 다만 롤백은 값이 아니라 이미지를 되돌리므로, 바꾼 값이 문제를 일으키면 롤백이 아니라 값을 되돌리고 다시 배포한다.

### E. `FitHttpMetricMissing`, 배치·Modal 지표 알림이 계속 울린다

BE가 아직 그 지표를 내지 않는 것이다(BE 계약 #11 미이행). 서비스 장애가 아니다. 지금 울리는 `FitBeProdDown`, `FitHttpMetricMissing`도 prod가 master 미리보기라 BE의 관리 포트(8081)와 지표가 없어서이고, 첫 prod 배포 뒤 풀린다.

## 3. 되돌리기

- 롤백(`rollback.sh`)을 되돌리려면 한 번 더 실행한다. 지금 색과 이전 색을 다시 바꾼다. 마이그레이션은 어느 방향에서도 건드리지 않는다.
- 위 확인 명령은 읽기 전용이라 되돌릴 것이 없다.
- 같은 SHA 재배포는 반복해도 서비스 결과가 같고 롤백 대상도 유지된다(이미지는 있으면 다시 조립하지 않는다. 수정 전 스크립트로 한 재배포는 위 B절).
