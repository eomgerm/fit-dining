# RB-05 인증서와 TLS

- 검증 기준: develop `52c661d`, 2026-10-27. 서버 A·B와 노트북에서 확인 명령을 실제로 실행했다. 인증서 발급·갱신 실패 상황과 `ACME_MODE` 전환은 만나 보지 못했다(범위 참고).
- 쓰는 때: `FitCertExpiringSoon`(만료 14일 미만), `FitCertExpiringCritical`(7일 미만), `FitTlsProbeFailed`(B가 TLS 연결에 실패), `FitBackupCaddyStale`(caddy 백업이 9일 넘게 없음)이 울릴 때. 브라우저가 인증서 오류를 낼 때.
- 준비: [README.md](README.md)의 접속.

## 1. 구조와 평상시 값

- 엣지 Caddy가 80·443에서 `PROD_HOST`(`fitdining.co.kr`)와 `DEV_HOST`(`dev.fitdining.co.kr`)의 인증서를 직접 받고 갱신한다. 가비아에서 산 도메인이라 Let's Encrypt **HTTP-01(80번 포트)** 방식이다(DNS-01은 쓰지 않는다). 그래서 80은 갱신 때문에 늘 열려 있어야 한다.
- 인증서와 ACME 계정은 Docker 볼륨 `fit-edge_caddy_data`에 있다. 지우면 재발급 한도에 걸릴 수 있어서 지우지 않고 백업한다(`fit-backup@caddy.service`, 주 1회 일요일).
- 단계는 `/etc/fit/edge.env`의 `ACME_MODE`다. `staging`은 시험용 CA만 쓰고, `production`은 기본 이슈어(Let's Encrypt, ZeroSSL) 폴백을 쓴다. 2026-10-27 값은 `ACME_MODE=production`, `HSTS_MODE=off`다.
- 2026-10-27 상태: 두 호스트 모두 Let's Encrypt 인증서이고 만료일은 2027-01-20이다. B의 TLS 프로브(`a-tls-prod`, `a-tls-dev`)가 성공하고 남은 기간 85.2일이다.

## 2. 확인 명령

노트북에서(서버 밖에서 보이는 인증서):

```bash
for h in fitdining.co.kr dev.fitdining.co.kr; do
  echo | openssl s_client -connect $h:443 -servername $h 2>/dev/null | openssl x509 -noout -issuer -enddate -subject
done
```

서버 A에서:

```bash
sudo grep -E '^(ACME_MODE|HSTS_MODE)=' /etc/fit/edge.env                       # 값이 아니라 모드만 나온다
sudo docker ps --filter name=fit-edge-caddy-1 --format '{{.Names}} {{.Status}}'
sudo docker logs fit-edge-caddy-1 2>&1 | grep -E '"logger":"tls' | grep -E '"level":"(error|warn)"' | tail -n 5     # 인증서 오류·경고(없으면 비어 있다)
sudo docker volume ls --format '{{.Name}}' | grep caddy                        # fit-edge_caddy_data 가 있어야 한다
curl -s -o /dev/null -w '%{http_code}\n' -m 5 http://127.0.0.1/ -H 'Host: fitdining.co.kr'   # 80이 응답하는지(308 = HTTPS로 이동)
getent hosts fitdining.co.kr dev.fitdining.co.kr                               # A의 공인 IP(3.35.170.47)인지
sudo ufw status | grep -E '^(80|443)/tcp '
```

서버 B에서(B가 보는 남은 기간과 성공 여부):

```bash
curl -sG http://127.0.0.1:9090/api/v1/query --data-urlencode 'query=(probe_ssl_earliest_cert_expiry{probe=~"a-tls-.*"} - time()) / 86400'
curl -sG http://127.0.0.1:9090/api/v1/query --data-urlencode 'query=probe_success{probe=~"a-tls-.*"}'
```

2026-10-27 정상 값: 위 로그 필터 결과 0줄(`tls.cache.maintenance`의 "updated and stored ACME renewal information"만 정기적으로 나온다), `caddy_data` 볼륨 있음, 80은 308, DNS는 `3.35.170.47`이다.

로그 필터는 `"logger":"tls`로 건다. `tls`라는 글자만으로 찾으면 reverse_proxy 요청 기록(헤더에 `tls`가 들어 있다)이 섞여 오탐이 난다(2026-10-27에 겪었다).

## 3. 원인별 조치

Caddy는 만료 전에 알아서 갱신한다(Caddy의 기본 동작이다. 이 서버에서 실제 갱신을 본 적은 없다(미확인). 첫 발급은 2026-10-22였고 만료는 2027-01-20이라 첫 갱신은 약 2026-12월이다). `FitCertExpiringSoon`이 울리면 갱신이 막혀 있다는 신호다.

### A. 갱신이 안 된다(만료 14일 미만 알림, 로그에 `tls.obtain`·`tls.issuance` 오류)

1. **80이 밖에서 닿는가.** 노트북에서 `curl -sS -o /dev/null -w '%{http_code}\n' http://fitdining.co.kr/`가 응답해야 한다(308). 안 되면 ufw(`80/tcp ALLOW`)와 엣지 컨테이너의 게시 포트(`docker ps`의 `0.0.0.0:80->80`)를 본다. 클라우드 방화벽은 SSAFY 관할이라 우리가 볼 수 없다(설계 1.3절).
2. **DNS가 A를 가리키는가.** `getent hosts <호스트>`가 `3.35.170.47`이 아니면 가비아의 A 레코드를 고친다(TTL 600초). IP가 바뀌었으면 설계 위험 19와 RB-12(미작성)다.
3. **오류 내용을 본다.** 위 로그 명령에서 `msg`와 `error`를 읽는다. Let's Encrypt 한도(같은 이름 인증서 주 5회, 실패 시간당 5회. Let's Encrypt 문서 기준이고 이 서버에서 걸린 적은 없다)에 걸렸으면 한도가 풀릴 때까지 기다린다. 운영에서는 `acme_ca`를 지정하지 않아 한쪽이 안 되면 ZeroSSL로 폴백한다.
4. 고쳤으면 Caddy가 스스로 재시도한다. 설정을 다시 불러 재시도를 앞당길 수 있다: `sudo bash ~/fit-repo/infra/edge/edgectl.sh reload`(이 명령이 재시도를 앞당기는지는 확인하지 못했다). 몇 분 뒤 위 확인 명령으로 만료일이 늘었는지 본다.

### B. `ACME_MODE`가 `staging`이다(브라우저가 "신뢰할 수 없는 인증서"를 낸다)

staging 인증서는 브라우저가 신뢰하지 않는다. 운영으로 넘기려면:

```bash
sudo python3 ~/host/envset.py set edge ACME_MODE=production
sudo docker compose -p fit-edge -f ~/fit-repo/infra/edge/compose.edge.yml --env-file /etc/fit/edge.env up -d
```

`up -d`는 caddy 컨테이너를 다시 만든다(몇 초 끊긴다). 이어서 인증서가 발급되는지 위 로그와 `openssl`로 본다. 한 번에 한 환경씩 바꾸지 않고 `edge.env`가 두 호스트에 같이 적용된다는 점에 주의한다. 이 명령은 이번에 실행하지 않았다(범위 참고).

### C. 브라우저 오류인데 인증서는 정상이다

- 인증서 체인이나 만료가 아니면 HSTS 설정(`HSTS_MODE`)과 캐시를 의심한다. 지금은 `off`다. `on`으로 바꾸면 되돌리기 어렵다(브라우저가 HTTPS만 쓰도록 기억한다). 운영 인증서가 확정된 뒤에만 켠다(Jira S15P31A302-78).
- `FitTlsProbeFailed`만 울리고 인증서는 정상이면 B에서 A의 443이 닿는지 RB-01의 도달성 점검을 한다.

### D. 인증서 백업이 오래됐다(`FitBackupCaddyStale`)

```bash
sudo systemctl start fit-backup@caddy.service
sudo journalctl -u fit-backup@caddy.service -n 20 --no-pager
grep fit_backup_last_success_timestamp_seconds /var/lib/fit/metrics/fit_backup.prom
```

2026-10-27 caddy 백업의 마지막 성공은 2일 전(일요일)이었고, 주 1회라 9일을 넘기기 전까지는 정상이다.

## 4. 되돌리기

- `ACME_MODE`를 잘못 바꿨으면 `envset.py set edge ACME_MODE=<이전 값>`과 같은 `up -d`로 돌린다. 이미 발급된 운영 인증서는 `caddy_data`에 남아 재사용된다.
- `reload`는 문법이 맞는 설정만 적용하고 틀리면 직전 설정을 유지한다.
- `caddy_data` 볼륨을 지웠다면 최근 caddy 백업(RB-06의 복호화 절차)으로 복원한다. 볼륨 복원 절차는 RB-12(미작성)에서 다룬다.
