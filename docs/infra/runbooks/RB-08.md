- 쓰는 때: 시크릿이 채팅, 저장소, 로그, 화면에 노출됐을 때. 서비스에 접근할 수 있던 사람이 팀을 떠날 때. 종료 전 정리(RB-10). 외부 서비스(Modal, GMS, Apify, 소셜 로그인)가 키를 폐기하거나 재발급하라고 할 때.

## 1. 모든 회전이 따르는 약속

1. **값을 화면과 채팅에 내지 않는다.** 만들어서 바로 `envset.py`의 입력으로 파이프한다. 이 도구는 파이프로 받은 한 줄을 그대로 쓰고, 출력에는 키 이름과 글자 수만 낸다. 이미 값이 있으면 덮어쓸지 묻는데 `--yes`로 생략한다.

   ```bash
   openssl rand -hex 32 | sudo python3 ~/host/envset.py set prod --yes JWT_SECRET
   ```

2. **같은 값이 두 파일에 있어야 하는 쌍**(예: `data.env`의 `FIT_PROD_APP_PASSWORD`와 `prod.env`의 `SPRING_DATASOURCE_PASSWORD`)은 변수에 한 번만 만들어 두 번 보낸다. 값은 변수에만 있고 화면에는 안 나온다.

   ```bash
   pw="$(openssl rand -hex 16)"
   printf '%s\n' "$pw" | sudo python3 ~/host/envset.py set data --yes FIT_PROD_APP_PASSWORD
   printf '%s\n' "$pw" | sudo python3 ~/host/envset.py set prod --yes SPRING_DATASOURCE_PASSWORD
   unset pw
   ```

3. **받는 쪽을 먼저 바꾸고, 쓰는 쪽을 곧바로 바꾼다.** 둘 사이에는 연결이 실패하는 틈이 있다. 틈을 줄이려고 명령을 한 번에 이어서 돌린다.
4. **바꾸기 전에 파일 사본을 둔다.** 잘못 바꿨을 때 옛 값으로 돌아갈 수 있어야 한다. 끝나고 확인이 되면 지운다.

   ```bash
   sudo install -m 600 /etc/fit/<파일>.env /root/<파일>.env.bak-$(date +%Y%m%d)
   # 확인이 끝나면: sudo shred -u /root/<파일>.env.bak-*
   ```

5. **반영한다.** BE·FE 컨테이너는 env를 만들어질 때 한 번만 읽는다. 값을 바꿨으면 같은 SHA를 다시 배포한다(RB-02. prod는 반대 색을 새 값으로 띄워 전환하므로 끊기지 않고, dev는 잠깐 끊긴다). data, edge, obs, ops 스택은 해당 서비스를 다시 만든다(`envset.py`가 파일마다 반영 명령을 마지막 줄에 안내한다).
6. **확인하고 옛 값을 폐기한다.** 새 값으로 동작하는 것을 본 뒤에 옛 값(옛 키, 옛 비밀번호, 옛 웹훅)을 서비스 쪽에서 지운다. 회전 기록을 남긴다(날짜, 무엇을, 누가. 값은 적지 않는다).

## 3. 절차

### A. DB 비밀번호(앱, 마이그레이션, 모니터)

`data.env`가 DB role의 기준이다. 스크립트가 role의 비밀번호를 `data.env` 값으로 맞춘다.

1. 새 비밀번호를 만들어 두 파일에 넣는다(1절 2번의 방식). 예: prod 앱이면 `data`의 `FIT_PROD_APP_PASSWORD`와 `prod`의 `SPRING_DATASOURCE_PASSWORD`. 마이그레이션이면 `data`의 `FIT_MIGRATOR_PASSWORD`와 `migrate-prod`, `migrate-dev` 두 파일의 `SPRING_DATASOURCE_PASSWORD`(`set migrate-prod,migrate-dev` 처럼 쉼표로 한 번에 넣는다). 모니터면 `data`와 `obs`의 `FIT_MONITOR_PASSWORD`.
2. DB role의 비밀번호를 맞춘다. 이 순간부터 옛 비밀번호는 통하지 않는다.

   ```bash
   sudo bash ~/fit-repo/infra/data/ensure-databases.sh
   ```

3. 곧바로 그 환경의 BE를 같은 SHA로 다시 배포한다(RB-02). 이미 떠 있는 연결은 유지되지만 새 연결은 새 비밀번호가 필요해서, 재배포가 늦으면 연결 풀이 연결을 새로 만들 때 실패한다. 모니터면 `sudo docker compose -p fit-obs -f ~/fit-repo/infra/obs/compose.obs.yml --env-file /etc/fit/obs.env up -d --force-recreate postgres-exporter`처럼 해당 서비스를 다시 만든다(서비스 이름은 `compose.obs.yml`에서 확인한다 (미실행)).
4. 확인한다. BE가 정상인지(`smoke.sh`), DB 접속 수(RB-06 2절의 질의), `FitPostgresDown` 같은 알림이 없는지 본다.

**되돌리기:** 사본(1절 4번)의 값으로 두 파일을 되돌리고 같은 순서(`ensure-databases.sh` → BE 재배포)를 다시 한다.

### B. Redis 비밀번호

1. `data.env`의 `REDIS_<환경>_PASSWORD`와 `<환경>.env`의 `SPRING_DATA_REDIS_PASSWORD`를 같은 값으로 바꾼다(1절 2번).
2. Redis 컨테이너를 다시 만든다. AOF로 데이터는 돌아온다.

   ```bash
   sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env up -d redis-prod   # dev는 redis-dev
   ```

3. 곧바로 그 환경의 BE를 같은 SHA로 다시 배포한다. 그 사이 BE의 Redis 연결(로그인 세션, 멱등성 키, 호출 예산)이 실패한다.

**되돌리기:** 사본으로 되돌리고 같은 순서를 다시 한다.

### C. Garage(사진) 키

`init-garage.sh`는 이미 있는 키를 바꾸지 않는다. 그래서 **새 키를 먼저 만들어 두 키가 함께 동작하는 틈에서 옮기고 마지막에 옛 키를 지운다.** 이 순서는 노트북의 시험 스택에서 일회용 키로 확인했다. Garage 명령은 컨테이너 안의 `garage`를 쓴다.

```bash
G='sudo docker exec -e RUST_LOG=warn fit-data-garage-1 /garage -c /etc/garage/garage.toml'
$G key list                                    # 옛 키를 확인한다
ACC="GK$(openssl rand -hex 12)"; SEC="$(openssl rand -hex 32)"
$G key import --yes -n fit-prod-new "$ACC" "$SEC" >/dev/null               # 1. 새 키를 만든다(출력에는 비밀이 나올 수 있어 버린다)
$G bucket allow --read --write --owner fit-prod-photos --key "$ACC" >/dev/null   # 2. 버킷에 권한을 준다. 이제 옛 키와 새 키가 둘 다 된다
printf '%s\n' "$ACC" | sudo python3 ~/host/envset.py set data --yes S3_PROD_ACCESS_KEY
printf '%s\n' "$ACC" | sudo python3 ~/host/envset.py set prod --yes S3_ACCESS_KEY
printf '%s\n' "$SEC" | sudo python3 ~/host/envset.py set data --yes S3_PROD_SECRET_KEY
printf '%s\n' "$SEC" | sudo python3 ~/host/envset.py set prod --yes S3_SECRET_KEY
unset ACC SEC
```

3. prod BE를 같은 SHA로 다시 배포한다(RB-02). 새 키로 사진 업로드와 읽기가 되는지 본다.
4. 확인이 끝나면 **옛 키를 지운다**: `$G key delete --yes <옛 키 ID>`. 옛 키 ID는 위 `key list`에서 본 것이다. 지운 뒤 옛 키로는 접근이 거부된다(시험: HTTP 403).
5. 같은 일이 dev에는 `fit-dev-photos`, `S3_DEV_*`, `dev.env`로 한다.

> **2026-10-28 A에서 `garage` 명령이 지금은 안 된다**(컨테이너가 오래된 설정 디렉터리를 붙잡고 있다. [README.md](README.md)의 "스크립트 사본을 갱신한 뒤" 참고). 위 명령은 Garage 컨테이너를 다시 만든 뒤에 쓴다. 사진 백업은 S3 API로 읽어서 이 문제와 무관하게 동작 중이다.

`GARAGE_RPC_SECRET`과 `GARAGE_ADMIN_TOKEN`은 `data.env`의 값을 바꾸고 Garage 컨테이너를 다시 만들어 적용한다(`up -d --force-recreate garage`, 사진 API가 잠깐 끊긴다). 단일 노드에서 RPC 비밀을 바꿔도 데이터가 그대로인지는 시험하지 못했다 (미확인).

### D. 인증 시크릿

- **`JWT_SECRET`:** BE는 Base64로 디코드한 값이 32바이트 이상이어야 기동한다. `openssl rand -base64 48`로 만든다. `prod.env`와 `dev.env`를 따로 만들어 넣는다(서로 같을 이유가 없다). 같은 SHA 재배포로 반영한다. `SocialTokens`가 서명하는 소셜 로그인 state·가입 쿠키(10분)가 무효가 되어 진행 중인 흐름을 다시 시작해야 한다. 이메일 인증번호 HMAC에도 같은 키를 써서 교체 전 발급한 미확인 번호는 재발송해야 한다. 이미 확인한 이메일 인증 토큰은 SHA-256 해시로 확인하므로 이 키 교체와 무관하다. **Redis 로그인 세션에는 영향이 없고 전체 로그아웃 수단이 아니다.** 전환 중 옛 키·새 키 인스턴스가 섞이면 진행 중인 인증이 실패할 수 있다. 옛 키로 되돌리면 아직 만료되지 않은 옛 소셜 쿠키가 다시 유효해질 수 있다.
- **`AUTH_DEV_KEY`(dev만):** 32자 이상. 바꾸고 dev를 재배포하면 옛 키로는 `POST /api/auth/dev/token`이 403이다. prod에 이 키가 있으면 BE가 기동을 거부한다.
- **`AUTH_DEMO_PASSWORD`(dev):** 데모 계정이 이미 만들어져 있으면 env를 바꿔도 **계정의 비밀번호는 안 바뀐다**(BE는 그 이메일의 계정이 없을 때만 시드한다). 바꾸려면 데모 계정을 지우고 BE를 재시작해야 한다. 개발용이라 보통 그대로 둔다.

### D-1. 해당 환경 전체 로그아웃

`JWT_SECRET` 교체와 별도로 Redis의 **해당 환경 세션 네임스페이스만** 삭제한다. `application.yml`의 namespace는 `fitdining:session:${APP_ENV:local}`이고 indexed 저장소의 세션 본체는 `fitdining:session:<환경>:sessions:<id>`다. 인덱스·만료 보조 키까지 지우는 패턴은 prod `fitdining:session:prod:*`, dev `fitdining:session:dev:*`, 로컬 `fitdining:session:local:*`다. **운영에서 `FLUSHALL`을 사용하지 않는다. `FLUSHDB`도 사용하지 않는다.** 호출 예산 등 다른 키를 보존한다.

1. 점검 시간을 공지하고 해당 환경 배포를 멈춘다. 진행 중 요청이 세션을 다시 저장하지 못하도록 해당 환경의 실행 중인 BE를 모두 정상 종료한다(prod는 blue·green 모두 확인). 아래는 서버 A의 Bash에서 실행할 prod 예제다. 세션 값이나 키 이름은 출력하지 않는다.

   ```bash
   mapfile -t session_be < <(sudo docker ps --format '{{.Names}}' | grep -E '^be-prod-(blue|green)$')
   if ((${#session_be[@]})); then
     sudo docker stop --time 40 "${session_be[@]}"
     printf '중지한 BE(재시작 시 사용할 이름): %s\n' "${session_be[@]}"
   fi
   # be-prod-blue/green이 모두 중지됐는지 확인한다. 남아 있으면 삭제를 진행하지 않는다.
   sudo docker ps --format '{{.Names}}' | grep -E '^be-prod-(blue|green)$'
   ```

2. 마지막 명령의 출력이 없음을 확인한 뒤 prod Redis에서만 아래를 실행한다. Redis 컨테이너의 `REDISCLI_AUTH`를 사용하며, 비밀번호를 인자에 넣지 않는다. `SCAN`으로 범위를 좁히고 `UNLINK`로 세션 본체와 보조 키를 삭제한다.

   ```bash
   sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env exec -T redis-prod sh -eu -c '
     redis-cli --scan --pattern "fitdining:session:prod:*" |
     while IFS= read -r key; do
       redis-cli UNLINK "$key" >/dev/null
     done
   '
   # 중지 상태에서 0이어야 한다. 0이 아니면 원인을 확인하고 삭제·확인을 반복한다.
   sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env exec -T redis-prod redis-cli --scan --pattern 'fitdining:session:prod:*' | wc -l
   ```

3. 삭제 전 실행 중이던 BE만 다시 시작한다. Redis·BE readiness와 RB-02의 smoke를 확인한다. 이전 쿠키로 `GET /api/auth/me`가 401인지, 새 로그인과 CSRF 헤더를 보낸 변경 요청이 성공하는지 확인한다.

   ```bash
   if ((${#session_be[@]})); then
     sudo docker start "${session_be[@]}"
   else
     printf 'BE 목록 배열이 비어 있습니다. 아래 대체 절차로 활성 색을 확인하고 직접 시작하세요.\n'
   fi
   unset session_be
   ```

   배열이 비었거나 SSH 세션·셸이 바뀌었다면 1단계에서 출력한 중지 목록을 확인한다. RB-02의 배포 상태 확인 절차로 **활성 BE 색**을 확인한 뒤, 활성 색이 blue이면 `sudo docker start be-prod-blue`, green이면 `sudo docker start be-prod-green`을 직접 실행한다. 색을 추측해 두 컨테이너를 모두 시작하지 않는다. dev는 중지 기록을 확인한 뒤 `sudo docker start be-dev`로 시작한다. 직접 시작한 경우에도 위 readiness·smoke·기존 쿠키 401·새 로그인 확인을 마친다.

   dev는 컨테이너 필터를 `^be-dev$`, Redis 서비스를 `redis-dev`, 키 패턴을 `fitdining:session:dev:*`로 **모두 함께** 바꾼다. 삭제한 세션은 되돌리지 않는다. 백업으로 세션 키를 복원하면 강제 로그아웃을 취소할 수 있으므로 복원하지 않는다. 이 절차는 코드·compose 설정으로 작성했으며 운영에서 실행하지 않았다.

### E. 엣지: dev 접근 키, `/_ops` 자격

1. **`DEV_GATE_KEY`:** `openssl rand -hex 32 | sudo python3 ~/host/envset.py set edge --yes DEV_GATE_KEY` 뒤 caddy 컨테이너를 다시 만든다. 엣지가 잠깐 끊긴다(prod 포함). 팀원은 `https://<dev 호스트>/?k=<새 키>`로 다시 한 번 들어가야 쿠키가 새로 생긴다.

   ```bash
   sudo docker compose -p fit-edge -f ~/fit-repo/infra/edge/compose.edge.yml --env-file /etc/fit/edge.env up -d --force-recreate
   ```

2. **`/_ops` 자격:** 평문 비밀번호는 B의 `ops.env`, 그 해시는 A의 `edge.env`다. 만드는 명령은 [infra/ops/README.md](../../../infra/ops/README.md)의 "자격 만들기"를 따른다. 두 값이 어긋나는 동안 B의 외부 확인이 실패해 알림이 잠깐 울릴 수 있다. 환경변수는 컨테이너를 만들 때 읽으므로 A는 위의 caddy 재생성으로, B는 `ops.env` 반영 명령(`envset.py`가 안내한다)으로 적용한다.

### F. 알림 웹훅(Mattermost)

1. Mattermost에서 새 수신 웹훅을 만들고 옛 웹훅을 비활성화할 준비를 한다.
2. A의 `obs.env`(`MATTERMOST_WEBHOOK_URL`, 필요하면 `MATTERMOST_WEBHOOK_URL_DEV`)와 B의 `ops.env`(`MATTERMOST_WEBHOOK_URL`)에 새 주소를 넣는다. 주소가 비밀이라 파이프로 넣는다.
3. 반영한다(`envset.py`의 안내와 같다). 일일 요약은 실행할 때마다 읽으므로 따로 할 일이 없다.

   ```bash
   sudo docker compose -p fit-obs -f ~/fit-repo/infra/obs/compose.obs.yml --env-file /etc/fit/obs.env up -d --force-recreate obs-init prometheus alertmanager   # A
   sudo docker compose -p fit-ops -f ~/fit-repo/infra/ops/compose.ops.yml --env-file /etc/fit/ops.env up -d --force-recreate ops-init prometheus-b alertmanager-b   # B
   ```

4. 새 주소로 가는지 본다. 일일 요약을 한 번 올려 보면(`sudo python3 /usr/local/lib/fit/obs/daily-digest.py`, `--dry-run`을 빼면 실제로 올라간다) 확인된다. 그 뒤 Mattermost에서 옛 웹훅을 지운다.

### G. Grafana admin

`GRAFANA_ADMIN_PASSWORD`는 Grafana가 **처음 만들어질 때** 쓰는 값이라, env만 바꿔서는 이미 있는 관리자의 비밀번호가 바뀌지 않는 것으로 알려져 있다 (미확인, 이 서버에서 시험하지 않았다). 명령으로 바꾸고 `obs.env`의 값도 같게 맞춘다. 이 명령은 `--password-from-stdin`으로 비밀번호를 표준 입력에서 받는다(옵션 존재를 서버에서 확인했다).

```bash
pw="$(openssl rand -hex 16)"
printf '%s\n' "$pw" | sudo docker exec -i fit-obs-grafana-1 grafana cli admin reset-admin-password --password-from-stdin
printf '%s\n' "$pw" | sudo python3 ~/host/envset.py set obs --yes GRAFANA_ADMIN_PASSWORD
unset pw
```

### H. 백업 암호화 키(age)

백업은 `/etc/fit/keys/age-recipients.txt`의 공개키 모두에게 암호화된다. 개인키는 수신자(2명)의 노트북에만 있다.

- **수신자 추가:** 새 수신자가 자기 노트북에서 `age-keygen`으로 만들고 **공개키(`age1…`)만** 보낸다(공개키는 비밀이 아니라 채팅으로 보내도 된다). A에서 한 줄 더한 뒤 개수를 센다. 이후 만들어지는 백업부터 새 수신자도 풀 수 있고, 이미 만든 백업은 옛 수신자만 푼다.

  ```bash
  echo 'age1…' | sudo tee -a /etc/fit/keys/age-recipients.txt >/dev/null
  sudo grep -c '^age1' /etc/fit/keys/age-recipients.txt          # 수신자 수
  ```

  새 백업이 만들어지면(`sudo systemctl start fit-backup@pg.service`) 새 수신자가 RB-06 4절로 풀리는지 확인한다.
- **수신자 제거(개인키 유출 의심):** 그 줄을 지우고 새 백업을 바로 만든다. **옛 백업은 유출된 키로 풀 수 있다.** 금고(B)와 A의 옛 사본을 지울지 정한다(지우면 그 시점으로는 복원이 안 된다).

### I. A→B 금고 SSH 키

A의 `install.sh app`이 `/etc/fit/keys/vault_ed25519`를 만들고, B의 `vault-authorize.sh`가 그 공개키를 쓰기 전용으로 등록한다(`authorized_keys`에는 한 줄만 둔다).

1. A에서 옛 키를 치우고 새로 만든다: `sudo mv /etc/fit/keys/vault_ed25519{,.old}; sudo mv /etc/fit/keys/vault_ed25519.pub{,.old}; sudo bash ~/fit-repo/infra/backup/install.sh app` (설치가 새 키를 만들고 B에서 할 일을 안내한다).
2. B에서 안내된 대로 등록한다: `sudo bash infra/backup/vault-authorize.sh '<새 공개키 한 줄>' <A의 IP>`. 이 순간 옛 키는 못 쓴다. 그 사이 백업은 A의 `outbox`에 쌓였다가 다음 전송에 나간다.
3. `sudo systemctl start fit-backup@pg.service` 뒤 B에서 `incoming`에 도착하는지, `FitVaultStale`이 풀리는지 본다(RB-06 B절).

(이 절차는 시험하지 못했다. 스크립트의 설명을 따라 쓴 것이다.)

### J. GitLab 러너 토큰

GitLab에서 해당 러너의 토큰을 재설정(또는 새 러너를 만들어 새 토큰을 받는다)한 뒤, 서버에서 `sudo FIT_RUNNER_REREGISTER=1 bash ~/host/runner.sh register`로 다시 등록한다. 토큰은 숨김 입력으로만 받는다([infra/host/README.md](../../../infra/host/README.md)). 토큰을 채팅이나 문서에 붙이지 않는다. 등록하는 동안 그 러너의 CI 잡이 멈춘다. (미시험)

### K. 외부 서비스 키(Modal, GMS, Apify, 소셜 로그인)

1. 발급처(AI 팀의 Modal, SSAFY의 GMS, Apify, 각 소셜 제공자 콘솔)에서 새 키를 만든다.
2. 해당 환경의 env에 파이프로 넣는다. 예: `… | sudo python3 ~/host/envset.py set prod --yes MODAL_SECRET`. **환경마다 따로 발급한 키를 쓴다**(prod와 dev가 같은 키면 한쪽 유출이 둘 다 위험하다).
3. 같은 SHA를 다시 배포한다. 키가 어긋나는 동안 Modal이면 폴백이 늘고(RB-11), 소셜 로그인이면 그 제공자 로그인이 실패한다.
4. 동작을 확인한 뒤 발급처에서 옛 키를 폐기한다.
5. 소셜 로그인은 `AUTH_*_CLIENT_ID`와 `_SECRET`이 한 쌍이다. 둘 중 하나만 있으면 BE가 기동을 거부한다([env.md](../contracts/env.md)).

### L. 서버 접속 키(SSH)

- 팀원 터널 계정 `fit-dev`: 그 사람의 공개키 한 줄을 `/home/fit-dev/.ssh/authorized_keys`에서 지운다(팀을 떠날 때).
- 인프라 담당 개인 계정: 새 공개키를 `~/.ssh/authorized_keys`에 더하고 접속이 되는 것을 **다른 터미널에서 먼저 확인한 뒤** 옛 줄을 지운다. 비밀번호 로그인은 꺼져 있어 키를 잃으면 못 들어간다.
- SSAFY가 준 접속 키(`.pem`)는 우리가 바꿀 수 없다. 유출이 의심되면 SSAFY 담당에게 알려 교체를 요청한다.

## 4. 전체 되돌리기

회전은 (1) 사본으로 파일을 되돌리고 (2) 받는 쪽을 같은 순서로 다시 맞추고 (3) 같은 SHA로 다시 배포하는 것이 기본이다. 옛 값이 이미 서비스 쪽에서 폐기된 경우(소셜 secret, 웹훅)는 돌릴 수 없고 앞으로만 간다. 그래서 폐기는 새 값이 동작하는 것을 확인한 뒤에 한다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-28): 서버 A의 **임시 디렉터리에서** `envset.py`로 키를 넣고(파이프 입력) `--yes`로 덮어써서 글자 수만 출력되고 파일의 권한(640, root:docker)이 그대로인 것을 확인했다. Grafana의 `grafana cli admin reset-admin-password --help`로 `--password-from-stdin` 옵션이 있는 것을 확인했다. 노트북의 데이터 스택 시험(실제 Postgres·Redis·Garage 컨테이너)에서 `test-data.sh run rotation redis`가 통과했다(새 DB 비밀번호가 통하고 옛 비밀번호는 거부되며 원래 값으로 되돌아간다. Redis는 maxmemory 정책, prod와 dev 분리, AOF 복구). 같은 시험 스택에서 Garage 키 교체를 일회용 키로 따라 했다: 새 키 가져오기, 같은 버킷에 권한 주기(옛 키와 새 키가 둘 다 `RWO`), 새 키로 객체 올리기와 읽기(HTTP 200), 새 키를 지우고 다시 접근하면 거부(HTTP 403).
- 실행하지 못함: 운영 서버의 어떤 시크릿도 바꾸지 않았다(DB, Redis, Garage, JWT, 엣지, 웹훅, Grafana, age, 금고, 러너, 외부 키, SSH). A에서 Garage 명령은 컨테이너의 오래된 마운트 때문에 지금 쓸 수 없어서 서버에서는 못 돌렸다. 3절 A의 모니터 서비스 이름, E의 `/_ops` 자격 교체(해시를 만드는 명령 포함), G의 "env만 바꾸면 안 바뀐다"는 동작, H·I·J의 절차는 스크립트와 README를 읽고 쓴 것이다. 1절 4번의 사본 만들기와 지우기도 실행하지 않았다.
