- 검증 기준: develop `52c661d`, 2026-10-27. 서버 A·B에서 아래 확인 명령을 실제로 실행했다.
- 쓰는 때: 서버를 처음 받았거나 다시 만들 때, 서버가 설계대로인지 보고 싶을 때, 감시 체계 알림이 울릴 때(`FitScrapeTargetDown`, `FitOpsScrapeTargetDown`, `FitPortUnreachable`, `FitOpsWatcherDown`, `FitPortExposed`, `FitPortAuditStale`, `FitPortAuditMissing`, `FitProbeMetricMissing`, `FitVaultUnreachable`).

## 1. 서버 상태를 한 번에 본다

모두 읽기만 한다. 끝 줄이 정상 문구여야 한다.

서버 A:

```bash
sudo env FIT_PEER_IP=52.78.33.39 bash ~/fit-repo/infra/host/verify-host.sh | tail -n 2   # 호스트 정상
sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 2                                # 데이터 스택이 설계대로다
sudo bash ~/fit-repo/infra/obs/verify-obs.sh | tail -n 2                                  # 관측 스택이 설계대로다
sudo bash ~/fit-repo/infra/host/runner.sh status | tail -n 2                              # 러너 설정이 설계대로다
sudo python3 ~/host/envset.py status | tail -n 2                                          # 점검 통과(env 키와 형식)
sudo bash ~/fit-repo/infra/edge/edgectl.sh status                                         # 엣지와 활성 색
```

서버 B:

```bash
sudo env FIT_PEER_IP=3.35.170.47 bash ~/fit-repo/infra/host/verify-host.sh | tail -n 2
sudo bash ~/fit-repo/infra/ops/verify-ops.sh | tail -n 3                                  # B의 감시 구성이 설계대로다
sudo bash ~/fit-repo/infra/host/runner.sh status | tail -n 2
```

2026-10-27 정상 값: A는 verify-host 44 PASS, verify-data 36 PASS, verify-obs 27 PASS, envset status 123 OK이고 FAIL이 없다. B는 verify-ops 21 OK에 SKIP 1(밖에서 본 A의 `/healthz`가 200이 아님. A가 아직 master 미리보기라서 정상)이다. `FIT_PEER_IP`를 안 주면 verify-host가 "fail2ban ignoreip의 상대 서버"를 SKIP으로 둔다.

수집 대상이 죽었거나 지금 울리는 알림을 보려면 A나 B에서 Prometheus에 직접 묻는다(A와 B 모두 `127.0.0.1:9090`).

```bash
curl -sG http://127.0.0.1:9090/api/v1/query --data-urlencode 'query=up == 0'      # 죽은 수집 대상(결과가 비어 있으면 없음)
curl -s http://127.0.0.1:9090/api/v1/alerts | python3 -c 'import sys,json; print(sorted({a["labels"]["alertname"] for a in json.load(sys.stdin)["data"]["alerts"] if a["state"]=="firing"}))'
```

컨테이너가 다 떠 있는지는 `sudo docker ps --format '{{.Names}}\t{{.Status}}' | sort`로 본다. A는 `fit-data-*`(postgres, opensearch, redis-prod, redis-dev, garage), `fit-edge-caddy-1`, `fit-obs-*`(prometheus, alertmanager, grafana, node-exporter, cadvisor, blackbox, postgres-exporter, opensearch-exporter, dozzle)와 앱(`be-*`, `fe-*`)이다. B는 `fit-ops-*` 네 개(prometheus-b, alertmanager-b, blackbox, node-exporter)다.

## 2. 증상별 조치

### 수집 대상이 죽었다(`FitScrapeTargetDown`, `FitOpsScrapeTargetDown`, `FitProbeMetricMissing`)

1. 위 `up == 0` 결과의 `job`을 본다. `be`나 `caddy`는 첫 배포 전에는 없는 것이 정상이다(verify-obs가 SKIP으로 둔다).
2. 해당 컨테이너가 있는지, 왜 죽었는지 본다.

   ```bash
   sudo docker ps -a --format '{{.Names}}\t{{.Status}}' | grep -v ' Up '      # 떠 있지 않은 컨테이너
   sudo docker logs --tail 50 <컨테이너 이름>
   ```

3. 스택 전체가 내려갔으면 올린다. A는 `sudo bash ~/fit-repo/infra/deploy/fit-up.sh`(공유 망, data와 DB·버킷 초기화, 엣지, 앱의 활성 색, 관측 순서로 멈춘 컨테이너를 올리고 마지막에 스모크를 돈다. 상태는 바꾸지 않고 활성이 아닌 색은 올리지 않는다). B는 `sudo bash ~/fit-repo/infra/ops/ops-up.sh`(이미 떠 있으면 설정이 바뀐 서비스만 다시 만든다).
4. 다시 `up == 0`이 비는지 5분 안에 확인한다.

### Redis 컨테이너가 보이지 않는다(`FitRedisProdDown`, `FitRedisDevDown`)

cAdvisor가 `fit-data-redis-<환경>-*` 컨테이너를 보지 못한다는 뜻이다. 컨테이너가 멈췄거나 지워졌다. 떠 있지만 응답하지 않는 경우는 이 알림이 잡지 못해서, 로그인이 안 된다는 신고가 있는데 알림이 없으면 아래 4번의 BE readiness를 본다.

1. 컨테이너 상태를 본다.

   ```bash
   sudo docker ps -a --filter 'name=fit-data-redis' --format '{{.Names}}\t{{.Status}}'
   sudo docker logs --tail 50 fit-data-redis-prod-1      # dev는 fit-data-redis-dev-1
   ```

2. 멈춰 있으면 데이터 스택에서 그 서비스만 올린다. AOF(`appendonly yes`)라서 세션과 카운터는 돌아온다.

   ```bash
   sudo docker compose -p fit-data -f ~/fit-repo/infra/data/compose.data.yml --env-file /etc/fit/data.env up -d redis-prod   # dev는 redis-dev
   ```

3. 점검을 돌린다. 끝에 `데이터 스택이 설계대로다`가 나와야 한다. 방금 다시 만든 컨테이너는 healthy가 되기까지 몇 초 걸려서 처음에는 `healthy` 항목 하나가 실패로 나올 수 있다. 5초 뒤 다시 돌린다.

   ```bash
   sudo bash ~/fit-repo/infra/data/verify-data.sh | tail -n 5
   ```

4. 그 환경의 BE가 Redis에 다시 붙었는지(`/actuator/health/readiness`가 UP인지) 본다. 계속 DOWN이면 RB-08 B절 3번처럼 같은 SHA를 다시 배포한다.

### 밖에서 A에 닿지 않는다(`FitPortUnreachable`, `FitOpsWatcherDown`, `FitExternalDown`)

B가 A를 밖에서 두드려 알린다. 먼저 B에서 어느 경로가 막혔는지 가른다.

```bash
for p in 22 80 443; do (timeout 5 bash -c "</dev/tcp/k15a302.p.ssafy.io/$p" && echo "$p 열림") 2>&1 | tail -n 1; done
curl -sS -m 10 -o /dev/null -w 'A /healthz → %{http_code}\n' https://fitdining.co.kr/healthz
```

- 22도 안 열리면 A 서버나 네트워크 문제다. SSAFY 콘솔 권한이 없으므로 팀과 SSAFY 담당에게 알린다(RB-12의 전제, A 소실).
- 22만 열리면 A에서 엣지를 본다.

  ```bash
  sudo docker ps --filter name=fit-edge-caddy-1 --format '{{.Names}} {{.Status}}'
  sudo ufw status | grep -E '^(80|443)/tcp '
  getent hosts fitdining.co.kr dev.fitdining.co.kr
  ```

  엣지가 죽었으면 `fit-up.sh`로 올린다. ufw 80·443 규칙이 없으면 `verify-host.sh`가 FAIL로 알려 주고 `bootstrap.sh`가 고친다(아래 3절). DNS가 A의 IP(`3.35.170.47`)와 다르면 가비아에서 A 레코드를 고친다.
- 80·443은 열리는데 `/healthz`가 200이 아니면 RB-02다(BE 응답). 인증서 오류면 RB-05다.
- `FitOpsWatcherDown`(`/_ops/...`가 404)은 A의 `edge.env`(`B_IP`, `OPS_BASIC_AUTH_HASH`)와 B의 `ops.env`(`OPS_BASIC_AUTH_PASSWORD`)가 어긋난 것이다. `sudo python3 ~/host/envset.py status`로 두 파일의 키가 있는지만 보고, 자격 만드는 법은 [ops README](../../../infra/ops/README.md)의 "`/_ops` 자격 만들기"다.

### 예상 밖 포트가 열렸다(`FitPortExposed`)

B의 포트 감사가 A에서 22·80·443 말고 열린 포트를 찾았다. 먼저 어느 포트인지 B에서 본다.

```bash
grep -E '^fit_portaudit_(unexpected_ports|port_open)' /srv/vault/metrics/fit_portaudit_quick.prom
```

A에서 그 포트의 주인을 찾는다. Docker가 게시한 포트는 ufw를 우회하므로 ufw만 보지 않는다.

```bash
sudo ss -lntp | awk 'NR==1 || $4 ~ /^0\.0\.0\.0:|^\*:|^\[::\]:/'
sudo docker ps --format '{{.Names}}\t{{.Ports}}' | grep -E '0\.0\.0\.0|:::'
```

주인 컨테이너의 compose에서 `ports:`를 지우거나 `127.0.0.1:`로 묶고(저장소의 compose를 고치는 MR) 그 스택을 다시 올린다. 고친 뒤 B에서 `sudo systemctl start fit-port-audit-quick.service`로 바로 다시 감사해 `fit_portaudit_unexpected_ports`가 0인지 본다. 이 포트가 밖에서 쓰이던 것이면 닫기 전에 팀에 알린다.

### 포트 감사가 멈췄다(`FitPortAuditStale`, `FitPortAuditMissing`)

```bash
systemctl list-timers 'fit-port-audit*' --no-pager          # B. 타이머 둘이 보여야 한다
sudo journalctl -u fit-port-audit-quick.service -n 20 --no-pager
sudo systemctl start fit-port-audit-quick.service           # 지금 한 번 돌린다
```

주소를 찾지 못하는 등 감사를 못 하면 종료 코드 1이고 지표를 갱신하지 않는다. `ops.env`의 `PROD_HOST`가 맞는지 본다(`sudo python3 ~/host/envset.py status ops`).

### A에서 B의 22번이 안 닿는다(`FitVaultUnreachable`)

```bash
(timeout 5 bash -c '</dev/tcp/52.78.33.39/22' && echo 열림) 2>&1 | tail -n 1       # A에서
sudo fail2ban-client status sshd | grep -E 'Currently banned|Total banned'         # B에서. A의 IP가 막혔는지
```

B가 죽었거나 B의 ufw·보안 그룹이 A를 막았다. B에 접속이 되면 `verify-host.sh`로 ufw와 fail2ban(`ignoreip`에 A의 IP)을 본다. 백업 전송 쪽 조치는 RB-06이다.

## 3. 새 서버를 받았을 때(첫날)

설계 3절의 상태로 만든다. 몇 번을 실행해도 같은 결과이고, 마지막 줄이 `변경 없음`이면 이미 설계대로다.

1. 관리자 계정으로 키 SSH가 되는지 **다른 터미널에서 먼저 확인**한다. bootstrap이 비밀번호 로그인을 끈다(키가 등록된 일반 계정이 없으면 끄지 않고 멈춘다).
2. `scp -r infra/host <서버>:~/host`로 올린다(이 디렉터리만 있으면 된다).
3. 적용한다. `FIT_PEER_IP`에는 상대 서버의 공인 IP를 넣는다.

   ```bash
   sudo ROLE=app FIT_PEER_IP=<B의 공인 IP> bash ~/host/bootstrap.sh   # 서버 A
   sudo ROLE=ops FIT_PEER_IP=<A의 공인 IP> bash ~/host/bootstrap.sh   # 서버 B
   ```

4. 위 1절의 `verify-host.sh`가 전부 PASS인지 본다.
5. 서버 밖(노트북)에서 포트를 확인한다. 22는 열리고, 80·443은 엣지가 뜨기 전에는 닫혀 있다. 클라우드 방화벽(보안 그룹)은 SSAFY가 관리해서 우리가 볼 수 없다(설계 1.3절, 위험 19).
6. A는 이어서 env 파일을 채우고(`envset.py`, 계약은 [env.md](../contracts/env.md)) `fit-up.sh`로 data, 엣지, 관측을 올린다. B는 `ops.env`를 채우고 `ops-up.sh`를 돌린다. 러너는 [host README](../../../infra/host/README.md)의 "CI 러너"다.

## 4. 되돌리기

- 이 런북의 확인 명령은 모두 읽기 전용이라 되돌릴 것이 없다.
- `fit-up.sh`, `ops-up.sh`는 멈춘 것을 올리기만 해서 되돌릴 상태 변경이 없다. 잘못 올렸으면 그 스택만 내린다(`sudo docker compose -p <fit-data|fit-edge|fit-obs|fit-ops> down`, 볼륨은 지우지 않는다. `-v`를 쓰지 않는다).
- `bootstrap.sh`는 기존 `daemon.json`을 한 번만 `.fit-orig`로 백업하고, sshd 설정 검사(`sshd -t`)가 실패하면 이전 파일로 되돌린다. 다른 설정은 다시 실행하면 설계 값으로 돌아간다.
- 포트를 닫은 compose 수정은 MR을 되돌려 원래대로 한다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-27, A·B): 1절의 점검 스크립트 전부, `up == 0`과 firing 알림 질의, 밖에서 본 22·80·443 도달성과 `/healthz`, 포트 감사 지표와 타이머 확인, `ss`·`docker ps`로 리스너 찾기, fail2ban 상태.
- 실행하지 않음: `fit-up.sh`, `ops-up.sh`(서비스에 영향을 줄 수 있어서), `bootstrap.sh` 재실행(이미 PASS), `FitPortExposed` 조치(열린 포트가 없었다), 3절의 서버 첫날 전체 순서(2026-10-22에 A·B에서 한 번 했다. 이 런북으로 다시 따라 하지는 않았다).
- 실행하지 않음(2026-11-10 추가한 Redis 컨테이너 절): 알림 규칙은 promtool 단위 시험까지만 했고 서버에서 컨테이너를 멈춰 알림을 내 보지는 않았다. 조치 명령은 RB-08 B절과 `infra/data/README.md`의 명령을 가져왔고, 점검 문구(`데이터 스택이 설계대로다`와 재생성 직후 `healthy` 항목이 한 번 실패하는 것)는 2026-11-09 서버 실행에서 본 것이다.
