# RB-14 AI API(서버 A)를 켜고, 이상이 있을 때 보는 절차

- 검증 기준: 머지 전의 로컬 시험(`test-deploy.sh`의 `ai` 구역, `test-data.sh`의 `ai` 구역, `images-in-container.sh`의 AI 이미지)에서만 확인했다. **서버 A에서는 한 번도 실행하지 않았다.** AI 쪽 전제(아래 2절 0번)가 모두 develop에 들어오기 전에는 켜도 끝까지 동작하지 않는다.
- 쓰는 때: AI API를 처음 켤 때, 배포 로그나 완료 알림에 `AI` 경고가 붙었을 때, `ai-prod`나 `ai-dev`가 이상할 때, BE의 폴백 알림(`FitModalFallbackHigh`, RB-11)의 원인이 AI일 때.
- 준비: [README.md](README.md)의 접속. 설계는 [design.md](../design.md) 11.4절이다.

## 1. 알아 둘 것

- AI API는 **선택**이다. `/etc/fit/ai-<환경>.env`가 있는 환경에서만 이미지를 만들고 배포한다. 파일이 없으면 지금까지의 배포와 똑같다.
- AI가 죽어도 서비스는 산다. BE가 키워드 검색으로 대체한다(11.2절). 그래서 **AI 배포 실패는 BE·FE 배포를 막지 않는다.** 대신 사용자는 못 느끼는 실패라 로그와 알림, BE의 폴백 비율로 본다.
- `/healthz`가 503이면 AI가 저장소(DB)나 임베딩(Modal)을 쓸 수 없다는 뜻이다. 컨테이너가 떠 있어도 503이면 준비되지 않은 것이다.
- AI 전용 DB role(`fit_prod_ai`, `fit_dev_ai`)은 읽기 전용이고 뷰 `ai_place_search`, `ai_place_personas`(V26)와 `user_preferences`만 읽는다. 이 뷰를 BE 마이그레이션이 만들어야 한다.

## 2. 처음 켜는 절차(dev부터, 순서를 지킨다)

**2~5번은 스크립트가 한 번에 한다.** `sudo bash ~/fit-repo/infra/app/ai-env-init.sh dev`는 2번(비밀번호 만들기), 3번(role), 4번(AI env 파일과 값)을 하고, `... dev point-be`는 5번(BE의 `MODAL_*`)을 한다. 값은 서버에 이미 있는 것(`dev.env`의 GMS·Modal, `data.env`의 비밀번호)을 파이프로 옮기고 화면에는 나오지 않는다. 이미 값이 있는 키는 바꾸지 않아서 다시 돌려도 된다. 아래 번호별 설명은 손으로 할 때와 원리를 볼 때 쓴다.

0. **전제 확인.** 아래가 develop에 없으면 켜도 이미지 빌드가 막히거나 `/healthz`가 503이다(design.md 11.4절의 전제).
   - AI 코드: 원격 임베딩 호출이 있다, 로컬 인코더(`sentence-transformers`)가 선택 의존성이다(없으면 이미지 빌드가 `torch` 때문에 멈춘다), 장소를 BE 마이그레이션의 뷰 `ai_place_search`에서 읽는다.
   - BE 마이그레이션이 뷰 `ai_place_search`를 만들었다.
1. **백업 설치본을 먼저 갱신한다.** 복원 검증용 임시 DB가 AI role을 만들어야 덤프가 복원된다. A에서 `cd ~/fit-repo && sudo bash infra/backup/install.sh app`. 이 순서를 어기고 role부터 만들면 그 뒤 백업의 복원 검증이 실패해 덤프가 B로 가지 않는다. 반대로 설치본을 갱신하면 사진 백업(`fit-backup@photos`)이, 서버의 `~/fit-repo`를 새 코드로 갱신한 뒤에는 `infra/data`의 스크립트(`ensure-databases.sh`, `verify-data.sh`, `init-garage.sh`)가 `data.env`의 AI 비밀번호 두 개(2번)를 필수로 요구하며 없으면 멈춘다. 그래서 1번부터 3번까지는 이어서 한다. 2번을 넣기 전에 사진 백업이 돌면 그 회차는 멈춘다.
2. **`data.env`에 AI role 비밀번호 두 개를 넣는다**(16자 이상, 영문·숫자·`._~-`). 값은 `openssl rand -hex 16`로 만들고 숨김 입력으로 넣는다.
   ```bash
   sudo python3 ~/host/envset.py set data FIT_DEV_AI_PASSWORD FIT_PROD_AI_PASSWORD
   ```
3. **role을 만든다.** `sudo bash ~/fit-repo/infra/data/ensure-databases.sh`(몇 번 해도 같은 결과다). 읽을 뷰가 아직 없으면 "아직 없는 객체(건너뜀)"로 나오고, 마이그레이션 뒤 배포가 다시 맞춘다.
4. **AI env 파일을 만든다.** `envset.py`는 파일을 새로 만들지 않으므로 예제에서 복사한다(서버의 `~/host/envset.py`와 `env.md`도 develop 최신 것으로 `scp`해 둔다. `ai-dev`, `ai-prod` 이름을 안다).
   ```bash
   sudo install -m 640 -o root -g docker ~/fit-repo/infra/app/ai.env.example /etc/fit/ai-dev.env
   sudo python3 ~/host/envset.py set ai-dev APP_ENV=dev GMS_BASE_URL=<주소> EMBED_BASE_URL=<Modal 임베딩 주소>
   sudo python3 ~/host/envset.py set ai-dev DATABASE_URL GMS_API_KEY EMBED_KEY EMBED_SECRET   # 숨김 입력
   sudo python3 ~/host/envset.py status ai-dev
   ```
   `DATABASE_URL`은 `postgresql://fit_dev_ai:<2번의 비밀번호>@postgres:5432/fit_dev`다. 지금 dev.env에 있는 Modal 값(`MODAL_BASE_URL`, `MODAL_KEY`, `MODAL_SECRET`)이 임베딩 값이므로 AI env의 `EMBED_*`로 옮긴다.
5. **BE가 AI를 부르게 한다.** BE의 `MODAL_BASE_URL`을 `http://ai-dev:8000`으로 바꾸고 `MODAL_KEY`, `MODAL_SECRET`은 비운다(A 안의 호출이라 헤더가 필요 없다).
   ```bash
   sudo python3 ~/host/envset.py set dev MODAL_BASE_URL=http://ai-dev:8000
   sudo python3 ~/host/envset.py unset dev MODAL_KEY MODAL_SECRET
   ```
6. **배포한다.** GitLab의 `deploy:dev`를 Retry하거나 `build:images`부터 다시 돌린다(AI 이미지는 env 파일이 있어야 만들어진다). 배포 로그에서 `[ai]` 줄과 `AI 읽기 권한을 맞췄다`를 본다.
7. **확인한다.** 3절의 명령으로 `ai-dev`가 healthy이고 `/healthz`가 200인지 본다.
8. prod는 같은 순서로 하되 `ai-prod`, `fit_prod_ai`, `FIT_PROD_AI_PASSWORD`를 쓴다. prod는 dev에서 며칠 확인한 뒤에 한다.

## 3. 확인 명령(진단)

모두 읽기만 한다. 서버 A에서:

```bash
sudo docker ps --filter name=ai- --format '{{.Names}} {{.Image}} {{.Status}}'          # 떠 있나, 어느 SHA인가, healthy인가
sudo docker logs --tail 40 ai-dev                                                       # JSON 로그. 요청 본문은 없다
sudo docker exec fit-edge-caddy-1 wget -q -T 5 -O - http://ai-dev:8000/healthz          # 200이면 준비됨, 503이면 준비 안 됨
sudo grep -E '^AI_(DEV|PROD)_(TAG|PREV_TAG)=' /srv/fit/state/deploy-dev.env             # 배포 상태의 AI 태그
sudo tail -n 8 /srv/fit/state/history-dev.log                                           # 배포 이력(deploy ai ... ok/fail)
sudo python3 ~/host/envset.py status ai-dev                                             # env 점검(값은 안 나온다)
```

## 4. 원인별 조치

| 증상 | 원인 | 조치 |
|---|---|---|
| 배포 로그 `경고: [ai] ... 확인에 실패했다` | `/healthz`가 503이거나 컨테이너가 죽었다 | 3절의 `docker logs`로 이유를 본다. 아래 행을 따른다. BE·FE는 정상 배포됐다 |
| `/healthz` 503, 로그에 `store_failed` | DB를 못 읽는다. 뷰가 없거나 권한이 없다 | 뷰를 BE 마이그레이션이 만들었는지 본다. `sudo bash ~/fit-repo/infra/data/grant-ai-read.sh`로 권한을 맞추고 컨테이너를 다시 띄운다. `DATABASE_URL`의 비밀번호가 `data.env`와 같은지 본다(RB-08) |
| `/healthz` 503, 로그에 `embedding_failed` | 시작할 때 났으면 `EMBED_*` 값이 비었거나 주소가 틀렸다. `/healthz`가 200인데 검색 때만 나면 Modal 임베딩에 닿지 못한다(로그 `error`에 `HTTP 401` 등 실패 종류가 있다) | Modal 쪽은 RB-11을 따른다. `EMBED_BASE_URL`, `EMBED_KEY`, `EMBED_SECRET`이 맞는지 `status`로 본다 |
| 배포 로그 `AI API 배포를 건너뛴다` | `ai:<SHA>` 이미지가 없다(AI 이미지 빌드 실패) | `build:images` 잡 로그에서 `경고: AI 이미지를 만들지 못했다` 앞의 오류를 본다. 서버 의존성에 `torch`가 있으면 의존성 분리가 필요하다(AI 팀) |
| 검색은 되는데 응답의 `fallbacks`에 `INTERPRET_LLM_FAILED`, `RANK_LLM_FAILED`가 있고 로그에 `GMS 호출 실패: HTTP 403` | `ai-<env>.env`의 `GMS_BASE_URL`에 공급자 경로가 없다 | `https://gms.ssafy.io/gmsapi/api.openai.com/v1` 형식으로 고치고(`envset.py set ai-<env> GMS_BASE_URL=...`) 같은 SHA를 다시 배포한다(env는 컨테이너를 만들 때 한 번 읽는다) |
| 한동안 쓰지 않은 뒤 첫 검색이 503 `EMBEDDING_UNAVAILABLE`이고 곧 정상이 된다 | Modal 임베딩 앱의 콜드 스타트(17~85초). 마지막 요청 뒤 10분(`scaledown_window=600`)이 지나면 컨테이너가 내려간다. AI는 3초만 기다리고 실패로 본다(시간 초과는 다시 부르지 않는다) | 정상이다. 그동안 BE는 키워드 검색으로 대체한다. 자주 겪으면 Modal 앱의 상시 대기를 검토한다(GPU가 켜져 있는 시간만큼 비용이 든다) |
| 사전 점검 `ai-<env>.env: DATABASE_URL` 실패 | env 파일이 다른 환경의 DB나 role을 가리킨다 | `DATABASE_URL`을 이 환경의 `fit_<env>_ai`와 `fit_<env>`로 고친다 |
| 사진 백업이나 `ensure-databases.sh`가 `data.env에 FIT_..._AI_PASSWORD가 없다`로 멈춤 | 설치본이나 `~/fit-repo`는 새 코드인데 `data.env`에 AI 비밀번호를 아직 넣지 않았다 | 2절 2번대로 두 키를 넣고 1~3번을 이어서 마친다 |
| `FitContainerRestartLoop`, `FitContainerMemoryHigh`의 `ai-*` | 재시작을 반복하거나 한도(prod 512MB, dev 400MB)를 넘는다 | 로그를 본다. 모델이 올라가는 코드가 들어왔는지 의심한다(이 컨테이너는 모델을 올리지 않는다). RB-03 |
| BE 폴백 알림 | AI가 응답하지 않아 BE가 키워드 검색으로 간다 | 이 표의 위 행으로 AI를 고친다. 급하면 아래 5절로 끈다 |

## 5. 되돌리기와 끄기

- **이전 이미지로:** `bash ~/fit-repo/infra/deploy/rollback.sh <dev|prod> ai`(AI만). `rollback.sh <환경> all`은 AI도 함께 되돌린다. 이전 이미지가 없으면 하지 못한다고 알린다.
- **잠시 끄기(BE는 키워드 검색으로):** `sudo docker stop ai-prod`(또는 `ai-dev`). 다음 배포가 다시 띄운다. 오래 끄려면 BE의 `MODAL_ENABLED=false`로 호출 자체를 막는다(RB-11).
- **Modal 상시 가동(서비스 시간):** 임베딩 앱의 상시 가동은 Modal 앱 `fit-embed-warm`(`ai/server/warm.py`)이 10분마다 맞춘다. 한국 09~21시(2026-11-20까지)에는 컨테이너 1개를 켜 두고 그 밖에는 0이다. 켜 둔 시간만큼 GPU 비용이 든다. 시간과 끝 날짜는 `warm.py`의 `WARM_FROM_HOUR`, `WARM_TO_HOUR`, `WARM_UNTIL`이다. 멈추려면 ai/에서 `uv run modal app stop fit-embed-warm --env fit-prod`(미확인: 명령을 실행해 보지 못했다)로 이 앱을 멈추고 `server/embed.py`를 다시 배포한다(배포하면 상시 가동이 0으로 돌아간다). `embed.py`를 다시 배포해도 10분 안에 `fit-embed-warm`이 시간에 맞게 되돌린다.
- **영구히 끄기:** `/etc/fit/ai-<환경>.env`를 지우면(`sudo mv`로 옮겨 둔다) 다음 배포부터 AI를 만들지도 배포하지도 않는다. 떠 있는 컨테이너는 `sudo docker rm -f ai-<환경>`으로 치운다.

## 이 런북을 따라 해 본 범위

- 직접 실행함(2026-10-30, 노트북의 로컬 시험): 배포 시험의 `ai` 구역(AI 켜기 전/후, 준비 안 되는 배포와 직전 이미지 복귀, 이미지 없는 배포, 권한 맞추기 실패, 롤백, 환경이 섞인 env 파일 거부), 데이터 시험의 `ai` 구역(읽기 전용 role의 권한), AI 이미지 조립 시험.
- 실행하지 못함: 서버 A에서의 모든 단계(`install.sh`, `ensure-databases.sh`, env 파일 만들기, 배포, 확인 명령), 실제 AI 컨테이너와 실제 DB·Modal·GMS 연결, 3절과 4절의 로그 문구(`store_failed`, `embedding_failed`는 AI 코드의 이벤트 이름을 따랐고 실제 로그로 보지 못했다).
