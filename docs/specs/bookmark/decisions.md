## D-1 북마크가 장소를 가리키는 방식
- Status: provisional
- Decision: 북마크의 장소 id에는 `places`로 가는 FK를 두지 않고, 저장하기 전에 장소 기능의 `PlaceService.getPlace`로 장소가 있는지 확인한다(없으면 404, 검색 엔진이 없으면 503). 북마크 예외 처리기가 장소 예외를 404/503으로 직접 바꾼다(장소 예외 처리기는 장소 컨트롤러에만 걸려 있다). DB는 장소 id 양수 CHECK, 사용자 id의 `auth_users` FK, (사용자, 장소) 유일성을 지킨다. 리뷰(`reviews.place_id`, review D-21)와 같은 방식이라 지금 Mock 엔진에서도, -115 이후 DB 엔진에서도 동작한다.
- Default: 자동 제안(R1 Q1). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: `places(place_id)` FK → local/dev의 `places`가 비어 있고 Mock이 1..36을 내주므로, 실데이터 적재와 -115가 끝날 때까지 저장이 전부 실패한다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/place/PlaceService.java#getPlace` (reuse) — 저장 전 장소 존재 확인

## D-2 절대 일어나면 안 되는 것
- Status: provisional
- Decision: (1) 북마크의 주인은 인증 결과로만 정하고 요청 값으로 바꿀 수 없다. (2) 한 사용자의 북마크는 다른 사용자에게 보이거나 다른 사용자가 바꿀 수 없다(조회, 저장 여부, 해제 모두 그 사용자로 제한). (3) 토큰이 아직 유효해도 탈퇴한 사용자는 모든 북마크 API에서 401이다. (4) 같은 사용자, 같은 장소의 북마크는 최대 한 행이고, 중복이나 동시 저장도 성공하며 처음 저장 시각을 바꾸지 않는다. (5) 저장한 장소 보기에는 내가 저장한 장소만 나온다(남의 장소, 저장하지 않은 장소, 주변 추천이 섞이지 않는다). (6) 실패를 성공, 빈 목록, 미저장으로 보여 주지 않는다. 결과가 불명확하면(시간 초과 등) 다시 조회해 맞춘다. (7) 로그아웃이나 계정 전환 뒤 이전 계정의 캐시, 늦게 온 응답, 쓰기 결과가 새 계정 화면에 나오지 않는다. (8) 저장 목록을 만들려고 핏 점수나 추천 이유를 지어내거나 과거 검색 카드에서 끌어오지 않는다.
- Default: 자동 제안(R1 Q5, 두 모델 답의 합집합). grill 종료 때 사용자 확인으로 확정한다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/auth/repository/AuthUserRepository.java#existsByIdAndDeletedAtIsNull` (reuse) — 탈퇴한 사용자를 401로 막는 확인

## D-3 저장과 해제의 의미
- Status: provisional
- Decision: 장소별 자원에 `PUT`으로 저장, `DELETE`로 해제하고 둘 다 204다. 이미 저장한 장소를 다시 `PUT`해도 성공이고 저장 시각과 순서를 바꾸지 않는다. 저장하지 않은 장소를 `DELETE`해도 성공이다. `DELETE`는 장소 엔진을 부르지 않아 장소가 사라지거나 엔진이 멈춰도 내 북마크를 지울 수 있다. 동시 `PUT`도 DB 유일 제약과 충돌 시 무변경 삽입으로 모두 성공한다. FE는 같은 장소의 쓰기를 차례로 보내고, 오프라인에서 누른 쓰기를 연결이 돌아온 뒤 자동으로 보내지 않는다.
- Default: 자동 제안(R1 Q7). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: 토글 하나 → 시간 초과 뒤 재시도가 저장을 해제한다. `POST`가 409, `DELETE`가 404 → 두 번 누르기와 재시도가 오류가 된다.

## D-4 API 경로와 인증
- Status: provisional
- Decision: `GET /api/v1/me/bookmarks`(내 목록), `GET /api/v1/me/bookmarks/{placeId}`(`{bookmarked: boolean}`), `PUT`·`DELETE /api/v1/me/bookmarks/{placeId}`(204). 사용자는 토큰에서만 얻는다. 이 경로는 인증 인터셉터 범위 밖이라 리뷰처럼 컨트롤러가 `AuthUseCases.authenticate`를 직접 부르고, 모든 API에서 탈퇴하지 않은 사용자인지 확인한다. 북마크 예외 처리기는 `AuthFailure`의 상태 코드와 토큰 만료 `type`을 그대로 둔다. `/api/v1/me`는 새 경로다(기존 인증의 내 정보는 `/api/auth/me`).
- Default: 자동 제안(R2 Q13, 토론 뒤 합의). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: `/api/v1/users/{userId}/bookmarks` → 인증 인터셉터는 `UserController`나 지정 경로만 인증하므로(`AuthWebConfiguration`) 새 컨트롤러는 이득이 없고, 경로 userId와 토큰 비교만 늘어난다. `/api/v1/places/{placeId}/bookmark` + `/api/v1/me/bookmarks` → 개인 컬렉션 하나가 두 경로 계열로 나뉜다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/auth/ports/AuthUseCases.java#authenticate` (reuse) — 리뷰 컨트롤러처럼 Bearer 토큰에서 사용자 확인

## D-5 상세 화면의 저장 여부
- Status: provisional
- Decision: 로그인한 사용자는 장소별 저장 여부 API(D-4)로 상세의 "저장" 버튼 상태를 받는다. 저장 여부는 북마크 테이블만 보고 판단하고, 장소 상세 응답(검색 엔진 계약)은 바꾸지 않는다. 확인 중이거나 확인에 실패하면 저장됨으로도 미저장으로도 확정하지 않고 저장·해제를 막은 채 다시 시도할 방법을 준다(D-2의 6). 저장·해제가 성공하면 같은 사용자의 저장 여부와 목록 캐시를 함께 맞춘다. place 도메인은 auth 도메인을 직접 import하지 않고 app 계층이 인증을 이어 준다.
- Default: 자동 제안(R1 Q8 토론, R2에서 D-2와 맞게 실패 처리 수정). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: 장소 상세 응답에 `bookmarked` → 공개 상세를 개인화해 검색 엔진 계약과 캐시가 바뀐다. 내 목록 전체를 받아 포함 여부 확인 → 상세는 링크로 바로 들어올 수 있어 버튼 하나에 목록 전체를 받는다.
- Reuse: `fe/src/domains/auth/api/with-access-token.ts#withAccessToken` (reuse) — 로그인이 필요한 북마크 요청

## D-6 저장 목록의 크기와 순서
- Status: provisional
- Decision: 저장 개수 상한은 없다. 저장 시각 최신순, 같은 시각은 장소 id 내림차순이고 한 번에 전체를 돌려준다. 해제 뒤 다시 저장하면 새 저장 시각으로 맨 앞에 온다. 임의 개수로 조용히 자르지 않는다. 응답이나 지도 핀 수가 감당되지 않는다는 측정이 생기면 페이징을 다시 설계한다.
- Default: 자동 제안(R1 Q9). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: cursor paging → 장소가 300곳이라 지금은 필요 없고 지도 핀과 함께 쓰기 어렵다. 개수 상한 → 요청에 없던 제한이다.

## D-7 비로그인 사용자가 저장을 누를 때
- Status: settled
- Decision: 비로그인 사용자가 상세의 "저장"이나 첫 화면의 "저장한 장소" 버튼을 누르면 로그인이 필요하다는 안내를 띄우고 [로그인]과 [취소]를 고르게 한다. 취소하면 지금 화면에 그대로 있고 아무 요청도 보내지 않는다. 비로그인 사용자에게는 저장 여부 API를 부르지 않는다. `fe/AGENTS.md`의 "비회원 저장 시 로그인 안내"를 따른다.
- Rejected: 바로 로그인 화면으로 이동 → 와이어프레임 지침의 로그인 안내와 다르다. 버튼 숨기기 → 진입점이 사라져 기능을 알 수 없다.
- Reuse: `fe/src/domains/place/ui/place-detail-screen.tsx#PlaceDetailScreen` (modify) — 하단 막대 "저장" 버튼의 토스트를 저장·해제와 로그인 안내로 바꾼다 · `fe/src/domains/place/ui/search-screen.tsx#SearchScreen` (modify) — "저장한 장소" 버튼의 토스트를 저장한 장소 보기(미결 Q3)와 로그인 안내로 바꾼다

## D-8 로그인한 뒤 어디로 가나
- Status: provisional
- Decision: 안내에서 로그인을 고른 비로그인 사용자는 로그인한 뒤 지금처럼 홈(`/`)으로 간다. 누르려던 저장은 자동으로 실행하지 않는다.
- Default: 자동 제안(R2 Q11, 토론 뒤 합의). 원래 화면으로 돌아가게 하려면 로그인 공통 흐름(이메일, 소셜)을 바꾸는 별도 범위가 된다.
- Rejected: 누른 화면으로 복귀 → 로그인 성공 경로가 모두 `/`로 가고(`fe/src/app/login/page.tsx`) 소셜 로그인에 복귀 경로 계약이 없어 범위가 커진다. 로그인 뒤 저장 자동 실행 → 로그인하면서 계정이 바뀌면 다른 계정에 저장된다.

## D-10 place-search의 "준비 중" 동작 대체
- Status: settled
- Decision: 북마크 기능이 place-search의 AC-35("저장한 장소" 버튼 토스트)와 AC-40(상세 "저장" 토스트)의 저장 부분 동작을 대체한다고 북마크 spec에 명시한다. "공유" 버튼의 토스트와 "내 정보" 버튼은 그대로다. place-search 문서는 고치지 않는다(place-search D-85, D-94가 "기능이 생기면 동작만 바꾼다"고 정해 두었다).

## D-11 검사할 경계
- Status: provisional
- Decision: BE는 실제 PostgreSQL과 마이그레이션으로(리뷰의 `ReviewPersistenceTest`처럼) 유일성, 동시 `PUT`이 모두 성공하고 한 행이며 처음 저장 시각이 유지되는지, 사용자 간 조회·해제 격리, 정렬과 해제 뒤 재저장을 확인한다. 컨트롤러 테스트로 토큰 없음과 탈퇴 사용자의 401(모든 API), 저장의 404/503, 반복 `DELETE` 204와 엔진 미호출, 저장 여부 true/false를 확인한다. FE는 jsdom으로 상세 버튼의 확인 중·실패·저장됨·미저장 상태, 비로그인 안내의 로그인·취소, 성공·실패 뒤 표시와 캐시, 계정 전환 중 늦은 응답 버리기를 확인한다. 저장한 장소 보기의 화면 테스트는 Q3가 정해진 뒤 정한다. 두 계정으로 직접 확인하는 것도 한다.
- Default: 자동 제안(R2 Q12). grill 종료 때 사용자 확인으로 확정한다.
- Rejected: BE 테스트와 수동 확인만 → 이전 계정 캐시 노출, 실패를 미저장으로 보이는 문제, 지도에 주변 추천 핀이 남는 문제를 못 잡는다.

## 미결 질문

D-n이 아직 없는 질문이다. 정해지면 다음 D-n으로 들어간다.

- **Q3 저장한 장소 보기의 형태 (팀 확인 중).** "저장한 장소" 버튼(지도 오른쪽 위 북마크 아이콘 Fab)을 누르면 무엇을 보여 주나. ① 같은 첫 화면에서 지도 핀과 카드 목록이 내 저장 장소로만 바뀌는 저장 모드(돌아가기 있음), ② 저장 목록 전용 화면, ③ 지도 위 저장 목록 바텀시트. 두 모델은 ①을 골랐다(사용자 메시지 "메인 페이지에서 북마크 눌렀을때 나만의 장소들만 보여주면", Jira -114 "지도와 목록에 내가 저장한 장소만"). 하지만 `fe/AGENTS.md:32`가 와이어프레임 `Saved*`, `DetailSaved`(저장 목록과 상세 진입)를 참고 화면으로 지정하고, 원본(`design_fitdining_v1/`)을 grill한 기기에서 확인하지 못했다. 이 답에 따라 정할 것:
  - 목록 항목의 모양. 저장 목록에는 검색 때 계산되는 핏 점수와 추천 이유가 없다. 제안은 `{place: PlaceSummary, savedAt}`이고 장소 정보는 `PlaceService`로 읽는다(DB 전환 전에 `places` JOIN만 쓰면 Mock 환경에서 목록이 빈다).
  - 저장했던 장소가 지금 404이면 그 항목만 빼고 행은 해제 전까지 둘지, "볼 수 없는 장소"로 보일지. 엔진 503은 빈 목록이 아니라 다시 시도할 수 있는 실패로 보인다(D-2의 6).
  - 로딩, 진짜 0건, 네트워크 실패의 문구와 다시 시도. 목록에서 바로 해제할 수 있는지(제안: 해제는 상세에서만, 성공하면 목록과 핀에서 바로 빠진다).
  - 상세를 봤다가 뒤로 오면 어디로 가는지(제안: 저장 보기 유지), 저장 보기를 나가면 들어오기 전 화면으로 돌아가는지, 저장 보기 진입이 검색 기록에 쌓이지 않는지.
- **Q6 탈퇴한 회원의 북마크 (팀 확인 중).** 사용자는 "남겨둘 이유가 없다"며 탈퇴할 때 삭제하는 쪽으로 기울어 있다. 리뷰를 남기는 결정(review D-38)은 공개 글이라서이고 개인 기록인 북마크에 그대로 적용하지 않는다. 삭제로 정하면 탈퇴 처리(`be/src/main/java/kr/co/fitdining/api/user/UserService.java#withdraw`)에서 북마크를 지우는 범위와, 탈퇴와 동시에 들어온 저장을 어떻게 막는지 정한다. 남기기로 정하면 재가입한 새 계정에 이어지지 않는다고 적는다.
- **토스트 위치 (팀 확인 중).** 와이어프레임의 토스트가 화면 세로 가운데인지 하단 막대 바로 위인지. 지금 공통 토스트는 가로 가운데, 화면 아래에서 96px 위에 고정되고(`fe/src/shared/ui/overlay/toast.tsx`) 모서리만 둥글다. 와이어프레임 캡처는 가로 가운데, 하단 막대 바로 위의 알약 모양이다. 공통 컴포넌트라 바꾼다면 북마크만의 일인지 공통 수정인지 범위를 따로 정한다.
- **Q10 Mock 장소 id로 저장된 북마크 (사용자 확인 대기).** 두 모델의 제안: local/dev에서 Mock id(1..36)로 저장된 북마크는 시험 데이터라 -115가 장소 조회를 DB로 바꿀 때 지우고, 이 인수인계를 북마크 문서에 적는다. 운영은 Mock 엔진이 꺼져 있어(place-search D-63) -115 전에는 저장이 503이므로 Mock id 북마크가 생기지 않는다. 사용자가 아직 답하지 않았다.
