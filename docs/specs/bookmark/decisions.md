# 장소 북마크 decisions

Glossary: none · ADRs: none

Jira: S15P31A302-114 "사용자별 장소 북마크 추가". 2026-10-28 grill(`--auto`)의 중간 결정을 2026-10-29 grill에서 사용자가 확인하고 미결 질문(저장한 장소 화면, 탈퇴, 토스트 위치, Mock id)을 마저 정했다. 화면 기준은 와이어프레임 `Saved`, `SavedFull`, `SavedEmpty`, `SavedError`, `SavedNetError`, `DetailSaved`, `DetailSaveFail`, `StartGuest`다(`fe/AGENTS.md`가 적은 경로가 아니라 작성 시점 사용자 PC의 `Desktop/핏다이닝 디자인 v1/project/`에 있다).

용어: 화면 글자의 "저장"이 북마크이고 "저장 해제"가 북마크 취소다. **저장한 장소 화면**은 메인 첫 화면의 지도와 하단 패널이 내가 저장한 장소만 보이도록 바뀐 상태다(별도 페이지가 아니다).

## D-1 북마크가 장소를 가리키는 방식
- Status: settled
- Decision: 북마크의 장소 id에 `places` FK를 둔다(D-16). 저장하기 전에 장소 기능의 `PlaceService.getPlace`로 장소가 있는지 확인하는 단계는 그대로 둔다(없으면 404, 검색 엔진이 없으면 503). 확인과 저장 사이에 장소가 사라져 FK에 걸려도 없는 장소(404)다. 북마크 예외 처리기가 장소 예외를 404/503으로 직접 바꾼다(장소 예외 처리기는 장소 컨트롤러에만 걸려 있다). 키는 `(user_id, place_id)` 복합 기본키이고 별도 북마크 id는 없다. DB는 그 밖에 장소 id 양수 CHECK와 사용자 id의 `auth_users` FK를 둔다.
- Rejected: FK 없이 저장 전 확인만(이전 결정) → Mock 시절 번호로 저장된 행이 같은 번호의 다른 장소에 붙고, 장소가 지워지면 가리킬 곳 없는 행이 남는다. 대리키 `bookmark_id` → 북마크를 id로 가리킬 일이 없다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/place/PlaceService.java#getPlace` (reuse) — 저장 전 장소 존재 확인과 목록 항목 정보(D-13)

## D-2 절대 일어나면 안 되는 것
- Status: settled
- Decision: (1) 북마크의 주인은 인증 결과로만 정하고 요청 값으로 바꿀 수 없다. (2) 한 사용자의 북마크는 다른 사용자에게 보이거나 다른 사용자가 바꿀 수 없다(조회, 저장 여부, 해제 모두 그 사용자로 제한). (3) 토큰이 아직 유효해도 탈퇴한 사용자는 모든 북마크 API에서 401이다. (4) 같은 사용자, 같은 장소의 북마크는 최대 한 행이고, 중복이나 동시 저장도 성공하며 처음 저장 시각을 바꾸지 않는다. (5) 저장한 장소 화면에는 내가 저장한 장소만 나온다(남의 장소, 저장하지 않은 장소, 주변 추천이 섞이지 않는다). (6) 실패를 성공, 빈 목록, 미저장으로 보여 주지 않는다. 결과가 불명확하면(시간 초과 등) 다시 조회해 맞춘다. (7) 로그아웃이나 계정 전환 뒤 이전 계정의 캐시, 늦게 온 응답, 쓰기 결과가 새 계정 화면에 나오지 않는다. (8) 저장 목록을 만들려고 핏 점수나 추천 이유를 지어내거나 과거 검색 카드에서 끌어오지 않는다. (9) DB 모드에서 북마크가 다른 장소를 가리키지 않는다. (10) prod의 실제 북마크가 마이그레이션 때문에 지워지지 않는다. (11) 없는 장소를 저장하면 500이 아니라 404다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/auth/repository/AuthUserRepository.java#existsByIdAndDeletedAtIsNull` (reuse) — 탈퇴한 사용자를 401로 막는 확인

## D-3 저장과 해제의 의미
- Status: settled
- Decision: 장소별 자원에 `PUT`으로 저장, `DELETE`로 해제하고 둘 다 204다. `PUT`은 인증, 탈퇴하지 않은 사용자 확인(401), 이미 저장된 장소면 장소 확인 없이 204, 아니면 `PlaceService.getPlace` 확인(404/503), 충돌 시 무변경 삽입(`INSERT … ON CONFLICT DO NOTHING`) 순서다. 그래서 다시 `PUT`해도, 동시에 `PUT`해도 모두 성공하고 처음 저장 시각과 순서를 바꾸지 않는다. 저장 시각은 주입한 `Clock`에서 얻는다. 저장하지 않은 장소를 `DELETE`해도 성공이고, 해제는 행을 실제로 지운다. `DELETE`는 장소 엔진을 부르지 않아 장소가 사라지거나 엔진이 멈춰도 내 북마크를 지울 수 있다. FE는 요청 중 버튼을 막아 같은 장소의 쓰기가 겹치지 않게 하고(D-5), 오프라인에서 누른 쓰기를 연결이 돌아온 뒤 자동으로 보내지 않으며, 쓰기는 누른 계정의 토큰으로만 보낸다. 그사이 로그아웃이나 계정 전환(다른 탭 포함)이 있으면 보내지 않는다.
- Rejected: 토글 하나 → 시간 초과 뒤 재시도가 저장을 해제한다. `POST`가 409, `DELETE`가 404 → 두 번 누르기와 재시도가 오류가 된다. 리뷰처럼 `saveAndFlush` 뒤 제약 이름으로 오류 나누기 → 키를 직접 넣는 엔티티는 merge로 처리돼 저장 시각을 덮어쓰고, 동시 삽입은 PK 위반으로 트랜잭션이 깨진다. 이미 저장된 장소도 매번 장소 확인 → 엔진이 멈추거나 장소가 사라지면 저장된 장소의 재시도가 404/503 실패로 보인다(D-2의 6). DB `now()`로 저장 시각 → 고정 시계 테스트로 정렬을 검증할 수 없다.

## D-4 API 경로와 인증
- Status: settled
- Decision: `GET /api/v1/me/bookmarks`(내 목록, 항목 모양은 D-13), `GET /api/v1/me/bookmarks/{placeId}`(`{bookmarked: boolean}`), `PUT`·`DELETE /api/v1/me/bookmarks/{placeId}`(204). 사용자는 토큰에서만 얻는다. 이 경로는 인증 인터셉터 범위 밖이라 리뷰처럼 컨트롤러가 `AuthUseCases.authenticate`를 직접 부르고, 모든 API에서 탈퇴하지 않은 사용자인지 확인한다. 북마크 예외 처리기는 `AuthFailure`의 상태 코드와 토큰 만료 `type`을 그대로 둔다. `/api/v1/me`는 새 경로다(기존 인증의 내 정보는 `/api/auth/me`).
- Rejected: `/api/v1/users/{userId}/bookmarks` → 인증 인터셉터는 `UserController`나 지정 경로만 인증하므로(`AuthWebConfiguration`) 새 컨트롤러는 이득이 없고, 경로 userId와 토큰 비교만 늘어난다. `/api/v1/places/{placeId}/bookmark` + `/api/v1/me/bookmarks` → 개인 컬렉션 하나가 두 경로 계열로 나뉜다. 북마크 컨트롤러를 `api.place` 패키지 아래 두기 → 장소 예외 처리기(`basePackageClasses`)가 함께 걸린다.
- Reuse: `be/src/main/java/kr/co/fitdining/api/auth/ports/AuthUseCases.java#authenticate` (reuse) — 리뷰 컨트롤러처럼 Bearer 토큰에서 사용자 확인

## D-5 장소 상세의 저장 버튼
- Status: settled
- Decision: 로그인한 사용자는 장소별 저장 여부 API(D-4)로 상세 하단 막대의 저장(북마크) 버튼 상태를 받는다. 저장 여부는 북마크 테이블만 보고, 장소 상세 응답은 바꾸지 않는다. 확인 중에는 버튼을 막고, 확인에 실패하면 저장됨·미저장 어느 쪽으로도 보이지 않으며 누르면 다시 확인한다(D-2의 6). 버튼은 서버 응답을 받은 뒤 바뀌고 요청 중에는 눌리지 않는다. 결과별 토스트와 버튼 모양은 spec이 정한다: 성공, 4xx(되돌림), 5xx(실패 토스트와 다시 조회), 시간 초과·연결 끊김(다시 조회, 그것도 실패하면 연결 확인 토스트). 토스트는 지금 공통 토스트를 쓴다. place 도메인은 auth 도메인을 직접 import하지 않고 app 계층이 인증을 이어 준다.
- Rejected: 장소 상세 응답에 `bookmarked` → 공개 상세를 개인화해 검색 엔진 계약과 캐시가 바뀐다. 내 목록 전체를 받아 포함 여부 확인 → 상세는 링크로 바로 들어올 수 있어 버튼 하나에 목록 전체를 받는다. 공통 토스트를 와이어프레임의 알약 모양으로 바꾸기 → 모든 화면이 영향을 받아 북마크 범위를 넘는다. 누르자마자 버튼을 바꾸고 실패하면 되돌리기 → 요청 중 다시 누르기의 대기열과 되돌릴 기준 상태를 따로 정해야 한다.
- Reuse: `fe/src/domains/auth/api/with-access-token.ts#withAccessToken` (reuse) — 로그인이 필요한 북마크 요청

## D-6 저장 목록의 크기와 순서
- Status: settled
- Decision: 저장 개수 상한은 없다. 저장 시각 최신순, 같은 시각은 장소 id 내림차순이고 한 번에 전체를 돌려준다. 해제 뒤 다시 저장하면 새 저장 시각으로 맨 앞에 온다. 임의 개수로 조용히 자르지 않는다. 정렬은 최신순 하나이고 화면에 정렬 드롭다운을 두지 않는다(정렬 옵션은 고도화 때 더한다). 응답이나 지도 핀 수가 감당되지 않는다는 측정이 생기면 페이징을 다시 설계한다.
- Rejected: cursor paging → 장소가 300곳이라 지금은 필요 없고 지도 핀과 함께 쓰기 어렵다. 개수 상한 → 요청에 없던 제한이다. 와이어프레임의 "최신순" 드롭다운 → 고를 정렬이 하나뿐이다.

## D-7 비로그인 사용자가 저장을 누를 때
- Status: settled
- Decision: 비로그인 사용자가 상세의 저장 버튼이나 메인의 "저장한 장소" 버튼을 누르면 공통 확인 창으로 "로그인이 필요해요" 안내를 띄우고 [취소]와 [로그인](로그인 화면으로 이동)을 고르게 한다. 설명은 상세에서 "장소 저장은 로그인해야 이용할 수 있어요.", 메인 버튼에서 "저장한 장소는 로그인해야 볼 수 있어요."다(와이어프레임 `StartGuest`). 취소하면 아무 요청도 보내지 않고 지금 화면에 그대로 있는다(저장한 장소 화면에서는 그 화면의 [뒤로]와 같다, D-14). 비로그인 사용자에게는 저장 여부 API를 부르지 않는다. 만료된 AT는 지금처럼 RT로 한 번 갱신해 다시 보낸다. 북마크 요청이 그래도 401로 끝나면(갱신 실패, 탈퇴한 계정, 무효 토큰) 세션이 끝난 것으로 보고 인증 모듈의 `clearSession()`으로 앱의 로그인 정보를 지우며(지우지 않으면 로그인 화면이 이미 로그인됐다고 보고 홈으로 돌려보내 복귀와 401이 되풀이된다) 버튼을 비로그인 모양으로 둔다. 사용자가 누른 요청이면 같은 안내를 띄우고, 화면을 열 때 저절로 나간 조회면 창 없이 버튼만 바꾼다. 페이지를 열 때 로그인 복원 요청이 응답 없이 실패하거나 3초 안에 끝나지 않으면 지금 앱처럼 비로그인으로 본다(D-2의 6의 의도된 예외).
- Rejected: 바로 로그인 화면으로 이동(리뷰 작성, 내 정보의 방식) → 저장은 둘러보다 가볍게 누르는 버튼이라 보던 화면을 잃고, 와이어프레임의 로그인 안내와 다르다. 버튼 숨기기 → 진입점이 사라져 기능을 알 수 없다.
- Reuse: `fe/src/shared/ui/overlay/confirm-dialog.tsx#ConfirmDialog` (reuse) — 로그인 안내 창 · `fe/src/domains/place/ui/place-detail-screen.tsx#PlaceDetailScreen` (modify) — 하단 막대 저장 버튼의 "준비 중" 토스트를 저장·해제(D-5)와 로그인 안내로 바꾼다 · `fe/src/domains/place/ui/search-screen.tsx#SearchScreen` (modify) — "저장한 장소" 버튼의 "준비 중" 토스트를 저장한 장소 화면(D-12)과 로그인 안내로 바꾼다

## D-8 로그인한 뒤 어디로 가나
- Status: settled
- Decision: 북마크의 로그인 안내에서 [로그인]을 고르면 지금 화면 주소를 그 탭의 sessionStorage에 적어 둔다. 이메일·소셜 로그인과 소셜 가입은 모두 홈(`/`)에 도착하므로, 홈이 도착할 때 적어 둔 주소를 한 번 읽어 지우고 그 화면으로 보낸다. 상세에서 눌렀으면 그 장소 상세로, 메인 "저장한 장소" 버튼이나 저장한 장소 화면에서 눌렀으면 저장한 장소 화면 주소(D-12)로 간다. 로그인된 상태로 홈에 도착했을 때만 따르고, 로그인 없이 홈에 왔거나 남긴 지 10분이 지났으면 버린다. 같은 출처의 경로만 따른다. 누르려던 저장은 자동으로 실행하지 않는다. 인증 BE와 로그인 화면은 고치지 않는다.
- Rejected: 홈으로만 이동 → 보던 장소를 다시 찾아야 한다. 로그인 주소에 `next` 붙이기 → 소셜 로그인은 BE callback이 `/`로 고정해 보내(`SocialAuthController`) 다른 담당의 인증 BE를 고쳐야 한다. 앱 전체의 공통 복귀 장치로 만들 때 다시 본다. 로그인 뒤 저장 자동 실행 → 로그인하면서 계정이 바뀌면 다른 계정에 저장된다.
- Reuse: `fe/src/app/home/home-screen.tsx#HomeScreen` (modify) — 홈 도착 때 적어 둔 주소로 한 번 보낸다

## D-9 내 정보의 "저장한 장소" 메뉴
- Status: settled
- Decision: "내 정보" 화면의 "저장한 장소" 메뉴도 메인 버튼과 같은 저장한 장소 화면(D-12)을 연다. 별도 목록을 만들지 않는다. 이 메뉴로 들어왔으면 저장한 장소 화면의 [뒤로]는 내 정보로 돌아간다.
- Reuse: `fe/src/app/my/page.tsx#MyPage` (modify) — "저장한 장소" 메뉴의 토스트만 저장한 장소 화면 열기로 바꾼다

## D-10 place-search의 "준비 중" 동작 대체
- Status: settled
- Decision: 북마크 기능이 place-search의 AC-35("저장한 장소" 버튼 토스트)와 AC-40(상세 "저장" 토스트)의 저장 부분 동작을 대체한다고 북마크 spec에 명시한다. "공유" 버튼의 토스트와 "내 정보" 버튼은 그대로다. place-search 문서는 고치지 않는다(place-search D-85, D-94가 "기능이 생기면 동작만 바꾼다"고 정해 두었다).

## D-11 검사할 경계
- Status: settled
- Decision: BE는 실제 PostgreSQL과 마이그레이션으로(리뷰의 `ReviewPersistenceTest`처럼) 유일성, 동시 `PUT`이 모두 성공하고 한 행이며 처음 저장 시각이 유지되는지, 사용자 간 조회·해제 격리, 정렬과 해제 뒤 재저장을 확인한다. 컨트롤러·서비스 테스트로 토큰 없음과 탈퇴 사용자의 401(모든 API, 장소 확인보다 먼저), 저장의 404/503, 이미 저장된 장소의 `PUT`은 엔진이 없어도 204, 반복 `DELETE` 204와 엔진 미호출, 저장 여부 true/false, 목록에서 404 장소 빼기와 그 밖의 장소 조회 실패 시 목록 실패를 확인한다. FE는 jsdom으로 상세 버튼의 확인 중·실패·저장됨·미저장 상태, 비로그인 안내의 로그인·취소, 성공·실패·불명확 결과 뒤 표시와 캐시, 계정 전환 중 늦은 응답과 보내지 않은 쓰기 버리기, 오프라인 쓰기의 자동 재전송 없음을 확인한다. 저장한 장소 화면은 업종 탭 거르기와 개수, 0개와 탭별 빈 상태, 서버 실패와 연결 실패, 상세에서 돌아왔을 때 탭·패널 유지와 해제 반영을 확인한다. 두 계정으로 직접 확인하는 것도 한다. 로그인 뒤 복귀는 이메일 로그인으로만 직접 확인한다. 소셜 로그인도 홈(`/`) 도착 처리라는 같은 복귀 경로를 타고, local에 소셜 로그인 환경변수가 없다.
- Rejected: BE 테스트와 수동 확인만 → 이전 계정 캐시 노출, 실패를 미저장으로 보이는 문제, 지도에 주변 추천 핀이 남는 문제를 못 잡는다. 수동 확인에서 소셜 로그인 복귀도 한 번 → 이메일과 같은 복귀 경로이고 local에 소셜 로그인 환경변수가 없어 확인할 수 없다(2026-10-29 구현 중 사용자 결정).

## D-12 저장한 장소 화면
- Status: settled
- Decision: 로그인한 사용자가 메인의 "저장한 장소" 버튼을 누르면 별도 페이지가 아니라 메인 첫 화면의 지도와 하단 패널(중간·전체 높이)이 내 저장 장소로만 바뀐다(와이어프레임 `Saved`, `SavedFull`). 이 화면은 메인의 주소 `/?view=saved`(고른 업종 탭은 `category`)로 열려 브라우저 기록에 한 칸 쌓이고, 여기서 연 상세는 주소에 저장 목록에서 왔다는 표시를 받아 핏 점수를 숨긴다. 화면의 [뒤로]는 브라우저 뒤로 가기와 같다(이전 화면이 없으면 메인 기본 화면). 진행 중이던 검색은 뒤에서 마저 끝난다. 지도 핀은 순위 숫자 없는 북마크 모양이고, 화면 위에는 [뒤로]와 [내 위치로]만 있다(검색창과 오른쪽 위 버튼은 숨긴다). 카드는 한 번 누르면 상세로 간다. 왼쪽 위 [뒤로]는 들어오기 전 메인 화면(주변 추천이든 검색 결과든)으로 돌아간다. 목록의 장소를 누르면 장소 상세가 열리고 핏 점수와 추천 이유 없이 보인다(`DetailSaved`). 상세에서 [뒤로]를 누르면 메인 기본 화면이 아니라 저장한 장소 화면으로 돌아오고, 고른 업종 탭과 패널 높이도 유지된다. 상세에서 저장 해제한 장소는 돌아왔을 때 목록과 핀에서 빠져 있다. 목록 카드의 ⋯ 메뉴에서도 해제한다(처음에는 와이어프레임대로 넣지 않았다가 D-18에서 바꿈). 저장한 장소 화면을 연 것은 최근 검색이나 요청 기록에 남지 않는다.
- Rejected: 저장 목록 전용 페이지, 지도 위 바텀시트 → 와이어프레임이 메인 지도와 결과 패널 틀을 그대로 쓴다. 주소 없이 화면 상태로만 두기 → 로그인 뒤 복귀(D-8)와 내 정보 메뉴(D-9)가 가리킬 주소가 없고, 휴대폰 뒤로 가기가 저장한 장소 화면을 건너뛴다.
- Reuse: `fe/src/domains/place/ui/search-screen.tsx#SearchScreen` (modify) — 메인 화면에 저장한 장소 상태를 더한다

## D-13 저장 목록 항목과 업종 탭
- Status: settled
- Decision: 내 목록 응답은 항목마다 `{place: PlaceSummary, address, tags, openStatus, savedAt}`이고, 서버가 북마크마다 `PlaceService.getPlace`로 채운다. 핏 점수와 추천 이유는 없다(D-2의 8). 카드는 썸네일, 이름, 업종, 영업 상태, 거리, 주소, 태그 앞 2개를 보인다. 태그는 장소 상세의 `tags`를 그대로 쓰고 비어 있으면 태그 줄을 그리지 않는다. 거리는 FE가 내 위치로 계산하고 위치를 모르면 뺀다. 영업 상태는 요청 시각으로 계산되므로 저장한 장소 화면에 들어올 때마다(상세에서 돌아올 때 포함) 목록을 새로 받는다. 패널 머리는 "저장한 장소"와 지금 보이는 개수다. 업종 탭은 [전체]와 업종(`CategoryGroup`)마다 하나이고, 저장한 장소가 1개 이상이면 항상 보인다(0개는 D-14). 탭 목록은 업종 이름표 한 곳에서 만들어 따로 하드코딩하지 않아, 지역 확장으로 업종이 늘면 탭도 함께 는다. 탭은 받은 전체 목록을 FE에서 걸러 목록과 지도 핀에 함께 적용한다. 목록마다 북마크 수만큼 장소 조회가 나가는 것은 300곳 이하라 감수하고, -115에 여러 장소를 한 번에 읽는 조회가 필요하다고 인수인계한다.
- Rejected: 북마크 테이블에 장소 정보·업종 복제 → 업종이나 장소 정보가 바뀔 때 북마크도 고쳐야 한다. 업종별 목록 API → 전체가 300곳 이하라 화면에서 거르면 된다. 저장·해제 뒤 FE가 목록을 직접 고치기 → 204에는 항목 정보가 없고 서버 순서와 어긋날 수 있어 다시 받는다(저장한 장소 화면 안에서 해제한 장소만 빼는 것은 D-18).
- Reuse: `fe/src/domains/place/model/place-labels.ts#CATEGORY_LABELS` (reuse) — 업종 탭 목록과 이름

## D-14 저장한 장소 화면의 빈 상태와 실패
- Status: settled
- Decision: 저장한 장소가 0개면(`SavedEmpty`) 지도와 [뒤로]·[내 위치로]는 그대로이고, 패널에는 제목 "저장한 장소"만(개수·탭 없음) 두고 "아직 저장한 장소가 없어요" / "장소 상세에서 저장 버튼을 누르면 여기에 모여요." / [추천 받으러 가기]를 보인다. 이 버튼은 보던 검색 결과를 닫고(최근 검색 기록은 남김) 메인 기본 화면(주변 추천)으로 간다. 목록 요청에서 세션이 끝나면(401) 로그인 안내를 띄우고, 취소는 화면의 [뒤로]와 같다. 시간 초과는 서버 실패와 같게 보인다. 고른 업종 탭에만 없으면 버튼 없이 "저장한 카페가 없어요" 같은 짧은 안내다. 서버 실패(5xx, 검색 엔진 503)는 같은 패널 자리에 "저장한 장소를 불러오지 못했어요" / "잠시 후 다시 시도해 주세요." / [다시 시도]다(`SavedError`). 연결 실패는 지도 없이 전체 페이지로 [뒤로]와 제목, "인터넷에 연결되어 있지 않아요" / "연결을 확인하고 다시 시도해 주세요." / [다시 시도]다(`SavedNetError`). 저장했던 장소가 지금 404면 그 항목만 목록과 개수에서 빼고 북마크 행은 남긴다. 404가 아닌 장소 조회 실패가 하나라도 있으면 목록 전체를 실패로 보인다.
- Rejected: 404 장소를 "볼 수 없는 장소"로 표시 → 사용자가 할 수 있는 일이 없고 와이어프레임에 없다. 일부 장소만 실패했을 때 나머지만 보이기 → 실패를 빈 목록이나 누락으로 보이게 된다(D-2의 6).

## D-15 회원 탈퇴 시 북마크
- Status: provisional
- Decision: 탈퇴해도 북마크 행은 남기고, 북마크 테이블에 삭제 시각 컬럼을 두지 않는다. 탈퇴는 `auth_users.deleted_at`만으로 처리되고 탈퇴한 사용자는 모든 북마크 API에서 401이라(D-2의 3) 아무에게도 보이지 않는다. 탈퇴 처리(`UserService.withdraw`)는 바꾸지 않는다. 재가입은 새 사용자 id라 이전 북마크가 이어지지 않는다. 탈퇴와 동시에 들어온 저장이 탈퇴 뒤에 행을 남길 수 있지만 같은 이유로 보이지 않는다. 보관 기간은 탈퇴한 회원 행과 같이 PRD OQ-17(soft delete 탈퇴의 보관·파기)이 정해지면 따른다. 삭제로 바꾸려면 탈퇴 처리에 북마크 삭제와 저장 쪽 사용자 행 잠금을 넣고, 이미 탈퇴한 사용자의 행을 지우는 일회성 마이그레이션을 더한다. 다른 기능이 bookmarks를 직접 읽게 되면 탈퇴한 사용자의 행을 걸러야 한다.
- Default: 탈퇴한 사용자의 북마크 행은 남는다. 탈퇴 때 비공개 개인 데이터(취향, 소셜 연결)를 지우는 기존 처리와 다르고 남긴 행을 서비스 안에서 다시 쓸 길은 없지만, 회원 행 자체도 남는 지금은 팀 보관 정책(OQ-17)이 정해질 때까지 함께 보관한다. OQ-17이 정해지면 다시 본다.
- Rejected: 탈퇴 시 북마크 물리 삭제 → 기능상 차이가 없고 보관 정책은 회원 행과 함께 정한다. 북마크 테이블에 `deleted_at` → 유일 제약이 부분 인덱스가 되고 재저장 규칙(D-6)이 복잡해지는데, 사용자 행의 삭제 시각으로 충분하다.

## D-16 장소 FK와 기존 북마크 삭제
- Status: settled
- Decision: 새 마이그레이션 하나가 기존 `bookmarks` 행을 모두 지운 뒤 `place_id` → `places` FK를 `ON DELETE CASCADE`로 건다(장소가 지워지면 그 장소의 북마크도 지운다). 버전은 머지 때 마지막 번호의 다음이다. 기본키, 사용자 FK, 양수 CHECK는 그대로 둔다. 2026-11-02 확인: dev는 이미 DB 모드에 장소 300곳이 적재돼 있고 북마크는 시험 데이터 1행이다. prod DB에는 앱 테이블이 없어 지울 행이 없다. 그래서 "DB 엔진 전환과 같은 배포"라는 이전 조건은 이미 충족됐고 일반 배포로 나간다. 다만 prod를 사용자에게 열기 전에 나가야 한다(D-2의 10).
- Rejected: `places`에 없는 행만 지우기 → Mock 시절 번호가 우연히 겹친 행이 다른 장소에 붙은 채 남는다. Mock id 북마크를 DB 장소 id로 옮기기 → `places.place_id`는 적재할 때 새로 매겨져 Mock id와 맞는다는 보장이 없다. 행을 지우지 않고 FK만 더하기 → `places.place_id`도 1부터 매겨져 FK가 실패하지 않고 엉뚱한 장소에 이어진다. 장소 FK를 `RESTRICT`로 → 장소를 지우거나 다시 적재할 때 북마크가 막는다.

## D-18 목록 카드의 ⋯ 메뉴에서 해제
- Status: settled
- Decision: 저장한 장소 목록의 카드마다 오른쪽에 리뷰처럼 ⋯ 메뉴(접근 이름 "<장소 이름> 메뉴")를 두고, 메뉴 항목은 빨간 글자의 "해제" 하나다(2026-11-03 사용자 피드백, S15P31A302-141). 지금까지는 장소 상세에 들어가야만 해제할 수 있어 불편했다. [해제]를 누르면 확인 창 없이 바로 해제 API(`DELETE`, 이미 없어도 204)를 보내고, 응답이 올 때까지 그 장소의 [해제]를 다시 누를 수 없다. 성공하면 목록을 다시 받지 않고 받은 목록에서 그 장소만 빼고(카드, 지도 핀, 개수가 함께 줄고, 업종 탭이나 전체가 비면 D-14의 안내), 그 장소의 저장 여부 캐시를 "저장 안 함"으로 맞추며 "저장을 해제했어요" 토스트를 띄운다. 빼기만 하므로 D-13이 걱정한 항목 정보와 서버 순서 문제가 없다. 실패하면 카드를 남기고 "저장을 해제하지 못했어요. 다시 시도해 주세요."(연결 실패면 "인터넷 연결을 확인하고 다시 시도해 주세요.") 토스트를 띄운다. 401이면 목록 요청과 같이 세션을 지우고 로그인 안내를 띄운다(D-7). BE는 바꾸지 않는다.
- Rejected: 카드 오른쪽에 채워진 북마크 버튼 → 사용자가 리뷰처럼 ⋯ 메뉴로 하기로 했다. 리뷰 삭제처럼 확인 창 → 사용자가 바로 해제하기로 했다. 되돌리기 토스트 → 공통 토스트에 버튼이 없고 상세의 해제에도 없다. 해제 뒤 목록 다시 받기 → 패널이 로딩으로 바뀌어 깜빡인다.
