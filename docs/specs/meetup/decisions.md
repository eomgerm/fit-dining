# 모임 추천 decisions

Glossary: none · ADRs: none

Jira: S15P31A302-207 "모임 추천 스펙 문서 작성". 요구사항은 모임 추천 PRD(PRD FR-16~FR-29, PRD AC-36~AC-89, PRD D-08~D-41)이고, 화면 기준은 모임 추천 화면 예시(PRD §12)다. 이 문서의 결정 번호는 PRD의 결정 번호와 따로 매긴다. PRD의 번호는 앞에 "PRD"를 붙여 적는다(PRD D-30).

용어: **모임**은 모임장이 만든 장소 찾기 단위다. **프로필**은 모임 안에서 참여자 한 명을 나타내는 이름과 색이고, **모임 취향**은 프로필이 모임 질문에 남긴 답이다. **스냅숏**은 모임의 지금 상태를 한 번에 주는 응답이다. **추천기**는 모임 정보와 취향을 받아 장소 20곳과 점수를 돌려주는 BE 안의 인터페이스다.

## D-1 범위와 단계
- Status: settled
- Decision: 모임 추천의 BE·FE와, AI에 더하는 모임 전용 주소 두 개의 계약을 다룬다. 여섯 단계로 나눈다. ① 뼈대(모임 만들기, 프로필과 취향, 대신 쓰는 추천기로 추천과 결과), ② 투표와 정하기, ③ 추천 연동(AI의 모임 전용 주소와 BE의 AI 추천기), ④ 모임 지점, ⑤ 수명 주기(만료, 닫힘, 탈퇴, 모임 뒤), ⑥ 마무리(링크 미리보기, 회원 프로필로 바꾸기, 공개하는 홈 시작 버튼). 뼈대가 끝나면 장소 Mock 모드에서 만들기 → 참여 → 추천 → 결과가 끝에서 끝까지 이어진다. 구현 이슈는 이 단계 안에서 끝에서 끝까지 이어지는 조각으로 나눈다. BE·FE 이슈 하나가 BE와 FE를 함께 가져 이슈가 끝나면 장소 Mock 모드의 화면으로 확인되고, AI의 모임 전용 주소 두 개는 AI 담당 이슈로 따로 둔다.
- Rejected: 단계 안에서 BE, FE, AI로 나누기(처음 결정) → BE 이슈만 끝나서는 화면으로 확인할 수 없다. 리뷰 기능(S15P31A302-47~S15P31A302-55)도 이슈 하나에 BE와 FE를 함께 뒀다. AI 연결부터 → AI의 모임 전용 주소는 계약 합의와 구현이 필요해 그동안 화면과 상태 흐름을 만들 수 없다. 기능 전체를 한 번에 → 리뷰 spec의 Walking Skeleton처럼 가장 작은 흐름을 먼저 잇는 편이 다른 담당과 맞출 곳을 일찍 드러낸다.

## D-2 이름과 주소
- Status: settled
- Decision: 코드 이름은 `meetup`이다. BE 패키지 `kr.co.fitdining.api.meetup`, FE 도메인 `fe/src/domains/meetup`, API `/api/v1/meetups`, 모임 링크 `/m/{code}`, 테이블 접두사 `meetup`. 코드(`code`)는 무작위 128비트를 base64url로 쓴 22자다.
- Rejected: `group` → 시설 코드 `GROUP`(단체 이용), `category_group`, 방문 목적 `PURPOSE_GROUP`과 겹치고 SQL 예약어다. `gathering` → 온보딩 방문 목적 `GATHERING`과 겹친다. `meeting` → 회의로 읽힌다. 링크를 `/meetups/{code}`로 → 단톡방에 붙는 주소라 짧은 쪽이 낫다.

## D-3 상태와 권한의 기준은 BE다
- Status: settled
- Decision: 저장하는 상태(`phase`)는 WAITING, RESULT, VOTING, DECIDED 넷이다. PRD §5.1의 나머지 상태는 다른 값에서 얻는다. 계산 중은 RUNNING인 계산 행, 모임 뒤는 정함이고 오늘(KST)이 모임 날짜 당일 이후(날짜가 없으면 정한 당일부터), 닫힘은 모임 행이 없는 것이다(404, D-6). PRD §5.1의 상태·역할 표를 BE의 한 클래스로 옮기고, 스냅숏에 지금 이 사람이 할 수 있는 동작 목록(`allowed`)을 싣는다. FE는 그 목록으로 버튼을 보이고 숨기며 같은 표를 다시 만들지 않는다. 모임 뒤를 모임 날짜 당일부터로 두어 실제로 가기 전에 방문 평가가 남을 수 있는 것은 감수한다.
- Rejected: 일곱 상태를 모두 저장 → 계산 중은 대기와 결과 위에 겹치는 표시이고 모임 뒤는 시각으로 정해져, 저장하면 서로 어긋나는 값이 생긴다. FE가 상태와 역할로 버튼을 판단 → 같은 규칙이 두 곳에 생겨 PRD AC-75를 한 곳에서 검증할 수 없다. 모임 뒤를 모임 날짜 다음 날부터 → 모임 당일에 다녀온 사람이 그날 평가할 수 없다.

## D-4 동시에 온 요청은 모임 행 잠금으로 줄 세운다
- Status: settled
- Decision: 모임의 모든 쓰기는 `meetups` 행을 `FOR UPDATE`로 잡고 상태를 확인한 뒤 고친다. 8번째 프로필, 같은 이름, 계산 중복, 마감 뒤 투표가 이 하나로 처리된다. 유일 인덱스(이름, 색, 회원, RUNNING 계산)가 마지막으로 막는다. 부딪힌 요청은 409와 `type`으로 답하고, FE는 스냅숏을 다시 받아 짧게 알린다. 투표가 열린 뒤의 취향 저장은 받고, 응답의 지금 상태로 화면이 추천은 바뀌지 않는다고 알린다. 해석 주소는 잠금 밖에서 부르고, 저장할 때 잠금을 잡아 그사이 설명이 바뀌지 않았는지 확인한다. AI 호출 동안 그 모임의 다른 쓰기를 막지 않기 위해서다.
- Rejected: 낙관적 잠금(버전 컬럼) → 한 모임이 8명이라 경합이 작고, 재시도 처리가 요청마다 필요해진다. 저장 전 조회로만 막기 → 두 요청이 함께 통과한다(리뷰 D-3과 같은 이유).

## D-5 데이터 모델
- Status: settled
- Decision: 테이블은 네 개다. `meetups`, `meetup_profiles`, `meetup_profile_sessions`, `meetup_calculations`. 투표는 모임당 하나라 `meetups`의 칸(`poll_state`, `poll_anonymous`, `poll_place_ids`, `poll_tie_votes`)으로 두고, 표는 프로필당 하나라 `meetup_profiles`의 칸(`vote_place_id`, `vote_session_id`)으로 둔다. 프로필을 지우면 표도 함께 사라진다. `poll_state`는 한 번 열면 비우지 않는다. 다시 추천받을 수 없는지와, 정하기를 취소할 때 마감한 투표로 돌아갈지를 이것으로 판단한다(D-19). 마감할 때 동점이면 그 표 수를 `poll_tie_votes`에 고정한다. 마감 뒤 프로필을 지워도 투표 계속하기가 되는지와 "2표씩 동점" 문구가 바뀌지 않게 하기 위해서다. 다시 열면 비운다. 표가 후보 안의 장소인지는 서비스가 확인한다(`poll_place_ids`가 배열이라 FK가 없다). `vote_session_id`는 회원이 로그인으로 던진 표면 비어 있고, 세션 행이 지워지면 비운다(`ON DELETE SET NULL`). 정한 곳은 `decided_place_id`, `decided_how`(VOTE, PICK, DIRECT), `decided_at`이다. 프로필과 모임 취향은 한 화면에서 함께 남기므로 `meetup_profiles` 한 행에 둔다. 계산 결과(`result` jsonb)는 장소 id, 점수, 추천 이유, 덜 맞는 점, 프로필 번호별 취향 점수·근거 없음·놓친 메뉴를 담는다. 적용한 취향(`applied`)과 후보 없음 원인(`empty_reason`)은 따로 jsonb 칸에 둔다. 이름은 읽을 때 붙이고(PRD D-36), 장소 이름·영업 상태·대표 메뉴는 읽을 때 장소 카탈로그에서 가져온다. 계산 행은 마지막 성공 하나와 그 뒤의 실행 중이거나 실패한 하나까지만 남긴다. 새 계산을 시작할 때 이전 실패 행을 지우고, 성공하면 이전 행을 모두 지운다. 자식 테이블은 `meetups`에 `ON DELETE CASCADE`로 걸어 모임 행 하나를 지우면 모임 데이터가 모두 지워진다. `host_user_id`와 `user_id`에는 FK로 따라 지우기를 걸지 않는다(탈퇴가 회원 행을 지우지 않는다). 이름 겹침은 앞뒤 공백 제거, 유니코드 정규화, 소문자 변환을 한 `name_key`로 본다. 측정만을 위한 칸(연 수, 걸린 시간, H3 값)은 두지 않는다(D-6). 마이그레이션은 하나이고 번호는 병합 직전 develop의 가장 높은 번호 다음이다.
- Rejected: 취향을 따로 테이블로 → 프로필과 1:1이고 함께 읽고 쓴다. 결과를 장소마다 행으로 → 20곳을 항상 통째로 읽고 장소별로 찾을 일이 없다. 결과에 이름 저장 → 지운 프로필의 이름이 남는다. 모임 행을 남기고 내용만 비우기 → 지워졌는지를 행 수로 확인할 수 없다. 투표, 후보, 표를 따로 테이블로(처음 설계) → 투표는 모임당 하나, 표는 프로필당 하나라 1:1이고, 테이블이 늘면 지우기와 잠금 범위가 넓어진다. 동점 여부를 표에서 그때그때 얻기 → 마감 뒤 프로필을 지우면 투표 계속하기가 되는지와 동점 안내가 바뀐다. 성공할 때만 이전 계산 행 지우기 → 실패가 계속되면 실패 행이 쌓인다.

## D-6 닫을 때는 모임 행만 지우고 없는 링크로 보인다
- Status: settled
- Decision: 모임을 닫을 때 모임 행을 지우고 자식 행이 따라 지워진다. 남기는 것은 없다. 지운 코드와 처음부터 없던 코드를 구분하지 않고 둘 다 404다. 화면은 없는 링크 문구 하나로 두 경우를 함께 덮는다("없거나 끝난 모임이에요", "모임은 모임 날짜에서 7일 뒤, 또는 모임장이 탈퇴하면 사라져요"). 대신 사라지는 날을 미리 알린다. 취향을 남기기 전 안내(PRD FR-18)에 더해, 대기 화면의 모임 정보에 "○월 ○일까지 열 수 있어요"(스냅숏 `info.expiresOn`)를 보인다. 모임장의 대기 화면에서는 링크 보내기 구역 바로 위라 링크를 보낼 때도 보인다. 측정용 익명 집계도 남기지 않는다(2026-11-10). PRD의 측정(H3~H5)은 이번 범위에서 뺐다. H3는 저장한 결과의 참여자별 취향 점수(모임장 포함)로 잴 수 있고, 모임장 취향 점수 순서로 줄 세우므로 PRD의 정의(모임장 취향만으로 낸 전체 점수 순서)의 근사치다.
- Rejected: 닫힘 표식 테이블(코드, 닫힌 시각, 이유를 남겨 410과 닫힌 이유를 보이기) → 표식만을 위한 테이블과 정리 작업이 생긴다. 사라질 날을 미리 알리고 없는 링크로 보이기로 했다. 모임장 탈퇴로 닫힌 경우도 같은 화면이다. 익명 집계 테이블(처음 설계) → 지우기 전에 한 번 쓰는 테이블과 연 수·걸린 시간 같은 측정용 칸이 생긴다. 측정은 범위에서 뺐다.

## D-7 신원: 회원 세션, 모임 쿠키, 보기만
- Status: settled
- Decision: 요청한 사람은 이 순서로 정한다. ① 로그인한 회원이고 그 회원의 프로필이 이 모임에 있으면 그 프로필(모임장이면 HOST). ② 아니면 모임 쿠키가 가리키는 프로필. ③ 둘 다 없으면 보기만 하는 사람(VIEWER). 모임 쿠키는 이름 `fitdining_meetup`, HttpOnly, SameSite=Lax, `Path=/api/v1/meetups/{code}`, 만료는 모임 삭제 시각이고 Secure는 `auth.cookie-secure`를 따른다. 값은 무작위 256비트이고 DB에는 SHA-256 해시만 둔다. 프로필을 만들거나 다른 브라우저에서 자기 프로필을 고르면 발급한다. 비회원 프로필은 링크를 가진 누구나 고를 수 있고(PRD D-22), 회원 프로필은 그 회원으로 로그인해야 고른다. 표에는 던진 브라우저 세션을 남겨, 익명 투표에서 다른 브라우저로 고른 프로필에는 투표했는지만 보인다(PRD D-32). 모임 날짜를 바꿔 삭제 시각이 바뀌면 쿠키가 실린 다음 요청의 응답이 같은 값의 쿠키를 새 만료로 다시 준다. 그러지 않으면 날짜를 늦춘 모임에서 쿠키가 먼저 사라진다.
- Rejected: 서명한 쿠키(상태 없음) → 서명용 비밀값이 환경 변수 계약에 하나 더 생기고, 표를 던진 브라우저를 구분할 수 없다. 쿠키 경로를 화면 주소(`/m/{code}`)로 → API 요청에 실리지 않는다(PRD FR-28). 쿠키 하나에 여러 모임 → 모임마다 경로가 달라 서로 섞이지 않는 쪽이 단순하다. 로그인 세션에 프로필 저장 → 비회원은 세션이 없다.

## D-8 보안 설정과 쓰기 한도
- Status: settled
- Decision: 공개 경로는 스냅숏·결과·미리보기 GET과 프로필 만들기·고르기, 취향 수정, 투표다. 나머지 모임 경로는 인증이 필요하고, 모임장인지는 서비스가 확인해 403을 낸다. `/api/v1/meetups/`의 쓰기 요청은 로그인 여부와 상관없이 CSRF 토큰을 요구한다. S15P31A302-193이 모든 쓰기 요청에 CSRF를 걸었으므로 모임 경로에 따로 조건을 두지 않는다. 토큰은 세션 없이 `GET /api/auth/csrf`로 받고, FE 공용 클라이언트가 붙인다. `/api/v1/meetups/**` 응답에는 `Cache-Control: no-store`를 붙인다. 로그인 없는 쓰기는 Redis 고정 구간 카운터로 제한한다(키는 모임과 IP, 구간 15분, 시작값 120회. 같은 와이파이의 친구들이 한도를 함께 쓰기 때문이다). 참여자 이름, 모임 취향, 모임 설명은 로그에 남기지 않는다. 보안 설정 파일에는 모임 공개 경로와 `no-store`만 더한다.
- Rejected: 비회원 쓰기에 CSRF 생략(지금 설정 그대로) → 모임 쿠키로 쓰기를 하므로 다른 사이트가 대신 보낼 수 있다. 쓰기 한도를 DB 시도 기록으로(인증과 같은 방식) → Redis가 세션 저장소로 이미 필수이고 카운터가 더 단순하다. 쓰기 한도를 BE 메모리로 → Blue/Green의 두 색이 따로 센다.

## D-9 API의 모양
- Status: settled
- Decision: 스냅숏(`GET /meetups/{code}`)과 결과(`GET /meetups/{code}/result`)를 나눈다. 스냅숏은 가볍게 유지해 자주 다시 받고, 결과는 마지막으로 성공한 계산 id가 바뀔 때만 받는다. 다시 추천받는 중에도 이전 결과를 그대로 보이기 위해서다. 스냅숏은 `phase`, `afterMeetup`, `info`, `questions`, `me`, `allowed`, `profiles`, `pendingCount`, `calculation`(가장 최근 계산), `resultCalculationId`(마지막으로 성공한 계산), `poll`, `decision`을 담는다. 결과 카드의 장소 요약, 모임 시각 기준 영업 상태, 대표 메뉴, 단체·예약, 거리는 BE가 장소 카탈로그에서 읽어 붙인다. 응답 모양은 추천기 구현(D-11)과 상관없이 같다. 오류는 팀 컨벤션대로 ProblemDetail이고, 같은 409 안에서 구분할 것만 `type`(`urn:fitdining:meetup:...`)을 붙인다.
- Rejected: 하나의 응답에 결과 카드까지 → 투표 중 5초마다 20곳을 다시 보낸다. 화면마다 따로 API → 상태가 바뀔 때 화면들이 어긋난다.

## D-10 계산은 비동기로 하고 다시 받기로 끝을 안다
- Status: settled
- Decision: 추천받기는 계산 행(RUNNING)을 넣고 바로 202로 끝낸다. BE 안의 작업 스레드(취향 분석과 같은 방식의 `ThreadPoolExecutor`, 시작값 스레드 2·대기열 8)가 추천기를 부르고 결과를 저장한다. 대기열이 차면 계산 행을 바로 FAILED로 두고 202로 답한다. 계산은 시작할 때의 취향으로 하고 시작 시각과 포함한 프로필을 남긴다. RUNNING인데 시작한 지 45초가 지났으면 읽거나 새 계산을 시작할 때 FAILED로 바꾼다. 결과 저장은 그 행이 아직 RUNNING일 때만 하고, 늦게 끝난 결과는 버린다. 계산이 RUNNING인 동안 투표 열기와 정하기는 409 `calculating`이다. 끝난 계산이 투표나 정한 곳을 결과 상태로 덮지 않게 하기 위해서다. 45초는 저장한 해석을 읽지 못해 다시 해석하는 경우(계산, 해석, 계산으로 AI 호출 세 번, 한 번에 12초)에 여유를 더한 시작값이다. 실패하면 취향은 그대로 두고 다시 시도를 보이며 대체 순위는 만들지 않는다. 화면은 계산 중 1초(시작값)마다 스냅숏을 다시 받는다.
- Rejected: 요청을 붙잡고 기다리기 → 모임장이 새로 고치면 결과를 잃고, 다른 참여자에게 계산 중을 알릴 수 없다. 작업 큐 테이블 → 배포로 끊긴 계산은 읽을 때 실패로 바꾸면 되고 다시 시도는 모임장이 한다. SSE·WebSocket → BE와 FE에 실시간 전송이 없다(PRD D-31).

## D-11 추천기 포트와 두 구현
- Status: settled
- Decision: BE는 `MeetupRecommender` 인터페이스 하나로 AI를 가린다. 입력은 지역(역·동 또는 지점과 반경), 업종, 날짜·시간, 저장한 해석 조건, 참여자별 답(프로필 번호, 회원 id)이다. 출력은 장소별 모임 점수·추천 이유·덜 맞는 점·참여자 취향 점수와 놓친 메뉴, 적용한 조건, 후보 없음 원인(참여자 번호)이다. 구현은 둘이다. `StubMeetupRecommender`는 장소 Mock 모드에서 지역 안 장소 20곳에 정해진 규칙으로 점수를 붙인다. `AiMeetupRecommender`는 DB 모드에서 AI의 모임 전용 주소를 부른다. 어느 구현을 쓸지는 이미 있는 장소 Mock 모드(`PLACE_MOCK_ENABLED`)가 정하고, 추천기를 고르는 스위치를 새로 두지 않는다. DB 모드는 처음부터 AI 추천기를 쓴다. AI 모임 주소가 생기기 전(③ 전)에 DB 모드로 배포되면 계산은 실패로 보이고(D-16), 홈 시작 버튼을 붙이기 전이라 사용자에게는 보이지 않는다.
- Rejected: Mock 모드에서도 AI 호출 → 추천 검색과 같은 이유로 Mock 장소와 AI 장소의 id가 맞지 않는다(place-ai-search D-1). 포트 없이 서비스가 AI 클라이언트를 직접 → Mock 모드에서 화면과 상태 흐름을 만들 수 없다. 추천기를 고르는 설정 → 환경 변수 계약에 스위치가 하나 더 생긴다(D-24).

## D-12 추천 계산은 처음부터 AI의 모임 전용 주소로 한다
- Status: settled
- Decision: AI에 모임 전용 주소 두 개를 더한다. `POST /v1/meetup/interpret`는 모임 설명을 해석만 하고, `POST /v1/meetup/search`는 모임 계산을 한 번 한다. 거르기, 취향 합치기, 모임 점수, 참여자 취향 점수는 AI가 하고(D-13, D-15), 이 spec이 그 계약과 수용 기준을 정한다. 기존 `POST /v1/search`는 바꾸지 않는다. 계약은 회의에서 이 spec을 함께 보고 정한 뒤 AI 문서(`ai/docs/comparison/api.md`)에 옮긴다(2026-11-10). AI의 새 주소는 S15P31A302-196과 S15P31A302-200이 바꾼 지금 코드 위에 얹는다.
- Rejected: 기존 `/v1/search`를 다시 쓰는 단계를 먼저 두고 나중에 모임 전용 주소로 옮기기(2026-11-10 오전의 결정) → 두 방식을 바꿔 끼우는 스위치가 인프라에 하나 더 생긴다. 그 단계에서는 PRD와 다른 곳이 열 가지 생긴다(계산마다 해석이 돌고, 설명 속 지역을 만들 때 막아야 하고, 선호 음식은 가장 많이 고른 하나만 들어가고, 참여자 취향 점수의 맞음 기준이 AI와 BE 둘이 된다 등). BE에 취향 합치기·거르기·참여자 점수 판정이 생겼다가 옮길 때 버려진다. 기존 `/v1/search`에 속성을 더해 넓히기 → 일반 검색의 계약과 검증이 모임 규칙과 섞인다.

## D-13 AI와 BE의 경계
- Status: settled
- Decision: AI는 모임 설명 해석, 먹고 싶은 메뉴 해석, 거르기(지역, 업종, 날짜·시간, 못 먹는 음식, 메뉴 가격), 취향 합치기, 모임 점수, 참여자 취향 점수, 후보 없음 원인을 맡는다. AI 쪽은 지금 검색의 해석, 후보 뽑기, 거르기, 점수를 최대한 바꾸지 않고 다시 쓰고, 모임에 필요한 것만 더한다. BE는 모임 데이터 저장, 보일 질문 정하기, 순위 규칙(D-18), 카드 조립(D-9)을 맡고, 취향을 합치거나 후보를 거르지 않는다. AI에는 프로필 번호만 보내고 이름을 보내지 않는다. 회원 참여자는 `userId`를 함께 보내 AI가 평소 취향을 직접 읽는다. BE의 AI 호출은 `AiSearchClient`의 호출 뼈대(예산 12초, 동시 호출 한도, 차단기, 로그 규칙)를 함께 쓰고, 모임 계산과 일반 검색이 같은 한도를 나눈다.
- Rejected: BE가 취향을 합쳐서 보내기 → 회원의 평소 취향은 AI가 읽고, 참여자 한 명의 취향을 조립하는 일이 참여자 취향 점수에도 필요해 규칙이 둘로 나뉜다. BE가 참여자 취향 점수를 내기 → 모임 점수와 맞음의 기준이 달라져 카드의 추천 이유와 어긋난다. 모임 계산에 따로 호출 한도 → AI 컨테이너의 동시 처리 상한은 하나다(place-ai-search D-17).

## D-14 모임 설명 해석은 만들 때 한 번 하고 저장한다
- Status: settled
- Decision: 모임을 만들거나 설명을 고칠 때 설명이 있으면 해석 주소를 한 번 부르고, 받은 `conditions`(BE는 해석하지 않는다)와 요약(`summary`: 설명에 음식 종류·메뉴가 있는지)을 저장한다. 설명이 그대로면 다시 부르지 않는다. 계산은 저장한 `conditions`를 돌려보내므로 모임 설명으로 LLM을 다시 부르지 않는다. 모임 계산 주소 안에서 LLM을 부르는 것은 참여자의 먹고 싶은 메뉴 해석뿐이다(D-26). 저장한 조건이 없거나 읽지 못할 때 계산 전에 해석 주소를 다시 부르는 것은 예외다. 설명이 비면 부르지 않고 `conditions` 없이 계산한다. 해석 호출이 실패하면 모임은 만들고, 다음 계산을 시작할 때 한 번 다시 해석한다. AI는 이전 버전의 `conditions`도 읽는다(지금 검색의 `previousConditions`처럼). 읽지 못하면 400과 `code` `CONDITIONS_INVALID`를 주고, BE는 저장한 조건을 지운 뒤 같은 계산 안에서 한 번 다시 해석해 다시 부른다. AI를 다시 배포해도 살아 있는 모임의 계산이 계속 실패하지 않게 하기 위해서다. 설명에 지역이나 업종이 들어 있어도 막지 않는다. 계산 때 구조화된 값이 앞선다(D-15).
- Rejected: 계산마다 해석 → PRD FR-22와 어긋나고, 같은 설명에서 계산마다 조건이 달라질 수 있다. 해석이 실패하면 모임 만들기를 막기 → AI 장애가 모임 만들기까지 막는다. 설명 속 지역을 만들 때 막기 → 구조화된 지역이 앞서므로 필요 없다(PRD D-39).

## D-15 AI 모임 계산의 규칙
- Status: settled
- Decision: 계약의 의무는 다음과 같다. ① `area`(역·동 또는 지점과 반경 500m~5km)와 `category`(없으면 상관없음)가 `conditions` 속 지역·업종보다 앞선다(PRD D-39, D-40). 역·동은 이름으로 보내고 지금 검색의 지역 거르기를 그대로 쓴다. 다른 도시에 같은 이름의 동·구가 있으면 섞일 수 있다(감수). ② `when`의 날짜·시각에 영업하지 않는 곳, 브레이크타임인 곳, 1시간 안에 닫거나 브레이크타임이 시작하는 곳을 빼고, 날짜만 있으면 그 요일이 휴무인 곳을 뺀다. 전날 영업이 자정을 넘어 이어지는 시각은 영업 중으로 본다(PRD D-37, OQ-40). ③ 한 명이라도 못 먹는다고 한 음식 종류로 확인된 식당을 뺀다. 메뉴 가격 상한은 참여자들의 것 중 가장 낮은 값을 쓰고, 가게 가격이 그 110%를 넘는 곳을 뺀다(PRD D-12). ④ 모르는 값(영업시간, 음식 종류, 가게 가격)은 남긴다. ⑤ 취향은 PRD FR-22 규칙으로 합친다. 선호 음식은 모은 종류 중 가장 잘 맞는 하나로 세고(PRD D-24), 매운 음식은 빼지 않고 점수를 낮춘다(PRD D-14). 회원의 평소 취향은 중요 기준과 직접 입력 취향만 더한다. 질문에 하나도 답하지 않은 회원 참여자는 평소 취향만 합치고 참여자 취향 점수도 평소 취향으로 낸다. 질문지가 회원에게 평소 취향도 반영된다고 알리기 때문이다. 먹고 싶은 메뉴는 장소를 빼지 않고, 모은 메뉴 중 메뉴판에 있는 가장 잘 맞는 하나로 올린다(D-26). ⑥ 장소마다 참여자 취향 점수를 준다. 참여자 취향 점수는 근거가 없는 항목을 빼고 내며, 판정할 항목이 없으면 뺀다. 그 사람이 원한 메뉴가 메뉴판에 없으면 그 메뉴를 함께 준다. ⑦ 후보가 없으면 원인을 주고, 참여자 조건이면 프로필 번호를 붙인다. 자동으로 완화하지 않는다. ⑧ 요청 모양이 틀리면 400이고 취향을 조용히 빼지 않는다. ⑨ `conditions`가 없어도 계산한다. 이때는 모임 설명 해석(LLM)을 부르지 않고 업종 이름(식당·카페·술집, 상관없음이면 시작값 "맛집")을 후보를 뽑는 문장으로 써서 지금 검색처럼 후보를 뽑는다.
- Rejected: 지도 범위(사각형)로 지점 모임 거르기 → 모서리가 반경의 1.41배까지 들어온다. S15P31A302-196이 넣는 반경 거르기를 다시 쓴다. 틀린 취향을 빼고 계산(지금 `/v1/search`의 방식) → 취향이 빠진 결과가 조용히 저장된다. 자정 넘김을 그 요일 줄로만 보기(지금 AI의 방식) → 새벽 모임에서 전날부터 여는 곳이 빠지고, 카드의 영업 상태(BE 계산)와 어긋난다. 역은 코드, 동은 구와 동 이름 쌍으로 → 다른 도시의 같은 이름이 덜 섞이지만 AI의 지역 거르기를 고쳐야 한다. 설명이 빈 모임에서 지역 안 장소를 모두 점수 매기기 → 취향에 더 맞지만 벡터 없이 후보를 읽는 기능을 AI에 더해야 한다. 지금 검색을 최대한 그대로 쓰기로 했다. 모임장 취향만의 점수(`hostScore`)를 받아 H3 남기기 → 측정을 범위에서 뺐다(D-6).

## D-16 실패는 실패로 보인다
- Status: settled
- Decision: AI를 부를 수 없거나, 예산을 넘기거나, 응답을 읽을 수 없거나, AI가 400을 주면 계산은 FAILED다. 대체 순위를 만들지 않고, 남긴 취향은 그대로 두며, 모임장에게 다시 시도를 보인다. 저장한 해석 조건이 없는데 설명이 있거나 AI가 저장한 조건을 읽지 못하면 같은 계산 안에서 한 번 다시 해석하고, 그때도 실패하면 FAILED다.
- Rejected: 키워드나 카탈로그로 대체 결과(일반 검색의 방식, place-ai-search D-6) → 모임 점수와 참여자 취향 점수가 없어 덜 맞는 사람을 가릴 수 없고, 투표 후보의 근거가 없다.

## D-17 보일 질문
- Status: settled
- Decision: 보일 질문은 고른 업종으로 먼저 정한다. 카페면 음식 질문을 모두 숨기고, 술집이면 매운 음식만 묻는다. 식당과 상관없음이면 모임 설명에 음식 종류나 메뉴가 없을 때(해석 요약) 음식 종류와 먹고 싶은 메뉴도 묻는다. 메뉴 가격 질문은 가게 가격이 채워졌을 때만 보인다. 채워졌는지는 설정이 아니라 데이터로 본다. AI가 읽는 뷰(`ai_place_search`)에 `price`가 있는 장소가 하나라도 있으면 채워진 것이고, BE가 이 판단을 10분(시작값) 동안 기억한다. 지금은 뷰의 `price`가 모두 비어 있어 질문이 보이지 않는다(PRD D-33). 질문, 저장, AI 계약의 거르기는 지금 만들어 두고, 나중에 뷰를 고쳐 `price`를 채우면 코드 변경 없이 함께 살아난다. 해석 요약이 없으면(설명이 비었거나 해석이 실패함) 고른 업종에서 물을 수 있는 질문을 모두 보인다. 보이지 않는 질문의 답은 저장하지 않는다. 업종이나 설명을 고쳐 보일 질문이 바뀌면 이미 남긴 답은 지우지 않고 계산에 싣지만 않는다(PRD FR-16). 새로 보이는 질문은 건너뛴 것으로 보고, 다시 보이게 되면 남겨 둔 답을 다시 쓴다. 가게 가격이 채워져 가격 질문이 새로 보일 때도 같다. 가격 질문은 1만·2만·3만 원, 직접 입력, 상관없음 중에서 고른다. 직접 입력은 5,000~100,000원의 1,000원 단위(시작값)다. 지도의 반경처럼 자주 쓰는 값을 선택지로 보이고, 그 밖의 값은 직접 넣는다. 분위기 질문은 업종과 설명에 상관없이 늘 보인다. 그래서 해석 요약에는 분위기 여부를 두지 않는다.
- Rejected: 업종을 설명에서 해석 → 설명이 비면 업종이 섞이고, 음식 질문의 답과 결과가 어긋난다(PRD D-40). BE가 `conditions`를 읽어 음식 언급을 판단 → `conditions`의 모양에 BE가 묶인다. 요약은 AI가 준다. 가격 질문을 지금부터 보이기 → 고른 상한이 결과를 바꾸지 못하는데 조건 칩에는 적용된 것처럼 보인다(PRD AC-74). 가격 질문을 만들지 않고 미루기 → 가격이 채워질 때 테이블, API, AI 계약을 다시 고쳐야 한다.

## D-18 순위 규칙
- Status: settled
- Decision: 추천기가 돌려준 20곳에 BE가 순수 함수 하나로 처리한다. 장소마다 참여자 취향 점수가 50 미만인 사람이 있는지 보고, 없는 묶음을 앞에, 있는 묶음을 뒤에 둔다. 묶음 안에서는 모임 점수 순서이고 같으면 가장 낮은 참여자 취향 점수가 높은 곳이 앞이다. 모임 점수가 없으면(설명의 조건도 합친 취향도 없음) 묶음 안에서 추천기가 준 순서를 지키고, 카드에 핏 점수를 보이지 않는다. 카드의 잘 맞는 사람 표시는 넷 중 하나다. 모두, 반영된 수("3명에게"), 대체로(근거 없는 항목이 있음), 덜 맞는 사람의 프로필 번호. 덜 맞는 사람이 원한 메뉴를 그 장소가 팔지 않으면 덜 맞는 사람 줄에서 그 메뉴를 말한다(D-26). H3 값은 따로 남기지 않는다(D-6). 기준값 50은 코드 상수 한곳에 둔다(D-24). 순위, 묶음, 잘 맞는 사람 표시는 결과를 줄 때 저장한 점수로 정하고, 계산 뒤 지운 프로필은 빼고 판정한다.
- Rejected: 가장 낮은 점수로만 정렬 → 모두에게 평범한 곳이 위로 온다(PRD D-15). 순위 규칙을 AI에 두기 → 기준값과 카드 표시가 모임 화면의 규칙이라 BE 한곳에서 바꾸는 편이 낫다.

## D-19 투표와 정하기
- Status: settled
- Decision: 투표는 RESULT에서만 열고 후보는 결과 안의 2~3곳이며 익명이 기본이다. 한 프로필은 한 표이고, 표는 프로필 행의 칸이라 바꾸면 그 칸을 고친다. 한 표도 없으면 마감할 수 없다. 마감하면 가장 많은 곳이 하나일 때 DECIDED가 되고, 동점이면 투표를 닫은 채(VOTING, 투표 `state` CLOSED) 모임장의 선택을 기다린다. 동점일 때만 투표 계속하기로 다시 연다. 모임장은 RESULT에서 바로 정할 수 있고, DECIDED에서 다른 곳으로 바꾸거나 취소할 수 있다. 취소하면 투표가 있었으면 마감한 투표로, 없었으면 RESULT로 돌아간다. 투표를 한 번 열면 그 모임은 다시 추천받을 수 없다(PRD AC-54의 문구대로). 그래서 투표 칸(`poll_state`)은 한 번 열면 비우지 않는다(D-5). 동점으로 마감했는지는 마감할 때 고정한 값으로 본다. 모임 정보는 WAITING·RESULT에서 모두, VOTING·DECIDED에서는 날짜·시간만 고친다.
- Rejected: 마감한 투표에서 다시 추천받기 허용 → 결과가 바뀌면 후보가 결과에 없을 수 있고 PRD AC-54와 어긋난다. 늦게 온 사람의 취향은 투표 열기 전 경고(PRD D-38)로만 알린다. 동점을 자동으로 정하기 → PRD D-19는 모임장이 고른다.

## D-20 FE 구조와 도메인 경계
- Status: settled
- Decision: 경로는 `/m/new`(모임 만들기, 지도에서 고르기는 같은 페이지의 전체 화면 단계), `/m/[code]`(들어오는 곳. 대기, 정한 곳, 없는 링크), `/m/[code]/join`, `/profiles`, `/taste`, `/tastes`, `/result`, `/vote`, `/edit`다. 모임 코드는 `fe/src/domains/meetup`(`api`, `model`, `ui`)에 둔다. 도메인끼리 import하지 않는 규칙은 그대로 지키고, place·auth·review와 만나는 곳은 `app`에서 조합한다. 결과 카드는 본문(장소 상세 열기)과 아래 동작 영역(투표에 올리기, 여기로 정하기)을 나눈 새 카드이고, 핏 점수·순위 배지·영업 상태 같은 부품은 place 도메인 것을 `app`에서 가져다 조합한다. 옮기는 파일은 하나다. 네이버 지도 스크립트 로더와 타입을 `place-map.tsx`에서 `shared/lib`로 옮긴다. 인증은 따로 주입하지 않는다. 공용 클라이언트가 세션 쿠키로 보내고 쓰기 요청에 CSRF 헤더를 붙인다(S15P31A302-192). 참여자 화면의 작은 지도는 같은 지도 SDK로 그린다. 모임 지점 모임에서만 그리고, 못 불러오면 지점 이름과 반경만 보인다(PRD OQ-38). 회원과 모임장은 이름 옆 글자 대신 이니셜 아바타 오른쪽 아래의 배지(목록의 작은 아바타는 14px, 프로필 고르기의 큰 아바타는 22px)로 보인다. 모임장은 진한 주황 원에 흰 왕관, 다른 회원은 흰 원에 회색 테두리와 사람 아이콘이다. 모임장은 항상 회원이라 왕관만 붙이고 두 배지를 겹치지 않는다. 모양과 색이 함께 달라 색만으로 구분하지 않고, 배지에는 "모임장", "회원"이라는 이름이 있다. 프로필 고르기 화면 아래에 두 줄로 알린다. 첫 줄은 배지와 함께 "모임장 · 회원", 둘째 줄은 "회원 프로필은 로그인해야 들어갈 수 있어요"다. 왕관 아이콘은 아이콘 모음(`fe/src/shared/ui/icon/icons`)에 없어 새로 그린다. 정한 곳 화면 아래의 버튼은 결과 화면과 같은 "친구들 취향 보기"이고 같은 화면을 연다. 모임 정보 수정의 입구는 대기·결과 화면 모임 정보 오른쪽 위의 "수정" 하나이고, 참여자 화면의 내 취향 "수정"과 같은 모양이다. 모임장에게만(`EDIT_INFO`나 `EDIT_DATE`가 있을 때) 보이고, 투표 중·정함에서는 결과 화면 첫 줄의 같은 버튼이 날짜·시간만 고치는 화면을 열고, 투표 화면과 정한 곳 화면에는 두지 않는다. 모임장도 참여자라 자기 줄에 참여자와 같은 "수정"이 있다. 프로필 지우기는 모임장에게만 보이는 다른 사람 줄의 ⋯ 메뉴로 한다. 대기 화면에서는 친구 목록, 결과 뒤에는 친구들 취향 보기 목록의 줄이다. 결과 뒤에도 늦게 온 사람과 다른 브라우저로 연 사람이 참여할 수 있어야 하므로, 닫히기 전 모든 상태에서 "처음 왔어요"와 "내 이름 고르기"를 둔다.
- Rejected: 카드 부품을 `shared/ui`로 옮기기 → 검색 담당의 파일을 여럿 옮겨야 하고 조합만으로 된다. 모임 도메인이 place 도메인을 직접 import → ESLint 규칙이 막는다. 지도 로더를 `app`이 주입 → 스크립트 로더는 화면 조합이 아니라 공용 기능이다. 이름 옆 "회원", "모임장" 글자 → 이름 줄이 길어지고, 프로필 고르기의 네 칸 격자에서 줄마다 글자가 달라진다. 모임장 왕관과 회원 배지를 함께 붙이기 → 작은 배지 둘이 겹쳐 알아보기 어렵다. 정한 곳 화면의 "내 취향 보기" → 눌렀을 때의 화면이 정해져 있지 않았고, 정한 곳이 있으면 취향을 고쳐도 추천이 바뀌지 않아 수정 화면을 바로 여는 것은 맞지 않는다. 배지 설명 "회원은 로그인해야 고를 수 있어요" → 고르는 사람과 골라지는 프로필이 섞여 "회원이어야 고를 수 있다"로 읽힌다.

## D-21 FE 데이터와 다시 받기
- Status: settled
- Decision: 쿼리는 둘이다. 스냅숏(`["meetups", code]`)은 들어올 때와 화면으로 돌아올 때(TanStack Query 기본값) 다시 받고, 계산 중에는 1초, 투표 중에는 5초마다 받는다. 결과(`["meetups", code, "result", resultCalculationId]`)는 마지막으로 성공한 계산 id가 바뀔 때만 받는다. 쓰기는 리뷰와 같은 규칙이다(`networkMode: "always"`, 재시도 없음, 성공하면 스냅숏 무효). 409는 `problem.type`으로 구분해 짧게 알리고 스냅숏을 다시 받는다. 낙관적 갱신은 하지 않고, 투표만 누른 즉시 선택 표시를 바꾸고 실패하면 되돌린다. 질문지에서 로그인할 때는 쓰던 답을 sessionStorage에 두었다가 돌아와 채운다.
- Rejected: 모든 화면에서 짧은 주기로 다시 받기 → 투표 말고는 몇 초 늦어도 문제가 적다(PRD D-31).

## D-22 다른 도메인에 여는 자리
- Status: settled
- Decision: 홈(`search-screen.tsx`)은 왼쪽 위에 시작 버튼 자리를 열고 `app`이 버튼을 넣는다. 버튼의 위치와 모양은 화면 예시(모임장 1)대로다(PRD OQ-33). 장소 상세(`place-detail-screen.tsx`)는 점수와 추천 이유를 밖에서 받을 수 있게 하고, `/places/{id}?meetup={code}`로 열면 `app`이 모임 결과의 카드를 넘기며 개인 검색 점수는 쓰지 않는다. 방문 평가 작성은 주소로 방문일 기본값을 받고 방문일 범위 밖이면 무시한다. 로그인 복귀는 지금의 `login-return`(같은 탭, 10분)을 쓴다.
- Rejected: 로그인 복귀를 OAuth state로 바꾸기(PRD §7.4) → 인증 모듈을 고쳐야 한다. 메신저 안 브라우저 확인(PRD OQ-31) 뒤 따로 다룬다.

## D-23 수명 주기
- Status: settled
- Decision: 삭제 시각(`expires_at`)은 모임 날짜 + 8일의 0시(KST), 곧 모임 날짜 + 7일이 끝날 때이고(날짜가 없으면 만든 날 + 8일의 0시) 날짜를 고치면 다시 계산한다. 날짜는 대기·결과에서만 비울 수 있고, 비우면 비운 날 + 8일의 0시로 다시 계산한다. 이미 지난 시각으로 돌아가 그 자리에서 지워지지 않게 하기 위해서다. 스냅숏의 `info.expiresOn`은 열 수 있는 마지막 날이고, 대기 화면에 "○월 ○일까지 열 수 있어요"로 보인다(D-6). 모임 날짜는 오늘부터 30일(시작값)까지 고른다(PRD OQ-36). 그래서 비회원 정보는 38일을 넘겨 남지 않는다(열 수 있는 마지막 날은 만든 날부터 37일 뒤). 하루 한 번 예약 작업(KST 새벽, ShedLock)이 삭제 시각이 지난 모임을 지우고, 링크를 열 때도 기한을 확인해 지난 모임은 그 자리에서 지운다. 회원 탈퇴는 `UserService.withdraw`가 모임 쪽을 직접 부른다. 그 회원이 만든 모임을 모두 지우고, 그 회원의 프로필을 지운다(표와 쿠키 세션이 따라 지워진다). 모임 뒤는 시각으로 판정하고, 회원 참여자에게 방문 평가 주소를, 비회원에게 로그인 안내를 보인다.
- Rejected: 탈퇴를 FK로 따라 지우기 → 탈퇴가 회원 행을 지우지 않는다. 열 때만 기한 확인 → 아무도 열지 않는 모임의 데이터가 남는다(PRD §7.2).

## D-24 스위치를 두지 않고 홈 시작 버튼으로 공개한다
- Status: settled
- Decision: 기능을 켜고 끄는 스위치를 두지 않는다. 환경 변수 계약과 FE의 `/config.json`을 바꾸지 않는다. 공개는 홈의 시작 버튼을 붙이는 것으로 하고, 시작 버튼은 가장 마지막에 붙인다. 그 전에는 모임 화면과 API가 배포돼 있어도 주소(`/m/new`)를 아는 사람만 들어온다. 링크 미리보기와 첫 참여는 prod에 배포한 뒤 시작 버튼을 붙이기 전에 주소로 확인한다. 문제가 생기면 배포를 되돌린다. 메뉴 가격 질문도 스위치로 숨기지 않는다. 가게 가격이 채워졌는지를 데이터로 판단해 보인다(D-17). 추천기를 고르는 스위치도 없다(D-11). 기준값은 코드 상수 한곳에 모으고 환경 변수로 빼지 않는다(PRD OQ-29).
- Rejected: 기능 스위치(`fitdining.meetup.enabled`와 `/config.json`의 값) → 환경 변수 계약과 배포 설정에 값이 하나 더 생기고, 켠 상태와 끈 상태를 둘 다 시험해야 한다. 메뉴 가격 질문 스위치 → 가게 가격이 채워졌는지는 데이터로 알 수 있어 따로 켤 값이 필요 없다. dev 서버에서 확인 → 쿠키 게이트 때문에 메신저 미리보기 봇과 처음 온 참여자가 열 수 없다(PRD OQ-31). dev 게이트에서 `/m/` 경로만 열기 → 엣지 설정을 고쳐야 하고 dev 앱 일부가 밖에 열린다.

## D-25 PRD에 없어 정한 것
- Status: settled
- Decision: 모임장은 자기 프로필을 지울 수 없다. 모임을 만든 직후 모임장에게 프로필이 없으면 대기 화면 대신 질문지를 연다. 로그인한 회원에게 자기 프로필이 없고 그 브라우저에 비회원 프로필 쿠키가 있으면, 비회원 프로필로 들어가고 회원 프로필로 바꿀지 한 번 묻는다(PRD D-35). 로그인 세션이 끝난 모임장(운영에서 24시간)이 링크를 열면 보기만 하는 사람으로 보이므로, 프로필 목록에서 회원 프로필을 고르면 로그인 안내로 이어지고 로그인 뒤 그 모임으로 돌아온다. 모임 날짜·시각은 지금(KST)보다 앞일 수 없다.
- Rejected: 모임을 만들 때 모임장 프로필도 함께 받기 → 보일 질문이 모임 설명 해석에 달려 있어 모임을 먼저 만들어야 한다.

## D-26 참여자의 먹고 싶은 메뉴
- Status: settled
- Decision: 음식 종류 질문 아래에 건너뛸 수 있는 먹고 싶은 메뉴 칸(예: 곱창, 마라탕, 20자까지, 시작값)을 둔다. 음식 종류 질문과 함께 보이고 숨는다(D-17). 프로필에는 적은 글 그대로(`want_menu`) 두고, 계산할 때 AI 요청의 `members[].wantMenu`로 보낸다. AI는 계산 한 번에 참여자들의 글을 모두 모아 LLM을 한 번만 불러 메뉴로 해석한다. 적은 사람이 없으면 부르지 않고, LLM이 실패하거나 기다리는 시간을 넘기면 지금 검색의 규칙 해석(낱말표)으로 대신한다. 기다리는 시간은 계산 예산 안에 들어가게 짧게 둔다(시작값). 글에서는 메뉴만 쓰고 지역·시간·가격·분위기 같은 다른 조건은 버린다. 참여자가 적은 글이 모임의 다른 조건을 바꾸지 못하게 하기 위해서다. LLM에는 글만 보내고 누가 적었는지는 AI 서버 안에서만 안다. 메뉴는 장소를 빼지 않는다. 모임 점수는 모은 메뉴 중 메뉴판에 있는 가장 잘 맞는 하나로 올리고(선호 음식과 같은 규칙), 참여자 취향 점수에는 그 사람이 원한 메뉴를 항목으로 넣는다. 메뉴판을 모르는 곳은 그 항목을 뺀다. 덜 맞는 사람 규칙(D-18)은 그대로이고, 덜 맞는 사람이 원한 메뉴가 그 장소에 없으면 카드에 "도윤님이 원한 곱창은 아니에요"처럼 알린다. 결과 위 조건 칩에는 해석한 메뉴를 "곱창 원해요"처럼 보인다. 같은 글도 계산마다 해석이 조금 다를 수 있다(감수). 메뉴 이름만 꺼내므로 차이가 작다(PRD D-41). 여러 메뉴를 적었으면 그중 하나도 메뉴판에 없을 때 놓친 것으로 보고 적은 순서의 첫 메뉴를 말한다. 카드에는 덜 맞는 사람의 놓친 메뉴만 보인다.
- Rejected: 참여자가 남길 때마다 해석 → LLM 호출이 참여자 수와 수정 횟수만큼 늘고, 남기기가 해석을 기다리거나 해석 실패를 따로 다뤄야 한다. 해석 결과를 프로필에 저장 → 칸이 하나 더 늘고 글이 바뀔 때 지우는 규칙이 필요하다. 계산 때 한 번이면 충분하다. 낱말표로만 맞추기 → 외부로 나가는 글은 없지만 표에 없는 말("얼큰한 국물", 줄임말, 오타)을 못 맞춘다. 낱말표는 실패할 때 대신하는 데만 쓴다. 메뉴로 거르기(지금 검색의 방식) → 메뉴가 갈리면 후보가 크게 준다. 음식 종류를 고르면 세부 메뉴 칩 펼치기 → 메뉴 분류표를 새로 만들고 가게 데이터와 맞는지 확인해야 한다. 결과 뒤 메뉴로 투표 → 추천 정확도는 그대로라 문제를 풀지 못한다.
