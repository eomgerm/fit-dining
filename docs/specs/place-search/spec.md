# 장소 검색 (place-search)

Status: approved
Decisions: [decisions.md](decisions.md) · Glossary and ADRs: none

## Problem

사용자는 자연어로 장소를 찾고 싶다. 입력하는 동안 장소 후보를 보고, 요청을 보내면 추천 장소를 지도와 카드 목록으로 받고, "더 조용하게" 같은 후속 조건으로 결과를 좁히고, 이번에 한 요청들을 되돌아보고, 카드를 눌러 장소 상세와 추천 이유를 보고 싶다. 화면 기준은 Figma "5. 검색·추천 결과"(5-01, 5-03~5-07)와 "6. 장소 상세"(6-01, 6-02, 6-04, 6-05)다(D-49). 첫 화면(아래 검색창, 주변 추천 카드, 최근 검색, 지도 위 버튼)은 S15P31A302-42에서 와이어프레임 `Start`, `StartRecent`, `StartNoLoc`, `Typing`, `Results`를 따른다(D-80). 같은 작업에서 입력 중(`Typing`), 검색 중(`Loading`), 요청 기록(`RequestHistory`), 과거 결과(`PastResult`), 장소 상세(`Detail`, `DetailMenu`, `DetailInfo`)도 와이어프레임에 맞춘다(D-87~D-94). 장소 상세의 리뷰 탭과 "방문 평가 남기기"는 리뷰 담당이 상세 화면이 연 자리에 붙인다(D-86).

검색의 내부 로직(요청 해석, 임베딩, OpenSearch 질의, 점수 계산)은 AI 파트가 맡고 아직 데이터 구조와 전달 방식이 정해지지 않았다. 이 기능은 Spring BE와 Next.js FE를 연결하는 부분을 Mock 데이터로 끝까지 동작하게 만들고, 확정되면 구현과 DTO 레이어만 교체할 수 있게 한다(D-49, D-62, D-64). 이후 place-lookup-db가 DB 모드 엔진을, place-ai-search가 그 엔진에서 AI 검색 API를 부르는 연결(AI를 쓸 수 없으면 카탈로그 키워드 검색으로 대체)을 더했다.

S15P31A302-203 전에는 위치 권한을 허용한 사용자의 검색에 지역 정보가 하나도 가지 않았고, "이 지역에서 검색"이 보던 요청의 `previousConditions`를 다시 보내 AI가 원래 문장의 지역("강남역")을 다시 읽었으며, 결과가 와도 지도가 결과로 옮겨지지 않았다. 이번 반복은 새 검색과 "이 지역에서 검색"에 사용자에게 보이는 지도 영역을 담고 후속 조건에는 기준 요청의 영역을 이어 담으며, "이 지역에서 검색"을 `POST /api/v1/places/search/region`으로 보내며, 새 검색과 후속 검색의 결과에 지도를 맞춘다(D-109, D-110).

S15P31A302-204 전의 홈은 고정 문장 "근처 맛집"만 보내 전국 후보 100곳을 받고 FE가 기기 위치(없으면 역삼역) 기준 1km로 잘랐다. 장소 데이터가 여러 지역으로 늘면서 구로처럼 1km 안에 남는 곳이 없으면 홈이 비었고 빈 이유도 보이지 않았다. 이번 반복은 홈이 보이는 지도 영역으로 `POST /api/v1/places/nearby`를 불러 서버가 거른 카드를 그대로 보이고, 홈에서도 "이 지역에서 검색"으로 카드를 다시 받으며, 영역 안에 장소가 없으면 그 이유를 보인다(D-82, D-111).

## Assumptions

### BE 요청과 검증

1. 장소 `id`는 정수다. BE는 `long`, JSON은 숫자, FE는 `number`다. 값은 JavaScript의 안전한 정수 범위(2^53 - 1) 안이라고 가정한다(D-64).
2. `mapBounds`는 `{swLat, swLng, neLat, neLng}`이고 하위 필드는 `Double`이다. BE는 내용을 검증하지 않고, 빠지거나 `null`인 하위 필드도 그대로 엔진에 넘긴다(D-64). 이 규칙은 `/places/search`의 것이다. `/places/nearby`와 `/places/search/region`은 네 값이 모두 있어야 하고 검증한다(place-ai-search AC-29).
3. `q`와 `query`는 `@NotBlank`와 `@Size(max = 200)`(UTF-16 문자 수)로 검증하고, 어기면 400이다. `q`는 파라미터 어노테이션만으로 Spring MVC 내장 메서드 검증을 받고(컨트롤러 클래스에 `@Validated`를 붙이지 않는다), `query`는 `@Valid @RequestBody PlaceSearchRequest`로 검증한다. `q` 누락도 400이다. 상한 200은 이 spec이 정하는 임시 값이다(D-10, D-64, D-59).
4. 존재하지 않는 `id`는 404, 경로의 `id`가 정수가 아니면 400이다. `PlaceService`가 `findPlace`의 빈 값을 404 예외로 바꾸는 것은 AC-14의 "가공"이 아니다(D-10, D-62, D-64, D-56).
5. `spring-boot-starter-validation`은 사용자가 `be/build.gradle`에 추가한다. 구현은 의존성이 들어온 것을 확인하고 시작하며 그 밖의 `build.gradle` 변경은 하지 않는다. 형식 검증(400)은 요청이 컨트롤러에 들어오기 전에 일어나므로 엔진 유무 확인(503)보다 먼저다. AC-14는 엔진 반환값을 가공하지 않는다는 뜻이며 요청 검증을 막지 않는다(D-55, D-10, D-62).
6. `PlaceController`는 `PlaceService`에 위임만 한다(`@RequiredArgsConstructor`, try-catch 없음). `PlaceService`는 `PlaceSearchEngine` 빈을 직접 주입받는다(환경마다 Mock 또는 DB 모드의 엔진이 정확히 하나, `docs/specs/place-lookup-db/spec.md`). 장소가 없으면 404 예외(`PlaceNotFoundException`)를 던지고, 503 예외(`PlaceSearchUnavailableException`)는 엔진이 던진다(D-56, D-63, place-lookup-db#D-2).
7. 오류 응답은 `PlaceExceptionHandler`(`@RestControllerAdvice(basePackageClasses = PlaceController.class)`) 하나로 ProblemDetail을 만든다. `detail`은 일반 문구이고 예외 메시지와 요청 본문은 응답에 담지 않는다. 검색어와 요청 본문은 로그에도 남기지 않는다(DB 접근 오류의 예외 객체만 서버 로그에 남는다). 처리 대상은 검증 실패(`MethodArgumentNotValidException`, `HandlerMethodValidationException`), `HttpMessageNotReadableException`, `MethodArgumentTypeMismatchException`, `MissingServletRequestParameterException`, `InvalidCursorException`(400), 장소 없음(404), 검색을 쓸 수 없음(503: 엔진이 던진 `PlaceSearchUnavailableException`과 DB 접근 오류)이다(D-10, D-20, place-lookup-db#D-14).
8. 엔진이 잘못된 `cursor`를 알리는 방법은 `kr.co.fitdining.api.place.engine.InvalidCursorException`(`RuntimeException` 하위)을 던지는 것이다. 이 예외는 `PlaceSearchEngine` 계약의 일부이고 다른 예외는 400으로 바꾸지 않는다. 컨트롤러는 `cursor`를 해석하지 않는다(D-10, D-62).
9. 알 수 없는 속성 거부와 null 필드 생략은 `application.yml`의 전역 JSON 설정이다. 정확한 속성 이름은 Spring Boot 4.1.1(Jackson 3)에서 구현 때 확인한다. 거부는 `mapBounds` 같은 중첩 record에도 적용하지만 `previousConditions` 내부와 `preferences` 원소에는 적용하지 않는다(D-41, D-64).
10. 역직렬화되는 record(요청 DTO와 `places.json` 매핑)의 숫자와 boolean은 박싱 타입이다. 선택 필드의 명시적 `null`은 없는 것으로 본다. 타입은 Jackson 기본 변환을 따른다(`"query": 123`은 문자열로 받는다). 변환할 수 없는 값(문자열 자리의 객체, `previousConditions` 자리의 배열 등)만 400이다. `preferences`는 온보딩 답 모양의 `Preferences` 객체(`mood`, `priorities`, `purposes`, `tastes`, 가입과 같은 검증. place-ai-search#D-4), `previousConditions`는 `Map<String, Object>`(JSON 객체)다(D-41, D-64).
11. 응답에서 null인 선택 필드는 JSON에서 생략하고, `conditions: {}`와 빈 목록은 그대로 내보낸다. `conditions` 내부의 null 값은 생략하지 않는다(`@JsonInclude(content = ALWAYS)`)(D-41, D-61).
12. 프레임워크 로거는 기본 수준을 유지하고, JSON 파싱 오류 메시지가 입력을 로그에 남기는지는 AC-13 테스트로 확인한다. 테스트가 실패하면 해당 로거의 수준을 올리는 것은 허용한다(D-20).

### Mock 엔진

13. Mock 스위치는 환경변수 `PLACE_MOCK_ENABLED`(속성 `place.mock.enabled`, 코드 기본값 꺼짐)이고 local과 dev에서만 켠다. `be/.env.example`에 `PLACE_MOCK_ENABLED=true`로 넣는다. `docs/infra/contracts/env.md`와 `infra/` 아래 파일은 고치지 않고, 계약 등록은 인프라 담당에게 알린다(D-63).
14. Mock은 `classpath:mock/places.json`을 Spring의 JSON 매퍼로 읽는다. 파일은 `{"places": [{"card": PlaceCard, "detail": PlaceDetailResponse}]}` 형태로 DTO 필드와 정확히 맞추고(전역 알 수 없는 속성 거부를 받는다), `card.place`와 `detail.place`는 같은 값이다. 장소는 30~40곳이고 `id`는 파일에 1부터 차례로 적는다. 파일은 정제한 네이버 수집 데이터로 생성 스크립트가 만들고(규칙은 place-catalog spec의 "적재·mock 변형 규칙"), 사진은 원본 URL이며 없으면 FE가 자리표시 그라데이션을 그린다(D-63, D-64, D-60, place-catalog#D-19).
15. Mock은 요청 헤더 `X-Mock-Scenario`를 현재 요청(`RequestContextHolder`)에서 읽는다. `PlaceSearchEngine`의 메서드 인자에는 시나리오를 넣지 않는다. 헤더는 검색에만 적용되고 알 수 없는 값은 정상 결과다(D-63, D-62).
16. Mock의 `/places/search`는 질의, `mapBounds`, `preferences`를 무시하고 모든 장소를 `score` 내림차순(같으면 파일 순서)으로 돌려준다. `totalCount`는 장소 수다. 질의에 "근처"가 있어도 결과는 같고 `nearby`는 false다. 헤더 `empty`이면 `items: []`, `totalCount: 0`, `emptyReason`이 있다. Mock의 `/places/nearby`와 `/places/search/region`은 같은 순서에서 지도 영역 안 장소만 고르고, 규칙은 place-ai-search AC-33이다(D-63, place-ai-search#D-18).
17. Mock의 `conditions`는 `previousConditions`가 있으면(`null`이 아니면, 빈 객체 `{}`도 포함) 그대로, 없으면 `{}`다. `previousConditions`가 있으면 `changeSummary`는 "요청하신 조건을 반영했어요"이고 없으면 생략한다(D-63, D-50). 이 규칙은 `/places/search`의 것이다. Mock `/places/search/region`의 `conditions`는 받은 `conditions`이고 `changeSummary`는 없으며, `/places/nearby`는 `conditions: {}`다(place-ai-search AC-33).
18. Mock의 `cursor`는 십진수 오프셋 문자열의 base64url 인코딩(패딩 없음)이다. 빈 문자열은 없는 것(첫 페이지)으로 본다. 패딩이 있거나 base64url이 아니거나, 풀어낸 값이 `0` 또는 `[1-9][0-9]*` 형식의 `int`가 아니면 400이다. 오프셋이 장소 수 이상이면 빈 페이지이고 `nextCursor`와 `emptyReason`이 없다. `/places/search`에서 `cursor`가 있으면 항목을 고를 때 `query`, `mapBounds`, 헤더를 무시하고 오프셋만 따른다. `/places/search/region`의 `cursor`는 같은 형식이고, 그 요청의 `mapBounds`로 거른 목록에서 오프셋을 센다. REGION 응답의 `totalCount`, `conditions`, 빈 페이지 기준은 이 문단이 아니라 place-ai-search AC-33을 따른다. `/places/search`의 커서 응답은 `nearby: false`, `totalCount`는 장소 수, `emptyReason`과 `changeSummary`는 없고 `conditions`는 17번을 따른다. FE는 커서 응답의 `totalCount`, `conditions`, `changeSummary`를 쓰지 않는다(D-50, D-63).
19. Mock 자동완성은 "이름 접두 일치"(이름이 `q`와 같거나 `q`로 시작) 장소를 먼저, 그다음 "포함 일치"(이름이나 메뉴 이름에 `q`가 들어 있거나, `q`가 업종 한글 이름(식당, 카페, 술집)이나 코드의 부분 문자열인) 장소를 담는다. 각 단계 안은 파일 순서이고 장소 항목은 최대 5개다. 매칭은 `q`의 앞뒤 공백을 제거하고 대소문자를 구분하지 않는다. 역 이름은 매칭하지 않는다. 이름으로 일치하지 않고 메뉴 이름으로만 일치한 항목은 `matchedMenu`에 파일 순서상 첫 번째로 일치한 메뉴 이름을 담는다. 이름으로 일치한 항목에는 담지 않는다(D-63, D-64). 이 규칙은 Mock 엔진의 것이다. `place.mock.enabled`가 꺼졌거나 없을 때(DB 모드)의 자동완성은 이 규칙이 아니라 `docs/specs/place-lookup-db/spec.md`의 키워드 매칭 규칙(단어 단위 AND, 위치 매칭, 한글 조합)을 따른다.
20. 자동완성의 `ACTION` 항목(`label` "이 조건으로 추천받기")은 항상 포함된다. 이름 접두 일치가 있으면 맨 뒤, 없으면 맨 위다. `PLACE` 항목에는 `label`이 없다(D-63, D-64). DB 모드에서는 "이름 접두 일치"가 키워드 매칭의 순위 0(이름이 입력 전체로 시작)이다(`docs/specs/place-lookup-db/spec.md`).
21. Mock의 영업 상태(`openStatus`)는 요청 시각(`Asia/Seoul`)과 그 장소의 `hours`로 place-catalog spec의 "영업 상태 규칙"대로 계산한다. 구간은 모두 시작 포함, 끝 제외이고, 어제 영업의 자정 넘은 부분과 다음 날로 이어지는 영업(24시간)을 한 구간으로 본다. 영업 구간 밖이면 `CLOSED`이되 오늘이 정보 없음이거나, 오늘이 영업일이고 오늘 첫 구간 시작 전인데 어제가 정보 없음이면 `UNKNOWN`(오늘이 휴무일이면 어제와 상관없이 `CLOSED`), 브레이크(하루에 여럿일 수 있다) 안이면 `BREAK`, 구간 끝 60분 전부터 끝 전이면 `CLOSING_SOON`, 그 밖에는 `OPEN`이다. 브레이크 시작 전은 `CLOSING_SOON`으로 보지 않는다. `places.json`의 `openStatus`는 `UNKNOWN`으로 적어 두고 응답할 때 계산값으로 바꾼다(카드와 상세 모두). 시각은 주입한 `java.time.Clock`으로 읽어 테스트에서 고정할 수 있게 한다(없으면 `Asia/Seoul` 시스템 시계)(D-64).
22. Mock의 추천 이유, 주의점, 핏 점수 설명, 주소, `emptyReason`은 고정 한글 문자열이다. `labels`는 2개, 상세 `tags`는 2~4개, `scoreItems`는 2~4개이고 그중 하나 이상은 `matched: false`다. 요일은 `MON`~`SUN`, 시각은 `HH:mm`이다(D-63, D-64).

### FE 검색 흐름

23. FE는 항상 상대 경로 `/api/v1/...`를 부른다. `rewrites`는 `process.env.NODE_ENV === 'development'`일 때만 `/api/:path*`를 `${BE_INTERNAL_URL ?? 'http://localhost:8080'}/api/:path*`로 넘기고, 그 밖에는 빈 배열을 돌려준다. 운영에서는 Caddy가 같은 역할을 한다(D-69).
24. 결과가 없을 때는 화면 아래쪽에 떠 있는 검색창(자동완성 있음, `maxLength` 200, 후보는 검색창 위에 열림)이 보이고, 엔터, 추천받기 버튼, `ACTION` 선택은 새 검색이다. 결과가 있을 때는 이 검색창이 사라지고 결과 패널 아래 입력창("조건을 더 말해 보세요", 자동완성 없음)이 보이며 그 입력은 항상 후속 조건이다. 결과 목록은 그 입력창 위에 있다. 패널의 "새 검색"은 결과, 조건, 커서를 비우고 아래 검색창으로 돌아간다. 여기서 "결과가 있을 때"는 지금 보는 요청이 있을 때이며, 첫 페이지 응답이 0건(`emptyReason`)이어도 결과 패널에 원인과 수정 제안을 보여 주고 후속 입력창과 "새 검색"을 둔다(D-50, D-73, D-81).
25. 후속 조건은 새 입력을 `query`로, 기준 요청의 첫 페이지 응답 `conditions`를 `previousConditions`로 보낸다(빈 객체 `{}`여도 그대로 보낸다). `mapBounds`는 64번이다. 기준 요청은 항상 지금 보는 요청이다. 요청 기록의 "여기서 이어 검색"은 그 요청을 지금 보는 요청으로 바꾸고 후속 입력창에 초점을 둔다("결과 보기"는 지금 보는 요청을 바꾸지 않는다, 57번). 후속 요청이 성공하면 그 새 요청이 지금 보는 요청이 된다(D-50, D-89, D-90).
26. 커서 요청은 첫 요청 본문(`query`, `previousConditions` 또는 region의 `conditions`, `mapBounds`)을 그대로 첫 요청과 같은 API(66번)로 다시 보내고 `cursor`만 더한다. 토큰과 `preferences`는 페이지마다 보낼 때 place-ai-search AC-26대로 정한다. 빈 다음 페이지를 받으면 이어 붙이기만 멈추고 결과 없음 화면을 띄우지 않는다. 다음 페이지는 스크롤 위치로 불러온다(IntersectionObserver)(D-50).
27. 요청 기록(5-07)은 지금 thread에서 성공한 첫 페이지 요청(새 검색, 후속 조건, "이 지역에서 검색", "이 조건으로 다시 검색")을 시간순 항목으로 쌓는다. 커서 요청은 새 항목이 아니라 그 항목의 불러온 항목에 이어 붙이고, 실패한 요청은 쌓지 않는다. "이 지역에서 검색" 항목의 문장은 기준 요청의 문장 그대로이고(D-76), 기준 요청은 그때 보던 요청이다. 요청 기록은 지금 thread(53번)의 요청만 보이고, "새 검색"을 누르면 다음 새 검색이 새 thread를 연다. 이전 thread는 최근 검색에서 다시 연다. 요청 기록은 결과 패널 머리글의 "요청 기록"으로 결과 패널 안에 펼친다(29번). 검색창의 기록 아이콘은 요청 기록이 아니라 최근 검색(53번)이다(D-89, D-91). 각 항목은 입력 문장, "<업종> <totalCount>곳 · 오후 h:mm"(업종은 첫 페이지 항목에서 가장 많은 업종의 한글 이름이고 같으면 식당, 카페, 술집 순, 곳 수는 첫 페이지 응답의 `totalCount`, 0건이면 "결과 0곳"), 기준 요청이 직전 요청이 아니면 "<n>번째 요청에서 이어 검색"(기준이 1번째면 "첫 요청에서 이어 검색"), 지금 보는 항목에 "보는 중"을 표시한다. 지금 보는 항목이 아닌 줄에는 "결과 보기"와 "여기서 이어 검색"이 있다. "결과 보기"는 네트워크 요청 없이 그 시점의 결과(불러온 페이지 포함)를 과거 결과 화면(57번)으로 보여 준다. 다시 보는 결과의 카드 영업 상태는 검색한 시각의 값이며, 정확한 상태는 상세 화면에서 새로 받는다(D-50, D-74, D-79).
28. 후속 조건 결과에는 응답의 `changeSummary`를 배너로 보여 준다. 칩은 지금 보는 요청에서 기준 요청을 따라 새 검색까지 거슬러 올라가며 만난 후속 입력들을 오래된 순서로 "추가 조건 · <입력>"으로 보여 준다(새 검색 A → 후속 B → 후속 C를 보면 B, C). 갈라진 다른 후속은 넣지 않는다(5-06). 칩은 FE가 요청 기록에서 만든다. 결과 패널 제목은 같은 사슬을 거슬러 올라간 새 검색의 문장이고, 후속 입력은 제목이 아니라 칩으로만 보인다. 검색 중과 실패에도 보낸 요청의 기준 요청에서 같은 제목을 찾는다(D-50, D-64, D-97).
29. 결과 패널은 중간(5-04)과 전체(5-05), 요청 기록 펼침의 세 상태다. 중간과 전체는 손잡이를 누르거나 끌어 바꾼다. 전체 상태에 "지도 보기" 버튼은 없다(D-98). 머리글의 "요청 기록 ⌄"를 누르면 패널이 지도 위 버튼 아래까지 펼쳐지며 결과 목록 자리에 요청 기록 타임라인이 보이고("요청 기록 ⌃"), 다시 누르거나 "여기서 이어 검색"을 누르면 펼치기 전 상태로 돌아간다. 펼친 동안에도 후속 입력창과 "새 검색"은 그대로다. 검색 중(5-03, 와이어프레임 `Loading`)에는 입력 문장, 깜빡이는 점과 "요청을 이해하는 중", "주변 장소를 찾는 중", "취향과 맞춰 보는 중"을 1.5초마다 차례로 바꾸는 문구(실제 진행 단계가 아닌 안내, 동작 줄이기 설정이면 움직임 없음), 빈 카드 자리표시를 보여 주고, 후속 입력창은 흐리게 비활성이며 최근 검색 버튼을 숨긴다(D-49, D-88, D-89).
30. 카드는 순위 번호, 사진(없으면 자리표시), 이름, 업종 · 거리(위치가 있을 때) · 영업 상태 문구(영업 중, 곧 마감, 브레이크타임, 영업 종료; `UNKNOWN`이면 생략), 라벨 2개, 주의점, 핏 점수를 보여 준다. 카드에 `score`가 없으면(AI 엔진 전) 핏 점수 영역을 그리지 않는다(place-lookup-db#D-12). 순위 번호는 지금 보이는 목록에서의 순서(1부터, 다음 페이지에서도 이어짐)다(D-70, D-64).
31. FE의 빈 입력 판정은 앞뒤 공백을 제거한 뒤 한다. 공백뿐인 입력은 자동완성과 검색 모두 요청하지 않는다(D-70, D-10).
32. 자동완성은 앞뒤 공백을 뺀 입력을 300ms 늦춘 값을 쿼리 키로 쓴다. 입력이 바뀌면 300ms를 다시 기다리고, 늦춘 값이 바뀌어 새 요청을 보내면 이전 요청을 Query가 넘긴 `signal`로 취소한다. 입력이 비면 기다리지 않고 후보 목록을 비우며 진행 중인 요청도 취소한다. 지금 키가 아닌 요청의 응답은 화면에 쓰지 않는다. 후보 줄은 이름, 업종 · 거리(위치가 있을 때) · "메뉴: <matchedMenu>"(있을 때)이고, 이름과 메뉴에서 입력을 공백으로 나눈 단어마다 대소문자를 무시하고 같은 부분을 강조하며 겹치거나 이어진 구간은 합친다(`model/highlight.ts`, place-lookup-db#D-6). `PLACE` 후보를 고르면 `/places/<id>`로 이동한다. 후보 상자는 응답의 `ACTION` 항목을 응답 안 위치와 상관없이 맨 위(강조 배경, 원 안의 반짝이 아이콘, ›)에 두고 `PLACE` 항목(원 안의 핀 아이콘)은 응답 순서대로 그 아래에 둔다(`model/suggestions.ts`의 `actionFirst`). 후보가 보이는 동안(검색창에 초점이 있고 공백을 뺀 입력이 있을 때) 지도 위에 어두운 막을 깔아 주변 카드와 지도 버튼을 가리고, 막을 누르면 검색창 초점을 풀어 후보를 닫는다. 검색창은 초점이 있으면 테두리를 강조하고, 입력이 있으면 최근 검색 버튼 대신 "입력 지우기"(✕) 버튼을 두며 누르면 입력을 비우고 검색창에 초점을 둔다(D-70, D-64, D-67, D-87).
33. `place-api.ts`는 공통 `request`로 BE를 부른다. 주소의 `?mock=empty`를 읽지 않고 어떤 요청에도 `X-Mock-Scenario`를 붙이지 않는다(D-95). 오류(`ApiError`의 http, network, timeout)는 한 줄의 일반 오류 문구로 보여 주고, 재시도는 공통 `QueryClient` 기본값(5xx와 연결 실패만 두 번)을 따른다(D-63, D-68, D-66, D-67).
34. 화면 문구는 쉬운 한국어다. `fe/src/app/layout.tsx`의 `metadata`를 서비스 이름("Fit Dining")으로 바꾼다(`lang="ko"`와 Pretendard는 S15P31A302-35에서 들어왔다). 지도 위 "저장한 장소"와 "내 정보" 버튼은 56번, 상세의 "공유"와 "저장" 버튼은 58번, "방문 평가 남기기"는 45번(리뷰 자리)을 따른다(D-66, D-49, D-85, D-86, D-94).

### FE 지도와 위치

35. `fe/src/app/config.json/route.ts`의 `GET`은 요청 때마다 `process.env`에서 읽어 `{ env, naverMapClientId? }`만 돌려준다(`env`는 `APP_ENV`, 없으면 `dev`. `naverMapClientId`는 `NAVER_MAP_CLIENT_ID`, 비어 있으면 생략). 빌드 때 미리 렌더링되면 값이 굳으므로 요청 시점에 실행되게 하고(`cacheComponents`가 켜져 있어 방법은 `fe/node_modules/next/dist/docs/`에서 확인), 응답에 `Cache-Control: no-store`를 둔다. FE는 `fe/src/shared/lib/runtime-config.ts`에서 `/config.json`을 페이지 세션에 한 번만 받아 메모리에 두고, `PlaceMap`은 `naverMapClientId`가 없거나 요청이 실패하면 지도 영역을 비운다(D-57, D-70).
36. 지도 스크립트는 `PlaceMap`이 처음 마운트될 때 한 번만 `<script>`로 넣고, 이미 로드됐으면 다시 넣지 않는다. URL은 `https://oapi.map.naver.com/openapi/v3/maps.js?ncpKeyId=<encodeURIComponent(Client ID)>`이며 `submodules`는 붙이지 않는다. `window.navermap_authFailure`는 스크립트를 넣기 전에 정의한다(D-70).
37. 지도 컨테이너는 CSS로 높이를 지정하고, 크기가 바뀌면 `map.setSize`를 호출한다. 결과가 바뀌어도 지도를 새로 만들지 않고 핀만 바꾼다(지도 사용량은 지도 생성 횟수로 집계된다)(D-70).
38. 핀은 `naver.maps.Marker`의 HTML 아이콘(`icon.content`)으로 순위 번호를 그린다. 선택된 핀은 강조 아이콘으로 바꾸고(`setIcon`) 가장 위에 그린다(`setZIndex`). 핀을 누르면 그 카드를 선택하고 목록을 그 카드로 스크롤한다. 선택되지 않은 카드를 누르면 지도를 `panTo`로 그 핀에 옮기고(줌 유지) 선택한다. 선택된 카드를 다시 누르면 `/places/<id>`로 간다. 지도가 없을 때도 같은 두 단계로 동작한다. 한 번에 선택된 카드는 하나이고, 보는 결과가 바뀌면(새 요청, "결과 보기") 선택을 비우며 다음 페이지를 이어 붙일 때는 유지한다(D-70).
39. "이 지역에서 검색"은 버튼을 누를 때 보이는 영역(65번)을 읽어 66번의 region 요청을 `cursor` 없이 바로 보낸다. 지역 고정 상태는 없다(후속 조건의 영역은 64번). 버튼은 결과가 있을 때 사용자가 지도를 끌거나(`dragend`) 확대·축소한(`zoom_changed`) 뒤에만 보이고, 버튼을 누르거나 보는 결과가 바뀌거나 "새 검색"을 누르면 다시 숨는다. 카드 선택이나 "내 위치"의 이동과 확대·축소(`panTo`, `morph`), 결과 맞춤 이동(69번), 다른 화면에서 돌아올 때 지도를 되살리는 일로는 보이지 않는다. 홈의 버튼은 조건이 달라 74번을 따른다(D-70, D-52, D-77, D-102, D-104, D-109, D-110).
40. 위치 요청은 앱을 열 때와 사용자가 "내 위치" 버튼을 누를 때만 한다. 근처 응답을 받았다고 요청하지 않는다. 앱을 열 때의 위치 결정은 페이지 세션에 하나인 `initialLocation()`이 맡고 다시 들어온 화면은 같은 결과를 기다린다. `navigator.permissions.query`가 `granted`이면 묻지 않고 위치를 받으며, 결과는 `located(here)`, `denied`(`permissions.query`가 `denied`), `failed`(허용했는데 위치를 못 얻음, 시간 초과 10초 포함), `unavailable`(`prompt`이거나 API가 없거나 실패해 요청하지 않음)이다. 진행 중인 `getCurrentPosition` 조회는 하나만 두고 버튼은 같은 결과를 기다린다. 5분 재사용은 모든 `getCurrentPosition` 호출(버튼, 앱을 열 때)의 `maximumAge: 300000`이다. 얻은 위치는 `search-store.ts`에 두고 지도에 내 위치 점을 표시한다. 기기 위치를 얻어서 지도를 옮기는 것은 62번의 처음 이동과 "내 위치" 성공뿐이다(카드나 핀 선택의 이동은 따로 있다). "내 위치"를 누르면 아이콘이 내 위치 점과 같은 파란색(`--color-location`)이 되고, 지도가 그 위치로 이동을 마치면(이동 뒤 지도의 `idle` 이벤트. 알림이 오지 않아도 1.5초 안에 끝난다. 지도가 이미 그 위치와 확대 정도라 움직이지 않으면 바로. "이미 그 위치"는 중심 차이가 약 1m 이내이고 확대 정도가 같은 것으로, 지금 구현의 판정을 따른다), 위치를 얻지 못하면, 다른 화면으로 가거나 지도가 새로 만들어지면 원래 색으로 돌아온다. 파란색인 동안 다시 누르면 무시한다. 어떤 경우에도 파란색이 남아 있지 않는다. 앱을 열 때의 위치 요청에는 버튼 색이 바뀌지 않는다. 다만 그 조회가 진행 중일 때 버튼을 누르면 그 순간부터 파란색이고 같은 조회의 결과를 기다린다. "내 위치"를 눌러 얻은 위치로 옮길 때는 확대 정도를 첫 화면과 같은 15로 맞추고(더 축소돼 있으면 확대, 더 확대돼 있으면 축소), 이동과 함께 한 번에 부드럽게 움직인다(`morph(좌표, 15)`). 처음 이동과 카드나 핀 선택으로 옮길 때는 확대 정도를 바꾸지 않는다. "내 위치" 버튼 실패 알림은 거부를 포함해 늘 "위치를 확인할 수 없어요"다 (D-52, D-83, D-100, D-101, D-104, D-108).
41. 위치를 얻지 못하면(거부, 오류, 시간 초과) "위치를 확인할 수 없어요"를(앱을 열 때 거부는 63번의 권한 문구를) 알리고 거리를 숨긴다. 검색 요청의 지도 영역은 위치 결과와 상관없이 64번이다. 근처 응답(`nearby: true`)을 포함해 FE는 받은 항목을 거리로 거르지 않고 서버 순서 그대로 보이며, 위치가 없어도 "위치를 확인하는 중"이나 지역 기준 안내를 띄우지 않는다. "내 위치" 버튼에서 실패해도 같다(D-52, D-111).
42. 거리는 haversine(지구 반지름 6,371,000m)으로 계산한다. 먼저 10m 단위로 반올림하고, 그 값이 1000m 미만이면 "350m", 이상이면 km로 소수 한 자리까지 "1.0km", "1.2km"로 보여 준다(995m는 "1.0km") (D-52).

### FE 첫 화면 (S15P31A302-42)

53. thread와 최근 검색: 새 검색 하나가 thread 하나를 시작하고, 그 뒤의 후속 조건, "이 지역에서 검색", "이 조건으로 다시 검색"은 같은 thread에 요청으로 쌓인다(LLM 대화와 같이 요청은 따로 보이고 조건은 `previousConditions`로, "이 지역에서 검색"은 `conditions`로 이어진다. 66번). "새 검색"을 누르면 지금 thread가 닫힌다. thread는 첫 페이지 응답을 받을 때마다 저장한다. 비회원은 `localStorage`, 회원은 서버다(search-thread, V11). 요청마다 id, 종류, 기준 요청, 문장, 시각, 첫 페이지 요청 본문, 첫 페이지 응답(`nextCursor` 없이)을 두고, 개수 제한과 지우기 규칙은 없다. 저장에 실패하거나 저장된 값의 형식이 틀리면 그 thread는 저장되지 않거나 버려지고 화면과 검색은 그대로 동작한다. 첫 화면 검색창과 후속 입력창의 최근 검색 버튼은 "최근 검색" 시트(thread 목록)를 연다. 줄은 thread의 첫 문장과 마지막 요청 시각("오늘 오후 2:10", 다른 날은 "10월 14일", 요청 기록의 시각처럼 기기 시간대 기준)이고 마지막 요청 시각 최신순이며 지금 thread에는 "보는 중"을 붙인다. 줄을 누르면 시트를 닫고 그 thread로 바꾼다. 그 thread의 마지막 요청이 지금 보는 요청이 되어 검색을 다시 하지 않고 저장된 그때 결과로 보이고(다시 연 thread의 요청은 저장한 첫 페이지뿐이고 다음 페이지를 부르지 않는다), 이어서 후속 조건을 보낼 수 있다. 비어 있으면 "아직 검색한 요청이 없어요. 원하는 분위기나 목적을 말해 보세요."를 보인다. 재로드하면 첫 화면에서 시작한다. 저장소는 `ui/thread-storage.ts`로만 읽고 쓴다(지금은 `saveTurn`, `useThreadList` 등이고 회원은 서버 API, 비회원은 기기를 쓴다. search-thread). thread의 모양, 요청 더하기(`appendTurn`), 정렬, 형식 검사, 시각 문구는 `model/search-threads.ts`의 순수 함수다(D-91).
54. 주변 추천 카드: 지금 보는 요청이 없고 검색 중이 아닐 때 첫 화면은 `POST /api/v1/places/nearby` `{mapBounds}`(70번)를 보내 받은 응답의 카드를 서버 순서대로 가로 목록으로 보여 주고, 지도에는 같은 순위 번호(1부터)의 핀을 찍는다. FE는 거리로 거르거나 개수를 자르지 않는다(BE가 10곳까지 준다). 이 요청은 요청 기록과 최근 검색에 넣지 않고, 쿼리는 `placeQueries.nearby(영역)`(기록 항목과 다른 키, 71번)다. 받은 카드는 장소별 최근 카드에 둔다. 영역 안에 장소가 없으면 응답의 `emptyReason`을, 요청이 실패하면 실패 안내를 카드 자리에 보인다(75번) (D-82, D-111).
55. 주변 카드의 거리는 기기 위치가 있을 때만 "350m"처럼 쓰고, 위치가 없으면(시도 전, 실패) 거리를 숨긴다(42번). 카드는 위쪽 사진(없으면 자리표시), 순위, 이름, 업종 · 거리(위치가 있을 때) · 영업 상태, 핏 점수(`score`가 없으면 그리지 않는다), 라벨 2개이며 주의점은 없다. 화면 폭이 640px 미만이면 선택된 카드는 검색창과 같은 폭(화면 좌우 16px 여백)으로 가운데에 놓이고 양옆 카드가 카드 사이 8px 간격 너머로 조금 보인다. 640px 이상이면 카드 폭은 320px이고 선택된 카드는 목록의 왼쪽 첫 자리에 놓인다. 넘기면 그 카드를 선택하고 지도를 그 핀으로 `panTo`한다. 핀이나 선택되지 않은 카드를 누르면 그 카드로 넘긴다. 선택된 카드를 누르면 `/places/<id>`로 간다. 첫 화면의 "내 위치" 버튼은 카드 목록 바로 위 오른쪽(목록이 없으면 검색창 위 오른쪽)에 있다(D-82, D-83, D-103, D-111).
56. 첫 화면과 결과 화면(결과 패널 중간 상태)의 지도 오른쪽 위에 "저장한 장소"(북마크 아이콘)와 "내 정보"(사람 아이콘) `Fab`을 세로로 둔다. "저장한 장소"는 저장한 장소 화면을 열고(bookmark), "내 정보"는 `/my`로 간다(S15P31A302-104). "내 주변 추천" 라벨은 그리지 않는다(D-85, D-80).
57. 과거 결과(와이어프레임 `PastResult`): 요청 기록에서 지금 보는 요청이 아닌 줄의 "결과 보기"는 지금 보는 요청을 바꾸지 않고 과거 결과 화면을 연다. 결과는 다시 받지 않는다. 이번 페이지 세션에 받은 요청은 캐시에 받아 둔 페이지를 그대로 보이며 다음 페이지를 더 부르지 않고, 다시 연 thread의 요청은 저장한 첫 페이지를 보인다. 영업 상태는 그때 값이다(D-79). 근처 응답도 거르지 않고 그대로 보인다(41번). 화면은 지도 왼쪽 위 "현재 검색으로" 버튼, 결과 패널 위쪽 "<시각> 결과 · “<문장>”"(시각은 53번과 같은 문구), 순위가 붙은 카드 목록과 핀, 패널 아래 "이 조건으로 다시 검색" 버튼이다(버튼 아래 안내 문구는 없다, D-98). 패널 머리글(요청 기록, 새 검색), 후속 입력창, "이 지역에서 검색"은 없고, "내 위치"는 있고 지도 위 버튼(56번)은 없다(D-98). 카드와 핀은 38번대로 동작하며 선택은 과거 결과를 열거나 닫을 때 비운다. "현재 검색으로"는 요청 기록을 펼친 결과 패널로 돌아간다. "이 조건으로 다시 검색"은 그 요청의 첫 페이지 요청 본문(다시 연 기록은 67번의 실행 요청, region 기록이 실행 불가면 67번의 안내)을 그대로 같은 종류와 기준 요청으로 보내고, 성공하면 새 요청이 지금 thread 끝에 쌓여 지금 보는 요청이 되며 과거 결과 화면이 닫힌다. 원래 요청과 결과는 그대로 남는다. 과거 결과 화면은 `search-store`에 있어 상세에 갔다가 돌아와도 그대로다(D-90).
58. 장소 상세의 모양(와이어프레임 `Detail`, `DetailMenu`, `DetailInfo`): 상단 막대 없이 사진(없으면 자리표시)이 화면 폭 가득 크게 보이고 아래쪽이 바탕색으로 흐려지며, 사진 위 왼쪽에 "뒤로", 오른쪽에 "공유" `Fab`을 띄우고 사진이 둘 이상이면 넘김 점을 둔다. 업종 · 거리, 이름, 핏 점수, 영업 상태와 오늘 안내, 상세 `tags`(검색 카드의 "내 취향" 근거와 문구가 같으면 주황, 그 밖은 회색. D-96)는 흐려진 사진 위 바탕에 둔다. 핏 점수는 "<점수> 핏 점수 ⓘ" 전체가 ⓘ 시트를 여는 하나의 버튼이다(카드에 `score`가 없으면 이 버튼은 없다). 탭은 화면 위쪽에 붙는다. 홈 탭은 섹션(추천 이유와 주의, 장소 정보, 메뉴, 리뷰 자리) 사이를 두꺼운 띠로 나누고(탭 바로 아래 첫 섹션에는 띠가 없다), 추천 이유 인용은 주황 선과 진한 본문으로 그리며, 추천 이유 아래에 주의점을 주의 안내로 보인다. `matched: false`인 `scoreItems`의 근거 부족 안내는 보이지 않는다(D-105). 장소 정보의 영업시간 줄은 "<영업 상태> · 오늘 08:00 – 22:00"이고 펼치면 정보 탭과 같은 요일별 표다. 전화 줄은 ›, 웹사이트 줄은 도메인만 보이고 바깥 링크 아이콘이 붙고, "정보 더보기 ›"는 가운데 둥근 테두리 버튼이다. 메뉴 머리글은 "메뉴 <개수> ›" 링크로 메뉴 탭을 열고, 미리보기는 대표 메뉴를 먼저, 나머지를 원래 순서로 6개까지 보인다. 메뉴 탭은 카테고리 이름을 작은 흐린 글씨로, 줄마다 64px 사진, 굵은 이름과 옆의 작은 라벨·"대표" 칩, 이름 아래 흐린 설명(두 줄까지, 넘치면 말줄임), 오른쪽 가격 원문을 두고 줄 사이를 선으로 나눈다. 정보 탭 영업시간은 위에 "<영업 상태> · <오늘 안내>"(45번)를 두고, 요일별 표에서 오늘 줄은 "<요일> · 오늘"로 굵게, 브레이크타임은 하나마다 "15:00 – 16:00 브레이크타임", 라스트오더는 "14:30, 21:30 라스트오더" 줄로, 휴무일은 "정기휴무 (매주 <요일>요일)", 정보 없는 요일은 "정보 없음", `00:00`–`00:00`은 "24시간 영업"으로 쓴다. 시각 범위는 "08:00 – 22:00"으로 쓰고, 마감 `00:00`은 "24:00", 자정을 넘는 영업은 "17:00 – 02:00"이다. 주소 줄에는 "주소 복사" 버튼(클립보드에 넣고 "주소를 복사했어요", 실패하면 "주소를 복사하지 못했어요")을 두고, 시설은 아이콘이 붙은 테두리 칩(이름 그대로, 비슷한 시설을 묶은 아이콘, 묶음에 없는 이름은 기본 아이콘)이고, 그 아래 "제목 · 내용" 줄, 맨 아래에 "정보가 실제와 다를 수 있어요"를 둔다. 하단 막대는 "저장"(북마크 테두리 버튼)과 리뷰 자리의 `bottomAction`을 나란히 둔다. "공유"는 누르면 "준비 중이에요" 토스트를 띄운다. "저장"은 북마크 버튼이다(bookmark). 리뷰 자리 안의 모양은 바꾸지 않는다(D-92, D-94, D-96).
59. 정보 탭 위치 지도: 주소 줄 아래에 높이를 CSS로 정한 작은 `PlaceMap`을 두고 그 장소 핀 하나만 찍으며 중심은 그 장소다. 정보 탭을 열었을 때만 만들고(지도 사용량은 지도 생성 횟수), 지도 키가 없거나 인증이 실패하면 지도 자리를 그리지 않는다. 내 위치 점과 "이 지역에서 검색"은 없다(D-93).
60. 앱 안에서 상세, 내 정보 같은 다른 화면에 갔다가 돌아오면 검색 화면은 떠나기 전 그대로다. 첫 화면 주변 카드 목록은 미끄러지지 않고 떠나기 전 선택된 카드 자리에 바로 놓이고, 검색 화면의 지도는 첫 화면, 결과, 과거 결과, 저장한 장소 화면 모두 떠나기 전 중심과 확대 정도로 보인다(상세 정보 탭의 위치 지도는 59번대로 그 장소가 중심). 선택된 장소는 바뀌지 않아 순위 배지, 핀, 카드 목록이 같은 장소를 가리키며, 지도를 되살리는 일로 "이 지역에서 검색" 버튼이 새로 나타나지 않고 떠나기 전 보이던 버튼은 그대로 보인다. 새로고침과 PWA 재로드는 D-27대로 이 항목에 들지 않는다. Next(`cacheComponents`)가 숨겨 둔 화면을 다시 보일 때 카드 목록과 지도를 새로 만들어도 이 상태를 지킨다(D-102).
61. 지도 화면 저장: 기기 `localStorage`의 `fd.map.view.v1`에 `{lat, lng, zoom}`을 쓴다. 지도가 멈출 때(`idle`)마다 한 번 쓰고, 지도를 만든 뒤 처음 도착하는 `idle`은 무엇이 일으켰든 쓰지 않으며(그 사이 코드 이동이 있어 `idle`이 합쳐져도 같다), 그 뒤의 `idle`은 코드가 옮긴 것이어도 쓴다. 권한과 로그인 세션에 상관없이 쓰고 로그인·로그아웃으로 지우지 않는다. 읽기와 쓰기는 try/catch로 감싼다. 읽은 값은 JSON 객체이고(배열, `null`, 문자열은 무시. 세 값 밖의 키는 있어도 무시하고 통과) 세 값이 유한한 숫자이며 `lat` -90~90, `lng` -180~180, `zoom` 6~21(네이버 지도 기본 줌 범위로 알고 있다. 구현 때 SDK로 확인하고 다르면 이 값을 spec 변경으로 바로잡는다)일 때만 쓰고, 하나라도 벗어나면 값 전체를 무시한다. 지도 화면을 위한 키는 이 하나뿐이고 기기 위치를 담은 키는 없다(비회원 thread 등 다른 기능의 저장은 그대로다). 화면이 숨겨졌다 다시 보일 때(60번)는 만들어 둔 지도를 그대로 쓰므로 `localStorage`를 읽는 때는 지도를 새로 만들 때뿐이다. "내 위치"로 옮긴 뒤의 저장값이 기기 위치 근처가 되는 것은 감수한다(기기 밖으로 나가지 않는다) (D-108).
62. 시작 화면과 처음 이동: 지도의 시작 화면은 저장된 화면이고 없으면 `DEFAULT_VIEW`(위도 37.5013, 경도 127.0396, zoom 15, SSAFY 서울캠퍼스)다. 기기 위치를 얻어서 코드가 지도를 옮기는 곳은 앱을 연 뒤 처음 위치를 얻었을 때(확대 정도 유지)와 "내 위치" 버튼 성공(`resetZoom`, D-104)뿐이며 `here`가 바뀐 것만으로는 옮기지 않는다. 카드나 핀 선택의 `panTo`(38번, 55번)는 따로 있다. 지도가 준비되기 전에 얻은 위치는 준비된 뒤 옮긴다. `initialLocation` 결과를 store `location`에 옮기는 규칙은 `located`→`ok`, `denied`·`failed`→`failed`, `unavailable`→`idle`이다. `searchStore`의 `initialView`(`pending`, `applying`, `done`)는 `pending`일 때 지금 보이는 화면이 처음 이동을 한 번 가져가 이동을 시작하는 순간 `applying`이 되고(지도가 준비되고 위치가 있을 때), `applying`일 때 다른 화면은 같은 이동이 끝나기를 기다린다. 위치를 못 얻었거나(`denied`, `failed`, `unavailable` 모두), 이동이 끝났거나(`panTo`가 끝났을 때. 이미 그 위치면 바로, 알림이 안 와도 1.5초 안에), 지도가 새로 만들어지거나 없어졌거나(키가 없거나 인증이 실패해 만들어지지 않는 경우 포함. Next가 화면을 숨기는 것은 지도가 없어진 것이 아니다), "내 위치" 버튼의 이동이 끝났거나 위치를 얻지 못했거나(버튼을 누르면 `pending`이나 `applying`인 처음 이동을 버튼이 가져가고, 누르는 순간 `done`이 되지 않으며, 버튼이 가진 동안 `done`이 되는 조건은 70번이다), 결과 맞춤 이동(69번)을 시작했거나(이때도 처음 조회는 위치를 받아 `here`에 두고 지도만 옮기지 않는다), 사용자가 지도를 끌거나 확대·축소했거나(코드가 만든 이동과 확대·축소는 제외하며, 39번의 "이 지역에서 검색" 버튼과 같은 구분을 쓴다), 지도가 실패했으면 `done`이고, `done`이면 effect가 다시 돌아도 처음 이동은 없다. 로그인 세션이 바뀌어도 되돌리지 않는다. 페이지 세션 안에서만 그렇고, 새로고침하면 `pending`으로 시작한다(D-27). 처음 조회와 버튼은 진행 중인 `getCurrentPosition` 하나를 함께 쓰므로 둘의 결과는 같고, 처음 조회의 결과를 받는 쪽이 `done` 뒤에 그 결과를 소비하는 경우가 생긴다. 이때 결과가 성공이면 `here`를 기록하고 `location`을 `ok`로 하며(내 위치 점) 지도는 옮기지 않으며, "내 위치" 버튼이 먼저 `here`를 정했으면 덮지 않는다. 결과가 실패이고 버튼이 먼저 성공했으면 `location`을 `failed`로 덮지 않는다. 처음 조회는 "내 위치" 버튼이 대신했거나 사용자가 지도를 움직여 `done`이 된 뒤에는 새로 `getCurrentPosition`을 부르지 않는다(진행 중인 조회가 있으면 그 결과를 기다린다). 지도가 실패하거나 없어져 `done`이 됐으면 권한이 허용일 때 위치는 받고 지도만 옮기지 않는다. 그래서 권한 확인(`permissions.query`)이 끝나기 전에 버튼을 누르면 호출은 버튼의 1회뿐이다. "내 위치" 버튼이 처음 조회를 대신한 뒤에는 처음 조회의 알림은 띄우지 않고 버튼 알림만 띄운다(63번). 코드가 시작한 이동과 확대·축소는 그 이동이 끝나는 `idle`까지 사용자 이동으로 세지 않는다. 처음 이동은 코드가 옮기는 이동이라 결과 화면의 "이 지역에서 검색" 버튼을 띄우지 않는다(39번). `initialView`가 `done`인지는 store에서 읽을 수 있고, 처음 홈 요청은 이것이 `done`이 되기를 기다린다(70번) (D-108, D-111).
63. 위치 알림: 처음 조회가 `denied`이면 "위치 권한이 꺼져 있어요. 브라우저 설정에서 허용해 주세요"를, `failed`이면 "위치를 확인할 수 없어요"를 지금 보이는 화면이 페이지 세션에 한 번만 띄운다. 조회를 시작한 화면이 숨겨져도 사라지지 않고, 결과가 올 때 보이는 화면이 없으면 다음에 보이는 화면이 띄운다. "내 위치" 버튼 실패 알림은 누를 때마다 띄운다 (D-83, D-108).

### FE 검색 지역과 결과 맞춤 이동 (S15P31A302-203)

64. 검색 요청의 `mapBounds`: 새 검색은 보내는 순간의 보이는 영역(65번)을 담고, 지도가 없으면 담지 않는다. 후속 조건은 지금 지도가 아니라 기준 항목의 실행 요청(이번 페이지 세션의 항목은 보낸 본문, 다시 연 thread의 항목은 67번으로 만든 실행 요청)의 `mapBounds`를 그대로 담는다(기준이 "이 지역에서 검색" 항목이면 그 영역, 기준에 없거나 기준이 67번의 실행 불가 region 기록이면 담지 않는다). 실패한 요청의 재시도는 처음 보낸 본문 그대로다(영역을 다시 재지 않는다). "이 지역에서 검색"은 버튼을 누를 때의 보이는 영역이다(버튼은 지도가 있을 때만 보인다). new·followUp 기록의 "이 조건으로 다시 검색"은 저장된 본문 그대로라 그때의 영역(없으면 없음)이다. 이 규칙은 위치 결과(`ok`, `failed`, `idle`)와 상관없고 지역 고정 상태는 없다. 홈 주변 카드 요청은 70번이다 (D-109, D-111).
65. 보이는 영역: 지도 컨테이너에서 화면 폭 전체의 가로 띠이고, 위 끝은 지도 위쪽에서 `safe-area-inset-top`만큼 내려온 곳, 아래 끝은 지도 아래쪽을 덮는 UI가 지도와 실제로 겹친 높이만큼 올라온 곳이다. 덮는 UI는 결과 화면에서는 결과 패널(패널이 지금 전체 상태나 요청 기록 펼침이어도 중간 상태일 때의 위 끝), 첫 화면에서는 화면 아래에 쌓은 묶음 전체("내 위치" 버튼, 대체 안내, 주변 카드 오류 안내, 빈 안내 상자, 지도 실패 안내, 주변 카드나 skeleton, 검색창 가운데 그때 있는 것. 그 위 끝)이고, 겹친 높이는 지도 아래 끝에서 그 UI 위 끝까지(겹치지 않으면 0)다. 화면 키보드, 키보드 때문에 위로 올라간 만큼, 자동완성 후보와 어두운 막, 위쪽 `Fab`과 "이 지역에서 검색" 버튼은 빼지 않는다(입력 전 화면 기준). 띠의 왼쪽 아래와 오른쪽 위 화면 좌표를 네이버 지도 SDK의 화면 좌표→위경도 변환으로 바꿔 `{swLat, swLng, neLat, neLng}`을 만든다. 띠의 높이가 0 이하이거나 지도 높이의 1/4 미만이거나 변환이 예외를 던지면 `getBounds()` 전체를 쓰고, 지도가 없으면 영역이 없다. 이 계산은 `PlaceMap`이 지도 핸들의 메서드로 내놓는다. 검색 화면은 덮는 UI의 위 끝(화면 좌표)을 재서 넘기고, `PlaceMap`이 자기 사각형으로 겹친 높이(지도 아래 끝에서 그 위 끝까지, 겹치지 않으면 0)를 계산한다(지도 사각형은 `PlaceMap`만 안다). 69번의 아래 여백도 같은 방법으로 잰 겹친 높이다 (D-109, D-110).
66. API와 region 요청: 요청 기록의 종류(`new`, `followUp`, `region`)로 API를 고른다. new·followUp은 `POST /api/v1/places/search`, region은 `POST /api/v1/places/search/region`이고, 첫 페이지, 다음 페이지(26번), 실패 재시도, "이 조건으로 다시 검색" 모두 그 종류의 API로 간다. 쿼리 키는 지금처럼 `["places", "search", <항목 id>]`다. region 요청 본문은 `{query, conditions, mapBounds}`(다음 페이지는 `cursor` 추가, FE는 `conditions`를 늘 보낸다)이고, `query`는 보던 항목의 요청 기록 문장(그 항목의 `query`, 27번. 결과 패널 제목이 아니다), `conditions`는 보던 항목의 첫 페이지 응답 `conditions`(빈 객체 `{}`여도 보낸다)이며 `previousConditions`는 없다. 토큰과 비회원 답, 15초 시간 초과, `X-Fallback` 읽기는 `/places/search`와 같다(place-ai-search AC-25~AC-27). 요청 기록 항목의 문장과 thread 저장은 지금과 같고(D-76), 이 항목을 기준으로 한 후속 조건은 이 항목의 응답 `conditions`를 `previousConditions`로, 이 항목의 `mapBounds`를 영역으로 보낸다 (D-109).
67. 저장된 기록의 실행: thread turn의 `request`는 저장 형식으로 읽기만 하고 다시 쓰지 않는다(새 turn을 붙이며 저장할 때도 이미 있던 turn은 읽은 값 그대로 둔다. 값이 같으면 되고 JSON 문자열이 바이트까지 같을 필요는 없다). region turn은 새 모양 `{query, conditions?, mapBounds}`이거나 옛 모양 `{query, previousConditions?, mapBounds?}`다(형식 검사는 지금처럼 `request.query`만 본다). 실행 요청은 함수 하나로 만들고 thread 열기, 열린 thread를 요청 기록으로 바꾸는 일, "이 조건으로 다시 검색"이 같이 쓴다. new·followUp은 저장된 본문 그대로이되 아는 필드만 옮긴다(`query`, JSON 객체일 때의 `previousConditions`, 객체이고 네 값이 모두 유한한 숫자일 때의 `mapBounds` 네 값. 그 밖의 키와 이 조건에 맞지 않는 값은 버린다). region은 `{query, conditions: request.conditions ?? 그 turn 응답의 conditions, mapBounds}`이고(`request.conditions`가 null이거나 JSON 객체가 아니면 없는 것으로 본다), `mapBounds`는 네 값(`swLat`, `swLng`, `neLat`, `neLng`)만 옮기며 `previousConditions`는 버린다. `mapBounds`가 없거나, 네 값 중 하나라도 없거나 유한한 숫자가 아니거나, 위도가 -90~90·경도가 -180~180 밖이거나, `swLat >= neLat`이거나 `swLng >= neLng`이면(place-ai-search AC-29와 같은 규칙) 실행 불가다. 실행 불가인 region 기록도 결과 보기, 요청 기록, 그 항목에서 "이 지역에서 검색"과 후속 조건(영역 없이)은 그대로 되고, 과거 결과 화면의 "이 조건으로 다시 검색"을 누르면 HTTP 없이 "다시 검색할 수 없어요" toast를 띄우며 과거 결과 화면은 닫지 않는다 (D-109).
68. AI 대체 안내 문구(place-ai-search AC-27의 표시 조건은 그대로라, 이번 페이지 세션에 받은 응답에만 안내가 있고 다시 연 thread의 기록에는 없다. 그 AC의 문구 목록은 이 번호가 region 문구로 넓힌다): 결과 패널과 과거 결과 화면에서 region 항목의 결과는 "지도 안의 장소만 보여드려요. 검색 조건은 적용되지 않았어요", new·followUp 항목의 결과는 지금 문구 "지금은 AI 추천을 쓸 수 없어 가게 이름·메뉴로 찾았어요"다. 홈 주변 카드의 안내(`/places/nearby`가 AI 대신 지도 영역 안 장소를 준 응답)도 region과 같은 "지도 안의 장소만 보여드려요. 검색 조건은 적용되지 않았어요"다 (D-109, D-111).
69. 결과 맞춤 이동: new·followUp 요청(실패 재시도와 "이 조건으로 다시 검색" 포함)의 첫 페이지를 받아 요청 기록에 넣은 뒤(검색을 버렸거나 로그인 세션이 바뀌어 버린 응답은 제외), 그 결과 화면에 그리는 핀으로 지도를 한 번 옮긴다. 핀이 2곳 이상이면 핀 위도·경도의 최솟값과 최댓값 사각형으로 `fitBounds`를 부른다. 여백은 아래가 결과 패널의 겹친 높이(65번)에 40px을 더한 값, 위가 `safe-area-inset-top`에 40px을 더한 값, 왼쪽과 오른쪽이 40px이다(40px은 선택된 핀 크기). 확대 정도 상한 17은 `fitBounds` 옵션 `maxZoom`으로 건다(1곳 `panTo`에는 쓰지 않는다. 네이버 지도 v3 `FitBoundsOptions`). 1곳이면 그 핀으로 `panTo`(확대 정도 유지), 0곳이면 옮기지 않는다. 맞춤 이동을 시작하면 남은 처음 이동(62번)은 하지 않는다(`initialView`를 `done`으로 한다. 처음 이동이 진행 중이었어도 맞춤 이동이 이어서 지도를 옮긴다). 맞춤 이동을 하지 않은 경우(0곳, region, thread 열기 등)는 처음 이동 상태를 바꾸지 않아, 처음 이동이 남아 있으면 62번대로 위치가 오면 한 번 옮긴다. region, 다음 페이지, 상세에서 돌아오기, thread 열기, "결과 보기"와 "여기서 이어 검색", 첫 화면은 옮기지 않는다. 이 이동은 코드 이동이라 그 이동이 끝나는 `idle`까지 사용자 이동으로 세지 않고 "이 지역에서 검색" 버튼(39번)을 띄우지 않는다. 지도가 실제로 움직이지 않으면(이미 그 중심과 확대 정도) 코드 이동 표시를 남기지 않아 다음 사용자 확대·축소를 놓치지 않는다. 지도가 없으면 아무것도 하지 않는다 (D-110, D-111).

### FE 홈 주변 카드 (S15P31A302-204)

70. 홈 요청과 처음 요청: 홈 주변 카드는 `POST /api/v1/places/nearby` `{mapBounds}`로 받는다(`preferences`는 보낼 때만이고 토큰, 비회원 답, 15초 시간 초과, `X-Fallback` 읽기는 `/places/search`와 같다). 본문에 `query`와 기기 좌표가 없고 요청 기록에 쌓지 않는다. 처음 홈 요청은 `initialView`가 `done`이 되고 지도가 준비된 뒤 한 번 보낸다(지도가 실패하면 요청하지 않고 75번의 안내를 보인다). 보내는 영역은 늘 그때 지도 화면에서 72번으로 읽은 영역이다. 위치를 못 얻었거나(`denied`, `failed`, `unavailable`) 권한이 없으면 지도는 저장된 화면(없으면 `DEFAULT_VIEW`)이나 그 뒤 사용자가 옮긴 화면이고, 처음 이동이 끝났으면 그 화면이다. 그때까지 카드 자리는 skeleton이다. 별도 대기 상한은 없고 위치 조회 timeout 10초(40번)를 따르며, "내 위치"가 띄운 브라우저 권한 창에 사용자가 답하는 동안과 `permissions.query`가 끝나지 않는 동안은 이 timeout이 흐르지 않아 그만큼 기다린다(따로 상한을 두지 않는다). "내 위치" 버튼은 처음 이동이 `pending`이거나 `applying`(처음 `panTo` 중)일 때 누르면 그것을 가져간다. 버튼이 가진 동안 `initialView`를 `done`으로 만드는 것은 버튼 이동이 끝나거나 위치를 못 얻은 것, 사용자가 지도를 끌거나 확대·축소한 것, 결과 맞춤 이동(69번)의 시작, 지도 실패뿐이고, 처음 조회의 결과(`unavailable`, `denied`, `failed`, `located`)와 처음 `panTo`의 끝은 `done`으로 만들지 않는다. 처음 홈 요청은 그 뒤의 화면으로 한 번 나간다. 처음 이동이 끝나기 전에 사용자가 지도를 끌거나 확대·축소하면 `done`이 되고, 처음 홈 요청은 지도가 멈춘(`idle`) 뒤의 화면으로 나간다. 홈이 아직 보이지 않는 동안(저장한 장소 화면 등) 처음 요청 시점이 되었으면 홈이 처음 보일 때 한 번만 보낸다. 처음 홈 요청이 나가기 전의 홈 진입(73번, 예: 앱을 열자마자 보낸 검색이 0곳이라 처음 이동이 남은 채 "새 검색"을 누름)은 따로 요청하지 않고 처음 홈 요청과 합쳐 `done` 뒤 그때 화면으로 한 번 보낸다 (D-108, D-111).
71. 영역 정규화와 cache: 요청 영역은 네 좌표를 소수 셋째 자리(0.001도)에서 가까운 값으로 반올림한 것이고(가운데 0.0005는 큰 쪽으로, `Math.round`와 같은 방향), 반올림으로 한 축의 폭이 0이 되면 그 축만 원본 SW를 내림, NE를 올림한 값으로 보정한다. key와 요청 본문에는 보정까지 끝난 같은 객체를 쓴다. 정규화한 영역이 유효하지 않으면(`NaN`, SW가 NE 이상, place-ai-search AC-29 위반) 요청하지 않고 75번의 지도 실패 안내를 보이며, 그 뒤 지도가 멈출(`idle`) 때 다시 잰 영역이 유효하면 그 영역으로 확정해 요청한다. nearby 쿼리 key는 `["places", "nearby", 정규화한 영역]`이고 `staleTime`과 `gcTime`은 10분이며 AI fallback 응답만 `staleTime` 0이다. 포커스와 재연결로는 다시 받지 않는다. 로그인 세션이 바뀌면 기존 `clearOnSessionChange`의 `queryClient.clear()`가 nearby cache를 지우고 새 코드는 없다(통합 테스트만 둔다) (D-111).
72. 홈 영역 확정: 홈 영역은 65번의 보이는 영역이고 덮는 UI의 위 끝은 홈 아래 묶음("내 위치" 버튼, 대체 안내, 오류 안내, 카드나 skeleton, 검색창)의 위 끝이다. 영역은 지도 크기가 SDK에 적용된 뒤에 읽는다. 지금 wrapper 크기가 마지막으로 `setSize`한 크기(아직 `setSize`가 없으면 지도를 만들 때의 크기)와 같으면 바로, 다르면 다음 `setSize` 적용 뒤에 읽고, `idle`이나 프레임 횟수에 기대지 않는다. 지도가 실패하거나 없어지면 영역은 없는 것으로 끝나고, 기다리는 사이 더 최신 홈 진입, 새 검색, 저장한 장소 진입이 있었으면 이전 결과는 버린다(진입마다 번호를 매겨 비교). 확정한 정규화 영역은 그때의 덮는 UI 위 끝과 함께 페이지 세션의 `searchStore`에 `homeBounds`로 두고, 끌기, 카드 `panTo`, "내 위치"로는 바꾸지 않으며 처음 홈 요청, 홈 진입, 74번의 버튼만 바꾼다. 아래 묶음 높이는 skeleton, 카드, 빈 안내, 오류마다 달라서 74번의 비교는 확정 때의 위 끝을 다시 쓴다. SDK가 `setSize` 직후 영역을 바로 갱신하는지는 실기기에서 확인한다(수동 확인) (D-109, D-111).
73. 홈 진입과 확정 전 표시: 홈 진입은 결과(`viewing`)·과거 결과·저장한 장소 화면을 보다가 첫 화면이 되는 것("새 검색", "추천 받으러 가기", 저장한 장소 화면에서 홈)과, 홈이 보이는 동안의 로그인 세션 변경이다. 앱을 홈 주소로 여는 것은 처음 홈 요청(70번)이다. 첫 검색이 실패해 지금 보는 요청이 없는 채 패널의 "새 검색"을 누르는 것은 실패에서 취소한 것이라 진입이 아니다. 전이는 render 중에 화면 컴포넌트의 지역 state로 판정해 그 렌더부터 이전 영역의 카드를 숨기고, store의 진입 번호 갱신과 영역 확정은 effect에서 한다(render 중에 외부 store를 쓰지 않는다). 같은 렌더에 겹치면 한 번이다. 진입마다 그때 화면의 영역을 확정해 nearby를 부른다. 확정이 버려졌거나(72번) 지도가 늦게 준비되어 홈이 보이는데 지금 진입의 영역이 없으면, 진입 이벤트를 기다리지 않고 그 영역을 확정한다. 검색 중이나 실패에서 취소해 첫 화면으로 돌아오는 것, 결과 화면으로 돌아오는 것, 상세 화면 왕복은 진입이 아니다. 로그인 세션이 바뀌면 `searchStore.reset()`이 `homeBounds`를 비우므로 홈이 숨은 동안 바뀌었어도 다음에 홈이 보일 때 새로 확정한다. 지금 진입의 영역이 정해지기 전에는 이전 영역의 카드, 핀, 빈 안내, 오류를 렌더 단계에서 그리지 않고 실제 카드와 같은 높이의 skeleton(접근성 이름 "주변 추천을 불러오는 중", 동작 줄이기면 움직임 없음)을 보인다. query cache는 지우지 않고, 확정한 영역이 같은 key의 fresh cache를 가졌으면 요청 없이 그린다. 그 cache가 stale이면(받은 지 10분이 지났거나 AI fallback) 그 카드를 그린 채 뒤에서 다시 받고(다시 받기가 실패해도 카드는 그대로이고 실패 안내와 연결 안내는 보이지 않는다), gc돼 데이터가 없으면 skeleton을 보이며 받는다. nearby 쿼리를 구독하는 화면이 없어진 동안에는 10분 뒤 gc될 수 있고, 홈 진입이 아닌 복귀(상세 왕복, 검색 취소·실패 복귀)에서 데이터가 stale이거나 없으면 이 규칙대로 같은 영역의 같은 key로 다시 받는다(영역과 선택은 그대로다). 카드가 보인 뒤 지도가 실패하면(늦게 온 인증 실패 등) 카드 대신 75번의 지도 실패 안내를 보이고 받은 cache는 둔다 (D-111).
74. 홈 "이 지역에서 검색" 버튼: 홈이 보이고, 사용자가 지도를 끌거나 확대·축소했거나 "내 위치"로 옮긴 적이 있고(카드를 넘길 때의 `panTo`는 세지 않고, "내 위치"는 지도가 실제로 움직였을 때만 센다. 이 표시는 처음 홈 요청, 버튼을 누를 때, 홈 진입 때 지운다), 지도가 멈출(`idle`) 때마다 `homeBounds`를 확정할 때와 같은 덮는 UI 위 끝으로 잰 정규화 영역이 `homeBounds`와 다르면 보인다(판정은 `idle` 때만 한다). 끌어서 같은 격자로 돌아오면 숨고, 지도 실패, 연결 오류 전체 안내, 영역 확정 전, 결과·저장한 장소 화면으로 바뀐 때에도 숨는다. 상세 왕복은 홈을 떠난 것이 아니라 버튼과 표시가 그대로다(60번). 결과 화면의 버튼(39번)과 같은 자리·모양이다. 누르면 마지막 `idle`에서 저장해 둔 덮는 UI 위 끝으로 그 순간 다시 잰 정규화 영역으로 nearby를 부르고, 그 영역과 같은 위 끝이 새 `homeBounds`가 되며(같은 key의 fresh cache면 HTTP 없음), 새 영역을 받기 전까지 이전 영역 카드와 핀 없이 skeleton을 보이고 선택은 첫 카드로 되돌린다. "내 위치"는 지도만 옮기고 카드를 다시 받지 않는다 (D-111).
75. 홈 빈 상태, 실패, 안내: 응답 `items`가 비고 `emptyReason`이 있으면 카드 자리의 상자(오류 상자와 같은 모양)에 `cause`와 `suggestion`을 `EmptyState`로 보인다. `emptyReason`이 없는 0곳은 아무것도 그리지 않는다. 요청이 실패하면 카드 자리에 실패 안내와 다시 시도 버튼을 보이고 연결이 없으면 연결 안내가 화면을 덮는다. 지도 SDK가 실패하면(키 없음, 인증 실패, 로드 실패, 71번의 유효하지 않은 영역) skeleton에 머물지 않고 카드 자리에 제목 "지도를 불러오지 못했어요", 설명 "주변 추천을 보려면 지도가 필요해요. 아래 검색창으로 장소를 직접 찾아볼 수 있어요."를 보이며 다시 시도 버튼은 없고 nearby 요청은 나가지 않는다. 검색창의 검색은 영역 없이도 동작한다(D-70). AI fallback 응답(카드 1곳 이상)에는 카드 위에 68번의 새 문구가 보인다. AC-18의 "카드 목록"은 결과 화면의 목록이고, 지도가 없을 때 홈 주변 카드는 이 번호의 지도 실패 안내다 (D-111).

## Usage

1. **입력 중 후보 (5-01)**: 화면 아래 검색창에 "역삼 쌀국수"를 입력하면 300ms 뒤 `GET /api/v1/places/suggest?q=역삼 쌀국수`가 나가고, "하노이 쌀국수 역삼점 · 식당 · 280m", "포레스트 키친 · 식당 · 600m · 메뉴: 양지 쌀국수"와 "이 조건으로 추천받기"가 뜬다. 거리는 위치를 얻었을 때만 보인다(D-32, D-70, D-52).
2. **추천 검색 (5-03, 5-04)**: 엔터를 치면 `POST /api/v1/places/search`가 `{query: "역삼에서 조용히 대화하기 좋은 카페", mapBounds: <주변 카드와 검색창 위로 보이던 지도 영역>}`으로 나가고, 응답의 카드 20개가 순위 번호와 함께 목록과 지도 핀으로 나오며 지도가 핀이 모두 보이게 옮겨진다. 스크롤하면 `nextCursor`로 다음 20개를 가져온다(D-32, D-50, D-70, D-109, D-110).
3. **후속 조건과 요청 기록 (5-06, 5-07)**: 패널 아래 입력창에 "더 조용하게"를 보내면 직전 응답의 `conditions`가 `previousConditions`로 나가고 "요청하신 조건을 반영했어요" 배너와 "추가 조건 · 더 조용하게" 칩이 보인다. 요청 기록에서 첫 요청의 "여기서 이어 검색"을 누른 뒤 "카페 말고 식당"을 보내면 첫 요청의 `conditions`가 기준이 된다(D-50).
4. **근처 검색과 내 위치**: 지금 보는 요청이 없을 때 "근처 카페"를 보내면 `POST /api/v1/places/search`가 일반 검색으로 나가고, Mock 응답은 `nearby: false`와 20곳 페이지다(AI가 `nearby: true`로 해석한 응답도 FE는 거르지 않고 서버 순서 그대로 보인다). 위치 요청은 앱을 열 때 권한이 이미 허용일 때와 지도의 "내 위치" 버튼뿐이며 근처 응답을 받아도 요청하지 않는다. 위치는 서버로 나가지 않는다(D-52, D-108).
5. **핀과 카드, 장소 상세 (6-01~6-05)**: 핀을 누르면 그 카드가 선택되고, 다른 카드를 누르면 지도가 그 핀으로 이동한다. 선택된 카드를 다시 누르면 `/places/…`로 가서 `GET /api/v1/places/{id}`로 사진, 영업시간, 메뉴, 시설을 가져온다. 추천 이유와 핏 점수 설명은 검색에서 받은 카드의 값을 쓴다(D-66, D-70, D-64).
6. **개발자가 결과 없음 응답을 볼 때**: BE Mock에 `X-Mock-Scenario: empty` 헤더를 붙여 검색을 직접 부르면(curl 등) 결과 없음 응답이 온다. FE의 결과 없음 화면은 테스트가 가짜 응답으로 확인한다(D-63, D-95).
7. **첫 화면 (와이어프레임 Start, StartNoLoc)**: 위치 권한을 이미 허용한 사용자가 `/`를 열면 지도가 저장된 화면(처음 쓰는 기기면 SSAFY 서울캠퍼스)으로 먼저 그려졌다가 위치를 얻으면 한 번 내 위치로 옮겨 가고, 아래 검색창 위에 "카페 온담 · 카페 · 350m · 영업 중" 같은 주변 카드가 가로로 넘어가며 지도에 1, 2, 3… 핀이 찍힌다. 권한을 허용하지 않은 사용자에게는 지도가 저장된 화면 그대로이고 그 화면 안의 카드가 거리 없이 보인다. 오른쪽 위의 북마크와 사람 버튼은 저장한 장소 화면과 `/my`로 간다(AC-35)(D-82, D-83, D-85, D-108).
8. **최근 검색 (와이어프레임 StartRecent)**: 어제 "역삼에서 조용히 대화하기 좋은 카페"를 검색한 사용자가 오늘 다시 열어 검색창의 기록 아이콘을 누르면 "최근 검색" 시트에 그 문장과 "10월 22일"이 보이고, 누르면 어제 받은 결과가 "10월 22일 결과 · “역삼에서 조용히 대화하기 좋은 카페”"로 다시 받지 않고 보인다. "이 조건으로 다시 검색"을 누르면 그 문장으로 새 검색이 나간다(D-91, D-90).
9. **지도 화면 복원**: 어제 대전 유성온천역 주변을 보다 앱을 닫은 사용자가 위치 권한 없이 오늘 앱을 열면 지도가 유성온천역 화면으로 열린다. 위치 권한이 있는 사용자가 구로에서 앱을 열고 지도를 선릉으로 끌어 두었다면, 상세에 다녀오거나 화면이 다시 마운트되어도 지도는 선릉에 그대로 있다. 위치를 기다리는 동안 지도를 끌었다면 늦게 도착한 위치는 점으로만 보이고 지도는 옮겨지지 않는다(D-108).
10. **이 지역에서 검색**: 구로 화면에서 "강남역 파스타"를 찾으면 지도가 강남역 결과 핀으로 옮겨진다. 지도를 선릉으로 끌어 "이 지역에서 검색"을 누르면 `POST /api/v1/places/search/region`이 `{query: "강남역 파스타", conditions: <강남역 결과의 conditions>, mapBounds: <패널 위로 보이는 선릉 영역>}`으로 나가고, 지도는 움직이지 않은 채 선릉 화면 안의 파스타 집이 나온다. 이어서 "조용한 곳"을 보내면 `/places/search`에 그 결과의 `conditions`와 선릉 영역이 그대로 나간다. 어제 저장된 옛 "이 지역에서 검색" 기록을 다시 열어 "이 조건으로 다시 검색"을 누르면 `previousConditions` 없이 그 기록 응답의 `conditions`로 region API가 나가고, 영역이 저장되지 않은 아주 오래된 기록이면 "다시 검색할 수 없어요"만 뜬다(D-109, D-110).
11. **홈 주변 카드와 이 지역에서 검색**: 구로에서 앱을 열면 지도가 구로로 옮겨진 뒤 그 화면의 영역으로 `POST /api/v1/places/nearby`가 한 번 나가고 구로 장소 카드가 보인다. 선릉에서 "새 검색"으로 홈에 돌아오면 지도는 그대로 선릉이고 선릉 영역의 카드가 새로 보인다. "내 위치"를 누르면 지도만 구로로 가고 카드는 선릉 그대로이며 "이 지역에서 검색"이 뜨고, 누르면 구로 카드가 나온다(10분 안에 받아 둔 영역이면 요청 없이). 영역 안에 장소가 없으면 카드 자리에 "이 지역 중 조건에 맞는 곳이 없어요" 같은 안내가 보인다(D-111).

## Acceptance criteria

- [x] AC-1: `GET /api/v1/places/suggest`는 `q`(1자 이상)에 대해 장소 후보(`type: PLACE`)와 "이 조건으로 추천받기"(`type: ACTION`)를 돌려준다. 장소 이름이 `q`와 같거나 `q`로 시작하는 후보가 있으면 그 장소가 맨 위이고, 없으면 `ACTION`이 맨 위다(메뉴, 업종 일치는 순서에 영향을 주지 않는다). 메뉴 이름으로 일치한 후보는 `matchedMenu`에 그 메뉴 이름을 담는다. (D-32, D-63, D-64) Mock 모드의 기준이다. DB 모드의 기준은 `docs/specs/place-lookup-db/spec.md`의 AC-1~AC-8이다.
- [x] AC-2: `POST /api/v1/places/search`에 헤더 없이 일반 질의를 보내면 항목 20개, `totalCount`, `nextCursor`가 온다. 그 커서로 다시 보내면 나머지 항목이 오고 `nextCursor`가 없다. 두 페이지의 항목은 겹치지 않는다. Mock 모드 기준이며, DB 모드의 페이지와 커서는 place-ai-search를 따른다. (D-50, D-63, D-64)

## Constraints

- FE는 팀 구조 `app → domains → shared`를 따른다. `src/app`에는 라우트와 레이아웃만 두고 장소 검색과 상세는 `src/domains/place`의 `model`(React와 fetch import 금지), `api`, `ui`로 나누며 도메인 안의 의존은 `ui → api → model` 방향뿐이다. 도메인을 모르는 코드는 `src/shared`에 두고 `/config.json`을 받는 모듈은 `src/shared/lib/runtime-config.ts`다. 파일 이름은 kebab-case, 테스트는 소스 옆 `*.test.ts(x)`, barrel 파일은 만들지 않는다. 같은 도메인 안은 상대 경로, 그 밖은 `@/` 경로로 import한다. BE 호출은 공통 `request`를 거치고 DTO 타입은 `model`에 둔다 (D-66)
- 서버 상태는 TanStack Query 캐시에 둔다. 쿼리 키와 `queryOptions`는 `place-queries.ts`에서만 만들고 `ui`는 그것을 넘겨 훅을 부른다. 서버가 모르는 화면 상태는 React 없는 모듈 `src/domains/place/model/search-store.ts`에 두고 `ui`의 훅이 `useSyncExternalStore`로 구독한다 (D-67)
- 화면의 색, 글자, radius, 그림자, 모션은 `globals.css`의 semantic 토큰만 쓰고 ESLint 디자인 시스템 규칙(날색과 임의 값 금지, `shared/ui` 컴포넌트는 variant와 size로 모양을 고르고 `className`은 배치만)을 지킨다. `shared/ui`에 있는 컴포넌트는 그대로 쓰고, 장소 전용 모양은 `src/domains/place/ui`에 만든다 (D-71)
- 화면 문구, 날짜, 입력 규칙은 React와 fetch 없이 Node 환경에서 테스트하는 `model`의 순수 함수 파일 `place-labels.ts`(한글 이름), `opening-hours.ts`(`Asia/Seoul` 기준 영업시간 문구), `highlight.ts`(자동완성 일치 부분 나누기), `place-id.ts`(상세 id 검사)에 둔다 (D-72)
- BE 엔진 관련 타입(`PlaceSearchEngine`, 그 구현, `InvalidCursorException`)은 하위 패키지 `kr.co.fitdining.api.place.engine`에 둔다 (D-62)
- 저장값 검사는 React와 fetch 없는 `model`의 순수 함수로 두고, `localStorage` 접근은 `ui`에서 한다 (D-66, D-108)
- 홈 영역 정규화는 React와 fetch 없는 `model`의 순수 함수로 두고, nearby cache key와 요청 본문에 그 결과 객체 하나를 쓴다 (D-111)
- 지도 화면은 `localStorage` 키 `fd.map.view.v1` 하나에만 쓰고 기기 위치를 담은 키는 만들지 않는다. 위치 조회 시간을 재는 임시 코드는 commit하지 않는다 (D-108)
- `fe/.env.example`에 `NAVER_MAP_CLIENT_ID`(빈 값)와 선택 값 `APP_ENV`, `BE_INTERNAL_URL`을 설명과 함께 두고, `fe/.gitignore`에 `!.env.example`을 더해 추적한다 (D-75)
