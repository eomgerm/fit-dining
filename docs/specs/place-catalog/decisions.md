# place-catalog decisions

Glossary: none · ADRs: none

## D-1 범위: 테이블을 만드는 마이그레이션만
- Status: settled
- Decision: 네이버 수집 데이터를 담을 장소 테이블을 Flyway 마이그레이션 하나로 만든다. 데이터 적재, JPA 엔티티, API가 DB를 읽게 바꾸는 일은 다음 작업이다. 지금 API는 계속 Mock(`classpath:mock/places.json`)으로 응답한다.
- Rejected: 마이그레이션과 적재를 함께 → 적재 규칙(변환기 수정 포함)이 아직 바뀌는 중이고, 지금은 DB에 데이터를 넣지 않기로 했다. API 연결까지 → place-search의 응답 계약(사진, 브레이크, `station`, 상세 `tags`)부터 정해야 한다.
- Reuse: `be/src/main/resources/application-migrate.yml#spring.flyway` (reuse) — 마이그레이션은 migrate 프로필의 Flyway(기본 위치 `db/migration`)로만 실행하고 새 파일은 그 시점 마지막 버전의 다음 번호로 붙는다 · `be/src/test/java/kr/co/fitdining/api/support/PostgresTestSupport.java#PostgresTestSupport` (reuse) — 테스트 DB를 마이그레이션 계정과 앱 계정으로 구성한다

## D-2 장소 식별자
- Status: settled
- Decision: `places.place_id`는 DB가 발급하는 bigint PK다(`GENERATED ALWAYS AS IDENTITY`). PK 열 이름은 `<테이블 단수형>_id`이고 그 PK를 가리키는 FK 열도 같은 이름이다(develop의 `reviews.review_id` ← `review_reason_tags.review_id`와 같은 방식). 리뷰 담당의 `reviews.place_id bigint`가 이 값을 가리킨다. 네이버 장소 번호는 `naver_place_id text`에 UNIQUE NOT NULL로 따로 두고 빈 문자열만 막는다. 다시 수집하면 `naver_place_id`로 같은 장소를 찾는다. 출처는 네이버 하나로 본다. 자식 테이블의 PK도 같은 방식이다(`place_hour_id` 등).
- Rejected: `naver_place_id`를 PK로 → API 계약의 장소 `id`가 정수(place-search 가정 1)이고, 외부 번호가 바뀌면 FK로 묶인 테이블이 모두 흔들린다. `naver_place_id`를 bigint로 → 계산할 일이 없는 외부 식별자이고 형식은 네이버가 정한다. 원본도 문자열이다. 숫자만 받는 CHECK → 형식은 네이버가 정한다(D-13). PK를 `id`로 → develop의 기존 테이블(`reviews.review_id`)과 이름 짓는 방식이 달라진다. `GENERATED BY DEFAULT` → 번호를 직접 넣을 일이 없고 기존 테이블과 다르다.

## D-3 테이블 나누는 기준
- Status: settled
- Decision: 장소 하나에 값이 하나인 것은 `places`에, 여러 줄인 것(영업시간, 메뉴, 사진, 지하철역, 버스 정류장, 좌석, 방송)은 자식 테이블에 둔다. 짧은 목록(시설, 결제 수단, 키워드, 카테고리 코드 경로, 다른 링크)은 배열이나 jsonb 열로 둔다. 비어 있는 값이 많은 열도 `places`에 그대로 둔다.
- Rejected: 상세 화면에서만 쓰는 값을 1:1 `place_details`로 분리 → 성능 이득이 작고(목록은 id로 PK 조회), 조회가 하나 늘어난다. 지금은 한 테이블로 둔다. 드문 값을 `extras jsonb` 하나로 → 타입과 제약이 사라지고 주차·반려동물은 필터가 될 수 있다.

## D-4 외부 리뷰 지표는 응답 제외 테이블로
- Status: settled
- Decision: 네이버 리뷰에서 나온 집계값(별점, 리뷰 수, 리뷰 주제, 리뷰 메뉴, 키워드 투표, 한 줄 평)과 수집 기록(수집 시각, 검색어, 순위, 저장 수, 추가 카테고리 코드)은 1:1 `place_naver_snapshots`에, 방문자 리뷰 사진은 `place_review_photos`에 둔다(D-7). 응답에 외부 리뷰 필드를 넣지 않는다는 place-search#D-41을 이 두 테이블을 응답이 읽지 않는 것으로 지킨다. 아무 설정 없이 읽어도 안전한 쪽이 기본이 되게 하려는 것이다. 검색 엔진이 쓸 수 있게 데이터는 남긴다.
- Rejected: `places`나 `place_photos`에 함께 두고 조건으로 거르기 → 읽는 곳마다 조건을 지켜야 하고, 하나라도 빠뜨리면(JPA 연관관계를 그냥 매핑하는 경우 등) 리뷰 내용이 응답에 나간다.

## D-5 리뷰 원문과 리뷰어 정보는 넣지 않는다
- Status: settled
- Decision: 리뷰 글, 리뷰어 닉네임과 ID, 블로거 프로필 사진은 이 DB에 넣지 않는다. 리뷰 원문은 검색 엔진(AI 파트)이 자기 DB에 둔다. 스키마는 이런 값을 담는 열을 두지 않는 것으로 지킨다. 집계값(주제·메뉴·키워드별 개수)과 네이버 한 줄 평은 원문이 아니다. jsonb 집계에 리뷰 발췌를 넣지 않는 것은 적재(다음 작업)의 의무다.

## D-6 다른 값으로 만들 수 있는 값은 저장하지 않는다
- Status: settled
- Decision: 저장된 다른 열에서 만들 수 있는 값은 열로 두지 않는다. 대표 사진(업체 사진 중 첫 장), 휴무 안내 문구(`closed`인 요일), 영업 상태(영업시간과 지금 시각), 기준 역까지 거리(좌표), 안심번호 여부, 링크 종류(`website`와 `extra_links` 모두 도메인으로 정한다), 네이버 장소 링크(`naver_place_id`), 사진 프록시 주소(원본 URL), 노키즈존(`facilities`의 "노키즈존"), 발렛(`facilities`의 "발렛파킹"), 지하철과 정류장 순서(도보 거리)가 해당한다. 이런 값은 BE가 계산해 API 응답에 담고 FE는 다시 계산하지 않는다. 예외는 기기 위치가 필요한 계산(내 위치에서의 거리, 위치는 서버로 보내지 않는다, place-search#D-41)과 화면 표시용 서식("08:00 – 22:00" 같은 문구)이다. 응답에서 이 규칙을 지키는 것은 place-search의 일이고, 그 spec을 다시 열 때 옮겨 적는다.
- Rejected: 수집 때 검색한 역(`station`) → 검색 키워드에서 붙은 값이라 실제 위치와 52곳이 어긋나고, 화면에서 쓰지 않는다. 수집 순간 영업 상태 → 그 순간의 값이라 쓰면 안 된다. 날짜가 붙은 시간표 표시(`hours_dated`) → 휴무를 어차피 정확히 판별할 수 없다. 행정구역 생성 열(`sido`, `sigungu`, `dong`) → 지금 지역 검색은 지도 사각형이고, 글로 적은 지역은 검색 엔진이 해석한다. 필요해지면 법정동 코드 하나를 더한다.

## D-7 사진
- Status: settled
- Decision: 사진은 원본 URL만 저장한다. 리사이즈 프록시 주소와 크기 후보는 응답할 때 BE가 만든다. 응답에 쓰는 업체 사진(`business`)과 메뉴판 사진(`menuBoard`)은 `place_photos`에, 저장만 하는 방문자 리뷰 사진(`aiView`, `placeReview`의 이미지)은 `place_review_photos`에 둔다(D-4). `aiView`의 주제("내부", "음식·음료" 등)는 `place_review_photos.theme`에 담는다. 업체 사진의 제목은 가게 이름뿐이라 담지 않는다. 메뉴판 사진은 `places`의 배열이 아니라 `place_photos`에 둔다.
- Rejected: 리뷰 사진을 `place_photos`에 함께 두고 `source`로 거르기 → D-4와 같은 이유. 영상(clip, cp0, `placeReview` 영상)과 `pai` → 재생할 수 없거나 출처가 불분명하다. 원본 크기(`width`, `height`) → 화면은 모두 정해진 틀에 잘라 넣어서 쓰지 않는다. 프록시를 포함한 URL 저장 → 화면마다 규격이 다르고 비공식 프록시가 바뀌면 데이터를 고쳐야 한다.

## D-8 메뉴 사진은 메뉴 행에
- Status: settled
- Decision: 메뉴 항목의 사진은 `place_menus.photo_urls text[]`에 원본 URL로 둔다. 메뉴 7,018개 중 77%가 1장, 12%가 2장 이상이다.
- Rejected: `place_photos`에 `menu_id`를 더해 함께 → 장소 사진과 메뉴 사진이 섞인 테이블이 된다.

## D-9 정렬
- Status: settled
- Decision: 메뉴와 사진(업체, 메뉴판, 리뷰)은 네이버 배열의 인덱스를 `sort_order`로 저장해 네이버 지도와 같은 순서로 보여 준다. 사진의 순서는 출처마다 따로 센다. 지하철역과 버스 정류장은 네이버 순서가 도보 거리순과 같아(300곳 전부) `sort_order` 없이 도보 거리와 PK로 정렬한다.

## D-10 영업시간
- Status: settled
- Decision: `place_hours`는 요일당 한 줄이다. 영업시간 묶음이 여럿이면(드라이브스루 등) 묶음 이름으로 나누고, 기본 묶음은 이름이 NULL이다. 마감이 개점과 같거나 이르면 다음 날 마감이고 24:00은 00:00으로 저장한다. 개점이 NULL이고 휴무가 아니면 정보 없음이다. 브레이크는 여러 개일 수 있어 jsonb 목록, 라스트오더는 시각 배열이다. 정기휴무 요일은 `closed = true`이고 휴무 안내 문구는 저장하지 않는다.

## D-11 지하철역은 글자로, 역 테이블과 공간 인덱스는 나중에
- Status: settled
- Decision: `place_subways`는 네이버가 준 역 이름과 호선을 글자로 담는다(`place_bus_stops`와 같은 모양). 역 좌표가 수집 데이터에 없어서 역 테이블(`stations`, `station_lines`)은 두지 않는다. 지도 사각형과 근처 검색용 공간 인덱스도 이번에 두지 않는다.
- Rejected: 역 테이블을 지금 → 공공데이터를 따로 넣어야 하고, 비어 있으면 `place_subways`를 채울 수 없다. earthdistance 공간 인덱스를 지금 → 300곳에는 필요 없고, 마이그레이션 계정이 확장을 만들 수 있는지 확인되지 않았다. 필요해지면 다른 마이그레이션으로 더한다.

## D-12 `places`에서 뺀 원본 값
- Status: settled
- Decision: 미쉐린 가이드(300곳 중 1곳)는 넣지 않는다. 주차는 무료 여부와 안내 글 두 열로 푼다. 반려동물 동반 여부는 `facilities`에 없는 "불가"(53곳)가 있어 열로 남긴다. 버스 정류장, 다른 링크, 결제 수단, 좌석, 방송, 주소 세 가지, 카테고리 코드, 키워드, 메뉴 수정일은 남긴다. 다른 링크(`extra_links`)는 URL 목록(`text[]`)이다.
- Rejected: 주차를 jsonb로 → 세 값뿐이고 그중 발렛은 `facilities`와 같다. 다른 링크를 네이버 종류와 함께 `[{type, url}]` jsonb로 → 종류는 사장님이 고른 값이라 일관성이 없고(같은 캐치테이블 링크가 "홈페이지"이기도 "예약"이기도 하다), 대표 홈페이지의 종류(`website_type`)를 뺀 것과 기준이 어긋난다.

## D-13 무결성과 인덱스
- Status: settled
- Decision: 제약과 인덱스에는 `<접두어>_<테이블>_<열 또는 뜻>` 이름을 붙인다(CHECK `ck`, FK `fk`, UNIQUE `uk`, 인덱스 `idx`, develop의 V4·V5와 같은 방식). 모든 자식 테이블은 `place_id`로 `places`를 가리키고, 장소를 지우면 자식 행도 지워진다(ON DELETE CASCADE). PostgreSQL은 FK에 인덱스를 만들지 않으므로 자식 테이블마다 `place_id`로 시작하는 인덱스를 둔다. CHECK는 우리가 정한 구분(대분류, 사진을 어느 테이블에 담을지 정하는 출처 구분, 요일)과 구조 규칙(개점과 마감의 짝, 휴무일의 시각 없음, 24:00 금지, 빈 장소 번호와 빈 묶음 이름 금지, 음수 순서 금지, JSON 목록 열의 배열 여부)에만 건다. 네이버가 정하는 값의 내용(가격, 가격 유형, 장소 번호 형식 등)은 묶지 않는다. NOT NULL은 장소를 알아보는 데 꼭 필요한 값(이름, 대분류, 좌표)과, 자식 행을 이루는 값(메뉴 이름, 역 이름, 정류장 이름, 좌석 이름, 사진 URL, 수집 시각)에만 건다. 이 값이 없는 자식 행은 적재에서 버린다. 방송은 어느 한 열이 행을 이루지 않아 모두 NULL을 허용한다. 네이버에서 비어 올 수 있는 그 밖의 값은 300곳에 모두 있더라도(주소 등) NULL을 허용한다. 우리 화면이 쓰는 목록 열은 빈 목록이 기본값이고, 스냅샷의 집계 jsonb는 수집되지 않음(NULL)과 빈 집계를 구분하려고 NULL을 허용한다. 전국으로 넓혀도 같은 구조를 쓴다.
- Rejected: 네이버 값에 CHECK나 NOT NULL(예: 가격 `>= 0`) → 전국으로 넓힐 때 새 값이나 빈 값이 들어오면 적재가 실패한다.
