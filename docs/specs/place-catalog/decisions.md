# place-catalog decisions

Glossary: none · ADRs: none

## D-1 범위: 마이그레이션, 로컬 적재, 상세 응답 계약 변경
- Status: settled
- Decision: 이번 반복은 세 가지다. ① 장소 테이블 8개를 만드는 Flyway 마이그레이션 하나. ② 수집 CSV를 변형해 로컬 DB에만 넣는 적재 스크립트(D-15). ③ 실데이터에 맞춘 상세 응답 계약 변경과 그에 따른 BE DTO, mock, FE 수정(D-17, D-18, D-19). API는 이번에도 mock(`classpath:mock/places.json`)만 읽는다. DB 조회(JPA 엔티티, 리포지토리), mock과 DB를 고르는 설정, AI 검색 응답(`placeId`)과의 연결, dev와 운영 적재는 다음 작업에서 함께 한다. 이 변경이 place-search spec의 DTO와 화면 규칙을 바꾸므로, place-search spec의 해당 문단도 같은 커밋에서 맞춰 고친다.
- Rejected: 마이그레이션만 → mock을 실데이터로 바꾸는 순간 브레이크 여러 개, 숫자 없는 가격 같은 계약의 빈틈이 화면에 드러난다. 상세를 DB에서 읽는 설정까지 지금 → 카드의 mock `id`와 DB `place_id`를 맞추는 일과 JPA가 함께 들어와 범위가 커진다. place-search를 따로 다시 열기 → 두 spec이 어긋난 채 남는다.

## D-2 장소 식별자
- Status: settled
- Decision: `places.place_id`는 DB가 발급하는 bigint PK다(`GENERATED ALWAYS AS IDENTITY`). PK 열 이름은 `<테이블 단수형>_id`이고 그 PK를 가리키는 FK 열도 같은 이름이다. 네이버 장소 번호는 `naver_place_id text`에 UNIQUE NOT NULL로 따로 두고 빈 문자열만 막는다. 다시 수집하면 `naver_place_id`로 같은 장소를 찾는다. 우리 테이블끼리는 `place_id`로만 잇고, 네이버 번호는 `places` 한 곳에만 둔다(`reviews`에도 더하지 않는다).
- Rejected: `naver_place_id`를 PK로 → API 계약의 장소 `id`가 정수이고, 외부 번호가 바뀌면 FK로 묶인 테이블이 모두 흔들린다. `naver_place_id`를 bigint로 → 계산할 일이 없는 외부 식별자이고 형식은 네이버가 정한다. 수집 원본 JSON도 문자열이며, 정제 CSV의 BIGINT는 정제 과정에서 붙인 타입이라 근거가 되지 않는다. 숫자만 받는 CHECK → 형식은 네이버가 정한다(D-13). PK를 `id`로 → develop의 기존 테이블(`reviews.review_id`)과 이름 짓는 방식이 달라진다.

## D-3 테이블 나누는 기준
- Status: settled
- Decision: 장소 하나에 값이 하나인 것은 `places` 열에 둔다. 주차, 반려동물, 콜키지, 찾아오는 길, 업체 소개 같은 정책·안내 값도 여기에 둔다. 여러 줄인 것(영업시간, 메뉴, 사진, 지하철역, 버스 정류장, 좌석, 방송)은 자식 테이블에 두고, 짧은 목록(시설, 결제 수단, 키워드, 카테고리 코드 경로, 다른 링크, 메뉴 라벨)은 `text[]`나 jsonb 열로 둔다. 비어 있는 값이 많은 열도 `places`에 그대로 둔다.
- Rejected: 정책·안내 값을 별도 1:1 테이블(`place_details` 등)로 → 상세 조회가 하나 늘 뿐 얻는 것이 없다. 드문 값을 `extras jsonb` 하나로 → 타입과 제약이 사라지고 주차·반려동물·콜키지는 필터가 될 수 있다.

## D-4 외부 리뷰에서 나온 값은 저장하지 않는다
- Status: settled
- Decision: 네이버 리뷰에서 나온 집계값(별점, 리뷰 수, 리뷰 주제, 리뷰 메뉴, 키워드 투표, 네이버 AI 요약 문구)과 방문자 리뷰 사진은 이 DB에 저장하지 않는다. 쓰는 곳은 AI 검색 파트이고 그쪽이 원본에서 가져간다. 응답에 외부 리뷰 필드를 넣지 않는다는 place-search#D-41은 이 값을 담는 테이블과 열이 없는 것으로 지킨다.
- Rejected: 응답이 읽지 않는 별도 테이블(`place_naver_snapshots`, `place_review_photos`)에 저장 → 이 DB에서 쓸 곳이 없다. `places`에 함께 두고 조건으로 거르기 → 읽는 곳마다 조건을 지켜야 하고 하나라도 빠뜨리면 응답에 나간다.

## D-5 리뷰 원문과 리뷰어 정보는 넣지 않는다
- Status: settled
- Decision: 리뷰 글, 사업자 답글, 블로그·카페 글 요약, 리뷰별 키워드, 리뷰어 닉네임과 ID, 작성자 해시(`author_hash`), 블로거 프로필은 DB와 mock 어디에도 넣지 않는다. 정제 CSV의 `external_*` 파일은 AI 검색 파트가 가져간다. 스키마는 이런 값을 담는 열을 두지 않는 것으로, 적재와 mock 생성은 이 파일들을 읽지 않는 것으로 지킨다.

## D-6 다른 값으로 만들 수 있는 값은 저장하지 않는다
- Status: settled
- Decision: 저장된 다른 열에서 만들 수 있는 값은 열로 두지 않고 BE가 응답할 때 계산한다. 대표 사진(업체 사진 첫 장), 휴무 안내 문구(`closed`인 요일), 영업 상태, 기준 역과 거리(좌표로 강남·역삼·선릉 중 가장 가까운 역), 안심번호 여부(번호 형식), 링크 종류(도메인), 네이버 장소 링크(`naver_place_id`), 사진 프록시 주소, 노키즈존과 발렛(`facilities`의 "노키즈존", "발렛파킹"), 지하철 순서(도보 거리)가 해당한다. FE는 다시 계산하지 않는다. 예외는 기기 위치가 필요한 계산과 화면 표시용 서식이다. 영업시간과 BE의 `openStatus`로 오늘 안내 문구("내일 02:00까지" 등)를 고르는 일은 화면 표시용 서식이다. 또 하나의 예외로 구(`district`)와 동(`dong`)은 저장한다. 주소를 해석해 뽑는 값이라 응답마다 계산하지 않고 적재 때 한 번 한다.
- Rejected: CSV의 `station_name`·`station_distance_km` 저장 → 좌표로 계산할 수 있다. 수집 순간 영업 상태 → 그 순간의 값이다. 날짜가 붙은 시간표 표시(`label_date`) → 휴무를 어차피 정확히 판별할 수 없다. 구·동을 응답마다 주소에서 계산 → 주소 형식이 일정하지 않아(지번 주소에 건물 표기 등) 매번 해석하는 것은 안전하지 않다.

## D-7 사진
- Status: settled
- Decision: 사진은 원본 URL만 저장한다. `place_photos`에는 업체 사진(`business`)과 메뉴판 사진(`menuBoard`)만 둔다. 이번 응답은 원본 URL을 그대로 담고, 리사이즈 프록시와 크기 후보(`src`/`srcSet`)는 하지 않는다. 업체 사진의 제목은 가게 이름뿐이라 담지 않는다.
- Rejected: 방문자 사진(`aiView`, `placeReview`), 클립, 영상, `pai` → 제3자 저작물이거나 재생할 수 없거나 출처가 불분명하다(D-4). 원본 크기(`width`, `height`) → 화면은 모두 정해진 틀에 잘라 넣는다. 프록시를 포함한 URL 저장 → 프록시가 바뀌면 데이터를 고쳐야 한다.

## D-8 메뉴 사진은 메뉴 행에
- Status: settled
- Decision: 메뉴 항목의 사진은 `place_menus.photo_urls text[]`에 원본 URL로 둔다(사진이 있는 메뉴 6,221개).
- Rejected: `place_photos`에 `menu_id`를 더해 함께 → 장소 사진과 메뉴 사진이 섞인 테이블이 된다.

## D-9 정렬
- Status: settled
- Decision: 메뉴와 사진(업체, 메뉴판)은 네이버 배열의 순서를 `sort_order`로 저장해 네이버 지도와 같은 순서로 보여 준다. 사진의 순서는 출처마다 따로 센다. 지하철역과 버스 정류장은 네이버 순서가 도보 거리순과 같아(600개 묶음 전부) `sort_order` 없이 도보 거리와 PK로 정렬한다.

## D-10 영업시간
- Status: settled
- Decision: 장소당 시간표 한 벌을 요일당 한 줄로 저장한다(`UNIQUE(place_id, day_of_week)`). 기본 시간표가 있으면 그것을, 없으면(스타벅스 12곳) "매장" 시간표를 쓰고 배달·드라이브스루·워크스루 시간표는 버린다. 마감이 개점과 같거나 이르면 다음 날 마감이고 24:00은 00:00으로 저장한다. 개점이 NULL이고 휴무가 아니면 정보 없음이다. 브레이크는 하루에 여러 개일 수 있어(최대 4개) `[{start, end}]` jsonb 목록, 라스트오더는 종류(마감 전, 브레이크 전) 없이 시각 배열이다. 정기휴무 요일은 `closed = true`이고 휴무 안내 문구는 저장하지 않는다.
- Rejected: 시간표 이름 열(`set_name`, 또는 코드 `service_type`)을 두고 모든 시간표 저장 → 화면은 한 벌만 쓰는데 조회마다 어느 시간표인지 골라야 하고, 해당 장소는 12곳뿐이다. 라스트오더를 `[{type, time}]`로 → 화면이 종류를 쓰지 않는다. 시각을 자정부터의 분(정수)으로 → 기존 규칙(D-10)으로 24:00과 자정 넘김을 모두 담을 수 있다.

## D-11 지하철역은 글자로, 역 테이블과 공간 인덱스는 나중에
- Status: settled
- Decision: `place_subways`는 네이버가 준 역 이름과 호선을 글자로 담는다(`place_bus_stops`와 같은 모양). 역 좌표가 수집 데이터에 없어서 역 테이블(`stations`, `station_lines`)은 두지 않는다. 지도 사각형과 근처 검색용 공간 인덱스도 이번에 두지 않는다.
- Rejected: 역 테이블을 지금 → 공공데이터를 따로 넣어야 한다. earthdistance 공간 인덱스를 지금 → 300곳에는 필요 없고, 마이그레이션 계정이 확장을 만들 수 있는지 확인되지 않았다.

## D-12 `places`에 담는 원본 값
- Status: settled
- Decision: `places`에는 대표 전화(`phone`, 일반 번호가 없으면 안심번호), 가게의 네이버 예약 페이지(`booking_url`), 주차·반려동물·콜키지의 가능 여부와 안내 글, 주소 세 가지, 다른 링크(죽은 링크 제외), 결제 수단, 사장님 키워드, 카테고리 코드, 메뉴 수정일을 담는다. 버스, 좌석, 방송은 자식 테이블에 남긴다. CSV 열과의 대응은 spec.md의 "적재·mock 변형 규칙"에 있다.
- Rejected: 일반 번호와 안심번호를 두 열로 → 화면은 번호 하나만 쓰고 안심번호 여부는 형식으로 안다. 톡톡 URL, 네이버페이, 쿠폰 수, 예약 가능 표시, 미쉐린(1곳), 저장수, 수집 시각·검색어·순위 → 쓰는 화면이 없다. 장소 구분은 `place_id`와 `naver_place_id`로 된다. 대관, 주류 주문 필수, 콜키지 주류별 정책, 주차 요금 상세 → 쓰는 화면이 없다. 다른 링크를 네이버 종류와 함께 jsonb로 → 종류는 사장님이 고른 값이라 일관성이 없다.

## D-13 무결성과 인덱스
- Status: settled
- Decision: PK 말고 제약과 인덱스에는 `<접두어>_<테이블>_<열 또는 뜻>` 이름을 붙인다(PK 제약에는 이름을 붙이지 않는다). 모든 자식 테이블은 `place_id`로 `places`를 가리키고 장소를 지우면 함께 지워지며(ON DELETE CASCADE), `place_id`로 시작하는 인덱스를 둔다. CHECK와 NOT NULL은 우리가 정한 구분과 구조 규칙, 장소와 자식 행을 알아보는 데 꼭 필요한 값에만 건다. 네이버가 정하는 값의 내용은 묶지 않고, 좌표에는 UNIQUE를 걸지 않는다. 전국으로 넓혀도 같은 구조를 쓴다. 전체 DDL은 spec.md에 있다.
- Rejected: 네이버 값에 CHECK나 NOT NULL(예: 가격 `>= 0`) → 전국으로 넓힐 때 새 값이나 빈 값이 들어오면 적재가 실패한다.

## D-14 입력 데이터
- Status: settled
- Decision: 기준 데이터는 저장소의 `data/naver-places/clean/`(정제 CSV 30개와 `DATA_DICTIONARY.md`, 2026-10-23 수집 300곳)이고, ERD는 `data/naver-places/erd/`에 둔다. 두 폴더는 리뷰 원문과 작성자 해시가 들어 있어 `.gitignore`(`/data/naver-places/`)로 커밋하지 않는다. CSV는 확정된 계약이 아니라 우리 스키마에 맞게 변형해서 쓰는 입력이다. 이름이 같아도 뜻이 다른 열(`phone`, `booking_url` 등)은 데이터 사전의 설명을 따른다.
- Rejected: CSV를 그대로 테이블로 옮기기 → CSV에는 정제용 파생 열, 추정(HEURISTIC) 열, 리뷰 원문이 섞여 있다.

## D-15 로컬 적재 스크립트
- Status: superseded by D-25
- Decision: 적재는 Python 스크립트로, `data/naver-places/` 안에 두어 git이 추적하지 않는다. 접속 대상은 명시한 호스트 인자로만 정하고(호스트 관련 환경 변수는 무시한다), 호스트가 `localhost`, `127.0.0.1`, `::1`이 아니면 접속하기 전에 끝나며, 로컬 앱 계정(DML만 가능)으로 접속한다. 장소마다 한 트랜잭션으로 `naver_place_id`로 장소를 찾아 갱신하고(`place_id`는 그대로), 그 장소의 자식 행은 지운 뒤 다시 넣는다. 변형 규칙(D-6, D-10, D-12, D-16)은 이 스크립트가 맡는다. 검증은 로컬 DB에 실제로 들어가는지까지이고, 끝날 때 테이블별 행 수와 버린 행 수를 출력한다. 적재 자동 테스트는 두지 않는다.
- Rejected: 모든 테이블을 비우고 다시 넣기 → `place_id`가 바뀌어 앱 리뷰가 엉뚱한 장소에 붙는다. Java(Spring 실행기)나 SQL `\copy` → 변형 규칙을 짜기 어렵고 앱 코드와 섞인다. 저장소에 커밋 → 데이터 파일이 없는 CI에서 돌 수 없고, 로컬 전용 도구다.

## D-16 메뉴
- Status: settled
- Decision: 메뉴는 거르지 않고 전부 넣는다. "[주문제작] 생화 케이크"처럼 일반 메뉴가 아닌 항목을 구분하는 값이 데이터에 없어서, 거르려면 이름 규칙을 코드에 박아야 하기 때문이다. 메뉴마다 순서, 카테고리, 이름, 설명, 가격 숫자(정가일 때만), 가격 원문, 가격 유형(`FIXED`/`DYNAMIC`/`FREE`/`RANGE`), 대표 여부, 라벨(`labels text[]`, "2인이상", "사전예약" 등), 사진을 담는다. "메뉴 정보 기준일"은 보여 주지 않는다.

## D-23 영업시간 응답과 영업 상태
- Status: settled
- Decision: 응답의 영업시간은 저장 규칙(D-10)을 그대로 따른다. 마감이 개점과 같거나 이르면 다음 날 마감, 24시간은 `00:00`–`00:00`, 정보 없는 요일은 시각 없이 `closed: false`다. 영업 상태는 어제 시간표의 자정 넘은 부분까지 보고 계산하고, 어느 영업 구간에도 들지 않을 때 오늘이 정보 없음이거나, 오늘 첫 영업 전인데 어제가 정보 없음이면 `UNKNOWN`이다(오늘이 휴무일이면 어제와 상관없이 `CLOSED`). 마감 시각에 다음 날 영업이 바로 이어지면 한 구간으로 보아, 24시간 가게가 매일 밤 "곧 마감"이 되지 않게 한다. FE는 "정보 없음"과 "24시간 영업"을 구분해 보이고, 마감 `00:00`은 화면에 "24:00"으로 쓰며 자정을 넘는 영업으로 치지 않는다. 오늘 안내는 자정을 넘는 영업이면 "내일 02:00까지", 어제 영업의 새벽 부분이면 "02:00까지", 24시간 영업이 다음 날로 이어지면 "24시간 영업"이다. `closedDayNote`는 정기휴무 요일로 만든다. 판정 규칙은 spec.md에 있다.
- Rejected: 개점 < 마감 가정 유지 → 실데이터에서 자정을 넘는 요일이 525개, 24시간 영업이 67개다. 정보 없음을 휴무로 표시 → 문 연 가게를 닫았다고 보여 준다. 24시간도 매일 23시에 "곧 마감" → 7일 내내 24시간인 곳이 매일 밤 잘못 보인다. "곧 마감" 상태 없애기 → place-search의 상태 정의와 문구를 바꾸는 일이라 범위가 커진다. 마감 `00:00`을 "내일 00:00까지"로 표시 → 24:00 마감 213개 요일이 자정을 넘는 것처럼 보인다. 어제가 정보 없음인 새벽을 `CLOSED`로 → 어제 영업이 이어지는지 모르면서 닫았다고 말한다. 자정 넘김도 "오늘 <마감>까지" → 새벽 마감이 "오늘 02:00까지"로 보이고 새벽에는 오늘 줄을 보고 잘못 안내한다. "`UNKNOWN` 없음" mock 규칙 유지 → 정보 없음은 실데이터에 있는 상태이고 화면에서 확인해야 한다.

## D-25 적재 스크립트를 저장소에 둔다(S15P31A302-113)
