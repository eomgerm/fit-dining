# 검색 조건 3차: 분류별 조건과 이번 요청만의 해석

요청 해석 결과(`Conditions`)를 분류별 칸으로 나누고, LLM은 이번 요청만 해석하게 바꾸는 설계다(S15P31A302-136, 2026-11-04). 끝나면 내용을 [spec.md](spec.md) 4.1과 [api.md](api.md)로 옮기고 이 문서는 지운다.

## 1. 왜 바꾸나

2026-11-03 점검에서 나온 구조 문제다.

- `codes` 한 칸에 특징(`QUIET`), 음식 종류(`FOOD_JAPANESE`), 매운맛(`FOOD_SPICY`), 시설(`PARKING`)이 섞여 있다. 쓰는 쪽이 다시 고른다(`Conditions.facilities`, `taste_select._group`, `scoring.from_reviews`). 점수용 코드표를 요청 해석의 틀로도 써서다.
- 같은 특징이 코드표에 있으면 `codes`, 없으면 `features`로 갈라진다.
- 피함을 담는 방식이 셋이다(`avoidCategories`, `avoidFoods`, 조각의 `want`).
- 후속이면 해석이 이전 조건을 합쳐 내서 이번에 말한 지역인지 알 수 없다. 지역 고르기가 원문이 요청문에 있는지로 짐작한다(`search._where`).
- `station`, `nearby`는 1차 칸이다. `station`은 거르기와 점수 어디에도 쓰지 않는다.

## 2. 결정

- 조건은 분류별 칸이다. 업종, 음식 종류, 맛, 메뉴, 특징, 시설, 인원, 지역, 시간, 가격, 가게 이름이다.
- 피함은 항목마다 `want`로 둔다. 피함을 받는 분류는 업종, 음식 종류, 맛, 메뉴뿐이다. 특징과 시설은 원함만 받고, 부정한 특징은 지금처럼 바라는 쪽으로 바꾼다("시끄러운 곳 말고" → `QUIET`). 특징에 피함을 열었을 때 "웨이팅 긴 데 싫어"가 짧은 대기를 피함으로 뒤집혔다(2026-11-02 평가).
- 맛은 음식 종류에서 나눈다. 지금은 매운맛(`SPICY`) 하나다. 인원은 목적 코드로 바꾸기 전 값을 둔다.
- LLM은 이번 요청만 해석한다. 이전 조건은 맥락으로 보여 주되 출력은 이번 요청의 조각이다. 이전 조건과 합치는 일은 코드가 분류별 규칙으로 한다. 규칙 해석도 같은 합치기를 쓴다.
- 공유 코드표(`fit_ai.features`)는 바꾸지 않는다. 점수용 코드는 해석이 끝난 뒤 `interpretation/codes.py` 한 곳에서 만든다.
- BE와 FE는 조건을 열어 보지 않으므로(BE `Map<String, Object>`, FE `Record<string, unknown>`) 코드를 바꾸지 않는다. BE가 검색 대화에 저장한 1차·2차 조건은 계속 읽는다.

## 3. 조건 모양

```jsonc
{
  "version": 3,
  "text": "선릉역 3만원 이하 초밥 매운 거 말고",
  "embeddingText": "3만원 이하 초밥",
  "categories": [{"code": "RESTAURANT", "want": true}, {"code": "CAFE", "want": false}],
  "foodTypes": [{"code": "FOOD_JAPANESE", "want": true}],
  "flavors": [{"code": "SPICY", "want": false}],
  "menus": [{"text": "스시", "value": "초밥", "spellings": [], "want": true}],
  "features": [{"text": "북적이는 데 말고", "value": "조용하고 차분한 곳", "code": "QUIET"},
               {"text": "충전되는", "value": "콘센트", "code": null}],
  "facilities": ["PARKING"],
  "partySize": 5,
  "locations": [{"text": "션릉역", "kind": "STATION", "value": "선릉역"}],
  "hours": [],
  "price": {"text": "3만원 이하", "maxWon": 30000, "cheap": false},
  "placeName": null
}
```

- 업종은 원함이 하나까지다.
- 특징의 `code`는 코드표의 성향 축·중요 기준·방문 목적 코드이고, 코드표에 없는 특징이면 null이다.
- `station`, `nearby`는 칸에서 빼고 지역에서 계산한다. 검색 응답 최상위 `nearby`는 BE가 쓰므로 그대로 낸다.

점수용 코드(`codes.score_codes`)는 특징 코드, 원하는 음식 종류, 원하는 맛(`SPICY` → `FOOD_SPICY`), 시설, 인원(1명 `PURPOSE_SOLO`, 4명 이상 `PURPOSE_GROUP`) 순서다.

## 4. 이전 조건과 합치기

| 분류 | 이번 요청에 있으면 |
| --- | --- |
| 업종, 지역, 가격, 가게 이름, 인원 | 바꾼다 |
| 음식 종류, 맛, 메뉴 | 같은 값은 이번 것으로 덮고 나머지는 잇는다("파스타 말고 피자"면 이전의 파스타는 피함이 된다) |
| 특징 | 잇는다. 반대 극이 오면 이전 것을 지운다 |
| 시간 | 같은 종류(요일, 마감, 시작)는 덮는다 |
| 시설 | 잇는다 |

해석 결과는 이번 요청의 조각(`turn`)과 합친 조건을 같이 낸다. 지역 고르기는 이번 요청의 지역을 바로 쓴다.

## 5. 옛 조건 읽기

`version`이 3이 아니면 2차 모양(`codes`, `avoidFoods`, `avoidCategories`, 분류별 조각)이나 1차 모양(`station`, `nearby`)으로 읽는다. `codes`는 코드표의 층으로 특징·음식 종류·맛·시설로 나누고, `avoidFoods`는 음식 종류와 맛의 피함, `avoidCategories`는 업종의 피함, `station`과 `nearby`는 지역으로 바꾼다. 코드 없는 특징 중 피함(`want`가 거짓)은 버린다. 특징은 원함만 받는다. 읽지 못하면 지금처럼 `PREVIOUS_INVALID`다.

## 6. 진행

| 단계 | 내용 | 결과 변화 |
| --- | --- | --- |
| P1 | 조건 타입, 옛 조건 읽기, 점수용 코드 모듈. 쓰는 쪽(검색, 서버)을 새 칸으로 바꾸고 응답 조건을 3차 모양으로 낸다. 해석은 지금 출력을 받아 새 조건으로 바꾼다 | 없음(점수 항목 순서가 분류 순서로 바뀌는 것만) |
| P2 | 규칙 해석을 이번 요청만 해석하게 하고 합치기를 넣는다. 항목 단위 부정 판정("싫어", "없는", "않은"), 규칙 해석의 벡터용 문장에서 부정된 말 지우기 | 규칙 해석 |
| P3 | LLM 출력을 이번 요청의 분류별 조각으로 바꾸고 코드 확인을 분류별 정책으로 정리한다. 해석 평가 80개×2를 다시 잰다(GMS 필요) | LLM 해석 |
| P4 | 지역 고르기를 이번 요청의 지역으로 바꾸고 이전 지역 짐작을 지운다. spec과 api.md를 고치고 BE·FE에 알린다 | 지역 고르기 |

배포 뒤 AI를 되돌리면 이전 AI는 3차 조건을 읽지 못해 후속이 새 검색이 된다(`PREVIOUS_INVALID`). 요청의 모르는 속성은 거부한다는 규칙(검색 spec D-41)은 3차 조건에도 그대로 둔다.

P1 확인(2026-11-04): 해석 평가 질의 80개와 후속 5개씩(규칙 해석), 이전 조건을 보여 주는 LLM 프롬프트 400개, mock 장소 검색 카드 1,678장을 P1 전 코드와 견줬다. 다른 것은 후속 조건의 코드 순서(처음 나온 순서 → 분류 순서) 19건뿐이다.

P2 확인(2026-11-04): 해석 평가 질의 80개의 규칙 해석은 P1과 견줘 67개에서 68개가 맞았다("시끄러운 곳 말고"의 `QUIET`). 나머지 바뀐 것은 벡터용 문장에서 부정한 말이 빠진 것뿐이다. 후속에서 이전 코드를 빼는 판단(`rules._kept_codes`)은 LLM 해석도 쓰므로 빼 달라는 말("말고", "빼고")만 그대로 본다.
