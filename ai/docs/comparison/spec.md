# 취향-가게 비교 베이스라인

Status: draft · Jira: S15P31A302-41, S15P31A302-136 · 작성일: 2026-10-23 · 고친 날: 2026-11-03

비교 파트는 검색 요청을 해석하고, 조건에 맞는 장소를 DB에서 뽑아 장소 프로필과 취향 프로필로 순위를 매긴 뒤 카드로 내보낸다. BE는 검색마다 AI를 한 번 부른다. AI는 장소 데이터를 들고 있지 않고 검색마다 Postgres 뷰 하나를 pgvector로 읽는다. 순서는 핏 점수로 정한다(2026-11-03). 요청 조각과 취향마다 리뷰 근거와 장소 정보로 조건 점수를 내고 합친다. LLM은 요청 해석에만 쓰고, 카드는 같은 조건 점수로 규칙대로 채운다. 다른 담당과 맞출 것은 6장, 다음 할 일은 7장에 있다.

목표: 11-02까지 검색 엔드포인트(`POST /v1/search`)를 배포하고 BE와 잇는다. 배포 위치는 Modal이다(10-29).

코드는 `ai/src/fit_ai/match/`(비교 로직)와 `ai/server/`(API 앱)에 있다. 검색 한 번의 흐름은 `match/search.py`가 잇고, `server/`는 요청 검사, 응답 변환, 로그만 한다. 공유 모듈 `fit_ai.features`, `fit_ai.embedding`, `fit_ai.gms`는 39 것을 그대로 쓴다.

## 1. 역할

분석은 프로필 두 개를 만든다. 39는 사용자가 한 일(온보딩 태그, 직접 입력, 리뷰 이유 태그)로 취향 프로필을, 40은 리뷰와 장소 정보로 장소 프로필을 만든다. 비교(41)는 검색할 때 요청을 해석하고, DB에서 후보를 뽑아 두 프로필로 정렬한 뒤 카드를 만든다. 비교는 두 프로필 JSON과 공유 모듈만 쓰고 분석의 내부 코드는 가져다 쓰지 않는다.

## 2. 결정 사항

| 항목 | 결정 |
| --- | --- |
| 정렬 방식 | 핏 점수 순서(2026-11-03). 1차는 LLMRank(LLM을 학습 없이 정렬기로 씀)였고, 평가 비교용으로 `match/ranking.py`에 남긴다 |
| 목표 | MVP 서비스 반영(첫 공개 11-06). 구현이 우선이고 라벨링·정량 평가는 공개 뒤로 미룬다 |
| 입력 | 취향(회원은 `user_preferences` 행, 비회원은 온보딩 답), 장소 프로필(`place-profile/v0`), 요청 해석 결과 |
| 장소 프로필 | 40이 만든다(10-23). 41은 읽기만 한다 |
| 장소 데이터 | AI는 들고 있지 않는다(10-23). BE와 40이 Postgres에 두고 AI가 검색마다 뷰 하나를 읽는다(10-26) |
| 호출 방식 | BE는 검색마다 AI를 한 번 부른다(10-26). AI가 해석, 거르기, 정렬, 카드까지 한다 |
| 배포 위치 | Modal(10-29). 직접 입력 해석·취향 프로필 API와 같은 AI API 앱 하나로 올린다. 검색은 `server/search.py`의 `router(deps)`다 |
| 요청 해석 | 41이 한다(10-23). GMS 1번, 실패하면 낱말 규칙 |
| 조건 이름 | 39 코드표(`QUIET`, `PURPOSE_GROUP` 등)를 쓴다. 코드표에 없는 시설 4개는 BE `Facility` 코드(`PARKING` 등)를 쓴다 |
| 후보 추출 | 업종·지역·뺄 업종·시설·영업시간·가격·메뉴로 거르기와 요청문 유사도 순서로 100곳 고르기를 SQL 한 번(pgvector)으로 한다(10-26, 100곳은 2026-11-03). 100곳 모두 점수를 매기고 점수순으로 20곳을 돌려준다. 지역은 역·동·구·지도 영역 여러 개를 OR로 묶는다(2026-11-02). 영업시간과 가격은 안 맞는다고 확인된 곳만 뺀다(2026-11-03). 메뉴는 그 메뉴를 판다고 확인된 곳만 남긴다(2026-11-03). OpenSearch는 쓰지 않는다 |
| 위치 우선순위 | 이번 요청에 말한 지역 → 지도 영역 → 이전 요청의 지역 → 위치로 거르지 않음 순서다(2026-11-02. 1차는 지도 영역 → 요청문의 역). 지도 영역은 지금 FE가 "이 지역에서 검색"을 눌렀거나 위치를 얻지 못했을 때만 보낸다(검색 spec 39·41번). 근처 검색은 따로 둔다(10-28) |
| 공유 모듈 | 39의 `fit_ai.features`, `fit_ai.embedding`(arctic-ko, 리비전 `55ec6e9`), `fit_ai.gms`를 쓴다(10-27) |
| 취향의 쓰임 | 후보를 찾는 데는 쓰지 않고 정렬과 카드에만 쓴다(39 spec 5단계, PRD FR-08) |
| 취향 전달 | 회원은 BE가 로그인으로 확인한 회원 id(`userId`)를 검색 요청에 넣고, AI가 `user_preferences`에서 직접 읽는다. 비회원은 기기가 저장한 취향을 검색 요청(`tasteProfile`)에 실어 보낸다(10-28, 39 spec, PRD FR-07). 비회원 취향은 기기가 저장한 온보딩 답이고, AI가 취향 프로필 계산 API와 같은 계산으로 `features`를 만든 뒤 회원과 같은 함수(`TasteProfile.from_stored`)로 읽는다(10-30) |
| 점수 방식 | 조각마다 조건 점수(리뷰 근거는 업종 범위 안 위치, 시설·음식 종류는 장소 정보)를 내고, 요청은 기하평균, 취향은 가중 평균으로 낸 뒤 0.7 : 0.3으로 합친다(2026-11-03, 4.3). 1차는 맞음 등급 구간 안의 순위였다(10-26) |

## 3. 전체 흐름

장소 프로필은 40이 미리 만들어 Postgres에 넣는다. AI는 BE 장소 정보와 40 프로필을 합친 뷰 `ai_place_search`를 읽는다. 이 뷰는 실제 DB가 없을 때 쓰는 임시 모양이고, 실제 DB는 저장 설계(`docs/specs/profile-storage/spec.md`, V6)의 `places`(장소 정보: 업종, 역, 좌표, 시설), `place_profiles`(요약, 특징별 리뷰 수), `place_personas`로 다시 맞춘다. 회원 취향은 AI가 `user_preferences`에서 읽고, 비회원 취향은 BE가 검색 요청에 실어 보낸다.

일반 검색(예: "역삼역 모임하기 좋은 술집")은 이렇게 흐른다.

```
[BE]   요청문, 이전 조건, 지도 영역, 취향 프로필을 AI에 넘긴다 (/v1/search 한 번)
[41]   요청 해석      역삼역, 술집, 모임 → 조건                 GMS 1번
       요청문 인코딩  embeddingText → 벡터                     fit_ai.embedding
       후보 추출      업종·지역·시설·시간·가격·메뉴로 거르고 가까운 100곳  SQL 1번(pgvector)
       점수           조건 점수 → 핏 점수 → 점수순 20곳         규칙
       카드 만들기    이유, 근거 항목, 라벨                     규칙
[BE]   카드에 장소 정보와 영업 상태를 붙여 FE에 넘긴다
```

근처 검색(예: "근처 조용한 카페")은 역으로 거르지 않고 100곳을 모두 돌려준다. 기기 위치를 서버로 보내지 않으므로 FE가 반경 안만 남긴다.

```
[41]   요청 해석      근처, 카페
       후보 추출      지역 없이 업종·시설·시간·가격·메뉴로 거르고 가까운 100곳
       점수           일반 검색과 같다
       카드 만들기    일반 검색과 같다
[FE]   폰의 현재 위치로 반경 안만 남긴다
```

LLM이 실패하면 해석은 낱말 규칙으로 한다. 점수는 LLM을 쓰지 않아 그대로다. 뽑힌 장소가 없으면 결과 없음 이유를 돌려준다. 단계마다 무엇이 실패하면 어떻게 되는지는 [api.md](api.md) 2장(`fallbacks`)과 4장(오류)에 있다.

## 4. 단계별 구성

### 4.1 요청 해석 (`match/interpretation/`)

요청문과, 후속 조건이면 이전 조건(FE가 돌려보낸 `conditions`)을 받아 조건을 낸다. LLM 해석과 규칙 해석 모두 이번 요청만 해석하고, 후속이면 이전 조건과 분류별 규칙으로 합친다. 해석 결과는 합친 조건과 이번 요청만의 조건(`Interpretation.turn`)을 같이 낸다. 조건은 BE와 FE에 불투명한 객체다. 3차 모양으로 바꾼 까닭과 합치기 규칙은 [conditions-v3.md](conditions-v3.md)에 있다(2026-11-04). 코드는 하는 일별로 나눴다. `segments`(조각 타입), `codes`(분류와 점수용 코드 잇기), `request`(조건과 같이 쓰는 함수), `merge`(이전 조건과 합치기), `rules`(규칙 해석), `checks`(코드 확인), `llm`(프롬프트와 출력 읽기)이고, 밖에서는 `fit_ai.match.interpretation`이 내보내는 이름만 쓴다.

| 조건 | 내용 |
| --- | --- |
| `version` | 조건 모양 판. 3이다. 없으면 2차 이전 조건으로 읽는다 |
| `text` | 해석한 요청문. 새 검색이면 요청문 그대로, 후속이면 이전 요청문 뒤에 이번 요청을 붙인 문장 |
| `embeddingText` | 후보 추출에 쓸 긍정형 문장. "시끄러운 곳 말고"는 "조용한 곳"이 된다. 벡터 검색은 부정을 알아듣지 못해서다. 역 이름과 "근처" 같은 위치 말은 코드로 지운다(10-28). 위치는 거르기가 맡고, 벡터에 남으면 이름이나 요약에 역 이름이 든 장소가 요청과 상관없이 올라간다. 지우고 남는 게 없으면 업종 이름을 쓴다 |
| `categories` | 업종 `[{code, want}]`(`RESTAURANT`, `CAFE`, `BAR`). 원함은 하나까지다. "카페 말고"는 `CAFE`의 피함이다 |
| `foodTypes` | 음식 종류 `[{code, want}]`(`FOOD_KOREAN` 등 5개). "한식", "일식집", "베트남 음식"처럼 음식 종류를 말했을 때만 넣는다. 메뉴("라멘", "돈가스")로 음식 종류를 짐작해 넣지 않는다(2026-11-03). "일식 말고"는 피함이다 |
| `flavors` | 맛 `[{code, want}]`. 지금은 매운맛(`SPICY`)뿐이다. 점수 코드표에서는 `FOOD_SPICY`다 |
| `menus` | 메뉴 `[{text, value, spellings, want}]`. 먹고 마시는 것은 모두 여기다(돈가스, 와인, 커피, 디카페인 포함). 음식 종류와 매운맛은 메뉴가 아니다. `spellings`는 메뉴판에 흔히 쓰는 같은 메뉴의 다른 표기다("돈가스"면 "돈까스", "돈카츠", 3개까지). 피하는 메뉴("오이 빼고")는 `want`가 거짓이다 |
| `features` | 특징 `[{text, value, code}]`. `code`는 39 코드표의 성향 축·중요 기준·방문 목적 코드이고 코드표에 없는 특징(콘센트, 반려견, 아이 동반, 룸)이면 null이다. 원함만 받는다 |
| `facilities` | 시설 코드(`PARKING`, `WIFI`, `GROUP`, `RESERVATION`). 원함만 받는다 |
| `partySize` | 인원. 점수에서는 1명이면 `PURPOSE_SOLO`, 4명 이상이면 `PURPOSE_GROUP`(임시)이다 |
| `locations` | 지역 `[{text, kind, value, walkMinutes, exit}]`. 여럿이면("강남역이나 역삼역") 그중 하나에 들면 된다. `kind`는 `STATION`(역), `AREA`(동네·거리·랜드마크), `HERE`(근처, 여기), `UNKNOWN`(회사 근처)이다. `walkMinutes`는 "걸어서 5분", `exit`는 "11번 출구"다. 서비스 역(`Conditions.station`)과 근처 검색 여부(`nearby`, 서비스 역 없이 `HERE`)는 지역에서 계산한다 |
| `hours` | 시간 `[{text, day, openUntil, openFrom, now}]`. "늦게까지"는 23:00, "새벽까지"는 02:00까지 여는 곳이다 |
| `price` | 가격 `{text, minWon, maxWon, cheap}`. "저렴한", "비싸지 않은"은 `cheap`이다. "가성비"는 가격이 아니라 특징 `VALUE_FOR_MONEY`다 |
| `placeName` | 가게 이름 `{text, value}`. "○○ 같은 곳"은 가게 이름이 아니다 |

점수와 취향 고르기가 쓰는 코드 목록(`Conditions.codes`)은 특징 코드, 원하는 음식 종류, 원하는 맛, 시설, 인원 순서로 만든다(`interpretation/codes.py`). 2차 이전 조건(`codes`, `categoryGroup`, `station`, `nearby`, `avoidCategories`, `avoidFoods`)도 읽어서 이 모양으로 바꾼다. BE가 검색 대화에 저장해 둔 조건이 후속 조건으로 돌아오기 때문이다.

`locations`부터 뒤는 분류별 조각이다(2026-11-02, 요청을 업종·지역·메뉴·음식 종류·시간·가격·가게 이름·특징·기타로 나눈다. 메뉴와 음식 종류는 2026-11-03에 나눴다). 조각마다 사용자가 쓴 말(`text`)과 LLM이 철자를 고치고 표준 이름으로 바꾼 값(`value`, "션릉역" → "선릉역", "스벅" → "스타벅스")을 같이 둔다. 표준 이름을 사전과 맞춰 보는 일은 그 조각을 쓰는 곳(지역 사전, 가게 이름 찾기)이 한다. 지역과 가게 이름에서 고친 말은 `Conditions.corrections`로 꺼낼 수 있다. 1차에 만든 이전 조건에는 조각이 없으므로 모두 기본값이 있고, 역과 근처는 지역 조각으로 바꿔 읽는다. 지역 조각으로 거르는 법은 4.2에 있다.

피하는 것은 업종, 음식 종류, 맛, 메뉴에만 항목마다 `want`로 둔다(2026-11-04). 그 밖의 부정은 1차처럼 바라는 쪽 코드로 바꾼다("시끄러운 곳 말고" → `QUIET`). 처음에는 모든 코드에 피하는 칸을 두었는데, LLM이 "웨이팅 긴 데는 싫어"를 짧은 대기를 피함으로, "매운 거 먹고 싶다"를 매운 음식을 피함으로 넣어 뜻이 뒤집혔다(2026-11-02 평가). 그래서 특징과 시설에는 피함을 두지 않는다. 요청에 피하는 말이 없으면 피함을 원함으로 되돌리는 규칙은 그대로다.

메뉴에 음식 종류 코드를 붙이던 것(1차, "라멘" → `FOOD_JAPANESE`)은 메뉴 판정이 없던 때의 대신이었다. 같은 "돈까스"가 질의마다 일식이 되기도 한식이 되기도 했고, 그 코드만 점수에 들어가 "역삼역 돈까스 맛집"의 1~10위가 돈까스를 팔지 않는 고기집(모두 100점)이었다(2026-11-03, 원본 300곳). 메뉴는 메뉴판으로 거르고(4.2), 음식 종류 코드는 음식 종류를 말했을 때만 둔다. 취향 분석도 메뉴 이름을 음식 종류 코드로 바꾸지 않는다.

LLM 해석은 이렇게 한다.

- GMS(`gpt-4o-mini`)를 공유 모듈 `fit_ai.gms`로 한 번 부른다. 공유 모듈은 호출이 실패하거나 JSON이 아니면 한 번 다시 부른다. 아래 출력 검사에 걸리면 다시 부르지 않는다.
- 프롬프트 규칙: 음식 종류·식사 메뉴와 "맛집"·"밥집"은 식당, 술 마시는 곳과 술 메뉴(하이볼, 와인)는 술집, 커피·음료·디저트 메뉴(케이크, 빙수)는 카페로 본다(디저트·술 메뉴는 2026-11-03). 벡터용 문장은 "~을 찾고 있어요" 없이 긍정형 검색어로, 리뷰에서 실제로 쓰는 말로 쓰게 한다("오래 기다리는 데 싫어" → "웨이팅 없이 바로 들어가는 곳"). 메뉴에는 음식 코드를 붙이지 않고 다른 표기를 같이 낸다. 부정한 조건은 바라는 쪽 코드로 넣고, 음식 종류·매운맛과 메뉴만 피함으로 둔다. 요청에 없는 코드는 넣지 않는다("식당"만 보고 `FOOD_KOREAN`, "모임"만 보고 시설 `GROUP`을 넣지 않는다). 분류별 조각의 꼴과 표준 이름 규칙을 적고, 평가 질의와 겹치지 않는 예시 9개를 넣었다.
- 출력은 이번 요청의 분류별 조각이다(2026-11-04, [conditions-v3.md](conditions-v3.md)). 업종·음식 종류·맛은 `{code, want}` 항목, 특징은 `{text, value, code}`(특징 코드표의 코드나 null), 시설은 코드 목록, 인원은 숫자다. 칸마다 고를 수 있는 코드만 보여 준다(특징 코드표에는 성향 축·중요 기준·방문 목적만).
- 이전 조건은 3차 조건 모양 그대로 보여 주되(벡터용 문장은 빼고) 뜻을 알아듣는 데만 쓰게 하고, 출력에는 새 요청에서 말한 것만 넣게 한다. 칸 이름이 다르면 LLM이 이전 역을 잇지 못했다(2026-11-02, 후속 12번 중 10번).
- 출력 검사: 모르는 코드는 버리고 모르는 업종·역은 null로 본다. 분류별 조각은 꼴이 틀린 조각만 버린다(틀린 시각 "25:00", 하한이 상한보다 큰 가격, 60분이 넘는 도보 거리 등). 지역 없이 1차 꼴(`station`, `nearby`)로 내면 지역 조각으로 바꾼다. 벡터용 문장에 글자가 없으면("...") 요청문으로 대신하고, 동네·랜드마크 원문은 지운다. 2차 꼴(`codes`, `category_group`, `avoid_foods`)로 내도 읽는다. JSON 객체가 아니거나 벡터용 문장이 문자열이 아니거나 `codes`, `nearby`의 타입이 틀리면 실패다.
- 코드 확인: LLM이 놓치거나 잘못 넣은 조각을 규칙 해석으로 바로잡는다. 규칙으로 확실히 잡히는 것만 고친다.
  - 후속에서 이전 조건을 다시 적은 조각: 원문이 이번 요청에 없는 지역·메뉴·특징·시간은 버린다. 합칠 때 이전 조건에서 다시 온다.
  - 지역: 이번 요청에 근처 말만 있으면 근처다. LLM이 지역을 비우면 규칙이 찾은 지역이다. 요청에 없는 근처 말로 낸 근처는 버린다("지금 열려 있는 카페", 2026-11-04).
  - 시설·인원: LLM이 놓친 시설을 규칙 값으로 더하고("주차되는"을 코드 없는 특징으로 냈다), 그 시설을 말한 코드 없는 특징은 뗀다. 인원은 규칙이 찾았으면 규칙 값이다.
  - 메뉴·특징: LLM이 놓친 것을 규칙 값으로 더한다. 이번 요청에 피하는 말("말고", "빼고", "싫어", "않은" 등)이 없으면 이번 요청의 메뉴를 원함으로 되돌린다.
  - 음식 종류·매운맛: LLM이 놓친 코드와 빼 달라는 음식을 규칙 값으로 더한다. 음식 종류나 나라를 말한 낱말("일식", "중국", "베트남" 등)이 없는데 LLM이 낸 음식 종류 코드는 뗀다. gpt-4o-mini는 메뉴에 코드를 붙이지 말라고 해도 "초밥"·"스시"에 일식, "쌀국수"에 아시아 음식을 붙였다(2026-11-03 평가, 6/160). 피하는 말이 없으면 빼 달라는 음식은 그 낱말이 요청에 있을 때 원함으로 되돌리고 없으면 버린다.
  - 시간·가격: 이번 요청에서 규칙이 찾았으면 규칙 값을 쓴다. 꼴이 정해진 말이라 규칙이 정확하다.
  - 가성비: 싼 곳을 찾는데 "가성비", "가격 대비" 같은 말이 없으면 `VALUE_FOR_MONEY`를 뗀다.
  - 업종: LLM이 비우면 규칙 값을 쓴다.
  - 빼 달라는 업종: 음식이나 메뉴를 빼 달라는 요청이면 요청에 이름("식당", "카페" 등)이 없는 업종은 LLM이 냈어도 뗀다. "강남역 일식 말고"에서 식당 전체가 빠졌다(2026-11-03).
- 후속이면 이번 요청의 조각을 이전 조건과 규칙 해석과 같은 규칙으로 합친다([conditions-v3.md](conditions-v3.md) 4장). 합친 요청문은 이전 요청문 뒤에 이번 요청을 붙인 것이다. "A 말고 B"는 A를 피함, B를 원함으로 내게 한다. 이번 요청이 "말고"로 빼거나 반대 극을 바란 이전 코드는 지운다("카페 말고 술집으로"에서 이전의 조용함은 남는다). LLM이 이전 벡터용 문장을 다시 쓰면(낱말 70% 이상이 이전 문장에 있으면) 이번 요청문으로 대신한다. 원하는 업종이 바뀌면 이전 메뉴는 버린다("초밥집"에서 "술집으로"). 바뀐 점(`changeSummary`)은 LLM이 쓴 한 문장이고, 없거나 60자를 넘으면 "요청하신 조건을 반영했어요"를 쓴다.

LLM이 꺼져 있거나 실패하면 낱말 사전으로 해석한다. "조용" → `QUIET`처럼 낱말이 들어 있는지만 본다. 업종과 역은 처음 나온 낱말로 정하되 "카페 말고"처럼 빼 달라는 말 앞의 것은 고르지 않고 빼 달라는 업종으로 둔다. 빼 달라는 업종은 업종 이름(카페, 술집, 식당, 밥집, 음식점)으로만 찾는다. "일식 말고", "포차 말고"는 업종 전체를 빼지 않는다(2026-11-03). 음식 낱말은 식당이다. 지역은 서비스 역(여러 개), 역 이름과 같은 동, 근처, 도보 거리("걸어서 5분"), 출구("11번 출구", 바로 앞의 역에 붙임)를 찾는다. 메뉴("스시" → "초밥"), 코드표에 없는 특징("충전" → "콘센트"), 시간("새벽까지", "일요일"), 가격("1만5천원 이하", "2만원대", "저렴")도 낱말과 꼴로 찾는다. "말고", "빼고", "싫어", "없는", "않은" 앞의 성향 축은 반대 극("북적이는 데 말고" → `QUIET`)으로, 음식·메뉴·업종은 피함으로 둔다("매운 건 싫어", "고기 없는", "카페 싫고"). 묻는 말("조용한 카페 없을까?")은 부정이 아니다. 부정한 말은 그 낱말 하나이고, 그 낱말이 "거", "데", "음식"처럼 뜻을 앞 낱말이 정하는 말이거나 메뉴이거나 앞 낱말과 묶였으면("일식이나 중식") 앞 낱말까지다. 반대 극이 없는 코드를 부정하면 버린다("데이트 말고"). "웨이팅"은 부정하면 짧은 대기다. 벡터용 문장에서는 부정한 말을 지운다(2026-11-04). 가게 이름, 다른 동네·랜드마크, 철자 교정은 못 한다. 후속이면 이번 요청만 해석하고 이전 조건과 분류별 규칙으로 합친다([conditions-v3.md](conditions-v3.md) 4장).

뽑힌 장소가 없으면 조건으로 만든 템플릿으로 이유를 준다. 예: "역삼역 술집 중 주차할 수 있는 곳이 없어요" / "주차 조건을 빼고 다시 찾아 보세요". 지도 영역이면 "이 지역", 지역이 여럿이면 "강남역 11번 출구·역삼역 도보 5분", 시설이 여러 개면 "요청한 시설을 모두 갖춘 곳이 없어요"로 바뀐다. 메뉴로 걸렀으면 시설보다 먼저 "강남역 식당 중 돈까스를 파는 곳이 없어요"(메뉴가 여럿이면 "삼겹살·냉면을 모두 파는 곳이 없어요") / "메뉴를 바꾸거나 빼고 다시 찾아 보세요"다(2026-11-03). 시설이 없고 영업시간으로 걸렀으면 "요청한 시간에 여는 곳이 없어요" / "영업시간 조건을 빼고 다시 찾아 보세요", 가격으로 걸렀으면 "요청한 가격대인 곳이 없어요" / "가격 조건을 빼고 다시 찾아 보세요"다. 거른 역·동·구에 장소가 하나도 없거나 랜드마크만 말했으면 "코엑스는 아직 준비 중인 지역이에요" / "강남역, 역삼역, 선릉역 근처에서 찾아 보세요"다(2026-11-02).

확인한 것(10-27, 실제 GMS): 유형별 질의 54개를 두 번씩 쟀다. 전부 맞음이 87%에서 98%로 올랐고 마지막 결과(v6)는 108번 중 106번이다. 벡터용 문장이 "..."로 나오는 일은 216번 중 12번(v4)에서 0번, 문장형으로 끝나는 일은 108번 중 41번(v5)에서 2번으로 줄었다. 평균 1.6초다. 규칙 해석은 87%다.

확인한 것(2026-11-02, 실제 GMS): 질의를 80개로 늘려 두 번씩 쟀다. 분류만 더한 프롬프트는 1차와 기대 답이 같은 47개에서 94번 중 77번만 맞혔다(1차 94번). 코드 확인을 더하니 `gpt-4o-mini`는 전체 160번 중 148번(1차 질의 90번), `gpt-4.1`은 160번 모두 맞혔고 평균 1.3초였다. 자세한 것은 `experiments/interpretation/README.md`에 있다. 해석 모델을 `gpt-4.1`로 바꾸려면 공유 모듈 `fit_ai.gms`가 모델을 고르게 해야 한다(지금은 `gpt-4o-mini` 고정).

남은 문제:

- "매운 거 말고 담백한 국물 요리"처럼 부정과 코드 밖 표현이 섞이면 엉뚱한 코드(`PURPOSE_TALK`)가 붙을 때가 있다.
- 코드표로 못 잡는 표현(와인, 디저트, 늦게까지, 반려견, 콘센트, 국물)은 벡터용 문장에만 남는다. 후보 추출에는 들어가지만 점수와 카드에서는 빠진다. 리뷰 문장에서 세어 점수에 넣는 일은 2차에 한다.
- 음식 종류 코드는 거르지 않고 점수에 쓴다(4.3). 장소의 음식 종류는 뷰의 `food_type`이다.
- 이번 요청만 분류별로 내게 바꾼 뒤(2026-11-04) 해석 질의 80개×2는 LLM 해석 156/160이다(전 149/160). 빠뜨리던 "인테리어 예쁜 카페", "뷰 좋은 루프탑 바", "주차되는 식당", "빨리 먹고 나올 수 있는"의 코드와 "회사 근처 점심"의 업종을 맞혔다. 남은 것은 "코엑스 근처 일식"에서 코엑스를 빠뜨리는 것(2번)과 "지금 열려 있는 카페"에 근처를 지어 낸 것(2번, 그 뒤 코드 확인으로 막고 2번 다시 재서 맞았다)이다. 평균 1.86초로 0.17초 늘었다.
- 평가 기대 답은 41이 정한 초안이라 팀 확인이 필요하다. 평가 질의로 프롬프트를 고쳐서 여기에만 맞춰졌을 수 있으니 새 질의로 다시 잰다.

### 4.2 후보 추출 (`match/candidates.py`, `match/pg_store.py`, `match/search.py`, `match/place.py`)

AI가 뷰 `ai_place_search`를 SQL 한 번으로 읽어 거르고 뽑는다. 뷰의 컬럼은 로컬 개발 DB(`scripts/dev_db.py`의 `SCHEMA_SQL`)에 있다. 검색 2차 컬럼은 BE 마이그레이션 V17~V19가 V12 뷰 뒤에 붙인다(`CREATE OR REPLACE VIEW`라 AI 계정 권한이 남는다, 2026-11-03). AI가 지금 읽는 것은 `dong`, `district`(`places`), `subways`(`place_subways`를 장소마다 모은 `[{station, exit, walk_minutes}]`), `hours`(`place_hours`를 모은 `[{day, open, close, closed, breaks}]`), `price`(가게 가격), `food_type`(음식 종류), `analyzed_review_count`(장소 분석이 읽은 리뷰 수, V18), 메뉴 거르기에 쓰는 `name`(가게 이름), `menus`(`place_menus`를 모은 `[{name, category, price, representative}]`), `category`(네이버 업종 이름, V19)다. 같이 더한 `pet_allowed`, `parking_free`, `corkage_allowed`는 특징 판정에 쓸 컬럼이고 아직 읽지 않는다. `price`는 리뷰 메뉴로 계산하는 값이라 장소 분석 적재가 채우기 전까지 NULL(모름)이다. V17~V19가 들어가기 전에 이 코드를 배포하면 검색이 SQL 오류(503)가 된다. 점수 기준을 만들려고 장소 전체도 읽는다(`PlaceStore.places`, 4.3). Postgres 저장소는 읽은 것을 5분 동안 다시 쓴다. 실제 장소 DB가 생기기 전에는 같은 행을 담은 JSON 파일(`PLACES_FILE`, 예시는 `samples/place/mock.json`의 BE Mock 장소)을 `match/json_store.py`가 같은 규칙으로 읽는다. 검색 흐름은 장소 저장소 인터페이스(`PlaceStore`)만 알아서 어느 쪽이든 그대로다.

거르기 규칙:

- 업종이 있으면 같은 업종만 남기고, 빼 달라는 업종("카페 말고")은 뺀다.
- 지역은 이번 요청에 말한 지역, 지도 영역(`mapBounds`, "이 지역에서 검색"), 이전 요청의 지역 순서로 하나를 고른다(2026-11-02). 이번 요청에 말한 지역은 이번 요청만 해석한 조건(`Interpretation.turn`)의 지역이다. 전에는 이전 지역에 없거나 원문이 요청문에 있는지로 짐작해서, 이전 지역 이름이 다른 말에 섞이면("강남구청") 다시 말한 것으로 봤다(2026-11-04에 고침). "회사 근처"처럼 어딘지 모르는 곳은 말하지 않은 것으로 본다.
- 지역이 여럿이면 그중 하나에 들면 남긴다(`match/candidates.py`의 `StationArea`, `RegionArea`).
  - 역: 도보 거리와 출구가 없으면 수집 역(`station`)이 같거나 가까운 역 목록(`subways`)에 그 역이 있는 곳이다. 원본 300곳 중 50곳은 수집 역이 가까운 역 목록에 없어서(강남에서 수집한 28곳은 가장 가까운 역이 신논현역) 둘 다 본다. 도보 거리("걸어서 5분")나 출구("11번 출구")가 있으면 가까운 역 목록만 보고, 도보 분을 모르는 곳은 뺀다. 서비스 역이 아닌 역(신논현역 등)도 가까운 역 목록으로 찾는다.
  - 동·구: 동(`dong`)이나 구(`district`)가 같은 곳이다. 행정동("역삼1동")은 법정동("역삼동")으로 찾는다. 동 정보가 없는 장소는 이름이 같은 서비스 역("역삼동"이면 역삼역)의 장소로 본다.
  - 근처("여기"): 지도 영역이 있으면 지도 영역이고, 없으면 위치로 거르지 않고 FE가 현재 위치로 거른다.
  - 그 밖의 동네·랜드마크(가로수길, 코엑스): 장소 데이터에 없어 거르지 않는다. 그것만 말했으면 찾지 않고 준비 중인 지역이라고 한다(4.1). 랜드마크 좌표 사전은 아직 없다.
- 결과가 없으면 거른 역·동·구마다 장소가 있는지 한 곳씩 더 찾아본다. 모두 없으면 준비 중인 지역이라고 한다.
- 요청에 시설(`PARKING` 등)이 있으면 그 시설이 없다고 확인된 장소만 뺀다. 시설 정보가 없는 장소(모름)는 남긴다. 장소 정보의 시설이 덜 채워졌을 수 있어서다.
- 영업시간은 요청한 요일 중 하루라도 안 맞는다고 확인되지 않은 곳을 남긴다(`OpenHours`, 2026-11-03). 그 요일에 쉬거나, 닫는 시각이 요청보다 이르거나, 여는 시각이 요청보다 늦으면 그 요일은 안 맞는다. 요일이 없으면 아무 요일이나 되고, 영업시간을 모르는 요일은 남긴다. 시간 조각이 나뉘어 와도 하나로 합친다("일요일"과 "새벽까지"는 일요일 새벽 2시까지). 6시 전으로 끝나는 요청("새벽 2시까지")은 다음 날이고, 닫는 시각이 여는 시각보다 이르면 다음 날 닫는다. 두 시각이 같으면 24시간 영업이다. "지금 영업 중"은 거르지 않는다. 검색 시각이 필요하고 BE가 카드에 영업 상태를 붙인다.
- 가격은 가게 가격(`match/price.py`)이 요청 범위를 여유 10% 넘게 벗어난 곳만 뺀다("2만원 이하"면 22,000원 초과, "2만원대"면 18,000원 미만이나 32,999원 초과). 가게 가격을 모르면 남긴다. 가게 가격은 대표 메뉴(없으면 전체 메뉴) 중 리뷰 언급 메뉴로 가중한 가격 중앙값이고, 맞춘 메뉴가 없으면 그 메뉴들의 중앙값이다(2026-11-02, 대표 메뉴 안에서만 맞추기는 2026-11-03). 리뷰 메뉴는 괄호·숫자 표기를 뗀 메뉴 이름이 그 말로 끝나거나 그 말 바로 뒤에 요리 방식·양을 뜻하는 말("전골", "모둠", "반마리" 등)이 올 때 맞춘다. "고기"는 "고기듬뿍 김치찌개"와 맞지 않는다. 원본 300곳 중 284곳에 정해지고 업종별 중앙값은 식당 21,000원, 술집 25,000원, 카페 5,550원이다(2026-11-03). 여유 폭은 시작값이다. "저렴한"은 거르지 않는다(같은 업종 하위 1/3 점수로 쓸 예정). 메뉴와 같이 온 가격("2만원대 파스타")도 아직 가게 가격으로 견준다.
- 메뉴는 그 메뉴를 판다고 확인된 곳만 남긴다(`PlaceFilter.menus`, 2026-11-03). 원하는 메뉴마다 사용자 말, 표준 이름, 다른 표기 중 하나가 메뉴판의 메뉴 이름, 네이버 업종 이름(`category`), 가게 이름에 들어 있어야 한다. 띄어쓰기와 기호를 지우고 영문은 소문자로 바꿔 견준다(`candidates.menu_key`, "[대표] 등심 돈까스(200g)"는 "대표등심돈까스200g"). 메뉴가 여럿이면("삼겹살이랑 냉면") 모두 있어야 한다. 메뉴판이 없는 곳도 업종 이름과 가게 이름으로 본다. 시간·가격과 달리 모르면 빼는 셈인데, 아무 가게나 그 메뉴를 팔 가능성은 낮아서다. 남는 곳이 없으면 결과도 비운다. 원본 300곳에서 "강남역 돈까스"는 0곳("강남역 식당 중 돈까스를 파는 곳이 없어요"), "역삼역 돈까스 맛집"은 "안주 돈까스"가 있는 1곳이다.
  - 넓은 말(커피, 음료, 술, 맥주, 와인, 칵테일, 디저트, 빵, 브런치, 고기, 해산물, 면, 국물 요리, 음식 종류 이름 등, `search.BROAD_MENUS`)과 피하는 메뉴로는 거르지 않는다. 넓은 말은 메뉴판에 그 이름이 잘 오르지 않는다. 원본에서 커피 메뉴가 있는 카페 60곳 중 메뉴 이름에 "커피"가 든 곳은 14곳, "선릉역 디저트 카페" 32곳 중 메뉴 이름에 "디저트"가 든 곳은 0곳이었다. 넓은 말과 메뉴를 잇는 사전은 보류했다(2026-11-03). 그때까지 업종과 요청문 유사도로만 찾는다.
  - "된소리를 예사소리로"(돈까스 = 돈가스) 같은 글자 바꾸기는 하지 않는다. "짬뽕"이 "잠봉"과 맞았다. 다른 표기는 LLM이 낸다.
- `profile.embedding`의 모델·리비전이 요청문 인코더와 같고 `prompt`가 `document`인 장소만 비교한다. 다른 장소는 빠진다. 모든 장소가 그러면 `/healthz`가 503 `MODEL_MISMATCH`, 일부만 그러면 200에 로그 경고다.

남은 장소 중 `embeddingText`를 질의 쪽(`query: ` 붙임)으로 인코딩한 벡터와 요약 벡터의 코사인 유사도가 높은 100곳을 뽑는다. 조건은 맞는데 요약이 덜 비슷한 곳이 점수를 받기 전에 잘리지 않게 넉넉히 뽑는다. 계산은 pgvector `<=>`가 하고, 장소가 300곳 남짓이라 인덱스 없이 전부 계산한다. 요약 벡터는 가져오지 않는다. 이 단계에서 취향은 쓰지 않는다.

장소 프로필은 이렇게 읽는다.

| 40 필드 | 쓰는 곳 |
| --- | --- |
| `summary.text` | 읽기만 한다(1차에는 정렬 LLM 입력이었다) |
| `features`의 `like_count`, `dislike_count` | 조건 점수(그렇다는 리뷰 수), 카드 라벨 |
| `summary.vector`(뷰의 `summary_vector`), `embedding` | DB 안의 유사도 계산과 모델 확인 |

- `schema`가 `place-profile/v0`이 아니거나 `summary.text`가 없으면 그 장소만 빼고 응답 `fallbacks`에 `PROFILE_INVALID`를 담는다.
- 프로필에 없는 조건은 근거 0(모름)으로 본다.
- 소음 축은 바꿔 읽는다(임시). 40은 손님이 느낀 쪽을 코드로, 좋았는지를 방향으로 적는다("너무 썰렁했어요"는 `QUIET` 아쉬웠어요). 카드는 그 조건을 채웠는지로 세므로 느낀 쪽의 좋았어요·아쉬웠어요를 모두 긍정으로, 반대 극의 것을 부정으로 본다.
- 쓰지 않는 필드: `personas`(공개 뒤 취향 벡터 점수와 주의점용), `evidence`(앱 리뷰만 세기와 인용용, 공개 초기에는 앱 리뷰가 거의 없다), 40 프로필의 `food_type`(뷰의 `food_type`을 쓴다), `features[].label`(카드 라벨은 41 규칙으로 고른다), 40의 `place_id`(뷰의 BE 장소 id를 쓴다).

확인한 것: 임시 Postgres(pgserver, pgvector)에서 거르기, 유사도 순서, 모델 확인, 깨진 프로필을 실제 SQL로 테스트했다. 영업시간·가격은 두 저장소가 같은 예시로 같은 장소를 뽑는지 보고, BE 마이그레이션 V1~V17을 임시 Postgres에 적용해 AI 저장소로 뷰를 읽었다(11-03). V18까지 적용해 뷰 컬럼 순서를 확인했다(11-03). 메뉴는 두 저장소가 같은 예시로 같은 장소를 뽑는지 보고, V19까지 적용해 뷰 컬럼을 확인했으며, 원본 300곳으로 JSON 파일과 개발 DB의 메뉴 검색 14개가 같은 후보를 내는지 봤다(11-03). 로컬 개발 DB(BE Mock 장소 30곳)로 검색 여섯 가지를 처음부터 끝까지 돌렸다. DB 시간은 0.01초 미만이다.

정할 것: 소음 축 읽기, 카드 라벨에 40 `label`을 쓸지.

### 4.3 점수 (`match/scoring.py`, `match/taste_select.py`)

취향 프로필은 이렇게 쓴다. 회원 취향은 AI가 취향 저장소(`TasteStore`)에서 회원 id로 꺼낸다. 실제 DB는 저장 설계(`docs/specs/profile-storage/spec.md`)의 `user_preferences`에서 취향 분석이 계산해 둔 `features`와, 칩(`tastes`) 중 코드가 없는 것을 취향 문장으로 읽는다(`TasteProfile.from_stored`). 회원 취향은 계산하지 않는다. 비회원 취향은 검색 요청에 실린 온보딩 답으로 취향 프로필 계산 API와 같은 계산을 해서 `features`를 만들고 같은 함수로 읽는다(`server/search.py`). 칩 벡터는 회원 행처럼 코드 없는 좋아함 칩의 것만 쓴다. 회원 취향은 파일로 대신하지 않는다. 샘플 회원 id가 실제 회원 id와 겹칠 수 있어서다. DB 접속 주소가 없으면 회원 검색은 취향 없이 정렬하고 `TASTE_INVALID`를 담는다.

- `features`: 요청과 겹치는 취향을 뺀 뒤 점수에 넣는다(아래 3번). 요청과 같은 코드인 취향도 뺀다. 카드의 취향 근거 항목에는 좋아함만 넣는다. 싫어함은 점수에만 들어가고 화면 문구가 정해지면 넣는다(2026-11-03).
- `free_texts`: 지금은 쓰지 않는다. 1차에는 벡터가 있는 문장을 정렬 LLM에 넣었다. 리뷰 문장에서 세어 점수에 넣는 일은 2차에 한다.
- 읽지 못하거나(형식이 깨짐, 비회원 취향의 모양이 틀림, 취향 저장소가 없거나 장애) 취향 50개·문장 20개를 넘으면 취향 없이 정렬하고 `TASTE_INVALID`를 담는다. 회원인데 저장된 취향이 없는 것은 실패가 아니라서 담지 않는다.
- 쓰지 않는 필드: `evidence`(업종별 근거 고르기용, 공개 뒤), `embedding`(취향 벡터 점수를 미뤄서), `original_text`(39가 다시 해석할 때 쓰는 원문).

요청과 겹치는 취향은 묶음으로 뺀다(PRD AC-28, AC-30). 요청에 소음 조건이 있으면 소음 취향을, 목적이나 인원이 있으면 방문 목적 취향을, 음식 종류가 있거나 메뉴로 걸렀으면 음식 종류 취향을, 매운맛이 있으면 매운맛 취향을 좋아함·싫어함 모두 뺀다. 메뉴("라멘")는 음식 종류보다 구체적인 요청이라 음식 종류 취향을 뺀다. 메뉴에 음식 종류 코드를 붙이던 때와 같은 결과다. 음식 종류를 찾아도 매운맛 취향은 남긴다. 중요 기준(가성비 등)과 시설은 요청과 겹쳐도 남긴다.

| 취향 | 요청 A "역삼역 모임하기 좋은 술집" | 요청 B "강남역 조용한 카페" |
| --- | --- | --- |
| `QUIET` 좋아함, 가중치 3 | 씀 | 뺌(요청에 소음 조건) |
| `LIVELY` 싫어함, 가중치 3 | 씀 | 뺌(요청에 소음 조건) |
| `PURPOSE_WORK` 좋아함, 가중치 1 | 뺌(요청에 목적) | 씀 |
| `VALUE_FOR_MONEY` 좋아함, 가중치 2 | 씀 | 씀 |
| 취향 문장 "점심엔 담백한 국물 요리가 좋아요"(벡터 있음) | 씀 | 씀 |

점수는 이렇게 낸다(2026-11-03).

1. **조건 점수**: 요청 조각과 취향마다 0~1을 낸다. 판정하는 코드는 카드 조건 18개와 코드표의 확장 코드(음식 종류, 매운맛, 빨리 나옴, 음악, 독특한 컨셉)다.

| 조각 | 근거 | 조건 점수 |
| --- | --- | --- |
| 리뷰 코드("조용한") | 그렇다는 리뷰 수, 분석 리뷰 수 | 업종 범위 안 위치(2번) |
| 시설("와이파이") | 장소 정보 | 있음 1, 없음 0, 모르면 범위 안에서 있는 곳의 비율 |
| 음식 종류("양식") | `food_type` | 같으면 1, 다르면 0, 모르면 범위 안에서 음식 종류를 아는 곳 중 그 종류의 비율 |

2. **업종 범위 안 위치**:
   - 범위는 요청한 업종이다. 업종을 말하지 않았으면 빼 달라는 업종을 뺀 전체다. 업종마다 언급 비율이 크게 달라서(작업 언급: 카페 6.8%, 식당 0.5%) 업종별로만 견주면 "작업하기 좋은 곳"에서 식당 1등이 카페 1등을 이긴다.
   - 범위 안 장소들의 언급 수로 가상 리뷰 수를 정한다(베타-이항 모형, 평균은 범위 전체의 언급 비율, 가상 리뷰 수는 최대우도). 장소마다 보정 비율 = (언급 수 + a) ÷ (리뷰 수 + a + b)로 줄 세운다. 리뷰가 적을수록 범위 평균 쪽으로 당겨진다.
   - 장소 하나의 위치는 그 장소의 진짜 비율이 될 수 있는 값마다(사후분포) 범위 안 장소들보다 높을 확률을 평균 낸 값이다. 리뷰가 많으면 보정 비율의 위치와 거의 같고, 적으면 가운데(0.5)로 간다. 샘플 카페 19곳의 '조용해요'는 100건 중 17건 0.91, 100건 중 0건 0.09, 6건 중 0건 0.42였다.
   - 범위 안 어느 곳도 말하지 않은 코드와 분석 리뷰 수를 모르는 장소는 0.5다.
   - 견주는 대상은 그 검색의 후보가 아니라 범위 안 장소 전체(`PlaceStore.places`)다. 그래서 같은 장소, 같은 요청이면 늘 같은 점수다.
3. **핏 점수**: 요청 점수는 요청 조건 점수의 기하평균이다(모두 원함, 하한 0.01). 취향 점수는 취향 가중치(1~3)로 낸 평균이고 싫어함은 1 − 조건 점수다. 핏 점수 = 100 × (0.7 × 요청 + 0.3 × 취향)이고, 한쪽만 있으면 그쪽만 쓴다. 판정할 요청 조각도 취향도 없으면 점수가 없다(응답에서 빠진다).
4. **순서**: 뽑은 100곳 모두 점수를 내고 점수 내림차순, 같으면 유사도 순서다. 점수가 없으면 유사도 순서다. 일반 검색은 20곳, 근처 검색은 100곳까지 준다.

1차 정렬(체크표 등급과 LLMRank)은 `match/ranking.py`에 남기고 검색에서는 쓰지 않는다. 1위가 늘 100점이고, 같은 장소가 함께 나온 후보에 따라 다른 점수를 받고, 판정하지 못한 요청(음식 종류 등)과 취향이 점수에 없어서 바꿨다.

확인한 것(2026-11-03, 장소 분석 샘플 62곳과 1차 검색 290건에 새 점수를 적용):

- 1위 100점 269/289 → 3/285(음식 종류가 정확히 맞는 요청만), 같은 장소·같은 요청의 점수 차 최대 26 → 0, "파스타 맛집"에서 음식 종류가 다른 곳의 평균 93 → 14, "인테리어 예쁜 카페"의 85점 이상 100% → 2%, 65~84점 카드 0% → 15%
- "시끌벅적한 술집"(활기참)도 판정된다. 1위가 64점에서 83점이 됐다.
- 290건을 계산하는 데 0.5초 걸렸다(같은 기준을 다시 쓸 때).

남은 문제:

- 코드 없는 조각("콘센트")과 취향 문장은 점수에 들어가지 않는다. 리뷰 문장에서 세는 단계(2차)에서 넣는다.
- 근거 항목의 `matched` 기준(0.7)과 요청 대 취향 비율(0.7 : 0.3)은 시작값이다. 평가 세트로 다시 정한다.
- 업종을 섞을 때 업종별 네이버 키워드 목록 차이로 불리한 업종이 생기는지 장소 분석과 본다.
- 메뉴는 거르기로만 쓰고 점수에는 넣지 않는다. 메뉴만 말한 요청("역삼역 라멘")은 판정할 조각이 없어 점수 없이 유사도 순서다. 그 메뉴로 알려진 곳(리뷰 언급)을 위로 올리는 일은 점수를 고칠 때 한다.
- 업종 중간이 50점이라 점수가 낮아 보일 수 있다. 화면 표시(숫자, 말)는 BE·FE와 정한다.

### 4.4 카드 만들기 (`match/cards.py`)

카드는 LLM 없이 규칙으로 만든다. 화면의 숫자와 문장은 근거와 정확히 맞아야 하는데 LLM에 맡기면 그럴듯한 숫자를 지어내거나 외부 리뷰 문장을 옮길 수 있다(PRD AC-08, AC-25). 출력이 길어져 느려지는 것도 이유다. 카드에는 BE `PlaceCard`의 AI 필드만 담고, 장소 이름·좌표·사진·영업 상태는 BE가 채운다.

| 필드 | 규칙 |
| --- | --- |
| `score` | 핏 점수 그대로(4.3). 없으면 빠진다 |
| `scoreItems` | 점수를 낸 조각 그대로다. 요청 조각 먼저, 그다음 좋아하는 취향. 카드 조건 18개와 확장 코드(음식 종류 등)다. `matched`는 조건 점수 0.7 이상(리뷰는 범위 상위 30%, 장소 정보는 있음)일 때 true, `evidenceCount`는 그렇다는 리뷰 수(장소 정보로 판정하면 0)다 |
| `reasons` | `matched`인 항목마다 하나, 최대 3개. 리뷰로 판정하면 `리뷰에서 "조용해요"라는 말이 많아요`, 장소 정보로 판정하면 문구 그대로(`주차할 수 있어요`, `양식이에요`). 인용은 넣지 않는다 |
| `labels` | 그렇다가 아니다보다 많은 특징 중 근거가 충분한 것 먼저, 그렇다가 많은 순서로 2개. 모자라면 업종·역 이름으로 채운다 |
| `caution` | MVP는 넣지 않는다 |

목록은 `score` 내림차순(점수가 없으면 유사도 순서)이다. 일반 검색은 20개, 근처 검색은 100개까지 보내고 `nextCursor`는 없다.

남은 문제(비교가 고칠 것):

- 라벨이 검색 조건과 상관없이 정해진다. 요청 조건과 맞는 특징을 먼저 고르는 안이 있다.
- 근거가 부족한 특징(리뷰 1개)도 라벨이 될 수 있다.
- 시설 이유는 제목과 칩이 같은 말이다.

화면 문구처럼 BE·FE가 정할 것은 6장에 있다.

### 분석 담당(39·40)

- 41 코드를 39 구조(`fit_ai/match/`, `server/`)로 옮기고 공유 모듈을 쓰게 했다(10-27). 39 브랜치가 develop에 먼저 합쳐져야 41을 합칠 수 있다.
- `fit_ai.gms`: 실패하면 늘 한 번 더 불러서 검색 중 최악의 응답 시간이 두 배가 된다(한 번에 5초면 해석 10초). 검색에서는 바로 규칙이나 유사도로 넘어가므로 다시 부르지 않는 선택지, 토큰 수, 출력 토큰 상한을 요청한다. `GMS_BASE_URL`은 `…/gmsapi/api.openai.com/v1` 형식이다.
- 40은 장소 요약을 `fit_ai.embedding.encode_documents`로 인코딩한다. 요청문은 같은 모듈의 `encode_queries`라 모델·리비전이 맞는다. SSAFY GPU 서버(5번 GPU)와 로컬에서 만든 벡터가 같았다(코사인 1.000000).
- 40 프로필과 요약 벡터를 뷰 `ai_place_search`로 읽을 수 있게 Postgres에 넣는다. 40 샘플 프로필(15~20곳)이 오면 7장 4번 확인에 쓴다.
- 가게 가격(4.2): 적재 때 `match/price.py`의 `store_price`로 정제 CSV의 메뉴판(`menu_items.csv`)과 리뷰 메뉴(`place_review_menus.csv`)로 계산해 `place_profiles`에 숫자만 넣고, 뷰 `price`가 그 값을 읽게 한다(2026-11-03 제안). 리뷰 메뉴 목록은 장소 테이블에 넣지 않는다(place-catalog D-4). 첫 공개 뒤 적재 스크립트를 다시 돌리면 앱 리뷰 값이 첫 적재 값으로 돌아가므로 공개 뒤에는 가격만 따로 넣는다.
- 취향·장소 프로필의 필드 이름이나 `layer` 값을 바꿀 때는 `schema` 버전을 올린다.
- 요청문 인코딩을 서버 안 모델로 할지, 임베딩 Modal 앱(`fit-embed`)을 부를지 정한다. Modal에서는 `fit-embed`를 부르는 쪽이 맞아 보인다. 컨테이너마다 모델(2GB 남짓)을 올리지 않아도 된다.
- 음식 종류 요청 때 매운맛 취향을 남기는 해석(4.3)이 39 spec의 뜻과 맞는지

### BE·FE

- BE는 검색마다 `/v1/search`를 한 번 부르고 카드에 장소 정보와 영업 상태를 붙인다([api.md](api.md) 2장).
- 뷰 `ai_place_search`를 누가 만들지, 40 프로필의 갱신 주기, 40 `place_id`와 BE 장소 id를 잇는 방법
- 뷰 검색 2차 컬럼(4.2)은 AI 파트가 BE 마이그레이션 V17~V19로 더한다(2026-11-03). 규칙은 place-ai-search spec "AI가 읽는 뷰"이고 AI 검색 배포보다 먼저 들어가야 한다. 머지 전에 develop의 가장 높은 번호 다음인지 다시 본다.
- 검색이 503일 때 BE가 대신 보여 줄 것
- 정렬 LLM을 빼서(4.3) 응답의 `rankedBy`는 `SCORE`나 `SIMILARITY`이고 `RANK_LLM_FAILED`는 더 나오지 않는다. 지표 계약(`docs/infra/contracts/metrics.md`)은 검색마다 정렬을 reranker 호출로 세기로 했는데(BE는 아직 구현 전, place-ai-search D-1), 이제 그 호출이 없다. BE가 구현할 때 reranker는 세지 않도록 BE·인프라와 맞춘다.
- 판정할 요청 조각도 취향도 없으면 카드의 `score`가 빠진다. FE는 점수가 없으면 점수 영역을 그리지 않는다.
- 싫어하는 취향 근거 항목의 문구. 지금 FE 문구("취향을 확인할 근거가 부족해요")는 싫어함에 맞지 않아 그 항목을 보내지 않는다.
- 회원 취향은 BE가 로그인으로 확인한 `userId`를 보내고 AI가 `user_preferences`를 직접 읽기로 합의했다(10-28). BE는 검색 요청에서 로그인 정보(`auth.identity`)를 선택으로 읽어 회원이면 AI 요청에 넣는다. 비회원은 기기가 저장한 취향을 BE가 `tasteProfile`로 그대로 넘긴다(10-28). 모양은 기기가 저장한 온보딩 답이고 `features`는 AI가 계산한다(10-30, [api.md](api.md) 2장). 코드 없는 칩의 벡터는 온보딩 담당이 비회원 칩에도 붙이기로 했다(10-30). FE 저장 검사는 아직 칩의 `vector`를 받지 않아 바뀌어야 한다.
- 근거 항목 문구: 화면은 "앱 리뷰 n개가 근거예요"인데 41은 외부 리뷰까지 센다. 앱 리뷰는 공개 초기에 거의 없어서 앱 리뷰만 세면 모든 항목이 "근거 부족"이 된다. 셀 범위와 문구를 정한다.
- "점수에 넣지 않았어요" 문구는 점수 방식과 맞지 않는다. "근거가 부족해요"로 바꾸기를 요청한다.
- 시설 항목은 근거 리뷰 수가 0이라 "리뷰 0개가 근거예요"가 된다. 시설 항목 문구를 따로 둔다.
- 근거가 충분한 조건이 없으면 추천 이유가 비어 있다. 영역을 숨길지 문구를 보여 줄지 정한다.
- 라벨이 모자랄 때 채우는 업종 이름("카페")이 카드의 업종 표시와 겹친다.
- 결과가 20개에서 끝나는 것(`nextCursor` 없음)

- 로컬 개발 DB(`scripts/dev_db.py`, BE Mock 장소 30곳)로 새 검색, 후속, 근처, 코드 없는 표현, 결과 없음, 취향 포함을 처음부터 끝까지 돌렸다. 검색 한 번 1.2~3.6초
- 연동 전 점검(맥락 없는 별도 세션의 실제 서버 테스트 105건, 코드 리뷰)에서 나온 문제를 고쳤다(10-27). 벡터용 문장 `"..."`, 잘못된 입력·데이터로 생기던 500, 빈 지도 영역, 후속의 역·근처 충돌, 프롬프트 크기, 검색 시간 상한, 조건 없는 요청의 LLM 등급, 로그 형식이다

남은 순서:

1. `api.md`를 BE·40·인프라에 전달한다
2. Modal에 띄운다. 임베딩·직접 입력 해석·취향 프로필 MR과 합친 뒤 AI API Modal 배포 일감에서 한다
3. 39 샘플 사용자 7명으로 정렬을 확인한다. 40 샘플 프로필이 오면 질의 10개로 카드와 핏 점수가 나오는지 확인한다(Jira 완료 기준, 10-31)
4. 실제 DB 300곳으로 점수 기준(가상 리뷰 수, `matched` 기준, 요청 대 취향 비율)과 라벨 규칙을 다시 본다
5. BE 연동(11-02)

해석은 하지만 거르기와 점수에 아직 쓰지 않는 값(2026-11-03 점검). 요청 해석 구조를 다시 짜고(조건 분류, 피함 표현 통일) 버그를 고친 뒤 하나씩 잇는다.

| 값 | 요청 예 | 지금 | 이을 곳 |
| --- | --- | --- | --- |
| 빼 달라는 음식 종류·맛(`foodTypes`, `flavors`의 피함) | "매운 건 싫어", "일식 말고" | 원하는 코드에서 빼기만 한다. 매운 곳, 일식집이 그대로 나온다 | 점수. 싫어하는 취향처럼 1 − 조건 점수로 요청 점수에 넣는다 |
| 피하는 메뉴(`menus[].want`가 거짓) | "파스타 말고", "오이 빼고" | 메뉴 거르기에서 건너뛴다(`search.menu_terms`) | 거르기나 점수. 가게를 대표하는 메뉴(대표 메뉴, 업종 이름)면 빼고, 그 밖은 감점하는 안을 본다 |
| 넓은 메뉴(`search.BROAD_MENUS`) | "강남역 고기", "디저트 카페" | 업종만 정한다. 메뉴로 거르지 않고 메뉴로 거른 요청으로도 보지 않아 음식 종류 취향이 남는다 | 점수. 넓은 말과 메뉴를 잇는 사전이나 메뉴판 분류(`menus[].category`)로 그 메뉴군이 있는지 본다 |
| 메뉴만 말한 요청 | "역삼역 라멘" | 판정할 코드가 없어 점수 없이 유사도 순서다 | 점수. 그 메뉴로 알려진 곳(리뷰 언급, 대표 메뉴)을 위로 올린다 |
| 코드 없는 특징(`features[].code`가 null) | "콘센트 있는", "강아지랑" | 쓰지 않는다 | 리뷰 문장에서 세어 점수에 넣는 일(2차)과 장소 정보(`pet_allowed` 등) |
| 가게 이름(`placeName`) | "투썸 신논현" | 쓰지 않는다. 벡터용 문장에 이름이 남는 것뿐이다 | 거르기. 가게 이름(`name`)으로 찾는다 |
| 싼 곳(`price.cheap`) | "저렴한", "비싸지 않은" | 쓰지 않는다 | 점수. 같은 업종·지역 안에서 가게 가격(`price`)이 낮은 쪽을 높게 친다. 가격 적재가 먼저다 |
| 부정 리뷰 수(장소 프로필 `neg`) | "작업하기엔 불편해요" | 점수는 그렇다는 리뷰 수(`pos`)만 본다(`scoring.Baseline.value`) | 점수. 아니라는 리뷰를 조건 점수에 반영한다 |

공개 뒤에는 라벨링과 정량 평가(nDCG@10, Recall@20), 페르소나 후보 경로, 코드 없는 조각과 취향 문장 점수, 주의점, 업종별 근거 고르기를 다룬다. 위치는 AI 쪽 우선순위를 바꿨다(4.2, 2026-11-02). 남은 것은 FE가 검색마다 지도 영역을 보내고(검색 spec AC-16 재검토), "이 지역에서 검색" 요청을 표시하고, 근처 검색을 지도 영역 검색으로 합치는 일이다.

## LLMRank 요약

1차 정렬의 근거다. 2차부터 검색은 핏 점수로 정렬한다(4.3).

출처: Hou 외, ECIR 2024 (https://arxiv.org/abs/2305.08845)

후보 목록을 LLM에 주고 순서를 매기게 하는 방식이라 학습이 필요 없다. 논문에서는 학습 없는 방법(BM25 등)보다 크게 앞섰지만 학습한 모델에는 못 미쳤다. 정답이 목록 끝쪽에 있으면 성능이 떨어지는 위치 편향이 있고, 인기 있는 아이템을 위로 올리는 경향도 있다. 후보는 한 번에 20개이고, 순서를 섞어 3번 돌려 합치면 위치 편향이 줄었다.

논문은 LLM에게서 순서만 받고 점수는 받지 않는다. 0~100 핏 점수는 서비스 요구라 따로 정했다(4.3). 등급은 Zhuang 외(NAACL 2024, https://arxiv.org/abs/2310.14122)를 참고했다. 문서마다 관련도 등급을 붙이게 하면 예/아니오보다 정렬이 좋아졌고 3~4단계가 가장 좋았다.
