# 취향-가게 비교 베이스라인

Status: draft · Jira: S15P31A302-41 · 작성일: 2026-10-23 · 고친 날: 2026-10-27

비교 파트는 검색 요청을 해석하고, 조건에 맞는 장소를 DB에서 뽑아 장소 프로필과 취향 프로필로 순위를 매긴 뒤 카드로 내보낸다. BE는 검색마다 AI를 한 번 부른다. AI는 장소 데이터를 들고 있지 않고 검색마다 Postgres 뷰 하나를 pgvector로 읽는다. 정렬은 LLMRank로 한다. 맞음 등급은 코드가 요청 조건 체크표로 정하고, LLM은 같은 등급 안의 순서를 정한다. 점수는 등급과 순위로, 카드의 나머지는 규칙으로 채운다. 다른 담당과 맞출 것은 6장, 다음 할 일은 7장에 있다.

목표: 11-02까지 검색 엔드포인트(`POST /v1/search`)를 배포하고 BE와 잇는다. 배포 위치(Modal dev 또는 SSAFY GPU 서버)는 정하지 않았다.

코드는 `ai/src/fit_ai/match/`(비교 로직)와 `ai/server/`(API 앱)에 있다. 공유 모듈 `fit_ai.features`, `fit_ai.embedding`, `fit_ai.gms`는 39 것을 그대로 쓴다.

## 1. 역할

분석은 프로필 두 개를 만든다. 39는 사용자가 한 일(온보딩 태그, 직접 입력, 리뷰 이유 태그)로 취향 프로필을, 40은 리뷰와 장소 정보로 장소 프로필을 만든다. 비교(41)는 검색할 때 요청을 해석하고, DB에서 후보를 뽑아 두 프로필로 정렬한 뒤 카드를 만든다. 비교는 두 프로필 JSON과 공유 모듈만 쓰고 분석의 내부 코드는 가져다 쓰지 않는다.

## 2. 결정 사항

| 항목 | 결정 |
| --- | --- |
| 정렬 방식 | LLMRank. LLM을 학습 없이 정렬기로 쓴다 |
| 목표 | MVP 서비스 반영(첫 공개 11-06). 구현이 우선이고 라벨링·정량 평가는 공개 뒤로 미룬다 |
| 입력 | 취향 프로필(`taste-profile/v0`), 장소 프로필(`place-profile/v0`), 요청 해석 결과 |
| 장소 프로필 | 40이 만든다(10-23). 41은 읽기만 한다 |
| 장소 데이터 | AI는 들고 있지 않는다(10-23). BE와 40이 Postgres에 두고 AI가 검색마다 뷰 하나를 읽는다(10-26) |
| 호출 방식 | BE는 검색마다 AI를 한 번 부른다(10-26). AI가 해석, 거르기, 정렬, 카드까지 한다 |
| 요청 해석 | 41이 한다(10-23). GMS 1번, 실패하면 낱말 규칙 |
| 조건 이름 | 39 코드표(`QUIET`, `PURPOSE_GROUP` 등)를 쓴다. 코드표에 없는 시설 4개는 BE `Facility` 코드(`PARKING` 등)를 쓴다 |
| 후보 추출 | 업종·역·지도 영역·시설로 거르기와 요청문 유사도 상위 20곳 고르기를 SQL 한 번(pgvector)으로 한다(10-26). OpenSearch는 쓰지 않는다 |
| 공유 모듈 | 39의 `fit_ai.features`, `fit_ai.embedding`(arctic-ko, 리비전 `55ec6e9`), `fit_ai.gms`를 쓴다(10-27) |
| 취향의 쓰임 | 후보를 찾는 데는 쓰지 않고 정렬과 카드에만 쓴다(39 spec 5단계, PRD FR-08) |
| 점수 방식 | 맞음 등급(4단계)의 점수 구간 안에서 순위대로 매긴다(10-26). 체크표가 있으면 등급은 코드가 정한다(10-27). 39 spec의 임베딩 가중합(요청 70% + 취향 30%)은 공개 뒤로 미룬다 |

## 3. 전체 흐름

장소 프로필은 40이 미리 만들어 Postgres에 넣는다. AI는 BE 장소 정보와 40 프로필을 합친 뷰 `ai_place_search`를 읽는다([api.md](api.md) 5장). 취향 프로필은 BE가 검색 요청에 실어 보낸다.

일반 검색(예: "역삼역 모임하기 좋은 술집")은 이렇게 흐른다.

```
[BE]   요청문, 이전 조건, 지도 영역, 취향 프로필을 AI에 넘긴다 (/v1/search 한 번)
[41]   요청 해석      역삼역, 술집, 모임 → 조건                 GMS 1번
       요청문 인코딩  embeddingText → 벡터                     fit_ai.embedding
       후보 추출      업종·역·시설로 거르고 가까운 20곳         SQL 1번(pgvector)
       정렬           체크표 → 등급(코드), 같은 등급 안 순서(LLM)  GMS 1번
       카드 만들기    이유, 근거 항목, 라벨                     규칙
[BE]   카드에 장소 정보와 영업 상태를 붙여 FE에 넘긴다
```

근처 검색(예: "근처 조용한 카페")은 LLM 정렬을 건너뛴다. 기기 위치를 서버로 보내지 않으므로 정렬하는 시점에는 어느 장소가 반경 안에 남을지 모른다.

```
[41]   요청 해석      근처, 카페
       후보 추출      업종·시설로만 거르고 가까운 100곳
       정렬           체크표 → 등급(코드), 같은 등급 안에서는 유사도 순서
       카드 만들기    일반 검색과 같다
[FE]   폰의 현재 위치로 반경 안만 남긴다
```

LLM이 실패하면 해석은 낱말 규칙으로, 정렬은 근처 검색과 같은 방식으로 한다. 뽑힌 장소가 없으면 결과 없음 이유를 돌려준다. 단계마다 무엇이 실패하면 어떻게 되는지는 [api.md](api.md) 4장(`fallbacks`)과 6장(오류)에 있다.

## 4. 단계별 구성

### 4.1 요청 해석 (`match/interpretation.py`)

요청문과, 후속 조건이면 이전 조건(FE가 돌려보낸 `conditions`)을 받아 조건을 낸다. 조건은 BE와 FE에 불투명한 객체다.

| 조건 | 내용 |
| --- | --- |
| `text` | 정렬 LLM에 넣을 요청문. 새 검색이면 요청문 그대로, 후속이면 합친 한 문장 |
| `embeddingText` | 후보 추출에 쓸 긍정형 문장. "시끄러운 곳 말고"는 "조용한 곳"이 된다. 벡터 검색은 부정을 알아듣지 못해서다 |
| `codes` | 39 코드표의 코드와 시설 코드(27개). 인원은 1명이면 `PURPOSE_SOLO`, 4명 이상이면 `PURPOSE_GROUP`(임시) |
| `categoryGroup`, `station` | 업종과 역. 요청에 없으면 null |
| `nearby` | 근처 검색인지. "강남역 근처"는 역을 기준으로 찾는 말이라 근처 검색이 아니다 |

LLM 해석은 이렇게 한다.

- GMS(`gpt-4o-mini`)를 공유 모듈 `fit_ai.gms`로 한 번 부른다. 공유 모듈은 호출이 실패하거나 JSON이 아니면 한 번 다시 부른다.
- 프롬프트 규칙: 음식·메뉴는 식당, 술 마시는 곳은 술집으로 본다. 메뉴는 음식 종류 코드로 바꾼다(파스타 → `FOOD_WESTERN`). 부정한 조건도 바라는 쪽 코드로 넣는다. 요청에 없는 코드는 넣지 않는다("식당"만 보고 `FOOD_KOREAN`, "모임"만 보고 시설 `GROUP`을 넣지 않는다). 평가 질의와 겹치지 않는 예시 5개를 넣었다.
- 출력 검사: 모르는 코드는 버리고 모르는 업종·역은 null로 본다. `nearby`가 null이면 false로 보고, 역이 있으면 근처 검색이 아니다. JSON 객체가 아니거나 벡터용 문장이 없거나 타입이 틀리면 실패다.
- 후속이면 이전 조건(벡터용 문장은 빼고)과 새 요청을 함께 넣고 합친 조건을 받는다. "A 말고 B"는 A를 빼고 B를 넣게 한다. 바뀐 점(`changeSummary`)은 LLM이 쓴 한 문장이고, 없거나 60자를 넘으면 "요청하신 조건을 반영했어요"를 쓴다.

LLM이 꺼져 있거나 실패하면 낱말 사전으로 해석한다. "조용" → `QUIET`처럼 낱말이 들어 있는지만 본다. 업종과 역은 처음 나온 낱말로 정하되 "카페 말고"처럼 빼 달라는 말 앞의 것은 고르지 않는다. 음식 낱말은 식당이다. 후속이면 이전 코드에 새 코드를 더하고 업종·역은 새로 말했을 때만 바꾼다. 부정 표현과 조건 빼기는 못 한다.

뽑힌 장소가 없으면 조건으로 만든 템플릿으로 이유를 준다. 예: "역삼역 술집 중 주차할 수 있는 곳이 없어요" / "주차 조건을 빼고 다시 찾아 보세요". 지도 영역이면 "이 지역", 시설이 여러 개면 "요청한 시설을 모두 갖춘 곳이 없어요"로 바뀐다.

확인한 것(10-27, 실제 GMS): 유형별 질의 54개로 쟀다. 전부 맞음이 87%에서 98%로 올랐고, 공유 모듈로 바꾼 뒤에도 54개 중 53개가 맞았다. 평균 1.4~1.6초다. 규칙 해석은 87%다.

남은 문제:

- "매운 거 말고 담백한 국물 요리"처럼 부정과 코드 밖 표현이 섞이면 엉뚱한 코드(`PURPOSE_TALK`)가 붙을 때가 있다.
- "역삼역 초밥집"에서 `FOOD_JAPANESE`가 가끔 빠진다(3번 중 1번).
- 코드표로 못 잡는 표현(와인, 디저트, 늦게까지, 반려견, 콘센트, 국물)은 벡터용 문장에만 남는다. 후보 추출과 정렬 LLM에는 들어가지만 체크표, 등급, 카드에서는 빠진다. "추가 조건"으로 따로 뽑아 LLM이 판정하게 할지 정한다.
- 음식 종류 코드는 거르기에 쓰지 않는다. 40 `food_type`이 오면 체크표나 거르기에 쓸 수 있다.
- 평가 기대 답은 41이 정한 초안이라 팀 확인이 필요하다. 평가 질의로 프롬프트를 고쳐서 여기에만 맞춰졌을 수 있으니 새 질의로 다시 잰다.

### 4.2 후보 추출 (`match/pg_store.py`, `match/place.py`)

AI가 뷰 `ai_place_search`를 SQL 한 번으로 읽어 거르고 뽑는다. 뷰의 컬럼은 [api.md](api.md) 5장에 있다.

거르기 규칙:

- 업종이 있으면 같은 업종만 남긴다.
- 지도 영역(`mapBounds`, "이 지역에서 검색")이 있으면 좌표로, 없으면 역으로 거른다. 근처 검색은 역으로 거르지 않는다.
- 요청에 시설(`PARKING` 등)이 있으면 그 시설이 없다고 확인된 장소만 뺀다. 시설 정보가 없는 장소(모름)는 남긴다. 장소 정보의 시설이 덜 채워졌을 수 있어서다.
- `profile.embedding`의 모델·리비전이 요청문 인코더와 같고 `prompt`가 `document`인 장소만 비교한다. 다른 장소는 빠지고 `/healthz`가 503 `MODEL_MISMATCH`로 알린다.

남은 장소 중 `embeddingText`를 질의 쪽(`query: ` 붙임)으로 인코딩한 벡터와 요약 벡터의 코사인 유사도가 높은 20곳(근처 검색은 100곳)을 뽑는다. 계산은 pgvector `<=>`가 하고, 장소가 300곳 남짓이라 인덱스 없이 전부 계산한다. 요약 벡터는 가져오지 않는다. 이 단계에서 취향은 쓰지 않는다.

장소 프로필은 이렇게 읽는다.

| 40 필드 | 쓰는 곳 |
| --- | --- |
| `summary.text` | 정렬 LLM 입력 |
| `features`의 `like_count`, `dislike_count` | 체크표, 정렬 LLM 입력, 카드 |
| `summary.vector`(뷰의 `summary_vector`), `embedding` | DB 안의 유사도 계산과 모델 확인 |

- `schema`가 `place-profile/v0`이 아니거나 `summary.text`가 없으면 그 장소만 빼고 응답 `fallbacks`에 `PROFILE_INVALID`를 담는다.
- 프로필에 없는 조건은 근거 0(모름)으로 본다.
- 소음 축은 바꿔 읽는다(임시). 40은 손님이 느낀 쪽을 코드로, 좋았는지를 방향으로 적는다("너무 썰렁했어요"는 `QUIET` 아쉬웠어요). 카드는 그 조건을 채웠는지로 세므로 느낀 쪽의 좋았어요·아쉬웠어요를 모두 긍정으로, 반대 극의 것을 부정으로 본다.
- 쓰지 않는 필드: `personas`(공개 뒤 취향 벡터 점수와 주의점용), `evidence`(앱 리뷰만 세기와 인용용, 공개 초기에는 앱 리뷰가 거의 없다), `food_type`(음식 종류로 거르지 않아서), `features[].label`(카드 라벨은 41 규칙으로 고른다), 40의 `place_id`(뷰의 BE 장소 id를 쓴다).

확인한 것: 임시 Postgres(pgserver, pgvector)에서 거르기, 유사도 순서, 모델 확인, 깨진 프로필을 실제 SQL로 테스트했다. 로컬 개발 DB(BE Mock 장소 30곳)로 검색 여섯 가지를 처음부터 끝까지 돌렸다. DB 시간은 0.01초 미만이다.

정할 것: 소음 축 읽기, 카드 라벨에 40 `label`을 쓸지.

### 4.3 정렬 (`match/ranking.py`, `match/evidence.py`, `match/taste.py`)

취향 프로필은 이렇게 쓴다.

- `features`: 요청과 겹치는 취향을 뺀 뒤 LLM에 글로 넣는다. 문구는 39 코드표의 `phrase`이고 가중치 2에는 "조금 강하게", 3에는 "강하게"를 붙인다. 카드의 취향 근거 항목에는 좋아함만 넣는다.
- `free_texts`: 벡터가 있는 문장만 원문 그대로 LLM에 넣는다. 벡터가 없는 문장은 39가 보관만 하는 문장이다.
- 읽지 못하거나(`schema`가 다르거나 형식이 깨짐) 취향 50개·문장 20개를 넘으면 취향 없이 정렬하고 `TASTE_INVALID`를 담는다.
- 쓰지 않는 필드: `evidence`(업종별 근거 고르기용, 공개 뒤), `embedding`(취향 벡터 점수를 미뤄서), `original_text`(39가 다시 해석할 때 쓰는 원문).

요청과 겹치는 취향은 묶음으로 뺀다(PRD AC-28, AC-30). 요청에 소음 조건이 있으면 소음 취향을, 목적이나 인원이 있으면 방문 목적 취향을, 음식 종류가 있으면 음식 종류 취향을, 매운맛이 있으면 매운맛 취향을 좋아함·싫어함 모두 뺀다. 음식 종류를 찾아도 매운맛 취향은 남긴다. 중요 기준(가성비 등)과 시설은 요청과 겹쳐도 남긴다.

| 취향 | 요청 A "역삼역 모임하기 좋은 술집" | 요청 B "강남역 조용한 카페" |
| --- | --- | --- |
| `QUIET` 좋아함, 가중치 3 | 씀 | 뺌(요청에 소음 조건) |
| `LIVELY` 싫어함, 가중치 3 | 씀 | 뺌(요청에 소음 조건) |
| `PURPOSE_WORK` 좋아함, 가중치 1 | 뺌(요청에 목적) | 씀 |
| `VALUE_FOR_MONEY` 좋아함, 가중치 2 | 씀 | 씀 |
| 취향 문장 "점심엔 담백한 국물 요리가 좋아요"(벡터 있음) | 씀 | 씀 |

정렬은 이렇게 한다. 체크할 조건이 있으면 등급은 코드가 정하고 LLM은 순서만 정한다(10-27).

1. **체크표**: 요청의 카드 조건(코드표 14개와 시설 4개)마다 장소별로 확인·반대·모름을 판정한다. 확인은 그렇다는 리뷰가 2개 이상이고 아니다의 2배 이상, 반대는 아니다가 더 많을 때, 나머지는 모름이다. 시설은 장소 정보(있음·없음)를 먼저 본다. 카드 근거 항목도 같은 판정을 쓴다.
2. **등급**: 체크표가 있으면 코드가 아래 기준으로 정한다. 체크할 조건이 하나도 없는 요청("강남역 카페", "국물 요리")만 LLM이 같은 기준으로 등급을 매긴다.

| 등급 | 기준 | 점수 |
| --- | --- | --- |
| 딱 맞음 | 요청한 조건이 모두 확인된다 | 85~100 |
| 대체로 | 반대가 없고 절반 이상 확인된다 | 65~84 |
| 일부 | 반대가 없고 확인이 절반이 안 된다(모두 모름 포함) | 40~64 |
| 안 맞음 | 반대가 하나라도 있다 | 0~39 |

3. **LLM 입력**: 요청문(후속이면 합친 문장), 고른 취향, 후보 20곳. 40 요약에는 리뷰 내용이 없어서 등급, 체크표, 나머지 특징의 리뷰 수를 붙인다. 예: `[3] 술집 | 술집, 이자카야. 역삼역 근처. | 등급: 딱 맞음 | 요청 조건: 모임하기 좋아요 확인(20/1) | 리뷰: 조용하고 차분한 곳 8/2`. 후보는 섞은 뒤 1부터 번호를 붙인다. 유사도 순서대로 넣으면 LLM이 앞쪽을 위로 올린다.
4. **LLM 출력**: 잘 맞는 곳을 최대 10곳 골라 순서를 받는다(`{"ranking": [{"id": 2}, {"id": 7}]}`). 같은 등급 안에서는 체크표에 없는 요청 내용(음식 종류 등), 그다음 취향을 보고 순서를 정하게 한다. 등급을 LLM이 매길 때만 `fit`을 같이 받는다. 20곳을 다 쓰게 하면 10곳에서 멈추거나 3초를 넘기는 일이 잦았다(10-26).
5. **점수**: 등급 순서로 놓고, 같은 등급 안에서는 LLM이 고른 순서, 그다음 고르지 않은 후보를 유사도 순서로 놓은 뒤 등급 구간을 순위대로 나눈다. 등급을 LLM이 매긴 경우 고르지 않은 후보는 10위보다 낮은 점수를 받는다.
6. **실패**: 후보 밖 번호, 중복, 모르는 등급이 있거나 GMS가 실패하면(한 번에 5초, 공유 모듈이 한 번 더 부름) LLM 없이 정렬하고 `RANK_LLM_FAILED`를 담는다. 등급을 코드가 정했으면 LLM이 아무것도 고르지 않아도 실패가 아니다.

LLM 없이 정렬할 때(근처 검색, LLM 실패)도 체크표가 있으면 같은 등급을 쓰고, 같은 등급 안에서는 유사도 순서로 점수 구간을 나눈다. 체크할 조건이 없을 때만 유사도 0.2~0.8을 0~100점으로 바꾼다.

확인한 것(10-27, 실제 GMS):

- 등급을 LLM에 맡겼을 때는 기준과 64%만 맞았다(같은 후보를 섞어 5번, 50건). 두 조건이 모두 확인인 세 곳이 100, 84, 74점을 받기도 했다. 코드가 등급을 정한 뒤로는 같은 검색이 100, 95, 90점(모두 딱 맞음)이다.
- 가짜 장소 20곳과 39 샘플을 본뜬 취향 두 개로 6번 돌렸다. 모두 성공했고 1.7~2.3초였다. 조용함을 좋아하는 사용자는 상위 8곳 중 6~8곳이 조용한 곳, 가성비를 좋아하는 사용자는 0~3곳이었다. 같은 입력에서 상위 5곳은 실행마다 3~4곳이 겹쳤다.

남은 문제:

- 확인 기준(2개, 2배)은 실제 데이터(장소당 리뷰 100건)에서 너무 느슨할 수 있다. 40은 업종 평균보다 비율이 높은지로 `label`을 붙인다. 40 데이터가 오면 확인 기준을 `label`로 바꿀지 본다.
- 같은 등급이 많으면 점수 차이가 작다(딱 맞음 16곳이면 100, 99, 98…).
- 실제 arctic 유사도는 0.4 안팎이라 체크할 조건이 없을 때 유사도 점수가 30점대에 몰린다. 실제 40 데이터로 범위를 다시 정한다.
- 순서를 섞어 여러 번 돌려 합치는 방식(LLMRank 논문의 부트스트래핑)은 공개 뒤에 검토한다.

### 4.4 카드 만들기 (`match/cards.py`)

카드는 LLM 없이 규칙으로 만든다. 화면의 숫자와 문장은 근거와 정확히 맞아야 하는데 LLM에 맡기면 그럴듯한 숫자를 지어내거나 외부 리뷰 문장을 옮길 수 있다(PRD AC-08, AC-25). 출력이 길어져 느려지는 것도 이유다. 카드에는 BE `PlaceCard`의 AI 필드만 담고, 장소 이름·좌표·사진·영업 상태는 BE가 채운다.

| 필드 | 규칙 |
| --- | --- |
| `score` | 정렬이 준 점수 그대로(4.3) |
| `scoreItems` | 요청 조건 먼저, 그다음 좋아하는 취향. 카드 조건 18개만 쓰고 겹치면 요청으로 한 번만 넣는다. `matched`는 체크표가 확인일 때만 true, `evidenceCount`는 그렇다는 리뷰 수다 |
| `reasons` | 확인된 항목마다 하나, 최대 3개. 리뷰로 확인되면 `리뷰에서 "조용해요"라는 말이 많아요`, 시설 정보로만 확인되면 조건 문구 그대로(`주차할 수 있어요`). 인용은 넣지 않는다 |
| `labels` | 그렇다가 아니다보다 많은 특징 중 근거가 충분한 것 먼저, 그렇다가 많은 순서로 2개. 모자라면 업종·역 이름으로 채운다 |
| `caution` | MVP는 넣지 않는다 |

목록은 `score` 내림차순이다. 일반 검색은 20개, 근처 검색은 100개까지 보내고 `nextCursor`는 없다.

남은 문제(비교가 고칠 것):

- 라벨이 검색 조건과 상관없이 정해진다. 요청 조건과 맞는 특징을 먼저 고르는 안이 있다.
- 근거가 부족한 특징(리뷰 1개)도 라벨이 될 수 있다.
- 시설 이유는 제목과 칩이 같은 말이다.
- 리뷰 2개만 있어도 "말이 많아요"가 나온다.

화면 문구처럼 BE·FE가 정할 것은 6장에 있다.

## 5. 기록과 최소 확인

공개 전에는 팀이 질의 10개의 결과를 직접 보고 이상한 순위가 없는지 확인한다. 검색마다 JSON 한 줄을 남긴다. 해석 방법과 실패 이유, 조건 코드와 업종·역, 후보 수, 정렬 방법과 실패 이유, 검사를 통과한 정렬 LLM 응답(후보 번호뿐), 단계별 시간(해석, 인코딩, DB, 정렬)이다. 요청문과 취향 내용은 남기지 않는다. 공유 GMS 모듈이 토큰 수를 돌려주지 않아 토큰 수는 남기지 못한다.

## 6. 다른 담당과 맞출 것

### 팀

- 검색당 LLM 호출이 2번(요청 해석 + 정렬)이다. PRD의 "검색 시 LLM 호출은 요청 해석 한 번뿐"을 바꿔야 한다.

### 분석 담당(39·40)

- 41 코드를 39 구조(`fit_ai/match/`, `server/`)로 옮기고 공유 모듈을 쓰게 했다(10-27). 39 브랜치가 develop에 먼저 합쳐져야 41을 합칠 수 있다.
- `fit_ai.gms`: 실패하면 늘 한 번 더 불러서 검색 중 최악의 응답 시간이 두 배가 된다(한 번에 5초면 해석과 정렬 각각 10초). 검색에서는 바로 규칙이나 유사도로 넘어가므로 다시 부르지 않는 선택지, 토큰 수, 출력 토큰 상한을 요청한다. `GMS_BASE_URL`은 `…/gmsapi/api.openai.com/v1` 형식이다.
- 40은 장소 요약을 `fit_ai.embedding.encode_documents`로 인코딩한다. 요청문은 같은 모듈의 `encode_queries`라 모델·리비전이 맞는다. SSAFY GPU 서버(5번 GPU)와 로컬에서 만든 벡터가 같았다(코사인 1.000000).
- 40 프로필과 요약 벡터를 뷰 `ai_place_search`로 읽을 수 있게 Postgres에 넣는다. 40 샘플 프로필(15~20곳)이 오면 7장 4번 확인에 쓴다.
- 취향·장소 프로필의 필드 이름이나 `layer` 값을 바꿀 때는 `schema` 버전을 올린다.
- 음식 종류 요청 때 매운맛 취향을 남기는 해석(4.3)이 39 spec의 뜻과 맞는지

### BE·FE

- BE는 검색마다 `/v1/search`를 한 번 부르고 카드에 장소 정보와 영업 상태를 붙인다([api.md](api.md) 2장).
- 뷰 `ai_place_search`를 누가 만들지, 40 프로필의 갱신 주기, 40 `place_id`와 BE 장소 id를 잇는 방법
- 검색이 503일 때 BE가 대신 보여 줄 것
- 취향 프로필이 검색 요청에 어떻게 오는지. 비회원은 기기가 요청에 실어 보낸다(39 spec). 지금 요청의 `preferences`(코드 목록)로는 가중치와 취향 문장을 싣지 못한다. 회원 취향을 DB에 두면 AI가 직접 읽는 방법도 있다.
- 근거 항목 문구: 화면은 "앱 리뷰 n개가 근거예요"인데 41은 외부 리뷰까지 센다. 앱 리뷰는 공개 초기에 거의 없어서 앱 리뷰만 세면 모든 항목이 "근거 부족"이 된다. 셀 범위와 문구를 정한다.
- "점수에 넣지 않았어요" 문구는 점수 방식과 맞지 않는다. "근거가 부족해요"로 바꾸기를 요청한다.
- 시설 항목은 근거 리뷰 수가 0이라 "리뷰 0개가 근거예요"가 된다. 시설 항목 문구를 따로 둔다.
- 근거가 충분한 조건이 없으면 추천 이유가 비어 있다. 영역을 숨길지 문구를 보여 줄지 정한다.
- 라벨이 모자랄 때 채우는 업종 이름("카페")이 카드의 업종 표시와 겹친다.
- 결과가 20개에서 끝나는 것(`nextCursor` 없음)

### 인프라

- AI 쪽에서 GMS를 부를 수 있는지. 지금 인프라 설계는 GMS 키를 BE 환경 파일에 둔다.
- AI 배포 위치(Modal dev 또는 SSAFY GPU 서버)와 거기서 Postgres에 붙는 방법(공개 범위, TLS, 허용 IP, 뷰만 읽는 계정, 접속 수 상한 60).
- BE 타임아웃([api.md](api.md) 8장)

## LLMRank 요약

출처: Hou 외, ECIR 2024 (https://arxiv.org/abs/2305.08845)

후보 목록을 LLM에 주고 순서를 매기게 하는 방식이라 학습이 필요 없다. 논문에서는 학습 없는 방법(BM25 등)보다 크게 앞섰지만 학습한 모델에는 못 미쳤다. 정답이 목록 끝쪽에 있으면 성능이 떨어지는 위치 편향이 있고, 인기 있는 아이템을 위로 올리는 경향도 있다. 후보는 한 번에 20개이고, 순서를 섞어 3번 돌려 합치면 위치 편향이 줄었다.

논문은 LLM에게서 순서만 받고 점수는 받지 않는다. 0~100 핏 점수는 서비스 요구라 따로 정했다(4.3). 등급은 Zhuang 외(NAACL 2024, https://arxiv.org/abs/2310.14122)를 참고했다. 문서마다 관련도 등급을 붙이게 하면 예/아니오보다 정렬이 좋아졌고 3~4단계가 가장 좋았다.
